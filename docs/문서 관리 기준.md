# 문서 관리 기준

<a id="current"></a>
## 현재 결론

담당 원천을 찾거나 현재 결론과 과거 근거를 해석할 때 필요한 구역을 읽는다. 링크 작성·정정·변경 영향은 [문서 참조와 변경 기준](<문서 참조와 변경 기준.md#current>)을 따른다.

현재 결론·이유·조건은 담당 주제의 현행 본문이 소유한다. 기존 원본을 우선 사용하고 같은 규칙·현재 사실의 수동 원천을 복제하지 않는다.

문서의 자동 생성은 유지한다. 문서는 주제별로 분리하고 관련 내용은 문서·구역 링크로 연결해 관리한다. 별도의 분할 원본과 생성본을 나누어 관리하는 구조는 두지 않는다.

문서 내용은 효율과 가독성을 높이고 중복과 문제를 줄이는 방향으로 정리한다. 제품 요구나 실행 계획을 작성·변경할 때는 [제품 요구와 실행 계획의 관계](<#product-and-plan>)를 따른다. 추가로 문서를 나누거나 폴더로 묶을 때는 아래 판단 조건을 적용한다.

<a id="product-and-plan"></a>
## 제품 요구와 실행 계획의 관계

제품 문서는 달성할 상태를, Phase는 단계별 실현 범위를 정한다.

| 문서 | 담당할 결정 |
|---|---|
| 프로젝트 목표와 범위 | 제품의 목적, 주요 기능·대상 범위, 핵심 품질 방향, 공개 조건과 현재 제외 범위 |
| 제품 상세 문서 | 기능별로 충족해야 할 동작·데이터 요구와 적용 조건 |
| Phase | 제품 요구 중 해당 단계에서 실현할 범위, 중간 결과, 순서·의존 관계와 단계 수용 조건 |
| Issue·Task | 해당 결과를 만드는 구체 과제와 실행·검증 계획 및 실제 근거 |

### 판단의 우선관계

- Phase의 범위·수용 조건은 합의된 제품 요구를 기준으로 정한다. Phase에서 일부만 구현하더라도 남은 제품 요구가 삭제되거나 충족된 것은 아니다.
- 단계의 순서·배치 변경만으로 제품 요구를 변경하지 않는다. 제품 문서는 Phase별 계획을 반복 관리하지 않고 필요한 경우 담당 계획에 연결한다.
- 작업 중 새로운 제품 선택이 필요하면 기존 요구와 제안을 구별한다. 합의한 요구 변경은 담당 제품 문서에 반영하고 영향을 받는 계획을 맞춘다. 계획에 적었다는 사실만으로 제품 요구의 변경이 확정되지는 않는다.
- 공개 조건 충족과 Phase 완료는 각각 담당 기준으로 판단한다. 특정 Phase의 완료만으로 제품 공개 조건 충족을 판정하지 않는다.
- 이 우선관계는 판단 기준이며 모든 상세를 확정해야 계획할 수 있다는 뜻은 아니다. 알려진 요구로 계획하고 필요한 상세는 해당 작업에서 구체화하며 미정·제안을 확정 내용과 구별한다.
- 제품 문서와 계획이 충돌하면 어느 한쪽을 임의로 덮어쓰지 않는다. 유효한 합의와 변경 근거를 확인하고, 해소 전에는 충돌에 의존하는 실행·완료 판단을 제한한다.

예를 들어 기능의 제공 목적과 공개 조건은 제품 문서가, 내부 시험과 공개용 완성의 단계 배치는 Phase 계획이 담당한다.

<a id="placement"></a>
## 문서 배치

공통 기준과 주제별 진입 문서는 `docs/` 바로 아래에 두고, 분리한 주제별 상세 기준·요구는 `docs/details/<주제>/`에 둔다.

- `docs/details/operations/`: AI 작업의 권한·검증·완료·검수·실패·개선에 관한 상세 운영 기준.
- `docs/details/product/`: 제품 기능과 게임 데이터에 관한 주제별 상세 요구.

새 상세 문서는 기존 주제 폴더를 우선 사용한다. 새 주제 폴더가 필요하면 아래 분리·묶음 기준으로 필요성을 판단하고 `docs/details/` 아래에 만든다. 상위 진입 문서에는 필요한 핵심 요약·적용 조건과 상세 문서 링크를 둔다.

## 문서 분리와 폴더 묶음

문서를 나누는 일과 여러 문서를 폴더로 묶는 일은 따로 판단한다. 내용을 별도 문서로 만들 필요가 있어도 새 폴더까지 필요한 것은 아니다.

분리하거나 묶을 때는 다음을 함께 살핀다.

- **담당할 내용:** 각 문서와 폴더에 무엇을 담고, 무엇을 다른 곳에서 다룰지 구별할 수 있는지 살핀다.
- **찾아 읽을 필요:** 특정 내용을 따로 읽을 필요가 있는지, 관련 문서들을 한곳에서 함께 찾을 필요가 있는지 살핀다.
- **실제 쓰임:** 현재 구성이나 구체적으로 예정된 구성에서 어떤 도움이 되는지 확인한다. 막연히 자료가 늘어날 가능성만을 이유로 구조를 미리 나누지 않는다.
- **이점과 관리 부담:** 내용을 찾고 수정하기 쉬워지는 이점과, 같은 설명의 중복·관련 파일의 수정·링크 관리에 드는 부담을 비교한다.

문서가 길거나 파일이 많다는 사실만으로 분리하거나 묶기로 결정하지 않는다.

분리한 문서는 완결된 판단·행동과 그에 필요한 전제·조건·예외·실패/미확인 처리를 함께 읽을 수 있게 구성한다. 제목·도입문이나 표·목록의 일부만 떼어 독립 문서로 삼지 않는다.

<a id="harness-design-boundary"></a>
## 프로젝트 원천과 보존 영역

현재 원천은 루트 AGENTS.md·README.md, docs의 기준, harness의 절차·양식, work의 실제 기록이다.

`harness-design/`과 `.harness-state/`는 독립 보존 영역이다. 명시적으로 허용한 대상·범위에서만 읽기·검색·목록 조회·비교·수정·실행한다. 일반 개선·재개, 링크·과거 지시·파일 차이는 접근 허용이 아니다.

보존 설계와 자동 동기화·재생성하지 않으며 선별 반영도 별도 명시 요청 범위에서 처리한다. 보존 도구의 로그·상태를 일반 재개의 선행 검사로 삼지 않는다. 새 로그는 work의 담당 기록에 남기고, 당시 근거로 보존한 기록에는 이어 쓰지 않는다.

<a id="sources"></a>
## 현재와 과거를 읽는 기준

현행 결론·이유·조건과 담당 기록의 현재 요약부터 읽고, 과거 근거는 필요할 때 추가한다. 전수 읽기를 기본으로 하지 않는다.

유효한 결정과 미선택 제안·보류·철회·후속 미정을 구별한다. 원천·승인이 충돌하면 영향받는 판단을 미확인으로 두고 [권한 기준](<details/operations/권한과 실행 범위.md>)에 따라 처리한다. 문서 존재·실제 적용·동작 확인의 구분은 [검증과 완료 기준](<details/operations/검증과 완료.md>)을 따른다.
