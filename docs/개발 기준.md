<a id="logging"></a>
## 로그 최소 기준

Spring Boot 기본 로깅 구성을 사용하고 Java 코드에는 이미 선택한 SLF4J·Lombok `@Slf4j`를 사용한다. 초기에는 기본 콘솔 출력과 로그를 남길 지점·수준을 관리한다.

| 수준 | 남길 내용·기본 처리 |
|---|---|
| ERROR | 예상하지 못한 실패와 원인 확인에 필요한 예외 정보 |
| WARN | 확인이 필요한 이상 상황 |
| INFO | 시작·종료 등 주요 실행 정보. 기본 콘솔 출력 수준 |
| DEBUG | 검색·루트 계산 등의 상세 처리·진단 정보. 평소에는 비활성화하고 필요할 때 해당 패키지의 출력 수준을 조정 |

필요할 때 상세 진단을 켤 수 있도록 해당 기능 구현 때 필요한 로그 지점을 함께 작성한다. 모든 정상 요청·중간 상태를 무조건 기록하지 않으며 로그 분량은 진단에 필요한 범위로 제한한다. 비밀번호·토큰·전체 요청 본문은 기본 수집하지 않는다.

출력 수준은 실행 설정에서 패키지별로 조정할 수 있게 한다. 상세 SQL 로그도 기본으로 켜지 않고 필요한 진단 범위에서만 사용한다. 별도의 로깅 라이브러리·복잡한 사용자 정의 설정을 초기 필수 구성으로 추가하지 않는다.

파일 보관·중앙 수집·분석 시스템과 구체 보관 정책은 운영 환경을 정하는 배포·운영 설계에서 결정한다. 기본 출력 설정은 기반 구축에서, 기능별 로그 작성 지점과 진단 정보는 해당 기능 구현·검증에서 확인한다.

근거: [Spring Boot 기본 로깅·출력 수준·파일 출력](https://docs.spring.io/spring-boot/reference/features/logging.html).

<a id="jpa-query-boundary"></a>
## JPA 조회·응답 구성 범위

`spring.jpa.open-in-view=false`를 사용한다. 필요한 DB 조회와 응답 DTO 구성을 서비스 트랜잭션 안에서 마치고 컨트롤러는 준비된 DTO를 반환한다. 응답 직렬화 중 JPA 연관 자료를 추가 조회하는 동작에 의존하지 않는다.

조회에 필요한 연관 자료를 트랜잭션 안에서 준비하지 않으면 이후 지연 로딩 접근에서 오류가 날 수 있으므로, 기능별 조회 설계·테스트에서 필요한 자료와 DTO 구성이 완료되는지 확인한다. 구체 조회 방식은 해당 기능의 설계에서 선택한다.

설정은 기반 구축에서 반영하고 실제 조회·DTO 응답 동작은 해당 기능에서 검증한다.

근거: [Spring Boot JPA open-in-view 설정](https://docs.spring.io/spring-boot/appendix/application-properties/index.html#application-properties.data.spring.jpa.open-in-view).

<a id="server-profiles"></a>
## 서버 환경별 설정 분리

Spring Boot 설정은 공통·로컬·테스트로 구분한다. YAML 형식을 유지하며 아래 위치에서 관리한다.

| 파일 | 역할 |
|---|---|
| `backend/src/main/resources/application.yaml` | 앱 이름·JPA·Flyway·기본 로그 등 공통 기준 |
| `backend/src/main/resources/application-local.yaml` | 로컬 실행·접속 설정. 개인 실제 값은 환경변수로 주입 |
| `backend/src/test/resources/application-test.yaml` | 테스트 전용 설정. Spring 설정이 필요한 테스트에 적용 |

로컬은 IDE 실행 설정이나 `SPRING_PROFILES_ACTIVE=local`로 local 프로필을 명시한다. 공통 파일에서 로컬 프로필을 활성값으로 고정하지 않는다. Spring 설정이 필요한 테스트는 test 프로필을 명시하고 개발 DB 대신 테스트용 연결을 사용한다.

DB 연동 테스트에는 이미 선택한 Testcontainers DB를 연결한다. 프로필 선택만으로 컨테이너가 시작된다고 가정하지 않고 테스트 설정에서 컨테이너 실행·접속 정보 연결을 구성한다. DB가 필요 없는 단위 테스트까지 컨테이너를 시작하지 않는다.

비밀번호 등 개인 값은 기존 환경변수 기준대로 주입하고, Compose의 루트 `.env`가 Spring Boot에 자동 적용된다고 가정하지 않는다. 운영 전용 설정은 실제 배포 환경을 정할 때 구체화한다.

파일·프로필·환경변수 전달과 테스트 DB 분리는 기반 구축에서 설정·검증한다.

근거: [Spring Boot 프로필](https://docs.spring.io/spring-boot/reference/features/profiles.html) · [외부 설정·환경별 파일](https://docs.spring.io/spring-boot/reference/features/external-config.html) · [Testcontainers 연결](https://docs.spring.io/spring-boot/reference/testing/testcontainers.html).

<a id="error-handling"></a>
## API 오류 처리 연결

`spring.mvc.problemdetails.enabled=true`를 사용해 Spring MVC 기본 오류를 ProblemDetail 형식으로 처리한다. 업무 오류와 예상하지 못한 실패는 `@RestControllerAdvice`의 공통 예외 처리에서 합의한 HTTP 상태와 RFC 9457의 `application/problem+json` 응답에 연결한다.

필요한 업무 오류 코드·필드별 입력 오류는 ProblemDetail 확장 필드로 제공하며 구체 목록·필드는 해당 기능의 API 설계에서 정한다. 예상하지 못한 오류는 일반적인 사용자 안내를 반환하고 상세 원인은 서버 로그에 남긴다. 내부 예외·SQL·비밀값을 응답에 그대로 노출하지 않는다.

기본 MVC 오류 처리와 공통 예외 처리의 우선순위·중복을 확인해 입력 오류 등이 일괄 500으로 바뀌지 않게 한다. 공통 처리 골격은 기반 구축에서 설정·검증하고 기능별 업무 오류 매핑은 해당 기능에서 구현·테스트한다.

근거: [Spring의 ProblemDetail·예외 처리·확장 필드 지원](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-ann-rest-exceptions.html).

<a id="internal-identifiers"></a>
## 공통 내부 ID

| 경계 | 기준 |
|---|---|
| DB 내부 | PostgreSQL `BIGINT` + DB의 IDENTITY 자동 발급 |
| Java 서버 내부 | `Long` |
| API·프런트 | 식별 ID는 JSON 문자열로 전달하고 TypeScript `string`으로 취급 |

ID의 API 표현은 DTO 경계에서 명시하고 수량·능력치나 모든 Long 필드를 전역 문자열로 바꾸지 않는다. `BIGINT` 전체 범위가 JavaScript 안전 정수 범위보다 넓으므로 ID의 값이 왕복 과정에서 바뀌지 않도록 한다. DB를 통해 쓰는 Java·Python 등은 같은 ID 발급 방식을 사용한다.

지속적인 대상과 특정 버전의 ID를 구분해 참조한다. 시즌 번호·버전 표기/정렬식·지역 정렬값과 별도 게임 코드/관리 코드 필드를 두지 않는 의미 규칙은 [제품 식별 기준](<details/product/게임 데이터 변경 관리.md#identity-information>)을 따른다. 내부 ID로 이 숫자들을 대체하거나 계산하지 않는다.

구체 테이블·IDENTITY의 DDL 옵션·기본키/유일성 제약·참조 일치 검사는 담당 DB 설계에서 정한다. IDENTITY만으로 유일성이 보장된다고 가정하지 않는다. 실제 스키마·Java 매핑·DTO 표현은 기반 데이터/DB 및 해당 API 과제에서 구현하고 자동 발급·값의 왕복 보존·참조 정합성을 검증한다.

근거: [PostgreSQL IDENTITY](https://www.postgresql.org/docs/18/ddl-identity-columns.html) · [정수 자료형](https://www.postgresql.org/docs/18/datatype-numeric.html) · [JavaScript 안전 정수 범위](https://tc39.es/ecma262/multipage/numbers-and-dates.html#sec-number.max_safe_integer).

<a id="datetime"></a>
## 날짜·시각과 미확인 값

| 구분 | 기준 |
|---|---|
| 날짜만 있는 값 | 시즌 시작일·종료일 등은 PostgreSQL `DATE` / Java `LocalDate`, API `YYYY-MM-DD` 문자열 |
| 정확한 시점 | 패치 적용 일시 등은 PostgreSQL `timestamptz(0)` / Java `Instant`, UTC 기준으로 저장·비교 |
| 정밀도·API | 서비스 데이터 시각은 초 단위. 저장·비교·API 전달 전에 초 미만을 절삭해 일치시키고 API는 소수 초 없는 UTC ISO 8601 문자열로 전달 |
| 화면 표시 | 일시는 기본 `Asia/Seoul`, 날짜만 있는 값은 해당 날짜 그대로 표시 |
| 미확인 | 확인되지 않은 날짜·일시는 `null`/미확인으로 구분하고 오늘 날짜·임의 자정·0시각으로 채우지 않음. 일시가 미확인이면 패치 현재/예정 판정도 미확인 |

원자료에 시간대가 없으면 임의로 UTC나 한국 시간으로 단정하지 않고 확인한 뒤 변환한다. 날짜만 알려진 패치 적용 일시를 임의 자정으로 보완하지 않는다. 화면 표시 시간대로 저장값을 덮어쓰지 않는다.

초 미만 값은 저장 전에 공통 기준으로 정규화하고 DB 정밀도 변환의 반올림에 처리를 맡기지 않는다. 원자료·검증 근거 보존은 기존 기준을 유지한다. 진행 중·해당 없음 등 별도 업무 의미와 미확인의 구분, 실제 미확인 값의 등록 허용 범위는 해당 데이터 설계에서 정한다.

기존 버전 번호·정렬식과 패치 현재/예정의 시각 비교 원칙은 유지한다. 서비스 자료 공개·적용 정책을 시간대 선택으로 함께 확정하지 않는다. 실제 값·시간대와 미확인 허용 범위는 자료 확인·등록 설계에서 확인하고, 저장·서버 비교·API 왕복·화면 표시의 경계는 해당 구현에서 검증한다.

근거: [PostgreSQL 날짜·시각·정밀도](https://www.postgresql.org/docs/18/datatype-datetime.html) · [Java Instant의 정밀도 정규화](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/time/Instant.html#truncatedTo(java.time.temporal.TemporalUnit)) · [Java LocalDate](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/time/LocalDate.html).

<a id="skill-json"></a>
## 스킬 연결별 JSON 저장·최소 검증

아이템–스킬 연결의 구조화 값은 PostgreSQL `jsonb`로 저장한다. 서버에서는 Boot의 Jackson JSON 트리(`JsonNode`)로 다루고 API에서는 JSON 값을 전달한다. 설명 원문 텍스트는 기존 역할대로 별도 문자열로 보존한다.

P1에서는 JSON 문법·저장 가능한 값과 실제 값의 저장/읽기 왕복 보존을 확인한다. 중복 객체 키는 트리 변환·DB 저장 전에 입력 파싱 단계에서 감지해 입력 문제로 확인하고 조용히 덮어쓰지 않는다. jsonb는 공백·객체 키 순서를 원문 그대로 보존하는 형식으로 취급하지 않는다.

실제 필수 키·내용 형식·값 범위, 스키마·JPA 매핑·숫자 값 보존은 담당 자료/스킬·DB·API 설계와 실제 입력으로 구체화·검증한다. 지금 전용 JSON Schema 도구나 원문 복제 필드를 추가하지 않으며 별도 원자료 보존 원칙은 유지한다.

아이템 버전 중심 보존과 특정 스킬 버전 직접 참조, `item_stat` 원본·`stat_json` 캐시 역할은 기존 합의를 유지한다. 수식 실행·조건문 평가·수식 참조 해석의 구체 논의·구현은 딜량 계산기 작업에서 수행한다.

근거: [PostgreSQL JSON·jsonb](https://www.postgresql.org/docs/18/datatype-json.html) · [Spring Boot JSON·Jackson 지원](https://docs.spring.io/spring-boot/reference/features/json.html).

<a id="stat-numeric"></a>
## 능력치 값의 수치 표현

능력치 원본 값은 PostgreSQL `NUMERIC` 계열로 저장하고 Java 서버에서는 `BigDecimal`로 다룬다. P1의 저장·조회·기본 능력치 합산에 적용한다. 정확한 기본 합산 중간에 불필요한 부동소수점 변환을 끼우지 않고 동일 입력의 합산은 필요한 범위에서 재사용한다.

백분율은 기존대로 `5%`를 `5`로 저장하며 능력치 종류의 `(%)` 구분과 `item_stat` 원본·`stat_json` 캐시 역할을 유지한다. 수량의 정수 저장은 능력치 소수 처리와 구분한다.

실제 허용 범위·소수 자릿수는 자료를 확인한 뒤 담당 데이터/DB/API 설계에서 스키마·검증 구현 전에 정한다. `NUMERIC(p,s)`와 JPA 매핑을 함께 정하고 자료 없이 임의의 최대값·고정 소수 자리수·반올림을 먼저 강제하지 않는다. API·프런트 표현도 이 범위·정밀도와 함께 구체화하며 원본·캐시·DB→API→화면의 값 보존을 확인한다. 초기 프런트 소수 계산 라이브러리는 추가하지 않는다.

이는 P1의 일반 능력치 수치 표현 기준이다. 수식·딜량 계산의 구체 정밀도·반올림 규칙은 해당 후속 기능에서 정한다. 실제 저장·매핑·합산·전달의 실행 근거는 해당 기능 과제에 남긴다.

근거: [PostgreSQL 정확한 수치 자료형](https://www.postgresql.org/docs/18/datatype-numeric.html) · [Java BigDecimal](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/math/BigDecimal.html).

<a id="images"></a>
## 이미지 보관·제공

DB에는 이미지 바이너리 대신 공통 이미지 루트 아래의 상대 경로를 기존 이미지 정보로 저장한다. 초기에는 `frontend/public/images/`의 정적 파일로 제공하고 공통 이미지 루트와 DB 경로를 합쳐 화면 URL을 만든다. 예를 들어 `items/example.png`는 기본 루트에서 `/images/items/example.png`로 제공한다. 개별 데이터에 외부 도메인을 고정하지 않으며 별도 이미지 관리 테이블·코드를 초기 필수로 추가하지 않는다.

이미지 내용이 바뀌면 새 파일명·경로를 사용하고 과거 버전이 참조하는 파일을 덮어쓰거나 임의 삭제하지 않는다. 준비되지 않은 이미지는 미등록·대체 표시로 구분하고 임의의 실제 게임 이미지를 만들어 채우지 않는다.

위 정적 방식은 파일 변경을 배포에 반영할 때 프런트 빌드·배포가 필요하다. 실제 원본 위치·형식·용량·파일 목록과 Git 저장 취급은 자료 확인·등록 설계에서 정한다. 전용 업로드·CDN·객체 저장소는 현재 초기 필수로 도입하지 않는다.

<a id="image-storage-followup"></a>
### 후속 저장소 검토

S3는 후속 이미지 저장소의 검토 후보로 둔다. 현재 S3 전환·도입 시점이나 CloudFront 등의 구성까지 확정한 것은 아니다. 파일 규모·업데이트 빈도로 정적 파일 재배포 부담이 커지거나 실제 공개 배포 환경을 정할 때 이미지 제공·배포 설계 담당이 검토한다. Task 005가 해당 과제에 이 조건을 연결한다.

전환 시 상대 경로를 객체 키에 대응시키고 공통 이미지 루트의 제공 위치를 변경하는 방향을 우선한다. 실제 파일 이관·권한·접근·캐시·비용과 과거 버전 이미지의 정상 제공을 확인한 뒤 전환한다. S3 + CloudFront는 이때 비교할 구성 후보이며 필요하면 비공개 S3 원본과 CloudFront 접근 제어를 사용한다. 서브 경로 배포·외부 이미지 루트도 실제 URL 구성과 함께 검증한다.

공통 배치·참조는 기반 구축·해당 조회 화면에서 구현하고, 실제 이미지 확보·변환·등록은 허용된 자료 처리 범위에서 수행한다.

근거: [Vite public 디렉터리](https://vite.dev/guide/assets.html#the-public-directory) · [Amazon S3](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html) · [CloudFront의 S3 원본 접근 제어](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-restricting-access-to-s3.html) · [S3 비용 항목](https://aws.amazon.com/s3/pricing/).

## 공통 데이터·버전 참조 전제

아래는 기존 제품 합의를 구현에 연결하는 경계다. 테이블을 새로 확정하거나 후속 기능을 P1에 추가하지 않는다.

| 논리 관계 | 따라야 할 원천·구현 전제 |
|---|---|
| 시즌 → 게임 패치·지역 | [시즌·버전·지역 의미](<details/product/게임 데이터 변경 관리.md#season-information>)의 번호·표기·정렬을 내부 ID와 구분한다. API 계약 버전·앱 버전과 게임 패치를 혼용하지 않는다. 실제 값은 자료 확인 후 등록한다. |
| 지속 대상 → 버전 이력 | [보존 원칙](<details/product/게임 데이터 변경 관리.md#version-applicability>)에 따라 아이템 단위로 보존하고 조회 대상 패치에서 유효한 이력을 선택한다. 최신 상태의 별도 원본 복제본을 전제하지 않는다. P1 상세의 v1.0.0 표시 제한으로 이력 보존을 생략하지 않는다. |
| 아이템 버전 → 원본 능력치·표시 캐시 | [능력치 요구](<details/product/아이템 탐색과 상세.md#stat-information>)의 원본/캐시 역할과 같은 버전의 값 일치를 유지한다. 원본 갱신·재생성·원자성의 구체 방식은 DB/자료·조회 설계에서 정한다. |
| 아이템 버전 → 스킬 대상·특정 스킬 버전·게임 패치 | [스킬 연결 요구](<details/product/게임 데이터 변경 관리.md#item-skills>)의 이중 참조와 대상/버전 일치를 보장한다. JSON·원문 역할과 [연결별 JSON 표현](<#skill-json>)을 유지하고 일치 검사 수단은 DB 설계에서 정한다. |
| 아이템 종류 계층 ↔ 별도 무기 종류 | [분류 요구](<details/product/아이템 탐색과 상세.md#classification>)를 따른다. 캐릭터 기능을 P1 선행 조건으로 추가하지 않으며 관계의 키·카디널리티는 DB 설계에서 정한다. |
| 아이템 → 제작·획득·배달·상태 | 조회·제작·계산이 같은 기준 패치와 대상의 자료를 사용하도록 참조를 설계한다. [획득 수량](<details/product/아이템 탐색과 상세.md#acquisition-quantity>)의 원자료 보존과 계산에서의 획득 가능 여부, [삭제·정정](<details/product/게임 데이터 변경 관리.md#change-and-correction>)의 의미를 구분한다. 임시 아이템의 루트 취급·제작 실험은 해당 기능 설계에 남긴다. |

구체 테이블·키·제약·참조 검사·인덱스와 패치별 유효 이력 조회 방식은 해당 DB/기능 설계에서 스키마·조회 구현 전에 정하고 테스트한다. 입력 오류 정정·서비스 적용·공개 정책을 버전 이력 선택 방식만으로 함께 결정하지 않는다. 독립 관리 전환 조건은 기존 제품 합의를 유지하고 수식은 딜량 계산기까지 논의하지 않는다.
