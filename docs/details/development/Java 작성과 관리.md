# Java 작성과 관리

<a id="current"></a>

운영·테스트 Java를 만들거나 옮길 때는 먼저 소유 모듈과 허용 패키지를 찾는다. 운영 동작을 수정하거나 제거할 때는 승인된 범위에서 변경분과 테스트 기대값을 대조한다. [공통 정책 파일](java-policy.json)은 편집·커밋 검사와 모듈·HTTP 검사가 읽는 허용 경로 원천이다. [Issue #106의 합의](../../../work/records/harness/issue-106/issue.md#decisions)

설치·승인 입력·재실행 방법은 [Java 편집·커밋 검사 실행](<Java 검사 실행.md>)을 따른다.

## 적용 대상

| 변경 | 필요한 확인 |
| --- | --- |
| 운영·테스트 Java 생성 또는 이동 | 목적지의 경로·패키지·이름을 확인한다. 이름 변경도 목적지 이름에 같은 기준을 적용한다. |
| 기존 Java 내용 수정 또는 동작을 제거하는 삭제 | 승인된 작업의 변경 대상·동작과 운영 코드·테스트 차이를 대조하고 유지할 동작을 회귀 확인한다. 이동에 동작 변경이 섞이면 두 확인을 모두 적용한다. |
| 모듈 의존·공개 HTTP 계약 또는 그 검사 입력 변경 | 실제 제출 후보의 모듈 접근·순환과 등록된 HTTP 계약을 대조한다. 정책·승인 입력을 변경한 범위도 승인 근거와 대조한다. |

초기 경로·이름 검사는 운영·테스트 Java의 소스 루트에 적용한다. Spring 설정 YAML, SQL·Flyway, Gradle 파일의 경로와 이름은 적용 대상 밖이다. 자동 생성 Java와 기존 파일의 일괄 정리는 적용 범위와 처리 방법을 별도로 결정한다. 적용 여부는 실제 Git 후보에서 확인한다. 후보에 추적된 백엔드가 없으면 Java·Spring 검사는 적용 대상 없음이며 정책 입력의 변경은 해당 승인 범위를 확인한다.

## 경로·이름·소유권

소스 루트는 운영 `backend/src/main/java`와 테스트 `backend/src/test/java`다. 두 루트에 `io.github.minokim.lumiawiki` 기본 패키지를 대응시킨다. 패키지 선언의 각 점 구분 요소는 하위 디렉터리와 대소문자까지 일치시킨다. 일반 소스 파일은 파일 이름과 같은 이름의 주 타입을 선언한다. 주 타입에는 클래스·인터페이스·레코드·열거형·어노테이션 타입이 포함된다. 패키지 요소는 소문자로 시작하며 소문자와 숫자를, 주 타입은 대문자로 시작하며 영문자와 숫자를 쓴다. `package-info.java`는 이미 허용된 패키지의 설명 파일로 선언과 경로를 확인한다.

업무 모듈은 소유하는 기능·데이터와 공개 범위를 명시하고 기본 패키지의 바로 아래에 둔다. 정책에 등록된 업무 모듈에 아래 패키지를 사용할 수 있다. 테스트에서 같은 역할의 파일은 같은 모듈·역할 패키지를 사용한다.

| 상대 패키지 | 책임 |
| --- | --- |
| 모듈 루트 | 모듈 전체의 설명과 구성 |
| `api` | 다른 모듈에서 사용할 수 있도록 명시적으로 공개한 계약과 계약의 값 타입 |
| `application` | 유스케이스 조정과 업무 흐름 |
| `domain` | 업무 규칙과 모델 |
| `infrastructure` | 모듈 소유의 저장소·외부 연동 구현 |
| `web` | HTTP 요청·응답과 컨트롤러. URL·메서드의 공개 계약은 HTTP 승인 기준을 적용한다. |

DTO와 매퍼는 사용 맥락을 소유한 역할 패키지에 두고, 여러 타입을 분리할 필요가 생기면 그 역할 아래의 정확한 경로를 승인받는다. 모듈이 공개하는 DTO는 `api`의 공개 타입으로 등록한다. `common`은 여러 업무가 쓰는 업무 모델의 소유지가 되지 않는다.

| 공용 위치 | 책임과 허용 참조 |
| --- | --- |
| 기본 패키지 | 운영의 `LumiawikiApiApplication`과 그 부트스트랩 테스트의 위치다. 앱의 기준 패키지와 스캔 설정을 유지한다. |
| `common.api` | 공통 HTTP 오류·요청 처리 기술 코드다. 업무 모듈·`dev`·공유 픽스처에서 공용 패키지를 참조할 때는 정책의 `commonContractTypes`를 사용한다. `common`은 업무 모듈·`dev`·픽스처에 의존하지 않는다. 프로젝트 공통 Spring 빈의 등록은 앱의 스캔과 구성에서 확인한다. |
| `dev` | 로컬·테스트 실행 전용 도구와 그 테스트의 위치다. 운영 업무 모듈과 `common`은 `dev`를 참조할 수 없다. `dev`는 필요한 경우 등록된 업무 모듈 공개 계약과 허용된 `common` 타입을 사용한다. 개발 HTTP 매핑은 실제로 개발 프로필에만 등록되어야 한다. |
| 테스트 `fixture` | 여러 테스트에서 재사용하는 테스트 전용 지원 코드의 위치다. 업무 모듈 전용 헬퍼는 해당 테스트 패키지에 둔다. 공유 픽스처는 공개 업무 계약과 등록된 `common` 타입을 사용하고, 운영 소스에서 참조할 수 없다. |

`common.api` 자체 테스트와 앱·공용 구성을 조립하는 테스트는 필요한 공용 빈 구현체를 직접 참조할 수 있다. 예를 들어 Phase 1의 기존 `FoundationApiTests`는 `ApiExceptionAdvice`와 `RequestIdFilter`를 조립한다. 업무 모듈·`dev`·공유 픽스처가 직접 사용하는 공용 타입에는 같은 허용 계약을 적용한다.

다른 업무 모듈의 타입은 대상 모듈의 `api`에 있고 정책에 등록된 공개 타입만 참조할 수 있다. Java의 `public` 선언만으로 공개 계약이 생기지 않는다. 공개 시그니처가 드러내는 타입도 해당 사용자가 참조할 수 있어야 한다. 테스트에는 같은 모듈의 운영 내부 타입에 대한 접근을 허용하되 타 모듈에 대해서는 공개 계약을 적용한다. 운영 소스의 모듈 간 참조로 직접·간접 순환을 검사하고 순환 경로를 표시한다. 테스트 전용 의존은 운영 그래프에 넣지 않는다. 기존 테스트의 경로는 생성·이동 때 대조하며, 배치 변경이 Spring 스캔이나 테스트 발견에 영향을 주면 해당 실행으로 확인한다.

## 새 패키지와 예외

| 상황 | 필요한 근거와 처리 |
| --- | --- |
| 이미 허용된 경로 | 승인된 Task가 파일의 생성·이동과 해당 목적을 포함하는지 확인한다. |
| 모듈 내부 하위 패키지 추가 | 기존 경로로 수용하기 어려운 이유, 정확한 경로·역할·한계를 승인된 Task 위임에서 확인한다. 소유 모듈과 공개 범위가 유지돼야 한다. 판단과 적용 근거는 Task에 남긴다. |
| 새 최상위 모듈, `common` 공유 범위 확대, 공통 허용 경로·예외 범위 변경 | 프로젝트 결정권자 또는 명시적으로 위임받은 승인권자의 사전 결정이 필요하다. 담당 Issue에 승인 결정과 근거를 남기고 Task에서 참조한다. |
| 임시 예외 | 대상·사유·적용 한계·종료 조건·정리 책임을 승인 기록에 남긴다. 종료 조건이 충족되면 효력이 끝난다. 연장은 새 승인으로 확인한다. |

정책과 대상 파일 또는 승인 기록을 같은 후보에서 변경할 수 있다. 변경된 정책·승인 기록은 후보의 Git 비교 기준과 별도로 확인한 승인 원천에 대조한다. 미승인 변경이나 만료 예외 의존이 확인되면 위반이다. 필수 원천을 읽거나 효력을 확인할 수 없으면 미확인이다.

## 공개 HTTP 계약

프로덕션에서 등록되는 프로젝트 소유 컨트롤러·라우터의 명시 HTTP 매핑을 공개 계약 대조에 포함한다. 인증을 요구하는 경로도 포함한다. 등록 프로필이 정책에서 허용한 개발 프로필에 한정되고 프로덕션 컨텍스트에서 등록되지 않는 매핑은 개발 전용으로 제외한다. URL에 `_dev`가 있는지만으로 제외를 판정할 수 없다. 프레임워크가 암묵적으로 제공하는 프로토콜 응답(예를 들어 GET의 암묵적 HEAD)과 프레임워크 자체 매핑은 프로젝트가 명시한 매핑과 구별한다. 소유 여부·등록 조건·지원 메서드를 확인할 수 없으면 해당 범위는 미확인으로 둔다.

대조 단위는 대문자 HTTP 메서드와 Spring이 최종 등록한 전체 경로 패턴의 쌍이다. 타입과 메서드 수준 경로를 합친 값을 사용하고 변수명·대소문자·슬래시는 등록 결과대로 유지한다. 여러 경로·메서드가 등록되면 쌍별로 비교한다. 경로나 메서드 교체는 기존 쌍의 삭제와 새 쌍의 추가다. 최초 목록이나 이후 추가·삭제의 승인 원천은 해당 쌍과 변경을 식별해야 한다. 승인된 빈 목록에도 확인 근거가 필요하다.

## 편집·커밋 검사와 모듈·HTTP 검사가 공유하는 입력

### 정책 파일

[java-policy.json](java-policy.json)은 UTF-8 JSON이다. `version` 1의 필드와 뜻은 아래와 같다. 경로는 저장소 상대 경로이며 구분자는 `/`다. 이름과 패키지는 대소문자를 구분한다.

| 필드 | 형식과 사용 방법 |
| --- | --- |
| `java.basePackage`, `java.sourceRoots` | 기본 패키지 문자열과 `production`·`test`별 소스 루트 문자열이다. |
| `java.packageSegmentPattern`, `java.typeNamePattern` | 경로의 각 패키지 요소와 일반 파일의 주 타입 이름에 적용하는 정규식이다. |
| `java.rootTypes`, `java.reservedPackages` | 각 소스 종류에서 허용하는 기본 패키지의 타입 이름과 예약 패키지 배열이다. 예약 패키지는 기본 패키지 상대의 정확한 패키지 이름이다. |
| `java.modulePackages` | 등록된 모듈에 공통 적용되는 정확한 모듈 상대 패키지 배열이다. 빈 문자열은 모듈 루트다. |
| `java.modules` | 최상위 모듈명에서 소유 정보로 연결하는 객체다. 각 모듈은 문자열 `owner`와 `responsibility`, 완전한 타입 이름 배열 `publicTypes`, `production`·`test`별 `extraPackages` 배열을 가진다. 추가 패키지는 모듈 상대 이름이다. 등록이 비어 있으면 허용된 업무 모듈이 아직 등록되지 않은 상태다. 예약 최상위 이름은 모듈명으로 사용할 수 없다. |
| `java.commonContractTypes` | 업무 모듈·`dev`·공유 픽스처가 사용할 수 있는 `common` 계약의 완전한 타입 이름 배열이다. |
| `http.developmentProfiles` | 프로덕션 미등록과 함께 확인할 개발 실행 프로필 배열이다. |

패키지 허용은 정확히 일치하는 이름을 기준으로 한다. 상위 경로의 허용은 하위 경로를 자동으로 허용하지 않는다. 공개 타입은 완전한 이름이 정확히 일치해야 한다. 중첩 타입 이름은 점으로 구분하고, 별도 공개할 중첩 타입도 명시한다. 중복 키나 필수 필드 누락, 지원하지 않는 버전, 판독할 수 없는 입력은 미확인으로 처리한다. 구조가 유효한 정책도 기준 후보와 다른 부분의 승인 범위를 확인한다. 최초 정책에는 확정 배정과 Issue 결정의 범위를 적용한다.

### 승인 근거와 실제 후보

검사는 실제 후보 식별자, 기준 Git 리비전, 변경 경로와 후보 정책을 입력으로 받는다. 편집 전에는 식별 가능한 편집 대상 경로를, 커밋 전에는 실제 스테이징 후보를, 제출 전에는 실제 Git 제출 후보를 사용한다. 승인 확인 결과는 실행 환경이 후보의 내용과 별도로 만들어 다음 항목으로 넘긴다.

| 확인 결과 | 필요한 값 |
| --- | --- |
| 대상 | `candidateId`(확인한 Git 트리·커밋 또는 편집 대상), `baseRevision` |
| Task 범위 `taskScope` | `source`(아래 승인과 동일한 원천 참조), `status`, `changes`. 각 변경은 저장소 상대 `path`, `operation`(`create`·`move`·`modify`·`delete`), 승인된 동작이나 목적의 `scope`를 기록한다. 이동은 목적지 경로와 `fromPath`를 함께 기록한다. |
| 개별 승인 `approvals` | 승인 ID를 키로 하여 `status`와 확인된 `record`를 전달한다. |

`status`는 `verified`, `confirmed-absent`, `expired`, `unconfirmed` 중 하나를 사용한다. 범위와 실제 대상이 일치하면 `verified` 근거를 적용한다. 필요한 승인 부재·효력 만료·범위 위반이 확인되면 위반이다. 원천 접근 실패, 권한·효력 불명, 확인 결과가 다른 후보에 대응하는 경우는 미확인이다. 동작의 의미와 테스트 기대값은 담당 작업의 승인 범위를 읽고 검수한다.

개별 승인 레코드는 확인된 Issue 결정 또는 승인된 Task 배정에 다음 형식으로 연결한다.

| 필드 | 형식과 사용 방법 |
| --- | --- |
| `id`, `kind` | 승인 식별자와 종류. 종류는 `delegation`(모듈 내부 위임), `policy`(정책·경계 승인), `exception`(임시 예외), `http`(공개 API 승인)다. |
| `source`, `approver` | 근거의 `ref`(결정이 담긴 리비전 또는 승인 이벤트 식별자), `path`, `anchor`와 승인 주체의 `id`, `authority`다. `authority`는 결정권이나 위임을 확인할 근거 참조다. |
| `scope` | `packages`, `policy`, `http` 배열을 가진다. 패키지 항목은 `source`(`production` 또는 `test`), `package`(완전한 이름), `owner`, `role`, `visibility`, `operations`(`create`·`move` 중 허용 동작)를 기록한다. 정책 항목은 `op`(`add`·`remove`·`replace`), `path`(정책 JSON 내 포인터), 해당하는 `before`·`after`로 정확한 변경을 기록한다. HTTP 개정 승인 항목은 `op`(`add`·`remove`), `method`, `path`로 쌍을 명시한다. 최초 HTTP 목록 승인에는 `initialHttp`에 전체 `method`·`path` 쌍 배열을 넣는다. 최초 목록이 비어 있음의 승인은 `initialHttp: []`로 명시한다. |
| `reason`, `limits` | 판단 이유와 적용 제약을 기록하는 문자열이다. 임시 예외에는 `endsWhen`(확인 가능한 종료 조건)과 `cleanupOwner`(정리 책임자)를 추가한다. |

정책 포인터에서 배열은 해당 필드의 전체 전후 값으로 비교한다. `add`는 `after`, `remove`는 `before`, `replace`는 양쪽 값과 대조한다. 모듈 내부 위임으로 허용하는 정책 변경은 승인된 대상 모듈의 `extraPackages` 추가에 한정한다. 후보가 제시한 `source`와 `approver`는 조회 단서다. 승인된 기준 리비전에 보존된 결정이나 권한을 확인할 수 있는 승인 이벤트 원문에 연결하고, 미수용 후보에만 있는 기록은 그 후보의 승인 근거로 사용할 수 없다. 변경 대상이 여러 건이면 각 건에 적용되는 근거를 확인한다.

공개 HTTP 승인 목록은 최초 목록의 승인 ID를 가리키는 `initialApproval`과 `entries` 배열을 가진다. 각 항목의 `method`, `path`, `approval`은 등록 쌍과 그 최초 또는 추가 승인 ID다. 최초 작성 시 `entries`의 쌍들이 확인된 `scope.initialHttp`와 일치해야 한다. 이후 개정에서는 승인된 기준 목록과 후보 목록의 차이를 구하고 변경별 승인 ID를 `changeApprovals`로 넘겨 `scope.http`와 대조한다. 삭제한 항목의 승인은 이 변경 근거에 보존한다. 실제 등록 집합은 후보 목록 전체와 대조한다. 최초 목록이 확인되지 않은 상태는 실제 매핑이 비어 있어도 미확인이다.

| 관찰 | 기대 판정 |
| --- | --- |
| 기존 허용과 승인된 Task 범위 일치, 또는 정확한 범위의 유효한 위임·승인 | 통과 |
| 확인된 경로·의존·HTTP 계약 위반, 근거가 없는 것으로 확인된 확대, 또는 만료 예외에 의존한 변경 | 위반 |
| 필수 원천·효력·후보의 내용을 확인할 수 없음 | 미확인 |
| 검사 대상 밖이라고 확인됨 | 적용 대상 없음 |

## 작성과 검수 예시

아래의 `items`와 `damage`는 가상의 업무 모듈이다. 예시의 이름은 실제 승인 목록이나 모듈 등록으로 사용하지 않는다.

[검사 입력과 기대 판정 예시](../../../work/records/harness/issue-106/artifacts/task-001-policy-cases.json)에서만 정책의 `java.modules`를 `exampleModules`로 대체한다. `exampleApprovals`는 가상 승인 레코드다. 사례의 `referenceState`와 `exampleTaskScope`는 독립 확인 결과를 모의한 값이다. `edges`의 타입 앞에는 기본 패키지를 붙이며 모든 참조는 운영 소스를 가정한다. HTTP 사례의 개발 전용 매핑은 프로덕션 미등록까지 확인됐음을 전제로 한다.

| 사례 | 기대 판정과 조치 |
| --- | --- |
| 등록된 `items` 모듈의 `backend/src/main/java/io/github/minokim/lumiawiki/items/application/ItemQuery.java`와 `backend/src/test/java/io/github/minokim/lumiawiki/items/application/ItemQueryTests.java`. 둘 다 `io.github.minokim.lumiawiki.items.application`을 선언한다. | 통과. `ItemQuery`와 대응 테스트의 소유는 `items`다. |
| 위 운영 파일을 `items/domain`에 옮겼는데 `items.application` 선언을 유지한다. | 위반. 역할에 맞는 목적지를 확정하고 패키지 선언·경로·참조를 함께 맞춘다. |
| `damage`가 등록된 `items.api.ItemReadApi`를 참조한다. | 역방향 경로가 없다면 통과. `items.infrastructure.ItemStore`를 직접 참조하면 위반이므로 필요한 조회를 `items`의 공개 계약으로 요청한다. |
| `items.web`이 `common.api.ApiFailure`를 사용한다. `common.api`에서 `items.api.ItemReadApi`를 사용하려 한다. | 앞의 참조는 통과. 뒤의 참조는 위반이므로 업무 처리 코드를 `items`에서 소유한다. |

**기존 Java의 수정·삭제** — 예를 들어 승인된 Task가 검색 결과의 폐기된 기본 정렬 제거만 허용하고, 없는 아이템의 `404`와 정상 응답의 필드·권한을 유지하도록 요구한다고 가정한다. 구현 전에 새 정렬 기대값으로 실패한 테스트를 기록한다(Red). 테스트 삭제나 기대값 완화가 승인에 없는 동작까지 바꾸는지 운영 코드와 함께 확인한다. 구현 뒤 같은 테스트와 `404`·응답 필드·권한의 관련 기존 테스트를 통과시킨 결과를 기록한다(Green). 환경 오류와 테스트 미실행은 미확인이다. 정렬 동작을 유지하는 내부 코드 이동이라면 승인된 예외 근거를 기록하고, 변경 전후 같은 관련 테스트의 통과를 확인한다. 실행 근거는 확인한 후보 식별자나 코드·테스트 지문, 실행 결과와 연결한다.
