# 최소 TDD hook 기준

<a id="current"></a>
## 적용

P1 동작 개발의 실수·근거 누락 방지를 위한 채택 기준이다. 실제 hook 코드·설정·등록·동작 검증은 첫 기반 구축에서 수행한다. 도구의 모든 쓰기 경로를 강제하거나 TDD의 의미를 자동 증명하는 장치로 보지 않는다. 조사·재검수 근거는 [Task 003 기록](<../../../work/records/phase-001/issue-15/artifacts/task-003-tdd-hook-proposal.md#research>)에 보존한다.

<a id="minimum"></a>
## 검사 시점·조건 — hook 두 지점과 결과 기록

별도의 AI 판정기 없이 로컬 검사기를 공유하는 안이다. 테스트 실행 래퍼가 결과를 기록하고, Codex 편집 전 hook과 Git 커밋 전 hook이 이를 읽는다. 기존 hook 설정은 설치 때 먼저 확인해 함께 연결하며 덮어쓰지 않는다.

| 시점 | 최소 조건·처리 |
|---|---|
| 작은 동작 착수 | 담당 Task 또는 직접 수행 Issue에 기대 동작·관련 테스트·대상 경로를 지정. 기존 기록을 재사용하고 별도 계획 원본을 만들지 않음 |
| Red 실행 | 정해진 테스트 실행 명령으로 실제 테스트를 실행해 결과 기록. 실행된 테스트가 있고 의도한 기대 동작이 실패했음을 확인. 종료 코드 하나만으로 판정하지 않음 |
| 구현 코드 편집 전 — Codex `PreToolUse` | 대상이 명확한 동작 코드 편집에는 현재 진행 중인 해당 동작 사이클의 유효한 Red 또는 등록된 예외가 필요. Green으로 종료한 사이클의 Red는 새 편집에 재사용하지 않음. 없으면 그 편집을 중단하고 필요한 다음 행동을 한 번에 안내. 테스트 작성·질문·조회는 막지 않음 |
| Green·리팩터링 뒤 | 같은 테스트와 관련 기존 테스트를 통과시키고 검증한 코드·테스트 내용에 대응하는 Green 기록을 갱신. Green 확인으로 해당 사이클과 그 Red의 구현 편집 허용권은 종료. 이후 새 동작은 새 Red, 순수 리팩터링·정정은 등록된 예외로 시작. 후속 코드·테스트·관련 설정 변경은 기존 Green을 무효화 |
| 커밋 전 — Git `pre-commit` | 스테이징된 동작 변경 범위와 검증한 후보 내용의 대응 확인. 완료 사이클의 Red/Green, 등록된 예외 또는 아래 기준의 기검수 통합 근거와 필요한 회귀 검사 근거가 없거나 내용이 다르면 커밋 중단. 검사기 자체는 테스트·자동 수정·커밋을 실행하지 않음 |
| PR 제출 전 | 기존 검수 절차에서 같은 검사기로 실제 제출 커밋의 내용을 확인. 동일 내용·명령·범위의 유효한 결과는 재사용 |

초기 편집 전 검사는 경로를 정확히 판독할 수 있는 `apply_patch`를 우선한다. 임의 셸 쓰기·외부 IDE 편집까지 완벽하게 사전 차단한다고 주장하지 않는다. 이 경로의 변경도 커밋 후보 검사에서 근거의 누락·불일치를 확인한다. 분류할 수 없는 동작 변경은 자동 통과시키지 않고 검수할 항목으로 남긴다. Git hook도 우회 가능한 로컬 장치이므로 기존 검수를 대체하지 않는다.

동작의 기대 결과·실패 이유가 타당한지, 테스트가 구현을 복제하거나 약화됐는지는 작성자와 기존 검수자가 판단한다. 기계 검사는 실제 실행·순서·범위·내용 대응을 확인하며 의미 판단을 대신하지 않는다.

Red의 편집 허용권과 완료 사이클의 검증 이력은 구별한다. 진행 중 사이클에서 필요한 여러 구현 수정을 할 수 있지만 Green으로 닫은 뒤에는 같은 경로·테스트·명령이라는 이유만으로 새 동작에 과거 Red를 사용할 수 없다. 원래 Red/Green은 제출·통합의 이력 근거로 보존한다.

<a id="exceptions"></a>
## 적용 범위·예외

- 대상: 서버 로직·API, 프런트 상태·사용자 조작, DB 구조·제약 등 동작 변경. 실제 대상 경로는 담당 작업에서 명시한다.
- 문서·정적 디자인·동작을 바꾸지 않는 단순 설정·생성물에는 Red를 요구하지 않고 기존의 적합한 검증을 수행한다. 동작을 바꾸는 SQL·설정을 단순 설정 예외로 숨기지 않는다.
- 순수 리팩터링은 변경 전 관련 테스트 통과를 기준으로 시작하고 변경 뒤 같은 동작·관련 테스트의 통과를 확인한다. 새 동작이 섞이면 해당 부분은 새 Red가 필요하다.
- 기검수 변경의 내용 보존 squash/merge와 검증 결과를 다른 worktree에서 확인하는 작업은 새 동작 작성과 구분한다. 보존된 원본 commit/tree·검증 범위·근거와 실제 통합 후보의 대응을 확인해 승계하며 과거 Red를 새로 만들지 않는다. 충돌 해결·새 동작·의존성 변경 등 달라진 부분에는 현재 범위의 TDD 또는 해당 예외와 필요한 결합 결과 회귀 검증을 요구한다.
- 테스트 실행 환경·무동작 타입/시그니처를 마련하는 초기 작업은 이유·범위와 별도 검증을 기록한다. 이 예외로 기능 로직 구현을 선행하지 않는다.
- 요구 오류나 테스트 오류 정정은 이유·기대 결과의 근거를 기록한다. 실패를 없애기 위한 assertion 삭제·기대값 복사는 허용하지 않는다. 테스트 내용이 바뀌면 기존 근거를 무효화하고 새 실행으로 확인한다.
- 환경 오류·Docker 연결 실패·테스트 미발견·명령 실패는 Red가 아니라 미확인이다. 원인을 해결하거나 제한을 기록하며 완료로 바꾸지 않는다.
- Red 중에도 질문·일시 중단·턴 종료는 허용한다. 완료·커밋 검사와 대화 종료를 구별한다.

<a id="evidence"></a>
## 근거·재사용

근거에는 담당 작업, 저장소·worktree, 작은 동작 식별자, 대상·테스트 경로, 실행 명령, 실행된 테스트와 실패/통과 결과, 순서, 관련 파일 내용의 지문을 포함한다. 지문은 실제 내용의 동일성 확인용이다. 관련 테스트 입력·의존성 잠금 파일·테스트 설정도 해당 범위의 재사용 조건에 반영한다.

테스트 실행 래퍼만 결과를 기록하고 hook 검사기는 읽기 전용으로 판정한다. 기계가 읽을 수 있는 테스트 실행 결과를 사용하며 대화의 “실패했다/통과했다” 선언을 실행 증거로 읽지 않는다. 비밀 환경변수·전체 대화를 수집하지 않는다.

진행 중 사이클의 실행 상태는 담당 작업의 Git 제외 임시 위치에서 관리한다. 제출 시 담당 기록에는 검증한 원본 commit/tree 또는 기준 commit과 대상 코드·테스트 내용의 지문, 실행 명령·결과, Red/Green 순서·검수 근거를 간결하고 다시 대조할 수 있게 보존한다. 임시 자료·브랜치 정리 전에 이 최소 근거가 원래 작업의 정식 기록에 남았는지 확인한다. 원시 출력의 영구 누적·중복 첨부는 기본으로 만들지 않으며 보존 영역 `harness-design/`·`.harness-state/`는 조회·기록 위치로 사용하지 않는다.

부분 스테이징은 작업 파일과 다르다는 이유만으로 거부하지 않는다. 실제 인덱스의 후보 내용이 검증한 후보와 일치하는지 판단하고, 일치하지 않으면 그 후보에 대한 검증이 필요하다. PR에서는 실제 제출 커밋을 같은 방식으로 대조한다.

다른 worktree의 진행 중 Red 편집 허용권은 재사용하지 않는다. 다만 기검수 통합 또는 명시적인 후보 검증에서는 보존된 원본·대상 내용·명령·근거와 현재 후보의 대응을 확인해 검증 결과를 승계할 수 있다. 원본 내용이 같아도 의존성·테스트 설정·결합 맥락이 달라지면 영향 범위의 Green/회귀 검증을 추가한다. 보존 근거가 없거나 대응이 미확인이면 자동 통과하지 않고 이를 미확인으로 반환하며 과거 Red를 꾸며 만들지 않는다.

<a id="cost"></a>
## 비용 기준

- hook의 AI·서브에이전트·네트워크 호출은 0회. TDD 사이클마다 테스트 작성자·구현자를 별도 호출하지 않는다. 기존 커밋 전 별도 검수는 유지한다.
- hook은 명시한 대상·근거·변경 목록만 읽는다. 전체 대화·work 기록·전체 저장소를 매번 탐색하지 않는다.
- hook은 테스트를 실행하지 않는다. 개발 사이클에서는 선택한 테스트·관련 기존 테스트를, 제출 전에는 영향을 받는 프로젝트 영역의 회귀 검사를 한 번 수행한다. 내용·명령·범위가 같으면 유효한 결과를 재사용한다.
- 검사 시간 목표는 호출당 3초 이내, 성공 시 무출력, 실패 시 이유·대상·다음 행동을 5줄 이내로 제한한다. 이는 미측정 제안값이며 첫 기반 구축에서 실측한다. 테스트 실행 시간과 구별하고 초과하면 검사 범위를 줄이거나 실행 시점을 조정한다.
- 검사 실패의 자동 재시도·자동 수리·`Stop` 기반 강제 이어하기는 초기 범위에서 제외한다. 시간 초과·판정 불능을 성공으로 취급하지 않고 제한을 반환한다.
- 지원 트리거·신뢰 설정·중복 실행 방지·해제 방법을 확인한 뒤 최소 두 지점만 연결한다. 기존 상태 검사와 같은 범위·근거 재사용 원칙을 따른다.

<a id="acceptance"></a>
## 첫 기반 구축에서 확인할 결과

1. Red 없이 대상 구현 편집 시 검사 실패, 실제 Red 확인 후 편집 허용. Green 종료 뒤 같은 경로·테스트·명령의 과거 Red로 새 동작 편집 시 거부하고 새 Red 또는 등록된 예외를 요구.
2. 유효한 Green·실제 제출 후보 내용 일치 시 정상 처리, Green 뒤 코드·테스트·관련 설정 변경 시 이전 Green 재사용 거부. 작업 파일과 다른 부분 스테이징이라도 검증한 후보와 같으면 허용하고 검증하지 않은 후보이면 미확인 처리.
3. 환경 오류·테스트 0개·대화상 통과 선언만으로 Red/Green을 만들지 못함.
4. 문서 변경·등록된 순수 리팩터링·테스트 환경 준비 예외가 정상 흐름을 막지 않으며 동작 변경 누락은 제출 검사에서 발견.
5. 실제 Codex 편집과 Git 커밋 경로에서 작동하고 Windows·worktree 분리·현재 hook 신뢰 및 기존 hook 보존을 확인.
6. 위 비용 목표·출력 제한을 실측하고 hook 상태가 Task 완료·부모 상태·PR 절차를 자동 변경하지 않음을 확인.
7. 내용 보존 squash/merge·다른 worktree 확인에서 보존된 원본·검수 근거와 현재 후보의 대응을 확인해 과거 Red 재실행 없이 통합 가능. 임시 자료 정리 뒤에도 최소 근거로 대조 가능하며 근거 누락은 미확인 처리. 충돌 해결·새 동작·의존성 변경은 달라진 범위와 결합 결과를 추가 검증하고 자동 면제하지 않음.

기준은 현재 Task 003에서 채택했고 실제 구현·검증은 첫 기반 구축 과제에서 수행한다. [Task 005](<../../../work/records/phase-001/issue-15/task-005.md#goal>)가 필수 결과와 수용 조건으로 배정하고 [Phase 착수 조건](<../../../work/records/phase-001/phase.md#tdd-readiness>)에서 첫 기능 구현 전 완료를 확인한다. 기준 채택은 hook 동작 검증 완료가 아니다.

생성·수정 후 자동 포맷과 커밋 후보의 형식 검사는 [코드 품질 기준](<코드 품질.md#formatting>)의 별도 단계로 연결한다. TDD 근거 검사기는 읽기 전용을 유지하며 형식 검사 비용과 TDD 검사 비용을 구분한다.
