## Spring 서비스·DB·Python의 갱신 역할

#43의 일반 갱신은 Java/Spring 서비스를 기본 처리 경로로 둔다. Spring 서비스는 업무 규칙·트랜잭션·갱신 순서와 오류/응답 처리를 담당하고, DB는 PK·UNIQUE·FK·NOT NULL 등 무결성 검사를 담당한다. F1~F3에서 확정한 키·참조/삭제·필수값 정책은 유지한다.

현재 서비스 범위의 변경 처리는 업무 변경 하나와 필요한 종속 값을 Spring 서비스 트랜잭션 하나로 처리하고, 실패한 업무를 부분 커밋/성공으로 표시하지 않는 최소 범위로 구체화한다. 합의한 기본 무결성/PK 보호·입력 검사와 종류 순환 방지는 유지한다. 동시성은 L-A에 따라 관련 쓰기에서 패치/지도 기준 표와 종류 부모 변경 범위의 순서를 맞춘다. 공개 조회에 같은 잠금을 요구하지 않으며 구체 SQL의 실제 검증은 생성 승인 뒤다. [잠금 계약](../../../db/model/writes-and-checks.md#catalog-locking)을 따른다.

공통 전체 advisory lock/고정 키·모든 쓰기의 기대 원본 비교·조회 격리 일괄 강화·신규 교정 DB 장부·공통 SQL 30초/상세 멱등·재시도 체계는 초기 범위에 두지 않는다. 등급은 지정 관리자가 원자료와 영향을 확인해 수정하며 코드는 기본 입력·DB 검사를 적용한다. 같은 대상의 오입력은 같은 ID에서 고치고 필요한 이유/근거를 기존 작업 기록에 남긴다. 교정/변경 자동 판별·교정 플래그/전용 진입점·등급 전용 guard는 두지 않는다. 실제 자료 수정은 #45의 허용 범위를 따른다. [업무 범위와 등급 규칙](../../../work/records/phase-001/issue-43/artifacts/task-001-updates.md#minimum-change-contract)을 따르며 M1~M3·P1·B1~B3, D1~D4 미정과 자료/DB/구현 보류를 적용한다.

동일한 업무 규칙을 공용 DB 함수에 병렬 구현하는 방식은 기본으로 두지 않는다. 추가 DB 함수·trigger·복합 검사·고정 필드 보호가 필요한지는 규칙의 성격과 서비스 밖 쓰기의 허용 범위를 구별해 별도로 결정한다. 업무별 정확한 변경 대상·필요한 잠금/격리·새 API/권한·개별 복구 수단은 해당 범위에서 정한다. 최소 트랜잭션 경계가 이들 세부를 자동 확정한 것은 아니다.

후속 획득의 지역 참조는 [C-A 계약](../../../db/model/consumer-references.md#current)에 따라 지속 region.id FK로 두고, 조회 패치에서의 소속은 서비스가 검사한다. 이 검사/저장과 지도·패치 순서 변경은 L-A의 관련 기준 표 잠금에 함께 참여한다. 초기 설치는 M-A의 공용 PK guard/8개 표/권한을 한 파일로 묶으며, 실제 생성 직전 전체 구조를 사용자에게 다시 확인받는다. 이 계약은 후속 본행의 전체 키/유효 구간이나 SQL 실행까지 승인한 것이 아니다.

Python에는 적합성이 확인된 개별 작업만 배정한다. 필요해지면 담당할 일·선택 이유·입출력·Spring/DB와의 연결·검증 방법을 제안하고 새 결정은 사용자에게 먼저 확인받는다. 현재 Python의 구체 역할·직접 DB 갱신·서비스 호출 방식이나 도구 도입은 정하지 않았다. 실제 자료 처리 수단은 담당 과제의 입력·권한·보류 조건을 따른다.

[담당 Task의 역할 분담과 후속 미정](../../../work/records/phase-001/issue-43/artifacts/task-001-updates.md#f4-path)을 따르며, 설계 채택을 실제 자료·DB 작업의 재개나 동작 검증 완료로 처리하지 않는다.

### 서비스 밖 SQL·자기 부모 CHECK·공통 PK 변경의 채택 범위

F4-S1에 따라 서비스 밖에서는 자료를 바꾸지 않는 조회와 사전에 검토한 예외 쓰기를 허용하는 원칙을 확정한다. 일반 등록/수정은 Spring 업무 경로를 따른다. 예외 쓰기는 대상·이유·필수 검사·동시 변경 통제·실패/복구를 준비한 작업 단위로 검토하며, 실제 SQL·대상 행·도구·교정 실행을 이 원칙만으로 승인하지 않는다. 서비스 안의 JPA·직접 작성 SQL은 Spring 업무 경로에 포함하고, 변경 함수·COPY 등도 실제 효과가 쓰기라면 같은 경계를 따른다.

F4-S2에 따라 종류의 자기 부모 참조는 DB CHECK로도 거부한다. 확인된 루트의 부모 NULL과 다른 종류를 가리키는 정상 부모는 유지한다. 미확인 부모를 루트로 만들지 않으며, 긴 순환·동시 부모 변경까지 이 CHECK만으로 보장하지 않는다. 실제 열/제약과 별도 순환·동시성 수단은 구현 전에 구체화한다.

F4-S3에 따라 Task 43-001의 기존 공통 행은 일반 UPDATE로 PK 값을 바꾸지 않는다. 참조 없는 행에도 같은 정책을 적용하고, 종류 이름/부모 대상 변경과 같은 ID의 등급 교정은 PK 값 변경과 구별한다. 보호 방식은 [P1의 채택 범위](#pk-update-protection)를 따른다. 구체 trigger/함수·표/열·오류 매핑·권한, ON UPDATE·명시 ID 복원 INSERT·시퀀스 정합성은 별도 확인한다. 후속 버전/연결 행의 미정 키 배치로 이 결정을 확대하지 않는다.

실제 계정/권한·전체 DB 복구·TRUNCATE/대량 제거·제약 해제·스키마 변경까지 예외 쓰기로 포괄 승인하지 않는다. 새 환경용 app/Flyway 접속 분리는 구현·격리 검증했지만 기존 DB의 실제 이관과 업무 표별 권한은 미적용이다. 설계로 직접 쓰기 차단까지 구현됐다고 표시하지 않는다. [확정한 정책과 잔여](../../../work/records/phase-001/issue-43/artifacts/task-001-updates.md#f4-direct-sql)를 따르고 실제 자료·DB 작업 보류는 유지한다.

### 공통 PK 값 변경의 보호 방식

F4-P1-A에 따라 Task 43-001의 기존 공통 행은 일반 AFTER UPDATE 행 trigger와 Spring 서비스 검사로 PK 값의 일반 변경을 보호한다. DB는 UPDATE 처리와 BEFORE trigger 처리 뒤의 이전/새 PK 값을 비교해 실제 값이 바뀌면 오류로 거부한다. Spring 서비스는 허용된 업무 속성의 갱신과 입력·업무 오류를 처리한다.

같은 PK 값 재대입은 PK 변경 오류로 거부하지 않고, 정상 업무 속성·종류 이름/부모 대상 변경·같은 ID의 교정은 각 계약을 따른다. SQL의 수정 열 목록에 PK가 있는지만으로 실제 값 변경을 대신 판정하지 않는다. 이 보호 방식은 전체 업무 흐름의 DB 병렬 구현이나 커밋까지 지연하는 constraint trigger를 확정한 것이 아니다.

이름/대상·오류·함수 권한은 [P1-N·E·R 채택 계약](#pk-guard-contract), 본문 구성과 초기 설치는 [P1-F·I 채택 설계](#pk-guard-body-install)를 따른다. 실제 표의 전체 DDL·마이그레이션 버전/파일 배치·요청 필드/예외 연결·역할별 소유/상속/권한 적용은 구현 전에 별도로 확인받는다. 실제 권한 분리·적용 시점·정비/복원·ON UPDATE·업무 단위/롤백 계약도 미정이다. [확정한 보호 방식과 잔여](../../../work/records/phase-001/issue-43/artifacts/task-001-pk-protection.md#f4-pk-guard)를 따르며 실제 SQL·DB 작업을 수행하거나 검증한 것으로 표시하지 않는다.

#### P1-N·E·R의 채택 계약

P1-N-A에 따라 공용 함수 `public.reject_common_pk_update()` 하나와 M-A의 지역 두 표를 포함한 아래 표별 AFTER UPDATE 행 trigger 이름을 사용한다. 함수는 인자 없는 trigger용 함수이며 이전/새 `id`만 검사한다. 다른 표 조회·동적 SQL·대상 표 자동 검색을 추가하지 않는다. 이는 구현할 이름/대상 계약이며 실제 DB의 존재·설치·검증을 뜻하지 않는다.

| 공통 대상의 PK                 | trigger 이름                              |
| ------------------------------ | ----------------------------------------- |
| `public.season.id`             | `trg_season_reject_pk_update`             |
| `public.game_patch.id`         | `trg_game_patch_reject_pk_update`         |
| `public.region.id`             | `trg_region_reject_pk_update`             |
| `public.item_category.id`      | `trg_item_category_reject_pk_update`      |
| `public.item_grade.id`         | `trg_item_grade_reject_pk_update`         |
| `public.weapon_type.id`        | `trg_weapon_type_reject_pk_update`        |
| `public.region_map_version.id` | `trg_region_map_version_reject_pk_update` |
| `public.region_map_member.id`  | `trg_region_map_member_reject_pk_update`  |

PK 외 필드·종류의 부모 참조·업무 번호/정렬값과 아이템/스킬·버전/귀속/관계 행·Flyway 관리 표로 자동 확대하지 않는다. 다른 컬럼·유일성·관계·지역의 시즌/이력 표현과 무기 종류 대응은 별도 확인한다.

P1-E-A의 DB 오류는 이 guard가 실제로 거부할 때 전용 SQLSTATE `LW001`, 고정 메시지 `Common primary key cannot be changed.`를 사용한다. 다른 제약이 먼저 거부하면 해당 코드를 유지하며 모든 PK 변경 시도가 항상 `LW001`을 낸다고 가정하지 않는다. 문구 파싱이나 모든 무결성 오류의 일괄 PK 오류 변환을 사용하지 않는다.

| 발생 단계                                                 | 확정한 응답 계약                                                                                   |
| --------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| Spring이 요청 계약에서 식별자 변경 시도를 명시적으로 확인 | 기존 400 `API_INPUT_INVALID`. 실제 입력 필드·DTO·수정 API는 해당 계약에서 확인                     |
| 저장/flush/커밋에서 예상 밖 guard 실패                    | 기존 500 `API_INTERNAL_ERROR`. 요청 잘못임이 확인되지 않은 실패를 사용자 오류로 일괄 전환하지 않음 |
| 관리 도구의 직접 SQL                                      | DB SQLSTATE·고정 메시지. HTTP 응답으로 취급하지 않음                                               |

기존 ProblemDetail·안전한 로그 정책을 유지하고 SQL·표/열·ID·내부 예외를 HTTP 응답에 추가하지 않는다. 원본 예외 메시지를 안전한 업무 오류로 포장하지 않는다. 실제 예외 원인/연결 오류의 식별과 Spring 연결 코드는 구현 전에 대조한다.

P1-R-A에 따라 함수는 `SECURITY INVOKER`, 탐색 경로 `pg_catalog`로 두고 소유/정의·trigger 설치 관리는 P2의 구조 변경 주체가 담당한다. 새 함수의 기본 `PUBLIC EXECUTE`를 회수하며 설치 주체는 필요한 함수 EXECUTE·대상 표 TRIGGER 능력을 갖도록 연결한다. 일반 DML 역할에는 직접 함수 EXECUTE를 미리 추가하지 않는 최소 권한 계약이다. 기존 다른 함수 전체의 권한을 일괄 바꾸지 않는다.

소유/설치 역할·업무 역할과 분리 시점은 [O-A·C-A·T-A 계약](<로컬 DB 최초 구동.md#pk-guard-role-install>)을 따른다. 스키마/표별 권한의 실제 GRANT/회수·기존 객체 이관·실행은 별도다. PostgreSQL 18의 생성/실행 경로에 근거한 계약이며, 적용 전에 비소유자 DML 역할이 직접 함수 EXECUTE 없이 guard를 실행하는지 격리 검증해야 한다. 검증 가정이 다르면 추가 권한을 임의로 부여하지 않고 다시 확인받는다. 현재 공용 개발 계정 유지와 실제 자료·DB 작업 보류를 지키며 권한 적용/검증 완료로 표시하지 않는다.

#### P1-F·I의 함수 본문·초기 설치 설계

P1-F-A에 따라 PL/pgSQL 함수 안에서 `OLD.id IS DISTINCT FROM NEW.id`를 비교하고 실제 값이 바뀔 때만 확정한 `LW001`·고정 메시지로 오류를 낸다. 정상 경로는 `RETURN NEW`로 마치며 각 AFTER UPDATE 행 trigger에는 WHEN이나 UPDATE OF를 넣지 않는다. 함수는 행을 수정하거나 오류를 조용히 무시하지 않는다. NOT NULL·다른 제약의 선행 실패와 기존 Spring 오류 계약은 유지한다.

P1-I-A는 신규 일반 표의 최초 설치에 적용한다. 공용 함수의 최초 CREATE와 PUBLIC EXECUTE 회수는 같은 마이그레이션 트랜잭션에 두고, 각 보호 표의 CREATE와 해당 trigger 부착도 같은 마이그레이션 트랜잭션에 둔다. 함수는 첫 trigger보다 먼저 한 번 생성한다. 여러 표를 한 설치 단위로 묶을 수 있으며 한 표당 한 파일을 강제하지 않는다.

최초 설치는 plain CREATE로 이름 충돌을 드러내고, 자동 OR REPLACE·DROP·IF EXISTS/IF NOT EXISTS로 교체하거나 건너뛰지 않는다. 반복 적용은 Flyway 이력으로 관리한다. Flyway가 관리하는 설치 단위에 별도 BEGIN/COMMIT을 추가하지 않으며 group/mixed/비트랜잭션 실행 같은 새 설정은 도입하지 않는다. 실제 트랜잭션과 실패 롤백은 격리 검증으로 확인한다.

실패한 표 설치 단위가 롤백되어 새 표만 보호 없이 남지 않아야 한다. 이전에 성공한 다른 마이그레이션까지 모두 되돌아간 것으로 보지 않는다. 기존 표·다른 객체 형태·분할 표를 대상으로 해야 하면 이 초기안을 자동 적용하지 않고 배치·검증을 다시 확인한다.

실제 표 DDL/생성 의존 순서·마이그레이션 버전/파일·역할별 구체 권한/기존 객체 이관·요청/예외 연결은 별도다. 소유/설치와 분리 시점은 [O-A·C-A·T-A 계약](<로컬 DB 최초 구동.md#pk-guard-role-install>)을 따른다. [확정한 문서 SQL 설계안과 검증 계획](../../../work/records/phase-001/issue-43/artifacts/task-001-pk-protection.md#f4-pk-body-ddl)을 구현 SQL 파일이나 실행 결과로 표시하지 않는다. 실제 자료·DB 작업 보류를 유지한다.

## 권한 목적의 목표 경계

F4-P2-A에 따라 업무·조회·예외 정비·구조 변경의 권한 목적을 구별하는 목표를 확정한다. 일상 업무/정비에는 소유권·슈퍼유저·구조/trigger 변경 능력을 주지 않는 방향이다.

| 권한 목적        | 확정한 목표                                                                             |
| ---------------- | --------------------------------------------------------------------------------------- |
| Spring 업무 처리 | 승인한 업무에 필요한 능력을 부여하고 구조/보호 장치 변경 능력과 구별                    |
| 조회             | 자료를 바꾸지 않는 합의한 조회. 함수 등의 간접 변경 능력도 실제 권한 확인에 포함        |
| 예외 정비        | S1의 검토된 대상·목적에 필요한 쓰기. PK 보호 해제·소유권·구조 변경을 자동 포함하지 않음 |
| 구조 변경/Flyway | 승인한 공용 SQL 이력과 보호 장치의 정의 관리. 일상 업무/조회/정비와 능력을 구별         |

소유/설치·업무 역할과 로컬 접속·분리 시점은 [O-A/C-A/T-A](<로컬 DB 최초 구동.md#pk-guard-role-install>)를 따른다. 조회/정비 역할·표/열 GRANT·최초 준비/기존 이관 수단은 해당 범위에서 확인한다. 현재 새 환경용 접속은 app/Flyway로 분리했고 최초 역할/권한을 격리 검증했다. 기존 DB의 상태/이관과 제품 표별 업무 권한은 미확인·미적용이다. 같은 DB 계정의 SQL이 Spring을 거쳤는지를 DB가 구별하지는 않는다.

P1의 PK 보호 방식과 P2의 권한 목적 목표를 구별한다. P1은 [AFTER UPDATE 행 trigger + Spring 검사](#pk-update-protection)와 [N·E·R 계약](#pk-guard-contract)을 채택했고 실제 DDL·예외 연결·역할별 권한 적용/검증은 별도 확인한다. [담당 검토와 잔여](../../../work/records/phase-001/issue-43/artifacts/task-001-pk-protection.md#f4-pk-guard)를 따르며 실제 자료·DB 작업 보류를 유지한다.

## 복원·정비 예외의 적용 시점

일반 저장/조회 구현은 정상 ID 발급·참조/업무 제약·PK 변경 거부와 해당 업무의 실패 처리를 준비한다. 명시 ID 복원·그에 따른 시퀀스 보정·기존 키 재배치·개별 예외 SQL의 전체 실행 절차는 실제 필요 시점에 따로 검토하며 일반 구현의 일괄 선행 조건으로 두지 않는다. 예외 수단이 미정이라는 이유만으로 독립적인 일반 구현을 막거나, 예외 검토 전 PK/권한 정책을 완화하지 않는다.

기존 DB를 계속 쓰는 경우의 필요한 대상별 소유/권한 이관은 T-A대로 최초 P1 설치 전에 수행한다. 빈 새 환경의 준비에 범용 이관/자동 복구 도구를 요구하지 않는다. 담당·필요 입력·시점은 [조건부 예외 표](../../../work/records/phase-001/issue-43/artifacts/task-001-pending.md#conditional-exceptions)를 따른다. 실제 자료·DB 작업과 구현 파일 생성 보류는 유지한다.
