# 테스트·TDD 개발 기준

<a id="current"></a>
## 테스트 구성·범위

| 대상 | 채택한 구성·범위 |
|---|---|
| 서버 로직·API | 기존 Boot 테스트 starter의 JUnit·Mockito와 MockMvc 계열 도구로 버전 선택·제작 관계·루트 계산의 핵심 규칙과 요청 검증 확인 |
| DB 연동 | Testcontainers로 테스트 전용 `postgres:18.6`을 생성해 Flyway 마이그레이션·JPA 매핑·핵심 저장/조회 확인. 개발 DB·데이터 볼륨과 분리 |
| 프런트 로직·컴포넌트 | Vitest + React Testing Library. 검색·필터 초기화, 장비 입력 변경에 따른 이전 결과 표시 등 핵심 상태·조작 확인 |
| 화면 사용 흐름 | 구현 화면을 실제 브라우저에서 조작해 목록→상세→복귀, 전체 제작 트리, 루트 입력·계산 흐름 확인. 초기에는 직접 조작 검증을 기본으로 하고 브라우저 자동화 도입은 반복 검증 부담에 따라 판단 |

사용자는 위 테스트 구성에 TDD를 함께 적용하기로 했다. 실제 테스트 구현은 해당 기능 작업에서 수행하며 핵심 판단·실패 조건에 필요한 자동 검증부터 둔다. 구현을 그대로 반복하는 테스트·고정 커버리지 수치·전체 화면 스냅샷을 초기 공통 완료 조건으로 두지 않는다. 브라우저 직접 조작 검증과 내부 자동 검증은 기존 화면 검증 기준에 따라 함께 수행한다.

추가 테스트 패키지·DOM 실행 환경·DB 연결 설정은 첫 기반 구축에서 호환되는 버전을 선정·잠금하고 실행 검증한다. 실제 테스트 결과는 담당 기능 기록에 남긴다.

<a id="frontend-testing"></a>
## 프런트 동작 검증

우선 검증할 예는 검색어·필터 변경과 초기화, 늦게 온 응답이 현재 결과를 덮어쓰지 않는 처리, 상세/목록 이동 시 조건 복귀, 버튼으로만 계산 요청 실행·입력 변경 뒤 이전 조건 결과 표시, 로딩·빈 결과·ProblemDetail 오류의 표시다. TanStack Query를 쓰더라도 이 제품 동작은 실제 컴포넌트와 조작을 통해 검증하고 라이브러리 내부 구현을 다시 테스트하지 않는다. 테스트별 Query 상태와 Router 맥락은 분리하고 필요한 API 경계만 제어한다.

실제 스크롤 위치·화면 배치·전체 사용 흐름은 기존 기준대로 브라우저에서 함께 확인한다. 모든 컴포넌트·정적 스타일에 테스트를 일괄 추가하거나 커버리지 수치·큰 스냅샷을 목표로 하지 않는다. 이번 질문으로 브라우저 자동화 도구나 추가 테스트 라이브러리를 새로 확정하지 않는다. 테스트 환경은 첫 기반 구축, 기능별 테스트 코드는 각 기능 구현에서 작성한다.

<a id="user-checklist"></a>
## 사용자 확인 목록

구현 전 조작·기대 결과의 작성·공유, 구현 후 AI 선검증·사용자 확인 안내는 [공용 검증 기준](<../operations/검증과 완료.md#user-verification>)을 따른다. 계획·실제 자동 검사·AI 브라우저 확인·사용자 응답을 구별해 담당 Task 또는 직접 수행 Issue에 기록한다.

<a id="tdd"></a>
## 기능 개발 순서

1. 기능 화면·입출력·주요 상태를 먼저 설계하고 검토한다. 동작 구현 전에 [사용자 확인 목록](<#user-checklist>)을 작성·공유한다. 기존 화면 설계 선행 기준을 유지한다.
2. 다음에 구현할 작은 동작의 기대 결과를 테스트로 작성하고 의도한 미구현 동작 때문에 실패하는지 확인한다. 도구·환경 오류를 의도한 실패의 근거로 보지 않는다.
3. 해당 테스트를 통과하는 최소 동작을 구현하고 관련 테스트를 실행한다.
4. 코드·테스트 구조를 검토하고 필요한 리팩터링 뒤 관련 테스트가 계속 통과하는지 확인한다. 다음 작은 동작에서 반복한다.
5. 기능이 갖춰지면 같은 확인 목록을 기준으로 실제 화면 조작과 필요한 내부 검증을 수행하고, AI 확인 결과·미확인과 사용자가 확인할 방법을 구분해 전달한다.

핵심 서버 로직·API·프런트 상태/상호작용과 DB 저장·제약 등 검증 가능한 동작에 적용한다. 문서·단순 설정·정적 화면 모양은 대상에 맞는 확인을 사용하며 TDD 형식을 강제하지 않는다. 동작 개발에서 테스트 우선 절차를 적용하기 어려운 예외는 담당 기능 Task에 이유·대체 검증을 남긴다.

실패·통과·리팩터링 후 재검증의 대표 근거는 담당 Task에 간결하게 기록한다. 모든 반복의 원시 출력·별도 첨부를 쌓거나 단순 구현을 복제하는 테스트를 늘리지 않는다. 테스트 환경·TDD 자동화와 화면 설계 → TDD 동작 개발 → 화면 검증의 배정·구현 시점은 [담당 Task의 인계 기준](<../../../work/records/phase-001/issue-15/task-003.md#tdd-automation-handoff>)을 따른다.

<a id="hook"></a>
## 최소 자동화와 착수 조건

[최소 TDD hook 기준](<TDD hook.md#minimum>)과 [자동 포맷 기준](<코드 품질.md#formatting>)을 적용한다. 첫 기반 구축에서 프로젝트 골격과 테스트 실행 명령을 만든 직후 연결·실측 검증하고, 첫 제품 기능의 동작 구현 전에 해당 근거를 확인한다. 기준만 채택한 상태를 실제 도입 완료로 보고하지 않는다. 실제 과제 배정은 [Task 003 인계](<../../../work/records/phase-001/issue-15/task-003.md#tdd-automation-handoff>)와 [Phase 선행 조건](<../../../work/records/phase-001/phase.md#tdd-readiness>)으로 추적한다.
