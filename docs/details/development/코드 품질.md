## TypeScript 7.0.2·6.0 호환 API 병행 확정

문제는 ESLint 자체보다 typescript-eslint가 사용하는 TypeScript 컴파일러 API다. 공식 지원 범위는 `>=4.8.4 <6.1.0`이며 Microsoft는 7.0의 API 미제공을 명시하고 6.0 호환 패키지와의 병행 방식을 안내한다.

기존 7.0.2 선택을 유지하면서 공식 npm alias 방식을 사용한다. `@typescript/native`라는 이름에 `typescript@7.0.2`를 연결해 타입 검사 명령 `tsc`를 제공하고, `typescript`라는 이름에는 `@typescript/typescript6`의 지원되는 6.0.x를 연결해 lint 도구가 필요한 API를 읽게 한다. 타입 검사를 두 컴파일러로 반복하지 않는다. 6.0.x의 실제 패치 버전은 기반 구축에서 배포 메타데이터·호환 범위를 확인해 기록한다.

설치 후 `tsc`가 7.0.2인지, typescript-eslint가 6.0 API를 읽는지와 실제 TSX·Hooks 정상/실패 예제를 확인해야 호환 해결로 판정한다. 향후 직접 지원이 확인되면 담당 구현 과제에서 호환성을 확인하고 호환 패키지를 제거한다. 현재는 위 병행 구성을 기준으로 삼는다.

## 문서·일괄 포맷팅과 hook 확정

문서 포맷은 Prettier로 관리하는 Markdown·JSON·YAML 등에 적용한다. Markdown은 `proseWrap: preserve`로 문단 줄바꿈을 유지하고 `embeddedLanguageFormatting: off`로 문서 안 코드 예제를 자동으로 다시 쓰지 않는다. 포맷 검사는 링크·내용·검수의 의미 확인을 대신하지 않는다.

루트 개발 도구용 `package.json`에 공통 명령을 두고, 작은 실행기가 Prettier와 backend의 Gradle Wrapper 명령을 호출한다. 앱 배치 `backend`·`frontend`·`db`는 유지한다. 프런트·문서의 Prettier는 공통 버전 하나로 관리하고 런타임 의존성으로 추가하지 않는다.

| 구현할 루트 명령       | 역할                                             |
| ---------------------- | ------------------------------------------------ |
| `npm run format`       | 관리 대상 전체의 Java·프런트·문서를 한 번에 포맷 |
| `npm run format:docs`  | 관리 대상 문서만 포맷                            |
| `npm run format:check` | 같은 범위를 수정 없이 검사. 형식 위반 시 실패    |

전체는 명시한 관리 대상·지원 형식 전체를 뜻한다. 루트 현재 안내·docs·harness·work의 현재 작성 문서·db의 Markdown 안내와 제품 코드를 허용 목록으로 지정하고, 새로 만드는 관리 문서도 포함한다. 보존 영역 `harness-design/`·`.harness-state/`는 경로 수집 전부터 제외한다. 외부 원자료·과거 원문/검증 증거 첨부·잠금 파일·생성물·빌드/캐시는 자동 수정 대상에서 제외한다. SQL은 원자료와 적용된 Flyway 이력의 무결성을 위해 초기 공통 자동 포맷 대상에 넣지 않으며 별도 수단을 무조건 추가하지 않는다.

자동 포맷은 다음 순서로 적용한다.

1. 기존 TDD `PreToolUse` 검사를 통과한 생성·수정 뒤 `PostToolUse`가 해당 허용 파일만 포맷한다. 초기에는 대상 경로를 정확히 얻을 수 있는 `apply_patch`를 연결하고, 삭제 파일은 처리하지 않는다.
2. 편집기가 한 수정은 저장 시 포맷으로 처리한다. 임의 셸·특수 도구를 포함한 모든 쓰기의 실시간 차단을 보장하지 않으며 명시적 포맷 명령과 커밋 검사로 보완한다. 별도 상시 파일 감시기는 초기 구성에 추가하지 않는다.
3. Git 커밋 전에는 실제 스테이징 후보의 형식을 읽기 전용으로 검사해 누락을 막는다. 부분 스테이징은 작업 파일이 아닌 후보 내용·설정으로 확인하며 자동 수정·자동 스테이징하지 않는다. 기존 TDD 근거 검사기는 그대로 두고 이 형식 검사를 같은 진입점에서 별도 단계로 연결한다. 이는 사용자 합의로 기존 근거 확인 전용 hook에 추가할 형식 검사이며 실제 연결은 첫 기반 구축에서 수행한다.
4. 포맷 후 최종 내용으로 테스트·검수 근거를 남긴다. 기존 Red/Green 뒤 내용이 바뀌면 해당 지문 근거는 그대로 재사용하지 않는다. 순수 포맷은 새 기능 Red를 요구하지 않는 비동작 예외로 기록하되 필요한 관련 재검증은 수행한다. hook이 스스로 테스트 결과를 갱신하거나 Green을 만들지 않는다.
5. 경로 정규화·파일별 중복 실행/수정 충돌 확인으로 범위 밖 쓰기와 재귀 포맷을 막는다. 성공은 무출력, 실패는 대상·이유·다음 행동을 짧게 알리고 자동 재시도·전체 저장소 재탐색·AI/네트워크 호출을 하지 않는다. 설치된 도구만 사용하고 hook에서 패키지·플러그인을 자동 설치하지 않는다. 실패·시간 초과·경로 판독 불능은 미확인으로 남겨 제출을 막고 편집 복구를 허용한다. `PostToolUse`의 실패는 이미 일어난 편집을 되돌린 것으로 보지 않는다.

Gradle 초기 구동·formatter 실행 시간은 기반 구축에서 실측한다. 기존 TDD 검사기의 3초 목표를 formatter를 포함한 측정 결과로 확대하지 않는다. 포맷이 느리면 대상 파일 제한·실행 방식부터 조정하고 형식 검증을 누락시키는 우회나 반복 모델 턴을 만들지 않는다.
