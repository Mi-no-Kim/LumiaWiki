# 게임 데이터 변경 관리

<a id="current"></a>

## 현재 결론

게임에서 실제로 바뀐 내용과 입력 오류의 정정을 구별하고 과거 기록/당시 상태를 보존한다. 수동 적용/되돌리기는 개별 변경 항목과 관련 영향을 기준으로 다룬다. 저장 구조·연결/복구 수단과 구체 운영 구현은 아직 정하지 않았다.

<a id="identity-information"></a>

## 내부 식별값과 지정한 숫자

대상 연결에 필요한 내부 식별값을 둔다. 별도의 게임 제공 코드나 관리용 코드 필드는 두지 않는다. 사용자가 규칙을 지정한 시즌 번호·시즌 및 버전 정렬값·지역 정렬값은 유지한다. 내부 식별값의 자료형·발급·API 전달은 [개발 기준](<../../개발 기준.md#internal-identifiers>)을 따른다. 구체 테이블·키·제약과 버전 참조 정합성의 구현은 후속 DB 설계에서 정한다.

<a id="season-information"></a>

## 시즌 정보

시즌에는 다음 정보를 구별해 둔다.

| 항목             | 규칙                                                                                         |
| ---------------- | -------------------------------------------------------------------------------------------- |
| 시즌 번호        | 1부터 시작한다.                                                                              |
| 표시 이름        | `시즌 1`과 같은 표시용 이름이다.                                                             |
| 시즌명           | 표시 이름과 별개의 문자열이다. 실제 값은 자료 등록 때 확인한다.                              |
| 내부 정렬용 숫자 | 시즌 1은 10, 시즌 2는 11이며 이후 시즌마다 1씩 증가한다. 시즌 번호와 별개 항목으로 관리한다. |
| 시작일·종료일    | 시즌의 시작일과 종료일을 저장한다.                                                           |

내부 식별값은 [공통 식별 기준](#identity-information)을 따른다. 날짜·미확인 값의 공통 처리는 [개발 기준](<../../개발 기준.md#datetime>)을 따르며 실제 미확인 값의 등록 허용과 시즌·버전 연결의 세부 제약은 해당 데이터 설계에서 정한다. 이번 정보 구체화의 담당 기록은 [Task 15-001](../../../work/records/phase-001/issue-15/task-001.md#registration-discussion)이다.

<a id="version-information"></a>

## 버전 정보와 정렬

버전에는 메이저 패치 번호와 마이너 패치 번호를 각각 필드로 두고, 소속 시즌의 내부 정렬용 숫자를 사용해 버전 정렬용 숫자를 정한다.

`버전 정렬용 숫자 = 시즌 정렬용 숫자 × 10000 + 메이저 패치 번호 × 100 + 마이너 패치 번호`

메이저 패치인 경우 마이너 패치 번호는 0이다. 별도의 적용 순서 필드는 두지 않고 정렬용 숫자를 사용한다. 이 규칙만으로 서비스의 자료 적용·공개 상태나 현재 적용된 최신 패치의 판정까지 확정하지 않는다.

버전 표기는 `시즌 번호.메이저 패치 번호.마이너 패치 번호`로 해석한다. 초기 기준인 `1.0.0`은 시즌 1·메이저 0·마이너 0이며, 시즌 정렬용 숫자 10을 사용한 버전 정렬용 숫자는 `100000`이다.

버전 이름(`version_name`)은 별도 정보로 둔다. 번호에서 생성한 문자열로 이 이름을 대체하지 않는다. 번호에 따른 표기·정렬 규칙은 유지하며 실제 버전 이름의 값은 자료 등록 때 확인한다.

버전별 패치 적용 일시를 저장한다. 내부 식별값은 [공통 식별 기준](#identity-information)을 따른다. 일시의 초 단위 정밀도·시간대·미확인 값 처리는 [개발 기준](<../../개발 기준.md#datetime>)을 따른다. 번호의 허용 범위와 실제 미확인 값의 등록 허용은 해당 데이터 설계에서 정한다.

게임 패치의 현재/예정은 패치 적용 시각과 현재 시각을 비교해 판정한다. 서비스 자료의 공개·적용은 이 판정과 별도로 다루며, 구체 방식과 자료가 준비되지 않았을 때의 동작은 해당 기능의 후속 설계에서 정한다.

<a id="version-applicability"></a>

### 변경이 있는 패치의 정보 등록

정보가 변경된 게임 패치에만 새 정보를 등록하고, 다음 변경 전까지 그 정보를 이어서 사용한다. 현재는 아이템 중심 방식으로 기본 정보·능력치·조합법·획득·배달 등 아이템 귀속 정보의 구성을 아이템 버전 기준으로 관리한다. 해당 구성에 변경이 있으면 새 아이템 버전으로 당시 구성을 보존한다. 이미 정한 스킬 대상·버전과 특정 스킬 버전 직접 참조는 유지한다. 구체적인 테이블·키 구성과 변경하지 않은 정보의 재사용 방식은 후속 설계에서 정한다.

조회는 이력에서 조회할 게임 패치에 유효한 아이템 버전을 선택하는 방식으로 한다. 현재 상태만을 위한 별도 사본은 두지 않는다. 이 선택은 지속적인 아이템 식별 대상이나 스킬 대상·버전의 구분을 없애는 것이 아니다. 선택한 버전의 능력치 표시용 캐시는 [능력치 원본·캐시 기준](<아이템 탐색과 상세.md#stat-information>)을 따른다.

정보별 독립 관리로의 전환 계획과 전환 조건은 [담당 Task](../../../work/records/phase-001/issue-15/task-001.md#version-strategy)에서 관리한다. 조회 시 같은 게임 패치의 유효 정보를 일치시키고 과거 정보를 보존하는 요구는 전환 전후에 공통으로 적용한다.

<a id="region-information"></a>

## 지역 정보

지역에는 내부 정렬용 숫자를 둔다. 시작값은 10, 증가값은 10으로 `10, 20, 30…`을 사용한다. 내부 식별값은 [공통 식별 기준](#identity-information)을 따른다. 구체적인 지역 순서 등 나머지 항목은 아직 정하지 않았다.

<a id="change-and-correction"></a>

## 변경·정정과 관련 영향

조회 정보의 버전을 일치시키고 현재 원본·과거 기록·목적별 가공 데이터를 구별한다. 과거의 유효한 근거를 현재 값으로 덮거나 특정 버전의 입력 오류 정정을 새로운 실제 게임 패치로 꾸미지 않는다.

패치 전체 원문, 대상별 원문 발췌, 서비스에서 구조화한 게임 변경 내용을 구별해 관리한다. 제공 SQL의 `patch_note.raw_text`, `patch_note_fragment`, `change_log`는 각각 이 역할에 해당한다. 실제 조회할 상태는 아이템 버전에서 읽고, 구조화한 변경 기록이 상태 저장을 대체하지 않는다. 원문·발췌·변경 기록의 구체 연결과 단계별 구현 범위는 후속 설계에서 정한다.

특정 패치의 일부를 수동 적용/되돌리는 기능을 포함하며 속성별 개별 변경 항목을 선택 단위로 삼는다. 동일 아이템의 여러 속성이 한 패치에서 함께 바뀌어도 각 속성의 변경을 따로 선택하여 적용하거나 되돌릴 수 있어야 한다. 선택한 항목에 연결돼 영향을 받는 모든 부분을 함께 조사/반영한다. 기능 확장에 따라 대상도 늘어나므로 완결된 영향 목록을 지금 고정하지 않는다. 사용자가 언급한 linked list는 연결 구상이며 물리 자료구조·갱신 알고리즘이나 Spring 채택을 확정한 것이 아니다.

입력 오류 정정의 구체 기록 방식은 후속 설계 때 정하며, 실제 게임 변경 기록과 섞지 않는다. 정정 저장/이력 방식·여러 항목의 묶음 처리·관련 대상의 구체 연결/복구와 화면은 미정이다. 실제 반영/미반영·검증/미확인·잔여는 [work](../../../work/README.md#start)의 담당 기록에서 확인한다. 실제 원자료/스키마가 주어지면 담당 원본을 참조하고 같은 사본을 독립 관리하지 않는다.

<a id="permissions"></a>

## 사용자 역할과 권한

수동 입력·정정·적용·되돌리기는 지정 관리자만 실행하고 일반 이용자는 공개된 조회·계산을 로그인 없이 사용한다. 관리자 계정/지정·인증 방식·세부 권한과 추가 계정 기능은 아직 정하지 않았다.

제품의 AI 변환·검토·공개 적용은 [단계적 전환](#ai-transition) 방향을 따른다. 도입 예정·비공개/미검증 자료의 구체 공개 시점과 세부 관리 권한은 후속 설계 대상이다.

<a id="ai-transition"></a>

## AI 변환의 입·출력과 단계적 전환

새로 게시된 패치노트 원문을 입력으로 받아 AI가 내용을 해석·구조화하고, 우리 서비스의 데이터로 자동 변환한다. 출력은 서비스에서 사용할 변환 자료이며, 아래 단계별 검토·공개 적용 흐름에 연결한다.

게시 감지·수집 방식, 변환 산출물의 구체 형식·저장/연결과 검증 절차는 후속 설계에서 정한다.

AI 변환 기능을 도입한 뒤에는 관리자 확인을 거치는 운영부터 시작해 AI가 맡는 범위를 점진적으로 넓힌다.

- 초반에는 AI가 패치노트의 아이템 변경 내용을 변환하고, 관리자가 내용을 확인·수정한 뒤 공개 적용한다.
- 이후에는 AI가 맡는 범위를 점차 넓힌다. 중간 단계를 몇 개로 나눌지와 각 단계의 구체 범위는 아직 정하지 않았다.
- 최종 목표는 AI가 변환 이후의 확인·수정·공개 적용 흐름까지 맡는 것이다.

초기 공개는 [프로젝트 공개 조건](<../../프로젝트 목표와 범위.md#delivery>)에 정한 AI 변환·관리자 확인/수정·공개 적용 단계에서 진행한다. 이후 단계별 AI 담당 확대의 전환 조건/시점·구체 검증 방법·오류/예외 처리와 관리자 개입 방식은 후속 설계에서 정한다. 초기 공개의 다른 기능·자료 조건도 해당 프로젝트 범위를 따른다.

<a id="item-skills"></a>

## 아이템 스킬의 대상·버전과 해석 범위

아이템 스킬은 지속적으로 같은 스킬을 가리키는 대상과 그 대상의 버전을 구별한다. 한 아이템에 여러 스킬을 연결할 수 있다. 초기에는 내부 이름과 설명 텍스트를 한 스킬 버전에 함께 보존한다. 스킬 버전에는 다음 필드를 둔다.

| 필드   | 의미                                  |
| ------ | ------------------------------------- |
| 대상   | 이 버전이 속한 아이템 스킬 대상 참조  |
| 이름   | 해당 버전의 내부 이름                 |
| 텍스트 | 해당 버전의 스킬 설명을 표현할 텍스트 |

JSON은 스킬 버전이 아닌 아이템과 스킬의 연결에 둔다. 아이템과 스킬의 연결에는 스킬 대상과 특정 스킬 버전을 모두 직접 참조하고 게임 패치 버전도 함께 참조한다. 지정한 스킬 버전이 속한 대상과 연결의 스킬 대상은 같아야 하며, 일치 검사 방식은 DB 설계 때 정한다. 실제 표시·해석할 설명은 지정한 스킬 버전을 따른다. 연결별 JSON에는 스킬 효과와 참조할 수식·계수를 구조화해 담고, 같은 스킬로 분류되면서 효과가 일부 다른 경우를 제어한다. 수식 정의는 별도로 두며 JSON은 이를 참조한다. 구체적인 테이블·키 구성과 연결의 변경 처리 방식은 후속 설계에서 정한다.

연결별 JSON의 저장 형식·P1 최소 검증은 [실제 개발 기준](<../../개발 기준.md#skill-json>)을 따른다. JSON의 소유·버전 참조·설명 텍스트와 수식의 역할은 이 문서의 기존 구분을 유지한다.

텍스트는 표시용이며 조건문과 함수를 사용할 수 있게 한다. 함수는 캐릭터 능력치 등을 입력받는 계산 결과를 표시할 수 있고, 조건문도 외부 정보를 참조할 수 있어야 한다. 실제 수식은 표시 텍스트와 별도로 정의한다. 텍스트는 연결별 JSON과 외부 정보를 사용해 표시를 제어한다.

외부 정보가 없는 일반 아이템 상세에서는 우선 텍스트 형태로 설명을 보여주는 방향이다. 텍스트 생성 문법, 조건별 문구와 외부 정보의 구체 처리 방식은 후속 설계에서 정한다.

한 스킬에 여러 작용이 포함될 수 있다는 도메인 설명도 유지한다. 허용 문법·함수 목록, JSON 스키마와 수식 참조 형식, 별도 수식 정의·이력, 외부 정보의 범위와 실행 방식은 아직 정하지 않았다. 아이템 중심 관리에서의 구체적인 연결·변경 처리, 내부 이름과 화면 표시·이름 검색의 관계도 후속 결정 사항이다. 단계별 구현 범위는 [P1의 합의한 범위](../../../work/records/phase-001/phase.md#agreed-data-scope)를 따른다.

수식에 관한 구체 논의는 [딜량 계산기 작업](<딜량 계산기.md#pending>) 때까지 미룬다. 그 전의 등록·표시·단계 범위 결정을 위해 수식 설계를 먼저 확정하도록 요구하지 않는다.

계산용 수식·실행 효과의 구체 지원 범위·표현·규칙·검증은 미정이다. 구조화할 방향의 합의와 실제 효과별 계산 지원·검증 완료는 구별한다. 표시 텍스트와 JSON에 같은 수식을 중복 관리하지 않도록 역할과 원천을 정한다. 계산 표현이나 템플릿을 마련하더라도 원래 설명 텍스트와 기존 도메인 정보는 보존한다. 계산 기능의 요구는 [딜량 계산기](<딜량 계산기.md#current>)를 따른다. 조합식/스탯 필터용 기본 능력치의 저장은 [아이템 능력치 기준](<아이템 탐색과 상세.md#stat-information>)을 따른다. 아이템 목록에서 스킬을 기준으로 필터하는 기능은 [아이템 탐색](<아이템 탐색과 상세.md#search-and-filters>)을 따르며, 계산 효과를 루트 필터·능력치 요약에 자동 반영하는 요구는 확정하지 않았다.

<a id="initial-data"></a>

## 자료의 대상과 기간

과거 자료는 정식 출시·시즌1·버전1.0.0을 시작 기준으로 한다. 아이템 정보·조합법·획득 지역을 다루며, 정보의 기본 틀은 [아이템의 다섯 정보 묶음](<아이템 탐색과 상세.md#item-information>)을 따른다. 초기 공개에 필요한 전체 기간은 [프로젝트 공개 조건](<../../프로젝트 목표와 범위.md#delivery>)을 따른다.

아이템 외 대상의 구체 목록·정보 항목·기준 버전·과거 제공 기간과 자료의 완성 판정·저장 방식은 미정이다. 사용자 자료의 확보·임시 변환·교정과 등록 순서는 [초기 자료 준비 계획](../../../work/records/phase-001/phase.md#input-workflow)에서 다룬다.

<a id="boundaries"></a>

## 관련 요구와 계획

루트 계산용 자료는 [루트 계산기](<루트 계산기.md#data-boundary>), 버전별 조회는 [패치 이력과 요약](<패치 이력과 요약.md#versioned-history>), 아이템 탐색·표시는 [아이템 탐색과 상세](<아이템 탐색과 상세.md#current>)가 담당한다. 공통 변경·정정·보존과 AI 운영 요구는 이 문서가 담당한다.

실제 변경 처리의 검증은 [P4](../../../work/records/phase-004/phase.md#goal), AI 변환의 초기 도입은 [P6](../../../work/records/phase-006/phase.md#goal) 계획에서 확인한다. 단계별 배치와 실행 상태를 이 문서에서 별도로 관리하지 않는다.
