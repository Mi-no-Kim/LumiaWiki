# 브랜치 관리 기준

<a id="current"></a>

## 적용

브랜치 계층·이름·분기·상위 변경 반영·정리·재개 기준을 둔다. [Git 공통 기준](<../../Git 작업 기준.md#current>)을 함께 적용하며, 실제 실행은 [Git 작업 절차](<../../../harness/Git 작업 절차.md#start>)를 따른다.

<a id="branches"></a>

## 브랜치

Phase에 속한 작업은 `main ← phase ← issue ← task`, 독립 Issue는 `main ← issue` 경로를 사용한다. 실행 단위를 나눌 필요가 있으면 독립 Issue 아래에도 Task를 둔다.

| 단계  | 이름                                               | 분기 기준·PR 대상                                                                      |
| ----- | -------------------------------------------------- | -------------------------------------------------------------------------------------- |
| main  | `main`                                             | Phase와 독립 Issue 결과를 통합한다.                                                    |
| phase | `phase/<Phase 순번>-<작업명>`                      | `main`에서 분기하고 `main`으로 PR을 만든다.                                            |
| issue | `issue/<실제 GitHub Issue 번호>-<작업명>`          | Phase 소속은 해당 `phase`, 독립 Issue는 `main`에서 분기하고 같은 대상으로 PR을 만든다. |
| task  | `task/<부모 Issue 번호>-<로컬 Task 순번>-<작업명>` | 부모 `issue`에서 분기하고 그 브랜치로 PR을 만든다.                                     |

[번호 표기](<../../작업 기록 체계.md#paths>)에 따라 Phase·Task 순번은 최소 세 자리, Issue는 실제 GitHub 번호를 쓴다. Task 순번은 GitHub sub-issue 번호와 구별하고, 작업 제목은 담당 기록과 PR에서 관리한다.

`<작업명>`은 각 단위의 목적을 드러내는 짧은 영어 단어를 소문자·숫자·하이픈으로 쓴다. Task 작업명에 부모 Issue의 작업명까지 반복하지 않는다. 예: `phase/001-core-foundation`, `issue/42-item-search`, `task/42-001-search-api`. 작업 제목 전체를 옮기지 않고, 제목·상태 변경만으로 브랜치 이름을 바꾸지 않는다. 작업명은 브랜치 식별에만 쓰며 기록 경로·커밋·PR 제목의 작업 식별 형식은 바꾸지 않는다.

<a id="independent-issues"></a>

### 독립 Issue·하네스 정비·긴급 수정

독립 Issue는 위의 Issue 이름을 그대로 사용하며, 작은 수정은 Issue 브랜치에서 직접 완결할 수 있다. Task를 두면 `task → issue`로 squash한 뒤 Issue를 `main`에 merge commit으로 통합한다. 기록은 [목적·소속에 따른 경로](<../../작업 기록 체계.md#paths>)를 사용하고 가짜 Phase·milestone을 붙이지 않는다.

독립적인 하네스 정비는 main 기준 독립 Issue의 브랜치 경로를 사용하고, 제품 작업에 수반하는 하네스 수정은 해당 제품 작업 브랜치와 PR에 함께 포함한다. 현황 표시는 [작업 목적에 따른 기존 범위](<../../작업 기록 체계.md#ownership>)를 따른다.

긴급 수정은 main에 있는 문제를 즉시 고쳐야 할 때 main 기준의 독립 Issue로 처리한다. 아직 main에 없는 Phase 내부 문제는 해당 Phase 경로를 유지한다. 긴급 수정 PR에는 main 기준으로 필요한 변경만 포함하고, 미완성 변경이 섞인 Phase·Issue 브랜치 전체를 main에 보내지 않는다. 하네스 정비·긴급 수정에도 기존 브랜치 이름과 커밋·검수 규칙을 적용한다.

<a id="remote"></a>

로컬 보존 전용인 `codex/local-history-before-init`은 전송 대상에서 제외한다.

## 브랜치 정리와 재개

### 병합 후 정리

| 대상  | 삭제 시점                                                                                       |
| ----- | ----------------------------------------------------------------------------------------------- |
| Task  | 부모 Issue에 squash 병합한 결과를 확인한 뒤. Issue·Phase 완료까지 기다리지 않는다.              |
| Issue | 소속 Phase 또는 독립 Issue의 main 병합 결과를 확인한 뒤. Phase의 main 병합까지 기다리지 않는다. |
| Phase | main 병합 결과를 확인한 뒤.                                                                     |

별도 보관 기간을 두지 않고 병합 마무리 과정에서 로컬·존재하는 원격 브랜치를 허용된 범위에서 정리한다. 삭제 전에는 실제 PR·head·base와 반영 결과, 미커밋 변경·병합 뒤 추가 커밋 등 미보존·미반영 작업, 해당 브랜치에 의존하는 미처리 하위 작업·열린 PR을 확인한다. 필요한 기록·검증 근거는 삭제할 브랜치에만 의존하지 않도록 보존한다. 조건이 충족되지 않으면 삭제를 미루고 남은 대상을 반환한다.

Task의 squash 결과는 원래 커밋과 다르므로 커밋 포함 여부만으로 삭제 가능 여부를 판단하지 않는다. 실제 squash PR과 부모에 반영된 결과를 대조한다. `main`과 로컬 보존 전용 브랜치는 정리 대상에서 제외하며, 브랜치 정리를 이유로 작업 기록·GitHub Issue를 삭제하지 않는다.

<a id="branch-resume"></a>

### 재사용과 새 분기

병합 전 대기·보류했던 동일 작업은 기존 브랜치에서 재개하고 [상위 변경 반영](#parent-updates)을 확인한다. 기록이 완료 상태여도 PR이 미병합이면 검수 보완은 같은 브랜치에서 진행할 수 있다. 병합 없이 PR만 닫았거나 작업을 취소한 경우에는 남은 변경의 보존·폐기와 재개 여부를 판단하며, 병합 완료의 정리를 자동 적용하지 않는다.

병합을 마친 브랜치는 남아 있어도 재사용하지 않고, 같은 이름으로 다시 만들지도 않는다. 종료 뒤 수정은 [새 요구·기존 수용 실패·기록 오류 판별](<../../작업 기록 작성 기준.md#close>)에 따라 다음과 같이 처리한다.

| 판별                            | 기록과 브랜치 처리                                                                                                  |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| 새 요구·범위                    | 새 작업 번호로 등록하고 새 브랜치를 만든다. 기존 작업을 관련 근거로 연결한다.                                       |
| 기존 수용 실패로 동일 작업 재개 | 기존 기록·GitHub 객체와 번호를 유지하고 재개 이유·수용 판단의 정정을 남긴다. 현재 직접 부모에서 새 브랜치를 만든다. |
| 기록 오류만 정정                | 해당 기록을 기존 문서 수정 경로에서 정정하며 원래 작업 전체를 자동 재개하지 않는다.                                 |

동일 작업의 병합 후 재개 브랜치는 작업명을 유지하고 최초 브랜치 이름 끝에 `-r2`, 이후 `-r3`처럼 차수를 붙인다. 작업명 없이 생성했던 브랜치는 병합 후 재개할 때 작업명을 정해 위 이름 형식에 맞춘다. 예: `task/42-001-search-api-r2`, `issue/42-item-search-r2`, `phase/001-core-foundation-r2`. 최초 브랜치를 1차로 보고 기존 브랜치·PR과 재개 이력에서 다음 차수를 확인한다. 차수는 브랜치 식별에만 쓰며 작업 번호·기록 경로·GitHub 번호를 바꾸지 않는다. 새 작업 번호를 발급한 경우에는 재개 차수를 붙이지 않는다.

새 브랜치는 기존 결과를 포함한 현재 직접 부모에서 분기하며, 종료된 브랜치의 끝에서 이어 만들지 않는다. 부모까지 종료됐다면 옛 계층을 자동 복원하지 않는다. main에 반영된 결과의 후속 수정은 새 독립 Issue를 기본으로 하되, 원래 단위의 수용 판단 자체를 정정하고 동일 작업을 재개하기로 했다면 필요한 범위만 재개한다. 옛 Task 번호를 유지하려는 이유만으로 종료된 부모를 모두 재개하지 않는다.

동일 작업의 병합 후 재개에도 기존 방향별 병합 방식·커밋·PR 형식을 적용한다. 제목의 작업 식별자는 유지하고 PR 본문에는 재개 이유와 이전 PR을 연결한다. 재개 차수만을 위한 별도 커밋 형식은 두지 않는다.

## 상위 변경 반영

새 하위 브랜치는 부모가 필요한 상위 변경을 포함하는지 확인한 뒤 분기하며 별도 갱신 merge를 만들지 않는다. 기존 미병합 작업은 재개할 때, PR을 생성할 때와 검수 후 최종 병합 전에 직계 부모의 최신 변경 포함 여부를 확인한다.

반영은 하위 브랜치에서 직계 부모를 일반 merge(`--ff`)하는 방식으로 통일한다. Fast-forward가 가능하면 새 커밋 없이 갱신하고, 이력이 갈라졌으면 merge commit으로 결합한다. 상위 커밋이 이미 포함돼 있으면 추가 merge를 하지 않는다. 일반적인 상위 변경 반영에는 rebase·cherry-pick을 사용하지 않는다. [상위로 결과를 통합하는 방식](<PR과 병합 기준.md#merges>)은 그대로 유지한다.

필요한 경로만 `main → phase → issue → task` 순서로 부모부터 갱신·확인한다. Phase 소속 Issue에 main을 직접 넣거나 Task에 Phase를 직접 넣어 중간 단계를 건너뛰지 않는다. 독립 Issue는 `main → issue → 필요한 task`를 따른다.

| 반영 방향         | 영향 확인 범위                                                   |
| ----------------- | ---------------------------------------------------------------- |
| main → phase      | 독립 변경·긴급 수정의 효과와 Phase 범위·계획·관련 동작의 양립    |
| phase → issue     | 공통 코드·자료·기준 변경과 Issue 목표·수용 조건·해결 계획의 양립 |
| issue → task      | 부모의 변경·기존 결과 유지와 Task의 대상·입력·구현·검증 조건     |
| main → 독립 issue | main 변경과 독립 Issue 결과의 양립                               |

반영 전에는 실제 부모·기준 커밋과 작업 트리·스테이징을 확인하고 미커밋 변경을 보존한다. 반영 후에는 선택한 상위 커밋의 하위 이력 포함, 충돌 해결과 양쪽 의도의 유지, 최신 부모 대비 하위 변경 범위를 확인한다. 관련 코드·자료·문서·기록과 정상 동작 중 달라진 영향만 추가 검증하고 유효한 기존 근거는 재사용한다. 필수 확인이 불충족·미확인이면 그 결과에 의존하는 상위 병합을 진행하지 않는다.

현재 하위 작업의 일부로 처리하며 별도 Issue·Task·PR을 기본적으로 추가하지 않는다. 허용된 작업 범위와 실제 저장소 보호 규칙을 따르고, merge commit이 생기면 `chore: <상위 브랜치> 변경을 <하위 브랜치>에 반영`으로 적는다. 내용이 달라지면 관련 문서·기록과 기존 PR·GitHub 게시물·검증 근거를 함께 맞추되, 정상 반영 확인만을 위한 기록 커밋은 만들지 않는다. 병합을 마친 기존 브랜치는 갱신 대상에서 제외하고, [재개 기준](#branch-resume)에 따라 새로 분기한다.
