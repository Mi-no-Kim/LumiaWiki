# 작업 기록 체계

<a id="current"></a>
## 현재 결론

작업 단위·소유·경로·상태를 판단할 때 필요한 구역을 읽는다. 작성할 정보와 시점은 [작업 기록 작성 기준](<작업 기록 작성 기준.md#current>), 실제 조작은 [문서 관리 절차](<../harness/문서 관리.md#entry>)를 따른다.

기록은 `work/records/`에 둔다. 신규 Issue·Task에는 정식 양식과 아래 다섯 상태를 적용한다. [도입 경계와 기존 기록](#format-adoption)을 먼저 구분하며 독립적인 단순 조회에 새 Issue·Task를 만들지 않는다.

<a id="format-adoption"></a>
## 정식 양식 도입과 기존 기록

- [고정 예외 목록](../harness/rule-comments.json)의 `legacyRecords`는 도입 때 실제로 존재한 Issue·Task·수행 기록의 정확한 경로다. Git 미추적 파일도 포함해 한 번 수집했으며 이후 자동 갱신하지 않는다.
- 목록에 있는 기존 기록은 본문·상태·결정·승인·검증 근거·링크를 그대로 유지한다. 재개·정정만으로 새 양식 전환을 강제하지 않으며 이번 정식 반영에서 수정하지 않는다. 과거 artifacts·시험 입력·지문은 당시 근거다.
- 목록 밖의 신규 정식 Issue·Task·수행 기록은 위치로 자동 발견해 새 양식·다섯 상태·해당 규칙 주석 검사를 적용한다. 신규 기록이 완료돼도 보호를 유지한다. 기록마다 수동 등록하지 않는다.
- 예외는 새 양식 도입에 따른 요구에만 적용한다. 기존 일반 검사·이미 명시 등록된 Issue 주석 보호를 없애지 않는다. 표준 경로와 다른 문서는 자동 보호 범위에 포함되지 않는다.
- 현재 기준·양식·skill·hook은 새 원천을 사용한다. 과거 기록의 당시 지침을 현재 작성법으로 사용하지 않는다. Phase 본문의 구조·실제 예정 상태는 이 도입으로 재작성하지 않는다.

<a id="ownership"></a>
## 단위와 소유

| 원천 | 담당 정보 |
|---|---|
| Phase의 phase.md | 공동 목표·범위·상태·수용 판단, 보유 Issue, 관련·의존 |
| Issue의 issue.md | 과제의 문제·범위·상태·수용 판단, 보유 Task와 확정 배정의 원본·근거, 관련 과제 |
| Task Markdown | Issue 아래 실행 단위의 배정 원본 참조·현재 계획·상태·자기 수용 판단과 수행 근거 |
| work/현황.md | 제품 작업의 상태 표시와 담당 기록 링크 |

자기 상태·수용은 자기 문서가, 자식 등록은 부모 문서가 소유한다. 자식의 부모 표시는 탐색 연결이다. 보유와 관련·기여·의존을 구별하며 같은 자식을 중복 보유하지 않는다.

자식 상세를 부모·현황에서 따로 관리하거나 완료·취소 개수로 부모 수용을 판정하지 않는다. 필수 자식을 취소하면 맡던 결과의 대체나 범위 변경을 함께 판단한다.

<a id="task-assignment"></a>
### Task 배정 원본과 현재 기록

신규 Phase 하위·독립 Issue는 같은 네 단계와 본문·규칙 주석을 사용한다. 독립 Issue는 부모 Phase 행만 생략하고 생성 근거를 남긴다. 생성 준비는 Phase 진행 AI 또는 독립 요청을 받은 AI가 맡고 같은 create-issue skill을 사용한다. 두 유형 모두 개별 실행·검증은 Task에 배정하고 Issue는 실제 자식 결과로 전체 수용을 판단한다. 생성 직후나 배정 전 취소에는 빈 Task를 만들지 않는다.

Issue는 Task의 결과·범위·완료 조건/확인 방법·기존 결정·제약·선행 입력·위임·사용자 확인 조건을 확정해 `artifacts/task-<순번>-assignment.md`에 전달한다. 원본 경로·전달본 식별·확정 근거는 Issue의 배정 결정이 관리한다. Task는 원본을 참조하고 현재 계획·합의·진행·자기 결과를 관리한다. Task 내부 설계·방법·상세 계획과 조사 결론은 생성 후 합의할 사항으로 구분하며 그 미정만으로 생성을 막지 않는다.

배정된 결과·범위·조건·권한을 바꾸면 Issue에서 변경을 판단하고 이전 원문·적용 근거를 보존한 뒤 Task의 참조·계획·영향받는 확인을 맞춘다. 배정 안의 상세 계획 조정은 Task에서 관리한다. 기존 유효 원본을 새 양식에 맞추려고 이동·복제하거나 기존 기록을 일괄 변환하지 않는다.

기존 Task·Issue의 수용을 위한 보완은 해당 작업에 포함한다. 같은 Issue 목표 안에서 별도로 실행·수용할 단위가 필요하면 Task로 나누고, 독립된 목표·수용 조건이면 별도 Issue로 구분한다. 작업 단위를 정한 뒤 [변경 목적별 커밋](<details/git/작업 커밋 기준.md#working-commits>)은 별도로 판단한다.

현황은 게임 자료 관리를 포함한 제품 개발·유지관리 작업을 표시하며, 하네스 자체 정비는 제외한다. 표시 여부는 파일 위치가 아니라 작업의 목적과 결과로 판단하며, 제품 작업에 수반한 하네스 수정은 별도 항목으로 등록하지 않는다.

현황의 ‘완료된 작업’에는 예정·진행·완료 작업과 담당 기록 링크를 두고, 완료만 `[x]`, 나머지는 `[ ]`와 실제 상태로 표시한다.

‘진행 중인 작업’에는 진행·검증 중인 항목의 현재 위치와 다음 행동을 짧게 표시한다. 두 구역의 상태는 같은 담당 원천을 따른다.

<a id="github"></a>
## GitHub 대응과 원본

로컬 작업 기록이 목표·범위·소유 관계·상태·수용 판단의 원본이다. GitHub Issue는 공유할 과제 전체의 명세, GitHub Task는 그 과제에서 배정한 작업의 명세다. GitHub 독자가 목적·범위·기대 결과와 완료 기준을 이해할 수 있게 작성하며, 로컬 본문의 구성과 운영 기록을 그대로 복제하지 않는다.

Issue·Task의 생성 본문은 작업 명세를, GitHub 상태·라벨·milestone·부모/자식 관계는 추적 정보를 담당한다. 관련 자료는 작업 이해·수행·검증에 필요한 경우에 연결한다. 로컬 원본과 발급 번호·URL의 대응은 등록 정보로 관리하며 본문의 필수 설명을 대신하지 않는다.

| 로컬 단위 | GitHub 대응 | 게시 양식 |
|---|---|---|
| Phase | milestone | [GitHub Phase](<../harness/templates/github-phase.md>) |
| Issue | issue | [GitHub Issue](<../harness/templates/github-issue.md>) |
| Task | 부모 Issue 아래의 sub-issue | [GitHub Task](<../harness/templates/github-task.md>) |

로컬 Phase·Task 순번과 GitHub milestone·sub-issue 번호는 별개다. 실제 객체가 있을 때 담당 기록에 저장소·번호·URL을 연결하며, 확인 전에는 가짜 번호·URL을 넣지 않는다.

GitHub의 변경·닫힘·진척률로 로컬을 자동 갱신하거나 수용을 판정하지 않는다. 반영할 변경은 로컬 담당 기록에서 먼저 판단·갱신하고, GitHub에 반영한 범위·미반영과 확인 결과를 구별한다. 객체 생성·변경은 허용된 외부 작업 범위에서 수행한다.

<a id="creation-scope"></a>
### 생성 요청의 기본 범위

Issue·Task 생성 요청은 본문 작성·검증, 로컬 기록 저장과 필요한 부모·현황 등록, GitHub 발급·게시·연결, 실제 등록 결과 확인까지 포함한다. 요청 범위 안의 GitHub 등록은 이미 허용된 행동으로 처리하며 반복 승인받지 않는다. 초안·본문만 작성하라는 요청이나 외부 등록 금지 등 명시적 제한이 있으면 그 범위를 우선한다.

생성 완료는 기록과 등록을 갖춘 상태다. 생성 요청 자체에는 Issue의 본작업 진행과 Task의 상세 계획 합의·실제 수행 등 작업 착수를 포함하지 않는다. 착수는 별도로 명시한 지시에 따라 처리한다. 같은 요청에서 생성과 착수를 함께 지시했다면 생성 완료와 착수 전 준비를 확인한 뒤 그 지시 범위에서 이어가며 재승인받지 않는다. 생성에 필요한 입력 대조·배정 확인·작성 검증을 본작업 착수나 단계 완료로 표시하지 않으며, 생성 권한만으로 브랜치 조작·커밋·push·PR을 진행하지 않는다.

새 Issue는 실제 번호가 없어도 전체 로컬 본문 초안과 게시 명세를 GitHub 발급 전에 작성·검증한다. 번호·정식 경로의 보정은 실제 발급 후 처리한다. Task는 로컬 본문과 확정 배정을 게시 원천으로 삼는다. [공통 작성 규칙](<../harness/문서 관리.md#github-projection>)과 아래 생성·등록 절차를 따른다.

기본 범위의 등록이나 연결이 미완료이면 본문 작성 결과와 생성 전체의 미완료를 구별해 반환한다. 실제 순서·초안 처리·부분 실패 복구는 [생성과 등록 절차](<../harness/문서 관리.md#create>)를 따른다.

<a id="github-state"></a>
### 상태 대응

| 로컬 상태 | Issue·Task | Phase milestone |
|---|---|---|
| 예정·진행 중·중단 | Open | Open |
| 완료 | Closed / Completed | Closed |
| 취소 | Closed / Not planned | Closed — 설명에 취소 상태·이유 표시 |

완료·취소는 로컬에서 먼저 판단하고 해당 객체에 반영한다. 자기 완료 조건을 충족했다면 PR 생성·병합 전에도 완료를 반영하며, 실제 병합·적용 확인이 수용 조건에 포함된 경우에는 이를 충족해야 한다. PR 병합을 닫힘의 자동 판단으로 사용하거나 부모를 자동으로 닫지 않는다. 라벨 표시의 이름·색상·적용 규칙은 [GitHub 라벨 기준](<GitHub 라벨 기준.md>)을 따른다.

<a id="paths"></a>
## 경로와 식별

- 제품 Phase: `work/records/phase-<로컬 순번>/phase.md`
- 제품 Phase 소유 Issue: 해당 Phase 아래 `issue-<실제 GitHub 번호>/issue.md`
- 독립 제품 Issue: `work/records/issues/issue-<실제 GitHub 번호>/issue.md`
- 독립 하네스 정비 Issue: `work/records/harness/issue-<실제 GitHub 번호>/issue.md`
- Task: 해당 Issue 바로 아래 `task-<Issue 안의 순번>.md`

독립 Issue는 수정 파일의 위치가 아니라 작업 목적으로 분류한다. 제품 작업에 수반하는 하네스 수정은 해당 제품 Issue에 함께 기록한다.

Phase·Task 순번은 최소 세 자리이며 999개 상한이 아니다. Phase는 records 전체, Task는 부모 보유 목록과 실제 파일에서 충돌을 확인한다. 사용한 순번은 완료·취소 후 재사용하지 않는다. Issue는 실제 GitHub 번호의 십진 표기를 쓰며 가짜 번호·자리 맞춤을 하지 않는다.

Phase 번호는 식별을 위한 순번이며 실행 순서나 우선순위를 뜻하지 않는다.

Phase·Issue 내부에 중간 `issues/`·`tasks/`나 Task별 본문 폴더를 두지 않고 상태·제목 변경만으로 이동하지 않는다. 소유 이관은 경로·등록·참조를 함께 확인하며, 완료·재개나 다른 목표의 참조만으로 소속을 바꾸지 않는다.

Task를 다른 Issue로 이관할 때는 Issue별 순번과 기존 식별자의 관계를 먼저 확인한다. 이관 방식과 필요한 번호 처리가 정해지지 않았다면 기록·등록·경로를 임의로 바꾸지 않고, 해당 이관에서 필요한 선택을 확인한다.

첨부는 필요한 경우 해당 Phase·Issue의 `artifacts/`에 둔다. Task 첨부는 부모 Issue 아래에서 해당 Task를 식별한다. 본문으로 충분하면 폴더를 만들지 않고 공통 자료를 복제하지 않는다.

임시는 필요한 Task만 `.tmp/issue-<실제 번호>/task-<순번>/`을 사용하며 [보존·정리 절차](<../harness/문서 관리.md#temporary>)를 따른다.

<a id="states"></a>
## 다섯 상태

| 상태 | 판단 |
|---|---|
| 예정 | 허용된 활동에 미착수. 신규·미착수에만 초기값으로 사용한다. |
| 진행 중 | 계획·논의·실행·확인·보완·검수·종료 확인을 진행한다. |
| 중단 | 다음 합의 행동이 구체 조건에 막히거나 추진을 멈췄다. 미착수 때도 가능하다. |
| 완료 | 자기 수용 조건과 필수 확인·관련 반영·기록·보존·정리·종료 처리를 충족했다. |
| 취소 | 목표 달성으로 처리하지 않고 작업을 닫는다. |

검증·검수 위치는 현재 진행 위치에, 중단 이유·해소/재개 조건은 막힌 조건에 둔다. 일부가 막혀도 허용된 독립 활동을 진행하면 진행 중을 유지한다. 상태·태그·계획은 권한·준비·실행이나 수용 근거를 대신하지 않는다. 조건 해소와 새 승인은 구분한다.

기존 예외 기록의 검증 중·대기·보류는 당시 표기로 읽는다. 새 체계에서 검증 중에 해당하는 활동은 진행 중, 대기·보류로 멈춘 경우는 중단에 대응하지만 이를 이유로 기존 파일을 치환하지 않는다. 실제 활동·중단·완료 상태를 예정으로 초기화하지 않는다.

부모·자식·GitHub 상태를 자동 전파하지 않는다. 자기 완료와 부모의 전체 수용은 별개이며 필수 자식의 취소·미수행이 남긴 결과를 따로 판단한다.
