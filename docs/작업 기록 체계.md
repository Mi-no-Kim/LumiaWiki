# 작업 기록 체계

<a id="current"></a>
## 현재 결론

작업 단위·소유·경로·상태를 판단할 때 필요한 구역을 읽는다. 작성할 정보와 시점은 [작업 기록 작성 기준](<작업 기록 작성 기준.md#current>), 실제 조작은 [문서 관리 절차](<../harness/문서 관리.md#entry>)를 따른다.

기록은 `work/records/`에 두고 기존 담당 기록을 우선 사용한다. 독립적인 단순 조회에 기록 탐색이나 새 Task·빈 계층을 강제하지 않는다.

<a id="ownership"></a>
## 단위와 소유

| 원천 | 담당 정보 |
|---|---|
| Phase의 phase.md | 공동 목표·범위·상태·수용 판단, 보유 Issue, 관련·의존 |
| Issue의 issue.md | 과제의 문제·범위·상태·수용 판단, 보유 Task, 관련 과제 |
| Task Markdown | Issue 아래 실행 단위의 목적·범위·상태·계획·완료 판단과 수행 근거 |
| work/현황.md | 제품 작업의 상태 표시와 담당 기록 링크 |

자기 상태·수용은 자기 문서가, 자식 등록은 부모 문서가 소유한다. 자식의 부모 표시는 탐색 연결이다. 보유와 관련·기여·의존을 구별하며 같은 자식을 중복 보유하지 않는다.

자식 상세를 부모·현황에서 따로 관리하거나 완료·취소 개수로 부모 수용을 판정하지 않는다. 필수 자식을 취소하면 맡던 결과의 대체나 범위 변경을 함께 판단한다.

현황은 게임 자료 관리를 포함한 제품 개발·유지관리 작업을 표시하며, 하네스 자체 정비는 제외한다. 표시 여부는 파일 위치가 아니라 작업의 목적과 결과로 판단하며, 제품 작업에 수반한 하네스 수정은 별도 항목으로 등록하지 않는다.

현황의 ‘완료된 작업’에는 예정·진행·완료 작업과 담당 기록 링크를 두고, 완료만 `[x]`, 나머지는 `[ ]`와 실제 상태로 표시한다.

‘진행 중인 작업’에는 진행·검증 중인 항목의 현재 위치와 다음 행동을 짧게 표시한다. 두 구역의 상태는 같은 담당 원천을 따른다.

<a id="github"></a>
## GitHub 대응과 원본

로컬 작업 기록이 목표·범위·소유 관계·상태·수용 판단의 원본이다. GitHub의 내용과 관계·표시는 로컬을 기준으로 반영한다.

| 로컬 단위 | GitHub 대응 | 게시 양식 |
|---|---|---|
| Phase | milestone | [GitHub Phase](<../harness/templates/github-phase.md>) |
| Issue | issue | [GitHub Issue](<../harness/templates/github-issue.md>) |
| Task | 부모 Issue 아래의 sub-issue | [GitHub Task](<../harness/templates/github-task.md>) |

로컬 Phase·Task 순번과 GitHub milestone·sub-issue 번호는 별개다. 실제 객체가 있을 때 담당 기록에 저장소·번호·URL을 연결하며, 확인 전에는 가짜 번호·URL을 넣지 않는다.

GitHub의 변경·닫힘·진척률로 로컬을 자동 갱신하거나 수용을 판정하지 않는다. 반영할 변경은 로컬 담당 기록에서 먼저 판단·갱신하고, GitHub에 반영한 범위·미반영과 확인 결과를 구별한다. 객체 생성·변경은 허용된 외부 작업 범위에서 수행한다.

<a id="github-state"></a>
### 상태 대응

| 로컬 상태 | Issue·Task | Phase milestone |
|---|---|---|
| 예정·진행 중·검증 중·대기·보류 | Open | Open |
| 완료 | Closed / Completed | Closed |
| 취소 | Closed / Not planned | Closed — 설명에 취소 상태·이유 표시 |

완료·취소는 로컬에서 먼저 판단하고 해당 객체에 반영한다. 자기 완료 조건을 충족했다면 PR 생성·병합 전에도 완료를 반영하며, 실제 병합·적용 확인이 수용 조건에 포함된 경우에는 이를 충족해야 한다. PR 병합을 닫힘의 자동 판단으로 사용하거나 부모를 자동으로 닫지 않는다. 라벨 표시의 이름·색상·적용 규칙은 [GitHub 라벨 기준](<GitHub 라벨 기준.md>)을 따른다.

<a id="paths"></a>
## 경로와 식별

- 제품 Phase: `work/records/phase-<로컬 순번>/phase.md`
- 제품 Phase 소유 Issue: 해당 Phase 아래 `issue-<실제 GitHub 번호>/issue.md`
- 독립 제품 Issue: `work/records/issues/issue-<실제 GitHub 번호>/issue.md`
- 독립 하네스 정비 Issue: `work/records/harness/issue-<실제 GitHub 번호>/issue.md`
- Task: 해당 Issue 바로 아래 `task-<Issue 안의 순번>.md`

독립 Issue는 수정 파일의 위치가 아니라 작업 목적으로 분류한다. 제품 작업에 수반하는 하네스 수정은 해당 제품 Issue에 함께 기록한다.

Phase·Task 순번은 최소 세 자리이며 999개 상한이 아니다. Phase는 records 전체, Task는 부모 보유 목록과 실제 파일에서 충돌을 확인한다. 사용한 순번은 완료·취소 후 재사용하지 않는다. Issue는 실제 GitHub 번호의 십진 표기를 쓰며 가짜 번호·자리 맞춤을 하지 않는다.

Phase 번호는 식별을 위한 순번이며 실행 순서나 우선순위를 뜻하지 않는다.

Phase·Issue 내부에 중간 `issues/`·`tasks/`나 Task별 본문 폴더를 두지 않고 상태·제목 변경만으로 이동하지 않는다. 소유 이관은 경로·등록·참조를 함께 확인하며, 완료·재개나 다른 목표의 참조만으로 소속을 바꾸지 않는다.

Task를 다른 Issue로 이관할 때는 Issue별 순번과 기존 식별자의 관계를 먼저 확인한다. 이관 방식과 필요한 번호 처리가 정해지지 않았다면 기록·등록·경로를 임의로 바꾸지 않고, 해당 이관에서 필요한 선택을 확인한다.

첨부는 필요한 경우 해당 Phase·Issue의 `artifacts/`에 둔다. Task 첨부는 부모 Issue 아래에서 해당 Task를 식별한다. 본문으로 충분하면 폴더를 만들지 않고 공통 자료를 복제하지 않는다.

임시는 필요한 Task만 `.tmp/issue-<실제 번호>/task-<순번>/`을 사용하며 [보존·정리 절차](<../harness/문서 관리.md#temporary>)를 따른다.

<a id="states"></a>
## 일곱 상태

| 상태 | 판단 |
|---|---|
| 예정 | 준비·등록했지만 아직 착수를 추진하지 않음. 목표·알려진 조건·미정을 남김 |
| 진행 중 | 허용된 활동을 수행 중이며 중간 확인·수정을 포함함 |
| 검증 중 | 자기 결과를 준비하고 수용·종료 조건을 확인 중임 |
| 대기 | 다음 행동이 구체 조건에 막힘. 착수 전에도 가능하며 조건·근거를 남김 |
| 보류 | 지금 추진하지 않기로 미룸. 이유·재검토 조건을 남김 |
| 완료 | 자기 수용과 필요한 관련 반영·보존·종료 처리를 현재 근거로 충족 판정함 |
| 취소 | 목표 달성으로 처리하지 않고 닫음. 이유·부분 효과·잔여 처리와 보존 근거를 남김 |

검사 결과·실행 권한·도구의 실행 표시는 업무 상태와 구별한다. 검증 실패를 별도 영구 상태로 추가하거나 대기 해소를 실행 승인으로 쓰지 않는다. 미래 후보에 상세 계획을 강제하거나 미정을 모두 대기로 바꾸지 않는다.

부모·자식 상태를 자동 전파하지 않는다. 부모 상태를 이유로 자식을 현황에서 누락하지 않는다. 현황 표시 대상인 독립 Issue는 소속 Phase가 없다는 이유로 누락하지 않는다. 과거에도 완료와 취소를 구별한다.
