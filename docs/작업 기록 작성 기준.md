# 작업 기록 작성 기준

<a id="current"></a>
## 현재 결론

진행 기록을 작성하거나 사전 논의·전환·종료 때 남길 정보를 판단할 때 필요한 구역을 읽는다. 단위·소유·경로·상태는 [작업 기록 체계](<작업 기록 체계.md#current>), 실제 조작은 [문서 관리 절차](<../harness/문서 관리.md#entry>)를 따른다.

<a id="minimum"></a>
## 필요한 정보와 작성 시점

| 시점 | 필요한 정보 |
|---|---|
| 생성 | 제목·기록 대상과 관계 |
| 예정 | 목표·알려진 조건과 미정 |
| 착수 전 | 허용 범위·실제 대상·수용 조건·계획과 예정 확인 |
| 현재 요약 갱신 | 자기 상태·진행 위치·다음 행동과 막힌 조건·근거 |
| 이력 보존이 필요한 사건 발생 | 당시 사실을 이해하고 영향·실패·복구를 판단하는 데 필요한 맥락과 근거 |
| 실제 검증 | 대상·입력·기준·방법·관찰·판정·한계와 근거 |
| 종료·인계 | 결과·반영·미반영·잔여·재개 조건과 필요한 보존·정리·현황 반영 |

<a id="recording-boundary"></a>
Task·Issue 본문에는 목표·범위·수용 조건·현재 유효한 결정과 이유·승인·제약·진행을 막는 실패/미확인·수용 결과와 한계·다음 행동을 기록한다. 같은 항목의 상황이 바뀌면 현재 내용으로 교체하며 요청별·실행별·재시도별 경과를 덧붙이지 않는다. 새로운 결정·조건은 필요한 항목에 추가할 수 있다.

현재 범위·결정·진행·수용 판단을 이해하는 데 필요한 결론은 본문에 둔다. 수행 재현·실패 분석에 필요한 상세 과정·출력·receipt는 담당 artifacts에 보존하고 본문에서 연결한다. 해결된 실패의 이유가 현재 제약으로 남으면 그 이유와 제약은 본문에 유지한다. 단순 정상 확인·반복 실행·Git 처리마다 새 로그나 첨부를 만들지 않는다.

관련 변경·판단·확인은 묶어 기록할 수 있으며, 원천 참조와 현재 적용 범위로 충분하면 전문이나 같은 근거를 반복하지 않는다.

문서 제목·본문·파일명·관리 데이터에 기록 날짜를 넣지 않는다. 사건의 순서와 검증 대상은 커밋·실행 ID·내용 지문·근거로 식별한다. 제품 자료의 날짜와 원본 실행 ID/시각은 보존한다.

기존 문서 검수에서 추가·변경한 내용의 기록 날짜, 필요한 현재 판단의 누락과 해결된 과정의 누적을 함께 확인한다. 자동 검사는 명시적 기록 날짜 필드·신규 날짜형 기록 파일명·본문의 실행 근거 전용 블록만 차단하며 일반 문장의 의미를 판정하지 않는다. 원본 payload는 artifacts의 코드 블록·기계 파일에서 보존한다.

변경된 Task·Issue 기록이 빈 줄 포함 100줄을 초과하면 경고한다. 경고만으로 제출을 실패시키거나 필요한 내용을 삭제·분리하도록 강제하지 않는다. artifacts와 미변경 기록에는 길이 경고를 적용하지 않는다.

[Phase](<../harness/templates/phase.md>)·[Issue](<../harness/templates/issue.md>)·[Task](<../harness/templates/task.md>) 양식은 해당 시점에 필요한 구역만 채운다. 긴 없음 목록·미발생 승인·성공 값을 만들거나 기존 기록을 새 양식으로 덮어쓰지 않는다.

<a id="conditional-writing"></a>
## 조건부 항목의 작성

이번 작업에서 판단할 조건부 항목만 기준 원천·조건·확인 대상·시점을 연결한다. 필요한 때 적용 여부와 이유를 남기고 실제 결과는 검증 근거로 연결한다. 유효한 근거는 재사용하며 무관한 조건의 부적용 사유를 나열하지 않는다.

모르는 조건이나 수행하지 못한 필수 확인을 해당 없음으로 처리하지 않는다. 조건 성립과 수행 성공을 구별하며 [검증과 완료 기준](<details/operations/검증과 완료.md>)을 따른다.

계획·관계 변경은 해당 내용과 근거를 갱신하고, 진행을 막으면 현재 요약에도 표시한다. 미정·제안·합의한 후속은 확정 내용과 구별하고 필요한 결정 시점이나 관련 원천을 남긴다.

<a id="verification-cases"></a>
## 재사용할 검증 사례와 실행 결과

반복 사용할 검증 상황·입력·기대 결과가 실제로 필요할 때 작성하며, 기존 담당 문서의 구역을 우선 사용한다. 모든 작업이 모든 사례를 실행하거나 평가 항목 수에 맞춰 독립 파일을 만들 필요는 없다. 필요하지 않은 사례나 값을 미리 채우지 않는다.

사례에는 관련 목표와 상황·전제, 대상·입력, 사용 환경과 권한·준비 조건을 둔다. 수행·관찰할 일과 기대 결과·판정 범위, 필요한 복구·관련 정상/변형 상황, 한계와 원천도 함께 읽을 수 있게 한다. 재사용할 조건·기대 결과가 바뀌면 해당 구역을 갱신한다.

기능·동작 변경의 [사용자 확인 목록](<details/operations/검증과 완료.md#user-verification>)은 동작 구현 전에 담당 계획·검증 구역에 작성해 공유한다. 같은 사례에 자동 검사·AI 직접 조작·사용자 확인의 방법·실제 결과·미확인과 근거를 구분해 연결하고, 구현 후 확인 요청에는 실제 실행/접속 방법·대상 버전/자료를 함께 제공한다. 사용자 응답이 없으면 사용자 확인 결과를 채우지 않는다.

정식 실행의 판정·확인 범위·한계와 근거 링크는 담당 Task 또는 직접 수행 Issue의 검증 구역에 갱신한다. 보존이 필요한 상세 관찰·출력·실패와 정식 실행 근거는 담당 artifacts에 둔다. Phase에 속한 발급 전 허용된 조사·관찰은 해당 계획에 둔다. 재사용 안내에 매 실행 이력을 쌓거나 이전 출력·근거를 덮어쓰지 않는다.

<a id="unissued"></a>
## 사전 논의와 정식화

Phase에 속한 사전 논의는 해당 계획에서 현재 문제·목적·허용 범위·판단 이유·남은 선택·다음 행동으로 갱신한다. 별도 이력은 [보존 범위](<#recording-boundary>)에 따라 필요한 경우에만 남기며, 정식 Task 상태나 가짜 번호를 쓰지 않는다.

정식화 시 식별자·기존 기록과 필요한 부모 등록·저장 위치를 확인한다. 현재 계획·진행·상태는 정식화한 단위가 소유한다. 사전 논의는 실행 승인·등록을 대신하지 않는다.

<a id="transitions"></a>
## 전환과 재개

계획한 전환에는 현재 작업의 실제 멈춘 상태·이유·전환 대상·복귀 조건·다음 행동을 보존한다. 기존 기록을 재사용하며 전환 자체를 이유로 단위를 늘리지 않는다.

준비·복귀는 [전환 절차](<../harness/문서 관리.md#transition>), 예기치 않은 중단은 [복구 절차](<../harness/문서 관리.md#recovery>)를 따른다. 재개에 필요한 자료를 유지하고 사후에 사전 기록을 만들지 않는다.

<a id="close"></a>
## 종료 뒤와 보관

정상 완료·취소·미완료 인계는 [종료 절차](<../harness/문서 관리.md#close>)에 따라 결과·잔여를 보존한다.

종료된 작업에 수정·재수행·새 작업이 필요한 요청이 들어오면 새 요구·기존 수용 실패·기록 오류를 판별한 뒤 처리한다. 단순히 과거 결과를 조회하는 요청에는 재개·분리 판단을 요구하지 않는다. 자동 재개·소속 변경·과거 근거 덮어쓰기를 하지 않는다.

이관된 과거 자료는 당시 근거다. 위치 이동을 내용 채택이나 삭제 허용으로 보지 않으며 실제 처리 범위·잔여를 남긴다. 정정·보존은 [정정·보존 기준](<문서 참조와 변경 기준.md#correction>)을 따른다.

토큰·비밀번호 등 비밀값은 기록·첨부에 넣지 않는다. 민감한 원자료가 필요한 경우에는 허용된 보관·접근 범위를 확인하고, 기록에는 필요한 사실과 참조만 남긴다.

보관 기록·결과·첨부는 Git 추적 대상으로 관리한다. 대용량 자료의 별도 보관이나 Git 추적 예외가 필요하면 대상·보관 위치·버전 식별·접근·복구 조건을 확인해 해당 자료의 방식을 먼저 정한다. 실제 Git 작업과 외부 쓰기의 권한은 별도다.
