# Git 작업 기준

<a id="current"></a>
## 적용

브랜치·커밋·PR·병합의 프로젝트 규칙을 둔다. 실행 흐름은 [Git 작업 절차](<../harness/Git 작업 절차.md#entry>), 제목·본문 양식은 [PR 템플릿](<../harness/templates/pr.md>)을 따른다.

공통 [권한](<details/operations/권한과 실행 범위.md>)·[검증과 완료](<details/operations/검증과 완료.md>), [기록 소유·상태](<작업 기록 체계.md#current>)·[작성 시점](<작업 기록 작성 기준.md#minimum>)은 기존 기준을 적용한다.

<a id="branches"></a>
## 브랜치

Phase에 속한 작업은 `main ← phase ← issue ← task`, 독립 Issue는 `main ← issue` 경로를 사용한다. 실행 단위를 나눌 필요가 있으면 독립 Issue 아래에도 Task를 둔다.

| 단계 | 이름 | 분기 기준·PR 대상 |
|---|---|---|
| main | `main` | Phase와 독립 Issue 결과를 통합한다. |
| phase | `phase/<Phase 순번>` | `main`에서 분기하고 `main`으로 PR을 만든다. |
| issue | `issue/<실제 GitHub Issue 번호>` | Phase 소속은 해당 `phase`, 독립 Issue는 `main`에서 분기하고 같은 대상으로 PR을 만든다. |
| task | `task/<부모 Issue 번호>-<로컬 Task 순번>` | 부모 `issue`에서 분기하고 그 브랜치로 PR을 만든다. |

[번호 표기](<작업 기록 체계.md#paths>)에 따라 Phase·Task 순번은 최소 세 자리, Issue는 실제 GitHub 번호를 쓴다. Task 순번은 GitHub sub-issue 번호와 구별하고, 작업 제목은 담당 기록과 PR에서 관리한다.

<a id="independent-issues"></a>
### 독립 Issue·하네스 정비·긴급 수정

독립 Issue는 위의 Issue 이름을 그대로 사용하며, 작은 수정은 Issue 브랜치에서 직접 완결할 수 있다. Task를 두면 `task → issue`로 squash한 뒤 Issue를 `main`에 merge commit으로 통합한다. 기록은 [목적·소속에 따른 경로](<작업 기록 체계.md#paths>)를 사용하고 가짜 Phase·milestone을 붙이지 않는다.

독립적인 하네스 정비는 main 기준 독립 Issue의 브랜치 경로를 사용하고, 제품 작업에 수반하는 하네스 수정은 해당 제품 작업 브랜치와 PR에 함께 포함한다. 현황 표시는 [작업 목적에 따른 기존 범위](<작업 기록 체계.md#ownership>)를 따른다.

긴급 수정은 main에 있는 문제를 즉시 고쳐야 할 때 main 기준의 독립 Issue로 처리한다. 아직 main에 없는 Phase 내부 문제는 해당 Phase 경로를 유지한다. 긴급 수정 PR에는 main 기준으로 필요한 변경만 포함하고, 미완성 변경이 섞인 Phase·Issue 브랜치 전체를 main에 보내지 않는다. 하네스 정비·긴급 수정에도 기존 브랜치 이름과 커밋·검수 규칙을 적용한다.

로컬 보존 전용인 `codex/local-history-before-init`은 전송 대상에서 제외한다.

<a id="branch-cleanup"></a>
## 브랜치 정리와 재개

### 병합 후 정리

| 대상 | 삭제 시점 |
|---|---|
| Task | 부모 Issue에 squash 병합한 결과를 확인한 뒤. Issue·Phase 완료까지 기다리지 않는다. |
| Issue | 소속 Phase 또는 독립 Issue의 main 병합 결과를 확인한 뒤. Phase의 main 병합까지 기다리지 않는다. |
| Phase | main 병합 결과를 확인한 뒤. |

별도 보관 기간을 두지 않고 병합 마무리 과정에서 로컬·존재하는 원격 브랜치를 허용된 범위에서 정리한다. 삭제 전에는 실제 PR·head·base와 반영 결과, 미커밋 변경·병합 뒤 추가 커밋 등 미보존·미반영 작업, 해당 브랜치에 의존하는 미처리 하위 작업·열린 PR을 확인한다. 필요한 기록·검증 근거는 삭제할 브랜치에만 의존하지 않도록 보존한다. 조건이 충족되지 않으면 삭제를 미루고 남은 대상을 반환한다.

Task의 squash 결과는 원래 커밋과 다르므로 커밋 포함 여부만으로 삭제 가능 여부를 판단하지 않는다. 실제 squash PR과 부모에 반영된 결과를 대조한다. `main`과 로컬 보존 전용 브랜치는 정리 대상에서 제외하며, 브랜치 정리를 이유로 작업 기록·GitHub Issue를 삭제하지 않는다.

<a id="branch-resume"></a>
### 재사용과 새 분기

병합 전 대기·보류했던 동일 작업은 기존 브랜치에서 재개하고 [상위 변경 반영](<#parent-updates>)을 확인한다. 기록이 완료 상태여도 PR이 미병합이면 검수 보완은 같은 브랜치에서 진행할 수 있다. 병합 없이 PR만 닫았거나 작업을 취소한 경우에는 남은 변경의 보존·폐기와 재개 여부를 판단하며, 병합 완료의 정리를 자동 적용하지 않는다.

병합을 마친 브랜치는 남아 있어도 재사용하지 않고, 같은 이름으로 다시 만들지도 않는다. 종료 뒤 수정은 [새 요구·기존 수용 실패·기록 오류 판별](<작업 기록 작성 기준.md#close>)에 따라 다음과 같이 처리한다.

| 판별 | 기록과 브랜치 처리 |
|---|---|
| 새 요구·범위 | 새 작업 번호로 등록하고 새 브랜치를 만든다. 기존 작업을 관련 근거로 연결한다. |
| 기존 수용 실패로 동일 작업 재개 | 기존 기록·GitHub 객체와 번호를 유지하고 재개 이유·수용 판단의 정정을 남긴다. 현재 직접 부모에서 새 브랜치를 만든다. |
| 기록 오류만 정정 | 해당 기록을 기존 문서 수정 경로에서 정정하며 원래 작업 전체를 자동 재개하지 않는다. |

동일 작업의 병합 후 재개 브랜치는 최초 브랜치 이름에 `-r2`, 이후 `-r3`처럼 차수를 붙인다. 예: `task/42-001-r2`, `issue/42-r2`, `phase/001-r2`. 최초 브랜치를 1차로 보고 기존 브랜치·PR과 재개 이력에서 다음 차수를 확인한다. 차수는 브랜치 식별에만 쓰며 작업 번호·기록 경로·GitHub 번호를 바꾸지 않는다. 새 작업 번호를 발급한 경우에는 재개 차수를 붙이지 않는다.

새 브랜치는 기존 결과를 포함한 현재 직접 부모에서 분기하며, 종료된 브랜치의 끝에서 이어 만들지 않는다. 부모까지 종료됐다면 옛 계층을 자동 복원하지 않는다. main에 반영된 결과의 후속 수정은 새 독립 Issue를 기본으로 하되, 원래 단위의 수용 판단 자체를 정정하고 동일 작업을 재개하기로 했다면 필요한 범위만 재개한다. 옛 Task 번호를 유지하려는 이유만으로 종료된 부모를 모두 재개하지 않는다.

동일 작업의 병합 후 재개에도 기존 방향별 병합 방식·커밋·PR 형식을 적용한다. 제목의 작업 식별자는 유지하고 PR 본문에는 재개 이유와 이전 PR을 연결한다. 재개 차수만을 위한 별도 커밋 형식은 두지 않는다.

<a id="parent-updates"></a>
## 상위 변경 반영

새 하위 브랜치는 부모가 필요한 상위 변경을 포함하는지 확인한 뒤 분기하며 별도 갱신 merge를 만들지 않는다. 기존 미병합 작업은 재개할 때, PR을 생성할 때와 검수 후 최종 병합 전에 직계 부모의 최신 변경 포함 여부를 확인한다.

반영은 하위 브랜치에서 직계 부모를 일반 merge(`--ff`)하는 방식으로 통일한다. Fast-forward가 가능하면 새 커밋 없이 갱신하고, 이력이 갈라졌으면 merge commit으로 결합한다. 상위 커밋이 이미 포함돼 있으면 추가 merge를 하지 않는다. 일반적인 상위 변경 반영에는 rebase·cherry-pick을 사용하지 않는다. [상위로 결과를 통합하는 방식](<#merges>)은 그대로 유지한다.

필요한 경로만 `main → phase → issue → task` 순서로 부모부터 갱신·확인한다. Phase 소속 Issue에 main을 직접 넣거나 Task에 Phase를 직접 넣어 중간 단계를 건너뛰지 않는다. 독립 Issue는 `main → issue → 필요한 task`를 따른다.

| 반영 방향 | 영향 확인 범위 |
|---|---|
| main → phase | 독립 변경·긴급 수정의 효과와 Phase 범위·계획·관련 동작의 양립 |
| phase → issue | 공통 코드·자료·기준 변경과 Issue 목표·수용 조건·해결 계획의 양립 |
| issue → task | 부모의 변경·기존 결과 유지와 Task의 대상·입력·구현·검증 조건 |
| main → 독립 issue | main 변경과 독립 Issue 결과의 양립 |

반영 전에는 실제 부모·기준 커밋과 작업 트리·스테이징을 확인하고 미커밋 변경을 보존한다. 반영 후에는 선택한 상위 커밋의 하위 이력 포함, 충돌 해결과 양쪽 의도의 유지, 최신 부모 대비 하위 변경 범위를 확인한다. 관련 코드·자료·문서·기록과 정상 동작 중 달라진 영향만 추가 검증하고 유효한 기존 근거는 재사용한다. 필수 확인이 불충족·미확인이면 그 결과에 의존하는 상위 병합을 진행하지 않는다.

현재 하위 작업의 일부로 처리하며 별도 Issue·Task·PR을 기본적으로 추가하지 않는다. 허용된 작업 범위와 실제 저장소 보호 규칙을 따르고, merge commit이 생기면 `chore: <상위 브랜치> 변경을 <하위 브랜치>에 반영`으로 적는다. 내용이 달라지면 관련 문서·기록과 기존 PR·GitHub 게시물·검증 근거를 함께 맞추되, 정상 반영 확인만을 위한 기록 커밋은 만들지 않는다. 병합을 마친 기존 브랜치는 갱신 대상에서 제외하고, [재개 기준](<#branch-resume>)에 따라 새로 분기한다.

<a id="working-commits"></a>
## 커밋

하나의 변경 목적을 단위로 하며, 해당 변경에 필요한 구현·자료·테스트·문서·작업 기록을 함께 포함한다. 파일 수나 시간으로 나누지 않고, 하나로 완결되는 변경을 구현과 문서 정리로 억지로 나누지 않는다. 목적이 다른 구현·오류 수정·독립적인 구조 정리는 나눌 수 있으며, 하나의 Issue·Task에 여러 커밋을 허용한다. Task 없이 직접 작업하는 독립 Issue에도 같은 규칙을 적용한다.

작업을 마치는 경우에는 현재 작업 브랜치에서 담당 기록의 결과·검증 근거·상태, 해당하는 부모의 진행 요약·필요한 등록, 관련 기준·안내와 표시 대상 현황까지 같은 변경에 반영한다. 자기 완료 조건을 충족한 작업은 완료로 표시하되 부모 완료로 자동 전파하지 않는다. PR 생성·병합이 아직 발생하지 않았다는 이유로 문서 갱신을 미루지 않으며, 그 사실을 미리 기록하지 않는다. 검수 후 수정에도 같은 원칙을 적용한다.

메시지는 `<유형>: <변경 내용의 한국어 요약>` 한 줄로 쓰고, 필요한 이유·제약·잔여만 본문에 보완한다.

| 유형 | 용도 |
|---|---|
| `feat` | 기능 추가 |
| `fix` | 오류 수정 |
| `refactor` | 동작을 유지하는 구조 변경 |
| `test` | 테스트 추가·수정 |
| `data` | 게임 자료 등록·정정·패치 반영 |
| `docs` | 문서 변경 |
| `chore` | 도구·설정·기타 정비 |
| `wip` | 중단을 위한 미완성 상태 보존 |

중단 보존이 필요하면 `wip:`를 사용하고 본문에 미완성·미검증 범위를 남긴다.

<a id="prs"></a>
## PR과 병합

PR은 담당 기록을 원본으로 결과·검증·수용 근거를 요약하고, [템플릿](<../harness/templates/pr.md>)으로 작성한다. 제목은 최종 결과를 설명하며 아래 통합 커밋 제목에서 자기 PR 번호를 제외한다. 범위가 바뀌면 제목·본문도 갱신한다. 하위 목록·검증·논의 전문과 같은 근거 링크를 반복하지 않는다. 중요한 통합 결정·범위 변경은 이유와 합의 근거를, 잔여·제약은 해당할 때만 남기며 PR 본문만으로 수용 범위를 축소하지 않는다.

긴급 수정은 결과 구역에 긴급한 이유와 수정 범위를 함께 적는다.

<a id="pr-review"></a>
<a id="merges"></a>

| 방향 | 검수 범위 | 연결 대상 | 병합 방식 |
|---|---|---|---|
| task → issue | Task 요구·수용 조건·직접 영향과 부모 통합 조건 | Task 기록, 부모 Issue, 실제 Task sub-issue | Squash merge |
| issue → phase | 필요한 Task 결과의 실제 반영·결합과 Issue 목표·수용·상위 통합 조건 | Issue 기록·GitHub Issue, 부모 Phase | Merge commit (`--no-ff`) |
| issue → main | Issue의 직접 수행 결과 또는 필요한 Task 결과의 실제 반영·결합, Issue 목표·수용 조건과 main 적용 영향 | 독립 Issue 기록·GitHub Issue, 필요한 Task 근거 | Merge commit (`--no-ff`) |
| phase → main | 필요한 Issue 결과의 실제 반영·결합과 Phase 범위·수용·main 통합 조건. 공개 조건은 Phase 범위에 포함될 때 확인 | Phase 기록·실제 GitHub milestone | Merge commit (`--no-ff`) |

유효한 하위 검증 근거를 재사용하고, 통합이나 검수 뒤 변경으로 달라진 영향을 확인한다. 단계가 올라간다는 이유로 하위 검증을 일괄 재실행하지 않는다. 하위 완료 개수로 상위 수용을 판정하지 않으며, 필수 하위 작업의 취소·연기는 결과의 대체나 합의된 범위 변경을 확인한다.

병합 전에는 head·base·변경 범위, 필요한 검증과 필수 지적 해결, 충돌 해결, 적용되는 저장소 필수 검사·리뷰, 제목·본문·통합 메시지를 확인한다. 반영하지 않은 지적은 판단 근거를 남기며, 병합 전에 필요한 필수 확인의 불충족·미확인을 후속으로 넘기지 않는다.

작성자는 자체 검수와 수정 후 재확인을 맡고, [별도 검수 조건](<details/operations/별도 검수.md>)에 해당하면 검토자를 연결한다. 병합 실행자는 작성자와 같을 수 있으며 허용된 범위에서 실행한다. 별도 에이전트 검수와 GitHub 정식 승인은 구별하고, 필수 승인 개수는 [저장소 설정 기준](<GitHub 저장소 설정 기준.md#review-checks>)을 따른다.

<a id="integration-messages"></a>
### 상위로 결과를 통합하는 커밋 메시지

| 방향 | 제목 |
|---|---|
| task → issue | `task(<부모 Issue 번호>-<Task 순번>): <Task 결과 요약> (#<PR 번호>)` |
| issue → phase / main | `issue(<Issue 번호>): <Issue 결과 요약> (#<PR 번호>)` |
| phase → main | `phase(<Phase 순번>): <Phase 결과 요약> (#<PR 번호>)` |

최종 반영 결과를 요약하고, 중요한 통합 이유·제약만 본문에 보완한다. 하위 커밋 목록·검증 로그·논의 전문은 반복하지 않는다. GitHub 자동 생성 메시지를 병합 전에 정리하고 PR 번호를 중복해서 붙이지 않는다.

<a id="references"></a>

`task(...)`는 부모 Issue 실제 번호와 로컬 Task 순번이며, 끝의 `(#번호)`는 통합 PR이다. 실제 GitHub 객체에만 `#번호`를 사용하고 sub-issue 참조는 본문에 실제 번호로 적는다.

<a id="github-closing"></a>
### GitHub 참조와 닫기

Task·Issue·Phase와 독립 Issue에 공통으로 병합에 따른 자동 닫기를 사용하지 않는다. PR 본문과 작업·squash·merge 커밋에서 `Closes`·`Fixes`·`Resolves` 등 같은 기능의 표현을 사용하지 않고, 연결은 `Refs #실제번호`나 일반 링크로 한다. GitHub `Development`의 자동 닫기용 연결도 만들지 않는다. 자동 생성된 통합 메시지도 같은 기준으로 확인한다.

PR의 닫기 키워드는 기본 브랜치 대상일 때 작동하고, 커밋의 키워드는 나중에 기본 브랜치에 들어갈 때 작동할 수 있어 단계별 완료 시점과 일치하지 않는다. 동작은 [GitHub 공식 설명](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)을 참고한다.

닫기·재개는 [로컬 상태 대응](<작업 기록 체계.md#github-state>)을 원천으로 [GitHub 반영 절차](<../harness/문서 관리.md#github-update>)에서 허용된 범위의 명시적 갱신으로 처리한다. PR 병합이나 미병합 종료만으로 해당 작업의 완료·취소를 판단하지 않는다.

<a id="post-merge"></a>
### 병합 후 확인

실제 반영 커밋·메시지·결과와 미리 작성한 기록의 일치를 확인하고 필요한 GitHub 표시와 [브랜치 정리](<#branch-cleanup>)를 수행한다. 차이·실패·추가 판단이 생기면 기록을 보완하며, 매번 병합 사실·커밋 정보를 중복 기록하거나 추가 커밋을 만들도록 요구하지 않는다. 병합 성공으로 작업 완료·상위 수용을 자동 판정하거나 병합 후에야 확인할 사항을 미리 충족으로 기록하지 않는다.

독립 변경·긴급 수정을 main에 반영한 뒤 중단했던 Phase는 [상위 변경 반영 기준](<#parent-updates>)에 따라 재개한다.
