# 공통 자료 갱신·검사안

<a id="current"></a>

Spring 업무 트랜잭션·DB 기본 검사·PK 보호와 U-A의 즉시 UNIQUE/단건 수정, A-A의 교정용 소속 행 DELETE·C-A 지역 참조·L-A 국소 잠금을 적용한다. N3의 서비스/저장소·격리 통합 테스트/재현 절차와 N4의 일반 오류·대기 처리는 확정 계약이다. 구체 SQL·저장/조회·DB 동작 검증은 미수행이며 실제 자료·DB 작업과 구현 파일 생성은 보류한다.

## 업무 단위와 종속 값

| 업무                     | 제안한 한 트랜잭션의 범위                                     | 검사/영향                                                                                            |
| ------------------------ | ------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 시즌/패치 등록·번호 교정 | 관련 시즌 행 → 패치 행 순으로 잠근 뒤 최신 원본으로 계산·저장 | 번호/업무 키·D2-P 기준, 시즌 정렬·영향 패치 정렬 재계산. 지도 시작 순서와 후속 참조 영향도 대조      |
| 종류 이름/부모 수정      | 아래 계층 잠금 뒤 최신 트리 검사·수정                         | 확인된 루트·부모 FK·자기 부모·긴 순환·형제/루트 동명. 아이템 버전 연쇄 생성 없음                     |
| 등급·무기 종류 속성 수정 | 지정 관리자 입력과 해당 행 잠금·기본 검사                     | 목록 안 동명/등급 동순위 금지·무기 대응 일대일. 교정/변경 자동 판별 없음                             |
| 지역 구성 새 등록        | 새 지역 대상이 필요하면 함께 생성하고 구성/소속 행 전체 저장  | 시작 패치 UNIQUE·지속 ID·구성 안 이름/순서/대상 UNIQUE. 빈 구성은 명시 입력일 때만                   |
| 기존 지역 구성 교정      | 기준 표 잠금 → 지정 구성/전체 소속 행 교체                    | 부분 커밋 없음. 다음 구성 전 적용 범위와 후속 참조 대조. 소속 행 직접 FK가 있으면 이 교체안을 재검토 |

업무별 기준 표/행 잠금 순서는 아래 L-A로 구체화한다. 모든 공통 표를 매 업무마다 잠그지 않는다. 소비 관계가 이미 있다면 정렬/구성 교정의 영향 검증을 해당 Task 003/004와 연결하며 검증하지 못한 관련 자료를 일치했다고 보고하지 않는다.

<a id="catalog-locking"></a>

## L-A — 관련 수정만 순서를 맞추는 잠금

한 수정은 지역 R에서의 획득을 저장하고 다른 수정은 같은 시점의 지도에서 R을 제거할 수 있다. 둘 다 상대의 예전 상태로 검사한 뒤 성공하지 않도록 관련 수정이 끝날 때까지 기다리고 최신 결과를 재검사한다. 일반 공개 조회는 계속한다.

현재 지도 행뿐 아니라 새 구성의 동시 추가도 검사 대상이다. 기존 부모 행 잠금만으로는 그 추가를 막지 못하므로 아래 READ COMMITTED 업무별 기준 표 잠금을 사용한다. 같은 기준 표의 다른 행 쓰기도 대기할 수 있으며 동일 행만 잠근다는 뜻은 아니다.

| 업무                                            | game_patch 잠금     | region_map_version 잠금 |
| ----------------------------------------------- | ------------------- | ----------------------- |
| 지역을 사용하는 후속 관계의 등록/수정·소속 검사 | SHARE               | SHARE                   |
| 지도 구성의 추가/교정·적용 시작 변경            | SHARE               | SHARE ROW EXCLUSIVE     |
| 새 패치 등록·시즌/패치 번호·정렬 교정           | SHARE ROW EXCLUSIVE | SHARE                   |

각 업무는 최초 DML/기준 조회 전에 필요한 가장 강한 모드부터 잡는다. 한 업무에 지도 변경과 패치 변경이 함께 있으면 두 표 모두 SHARE ROW EXCLUSIVE로 시작하고 도중에 SHARE에서 승격하지 않는다. 여러 대상의 순서는 game_patch → region_map_version → 필요한 item_category 표 잠금, 그 뒤 필요한 시즌/패치/업무 행을 종류별·ID 오름차순으로 잠근다.

후속 관계의 SHARE 잠금은 지도/패치 쓰기와 충돌해 소속 검사와 저장 사이 변경을 막는다. 지도 쓰기는 대기 뒤 최신 후속 관계를 읽어 자신의 영향 구간을 검증한다. 이 두 경로가 함께 참여해야 하며 서비스 밖 예외 쓰기도 같은 순서를 따라야 한다. 같은 표의 다른 쓰기는 대기할 수 있으나 일반 SELECT를 막는 모드는 아니다. [PostgreSQL LOCK](https://www.postgresql.org/docs/18/sql-lock.html)·[잠금 모드](https://www.postgresql.org/docs/18/explicit-locking.html)에 근거한 계약이며 실제 검증은 미수행이다.

공통 표 전체의 advisory 키/잠금·모든 조회의 격리 강화·자동 재시도는 추가하지 않는다. 비교 대안 L-B는 해당 업무를 SERIALIZABLE로 실행하고 실패 시 업무 전체를 다시 처리하는 안이다. 초기 구현은 채택한 L-A와 N4의 기존 설정에 따른 대기·실패 시 전체 롤백을 사용한다.

<a id="hierarchy"></a>

## 종류 계층과 같은 구성 교정

종류 부모 변경은 item_category의 SHARE ROW EXCLUSIVE 잠금 뒤 최신 트리를 읽어 순환 검사/수정하는 L-A를 따른다. 단일 행 잠금만으로 서로 다른 두 행의 부모 교환 순환을 막았다고 주장하지 않는다. DB 자기 부모 CHECK와 서비스의 긴 순환 검사는 별개다.

지도 구성 교정은 L-A에서 지도 버전 표 잠금 아래 지정 부모/소속 행을 처리한다. 새 시작 패치의 중복은 UNIQUE 실패로 업무 전체 롤백하며 자동 병합하지 않는다. 이 잠금이 과거 화면에서 만든 입력의 덮어쓰기를 감지하지는 않는다. 마지막 정상 업무의 완전한 입력을 반영하는 초기 후보와, 필요 시 해당 업무만의 기대 원본 검사/버전 표현을 추가하는 대안을 구별한다.

현재 app 후보의 지도 버전 UPDATE 권한은 적용 시작 패치의 교정과 잠금 능력에 연결한다. 잠금 절의 행 조회에는 UPDATE 능력도 필요하다. [SELECT 권한 설명](https://www.postgresql.org/docs/18/sql-select.html)을 따르되 PK/권한의 실제 허용·거부는 생성 승인 뒤 검증한다.

<a id="unique-timing"></a>

## UNIQUE 검사 시점과 여러 행 자리교환

U-A의 초기 범위는 일반 UNIQUE를 NOT DEFERRABLE로 두고 단건 수정과 명시된 전체 지도 구성 교정을 제공하는 것이다. 등급 순서나 패치 번호를 서로 교환하는 여러 행 일괄 업무는 초기 범위에 자동 포함하지 않는다. 빈 이름·가짜 번호·임시 순서로 제약을 우회하지 않는다.

향후 일괄 업무가 필요할 때의 U-B 비교안은 필요한 UNIQUE만 DEFERRABLE INITIALLY IMMEDIATE로 정의하고 명시된 일괄 업무에서 검사 시점을 늦추는 방식이다. 일반 FK 비지연 합의는 바꾸지 않는다. 정상 경로/커밋 실패 검증과 실제 필요한 일괄 기능 범위가 추가로 필요하다. 비지연 UNIQUE는 한 UPDATE 안의 여러 행 변경도 행별 충돌할 수 있어 단순히 SQL을 합치면 교환이 된다고 가정하지 않는다. [PostgreSQL UNIQUE 검사 시점](https://www.postgresql.org/docs/18/sql-createtable.html)을 따른다.

<a id="failure-and-verification"></a>

## N3~N4 — 실패와 확인 경로

N3의 초기 범위는 Spring 서비스·저장/조회 코드와 기존 격리 통합 테스트·사용자 재현 절차다. 새 HTTP API·관리 화면은 추가하지 않고 필요한 기능의 담당 범위에서 설계한다. 실제 재현 명령/입력·기대 결과는 구현 전에 Task의 확인 목록으로 공유하며 존재하지 않는 경로나 도구를 완료된 것으로 안내하지 않는다.

N4는 확인된 입력 오류를 기존 400 API_INPUT_INVALID, 없는 조회 대상을 404 API_RESOURCE_NOT_FOUND, 예상 밖 DB 실패를 500 API_INTERNAL_ERROR에 연결하는 계약이다. 알려진 제약과 SQLSTATE가 확인된 경우만 입력 오류로 분류하며 원문 메시지를 파싱하거나 모든 DB 제약 오류를 400으로 바꾸지 않는다. 실제 HTTP 연결은 해당 API를 만들 때 수행한다. P1의 LW001·서비스 입력 400/예상 밖 DB 보호 실패 500 계약은 유지한다.

검사/flush/커밋 실패는 업무 전체를 롤백하고 부분 성공으로 표시하지 않는다. 잠금 대기는 기존 연결/DB 설정을 따르며 별도 시간 제한·자동 재시도를 추가하지 않는다. DB에 한도가 없으면 대기가 길어질 수 있고 HTTP 요청 종료를 DB 취소/롤백 완료로 간주하지 않는다. 새 409/503 응답·교정 장부·모든 쓰기의 기대 원본 검사는 초기 범위에 추가하지 않는다.

전체 지도 교체의 마지막 쓰기 반영 한계, 초기 범위에서 제외한 여러 행 자리교환과 조회 일관성의 한계를 사용자에게 제시한다. 여러 SQL로 구성하는 제품 조회를 이 쓰기 잠금만으로 일관되게 읽는다고 주장하지 않으며 R-A 지도 선택/소속 행 읽기는 한 조회문으로 구성하는 안을 먼저 검토한다.

## 생성 승인 뒤의 예정 검증

- 동시 A→B/B→A 부모 변경에서 둘 다 성공해 순환이 남지 않는지 확인.
- 후속 관계의 소속 검사/저장과 새 지도 INSERT·교정·패치 순서 변경을 경합시켜 유효하지 않은 관계가 커밋되지 않는지 확인.
- 시즌 번호 교정과 패치 등록/수정의 경합에서 저장 정렬과 참조/지도 적용 범위 확인.
- 지역 소속 행 중간 실패 시 구성 전체 롤백, 다른 지도에서 이름/순서 재사용·과거 구성 보존 확인.
- 같은 구성의 경합, 과거 입력 덮어쓰기 한계와 선택한 UNIQUE/자리교환 범위를 확인.
- 잠금 대기/취소·DB 오류·PK guard를 성공으로 보고하지 않는지 확인. 지금은 DB를 만들거나 실행하지 않는다.
