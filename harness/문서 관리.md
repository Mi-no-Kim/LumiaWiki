# 문서와 작업 기록 관리 절차

<a id="entry"></a>
## 적용

문서·작업 기록을 생성·갱신·정정하거나 전환·복구·종료할 때 필요한 구역만 사용한다. 요청 범위·권한·수행·전체 완료 판단은 [공용 절차](<공용 절차.md#entry>)를 따른다.

문서의 담당 원천은 [문서 기준](<../docs/문서 관리 기준.md#current>), 작업 단위·소유·경로·상태는 [기록 체계](<../docs/작업 기록 체계.md#current>)에서 확인한다. 변경 후에는 해당 본문과 영향을 받은 참조·등록·표시를 확인한다.

이 절차의 작업 현황 갱신은 [기록 체계의 표시 대상](<../docs/작업 기록 체계.md#ownership>)에 한한다. 프로젝트 구성은 [현황 관리 기준](<../docs/문서 관리 기준.md#skill-hook-inventory>)과 아래 갱신 절차를 따른다.

<a id="skill-hook-maintenance"></a>
## 스킬·hook 현황 갱신

- 스킬은 [스킬 현황](<스킬 현황.md#current>), Codex/Git hook은 [hook 현황](<hook 현황.md#current>)을 원천과 같은 변경에서 갱신한다.
- 등록 위치는 `.agents/skills/*/SKILL.md`, `.codex/hooks.json`·`.codex/config.toml`, `scripts/hooks/`다. Git hook의 보조 파일은 정의의 `inventory-dependencies`, Codex hook은 현황의 `files`에 지정한다. 프로젝트 config는 모든 Codex 항목의 원천에 포함한다.
- `scripts/hooks/` 바로 아래에는 표준 Git hook 정의만 둔다. 보조 파일은 하위 폴더나 지정한 다른 경로에 둔다.
- `--describe`의 원천·`sourceDigest`와 해당 현황의 관리 데이터를 맞추고 `--render`의 표를 같은 문서에 반영한다. 두 현황을 함께 검사한다.
- 지문만 갱신해 동작 확인을 `verified`로 바꾸지 않는다. 근거가 없으면 `unverified`, 과거 확인을 보존하면 `stale`로 둔다. `verified`에는 일치하는 확인 지문·환경·범위·근거가 필요하다. 기록 날짜 필드는 넣지 않는다.

```text
python -B -X utf8 scripts/check-harness-inventory.py --candidate work --describe
python -B -X utf8 scripts/check-harness-inventory.py --candidate work --render
python -B -X utf8 scripts/check-harness-inventory.py --candidate work
python -B -X utf8 scripts/check-harness-inventory.py --candidate index
```

검사기는 읽기 전용이다. 실제 제출은 index, CI는 `--candidate HEAD`로 검사한다. 현황 파일 누락·원천 불일치·판독 실패를 통과로 처리하지 않는다.

<a id="inventory-hook-install"></a>
### 현황 검사 hook 설치·해제

```text
python -B -X utf8 scripts/install-harness-hooks.py --status
python -B -X utf8 scripts/install-harness-hooks.py
python -B -X utf8 scripts/install-harness-hooks.py --remove
```

기존 hook은 보존하고 먼저 실행한다. `core.hooksPath`는 변경하지 않는다. wrapper 정의 변경 시 기존 설치를 해제한 뒤 재설치한다. 중첩된 wrapper는 바깥부터 해제한다. 자기 wrapper·원본 백업이 변조된 상태에서는 해제하지 않는다.

<a id="create"></a>
## 생성과 등록

- 기존 담당 문서·기록으로 처리할 수 있으면 재사용한다. 새 문서가 필요하면 담당 원천과 저장 위치를 정하되, docs 문서는 [문서 배치 기준](<../docs/문서 관리 기준.md#placement>)을 따른다. 최종 위치에서 링크·표식을 맞춘다.
- 요청한 산출물 외의 첨부를 추가하기 전에는 [첨부 기준](<../docs/작업 기록 체계.md#paths>)에 따라 본문·기존 이력으로 충분하지 않은 용도와 이유를 확인해 사용자에게 알린다. 도구 출력이나 중간 검증 자료는 사용했다는 이유만으로 최종 보존 대상에 포함하지 않는다.
- 번호가 없는 새 Issue는 기존 담당 계획의 초안으로 [GitHub Issue 양식](<templates/github-issue.md>)을 준비한다. 기존 계획이 없는 독립 Issue는 현재 대화에서 등록용 초안을 준비한다. 허용된 등록으로 실제 번호·URL을 확보하고, 그 번호로 정식 Issue 기록과 해당하는 부모 등록을 갖춘 뒤 GitHub 본문의 원본 연결을 정식 기록으로 맞추고 [반영 결과](<#github-update>)를 확인한다. 등록이 허용되지 않았거나 번호를 확보하지 못했으면 초안을 유지하고 미반영을 구별한다.
- Phase·Issue·Task가 실제 필요한 경우에만 작업 목적·소속에 맞는 [경로·식별](<../docs/작업 기록 체계.md#paths>)과 기존 기록을 확인하고, 부모가 있는 단위는 부모 보유 목록도 확인한다. [Phase](<templates/phase.md>)·[Issue](<templates/issue.md>)·[Task](<templates/task.md>) 양식을 사용하며 번호·등록이 불확실하면 기존 파일을 덮어쓰지 않는다.
- 실제 자식이 생기면 부모 보유 목록에 등록하고 자식의 부모 탐색 연결을 맞춘다. 독립 Issue에 가짜 Phase를 만들지 않는다.
- 생성·등록 결과를 확인하고, 실행에 착수할 때는 [착수 전 정보](<../docs/작업 기록 작성 기준.md#minimum>)를 갖춘다. Phase에 속한 발급 전 논의는 [해당 계획](<../docs/작업 기록 작성 기준.md#unissued>)에 둔다.

<a id="update"></a>
## 기록과 현황 갱신

- 계획·상태·다음 행동은 담당 기록의 현재 내용으로 갱신하고, 상세 실행 근거는 [기록 경계](<../docs/작업 기록 작성 기준.md#recording-boundary>)에 따라 필요한 경우만 artifacts에 보존한다. 기존 근거를 연결하며 실행 경과를 본문에 누적하지 않는다.
- 제출 기록 검사는 `python -B -X utf8 scripts/check-work-records.py --candidate index`로 실행한다. CI는 `--candidate HEAD`로 첫 부모와 비교한다. 새 명시적 날짜/근거 블록 위반은 차단하고 변경된 Task·Issue의 100줄 초과는 경고만 한다. 미변경 과거 기록의 정리를 요구하지 않는다.
- 지속 결론이 바뀌면 담당 본문을 갱신하고, 필요한 경우 [주제 이력](<../docs/문서 참조와 변경 기준.md#history>)에 작업 근거를 연결한다.
- 현황의 항목·표시·링크가 달라질 때만 담당 원천을 먼저 저장·확인한 뒤 현황을 맞춘다. 오래된 현황으로 원천을 덮어쓰지 않는다.
- 새 작업이나 예정 작업이 담당 기록·계획에 추가되면 현황 표시 대상인지 확인한다. 표시 대상인 작업만 현황의 체크리스트에 연결한다. 착수·상태 변경·종료 시 해당 항목의 체크와 상태 표시를 맞추고, ‘진행 중인 작업’의 표시도 함께 갱신한다.
- 완료한 항목은 체크리스트에 남기고 ‘진행 중인 작업’에서 제외한다. 같은 작업이 재개되면 담당 원천의 현재 상태에 맞춰 체크와 진행 표시를 갱신한다.

<a id="github-update"></a>
### GitHub 반영

이미 GitHub에 게시된 작업의 로컬 목표·범위·계획·상태·주요 판단·결과가 바뀌면, 변경 내용을 확정해 공유하는 시점에 해당 게시물과 진행 요약·관계가 달라진 부모 게시물을 갱신 대상으로 선정한다. PR 생성·병합 여부와 별개로 허용된 외부 작업 범위에서 수행한다.

- [로컬 원본·대응 기준과 단위별 게시 양식](<../docs/작업 기록 체계.md#github>), [라벨 기준](<../docs/GitHub 라벨 기준.md>)에 따라 제목·본문과 해당 대상의 상태·종료 사유·라벨·관계를 맞춘다.
- 종료된 동일 작업을 재개하면 로컬 상태를 먼저 갱신한 뒤 기존 GitHub 객체를 다시 열고, Issue·Task는 상태 라벨도 교체한다. 종료된 작업의 새 요구로 별도 작업을 만들었다면 과거 객체는 닫힌 상태로 유지한다. PR 연결과 닫기에는 [Git 기준](<../docs/Git 작업 기준.md#github-closing>)을 적용한다.
- 신규 등록과 갱신 뒤에는 실제 저장소·번호·URL뿐 아니라 해당 양식의 부모·milestone·라벨·상태·원본 연결이 의도한 값인지 확인한다. 아직 원격에 없는 기록은 실제 로컬 경로로 표시하고, 유효한 원격 링크를 사용할 수 있게 되면 원본 연결도 갱신한다.
- GitHub가 먼저 닫히는 등 상태가 다르면 원인을 확인하고 로컬 판단에 맞춘다. 갱신 실패로 로컬 완료 판단을 되돌리거나 전체 반영을 완료로 보고하지 않는다.
- 새 번호·URL 연결이나 실패·미반영 등 담당 기록의 내용이 달라진 사항을 남기고, 실제 반영 범위와 확인 결과를 반환한다. 이미 기록된 내용과 일치하는 정상 갱신 확인만을 위해 별도 기록·커밋을 추가하지 않는다. 허용되지 않았거나 수행하지 못한 반영은 미반영으로 구별하고 남은 대상을 반환한다.

<a id="impact"></a>
## 정정과 참조·영향 확인

- [정정 기준](<../docs/문서 참조와 변경 기준.md#correction>)에 따라 현재 안 갱신과 사실 이력 보존을 구별한다. 당시 사실의 보존이 필요한 정정은 원 사건과 이유·근거를 연결한다.
- 규칙·조건이 바뀌면 [관련 사용처와 의존](<../docs/문서 참조와 변경 기준.md#impact>)을 확인해 필요한 반영을 수행한다. 오류를 사용한 후속 판단도 살피고, 이전 근거의 효력이 달라진 부분을 재확인한다.
- 이동·분할·경로·표식 변경 시 영향을 받는 참조를 새 위치에 맞춘다. 당시 근거를 보존하고 표식을 다른 사건에 재사용하지 않는다.

<a id="transition"></a>
## 계획한 작업 전환과 복귀

진행 중인 작업을 멈추고 다른 작업을 먼저 수행할 때 적용한다. 파일이나 절차 구역을 옮겨 다닌다는 이유만으로 별도 전환 기록을 만들지 않는다.

1. 현재 작업의 담당 기록에 멈춘 상태·이유·전환 대상·복귀 조건·다음 행동을 남긴다.
2. 다음 작업의 기존 기록을 재사용하고 목적·허용 범위·예정 확인과 필요한 등록·관계·현황을 준비한다. 필수 준비와 저장 결과를 확인한 뒤 착수한다.
3. 복귀할 때 선행 조건·현재 파일과 사용자 변경·이전 근거의 유효성을 확인해 현재 요약과 달라진 현황을 맞춘다. 재개에 필요한 자료와 과거 중단 근거는 유지한다.

<a id="recovery"></a>
## 중단과 부분 반영 복구

예기치 않은 중단·저장 실패 등으로 일부만 반영됐거나 반영 상태가 불확실할 때 적용한다.

1. 실제 파일·입력·사용자 변경과 완료·부분 반영·미수행·미확인을 대조한다.
2. 현재 권한과 근거에서 필요한 복구·재개·되돌림 범위를 정한다. 무조건 재실행하거나 과거 사본으로 덮어쓰지 않는다.
3. 허용된 처리를 수행하고 결과와 관련 영향을 확인한다. 사후 확인 사실은 당시 기록과 구별하며, 계속할 수 없으면 잔여·보존 근거·재개 조건·다음 허용 행동을 인계한다.

<a id="close"></a>
## 완료·취소·미완료 인계

작업 자체를 종료·취소·인계할 때 적용한다. 각 경우에 담당 기록의 결과·현재 요약과 달라진 현황을 맞춘다.

- 정상 완료는 자기 수용 조건과 실제 결과·필수 확인을 대조하고, 필요한 근거 보존·임시 정리를 마친 뒤 종료 처리를 확인한다.
- 취소는 이유·부분 효과·잔여 처리를, 미완료 인계는 현재 결과·필요 자료·미해결·재개 조건·다음 허용 행동을 남긴다. 필요한 자료를 유지하며 정상 완료의 정리를 자동 적용하지 않는다.
- 필수 저장·보존·정리·표시가 실패하면 해당 종료 처리를 미완료로 남기고 완료한 부분과 잔여를 구별한다. 필수 처리가 남은 작업의 전체 종료를 완료로 보고하지 않는다.

종료 뒤 수정·재수행·새 작업이 필요한 요청은 [새 요구·기존 수용 실패·기록 오류](<../docs/작업 기록 작성 기준.md#close>)를 구별한 뒤 처리한다.

<a id="temporary"></a>
## 임시 자료 보존과 정리

해당 Task의 임시 자료가 실제 있을 때 적용한다. 위치는 [경로 기준](<../docs/작업 기록 체계.md#paths>)을 따르며 유일한 원본·보존 근거의 저장소로 사용하지 않는다.

저장소 루트 `.tmp/`는 [Git 제외 설정](<../.gitignore>)에 따라 추적에서 제외한다.

1. 정상 완료 때 임시 자료 중 아직 보존하지 않은 필요한 결과·근거를 보존 위치로 옮기고 내용·출처·참조를 확인한다.
2. 더 쓰지 않는 해당 Task의 임시 자료만 절대 경로·소속·허용 범위를 확인해 정리하고 결과를 확인한다. 다른 작업·원본·사용자 파일·보존 영역은 제외한다.
3. 대기·보류·전환·중단·인계·취소에는 필요한 자료를 유지한다. 임시 자료가 없으면 폴더나 정리 작업을 만들지 않는다.
