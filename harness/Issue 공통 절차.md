# Issue 공통 절차

Phase 하위·독립 Issue는 같은 양식과 아래 네 단계를 사용한다. 생성 근거는 공통이고 부모 Phase 연결·등록만 소속이 있는 경우 적용한다.

Issue는 결정·Task 생성·최종 검사·종료를 맡고, 개별 실행·검증은 Task에서 한다. 작성과 기록은 [생성 지시서](<Issue 생성 지시서.md>)·[본문 양식](<templates/issue.md>)·[본문의 규칙 주석](<templates/issue.md#recording-guide>)을 따른다.

<a id="sequence-rules"></a>

## 고정 4단계

개별 Issue에서 아래 단계의 제목·번호·순서를 바꾸지 않는다.

<a id="start-check"></a>

<a id="input-rules"></a>

### 1. 입력·준비 확인

전달받은 내용을 확인하고 **2단계 논의를 시작할 준비를 갖춘다.** 여기서 확인하는 범위·권한은 논의를 위한 것이다. 과제의 상세 범위·해결 방법·결과 수용 조건 중 미정인 것은 2단계에서 정한다.

**할 일**

- 전달받은 목적·기대 결과·확정 조건·초기 결정 목록을 확인한다.
- 논의를 진행할 범위·권한과 필요한 입력·최소 기준·확인 방법을 확인한다.
- 부족한 정보와 준비는 기존 기록 확인·질문·기록 작성과 허용된 등록·브랜치·환경 준비로만 보완한다.

입력은 [입력 보존 기준](<Issue 생성 지시서.md#input-preservation>)을 따르며, 미정·미확인을 가정으로 채우지 않는다.

**완료 조건**

- 전달된 내용과 논의할 질문을 확인했다.
- 논의에 필요한 정보·권한·입력·기준·확인 방법을 갖췄다.
- 등록·부모 연결·브랜치·환경·선행 결과 등 필요한 준비가 실제로 갖춰졌다.

준비가 부족하면 본작업을 시작·재개하지 않는다. 준비를 이유로 조사·설계·구현·검증·Task 수행을 먼저 진행하지 않는다.

<a id="step-2"></a>

<a id="decision-rules"></a>

### 2. 논의·결정

미결정 사항의 답을 정하고 **그 결정에 따라 Task 배정을 확정한다.**

**할 일**

- 초기 결정 목록의 각 질문을 논의하고 답을 정한다.
- 결정 내용·이유·근거와 누가 어떤 방식으로 확정했는지 기록한 뒤 체크한다.
- 초기 결정 목록 전체를 확정한 뒤 Task를 나누고 배정한다.

AI가 스스로 결정하도록 허용된 범위를 벗어나는 선택은 결정 전에 사용자와 논의한다.

미결정 항목이 남아 있으면 기존 질문의 문구·순서·번호·표식을 유지한다. 질문을 수정·삭제·이동하지 않으며, 추가할 때는 합의한다. 미확인인 빈 목록이나 자리표시자는 결정 완료로 보지 않는다. 초기 질문이 없음을 입력·기존 합의의 근거로 확인한 경우에는 그 사실·확인 근거를 결정 구역에 기록하고 가짜 질문이나 `결정 1`을 만들지 않는다. 질문 목록 자체가 미확인이면 1단계의 입력 확인에 확인 대상·시점을 남긴다.

**완료 조건**

- 초기 결정 목록의 모든 항목을 확정했거나, 질문 없음이 확인된 근거를 남겼다. 질문이 없어도 아래 배정 조건 확인은 수행한다.
- 결정에 따라 각 Task의 담당 결과·범위·완료 조건/확인 방법, 이미 정한 동작·계약·제약과 선행 입력, AI에 위임한 판단·사용자 확인이 필요한 선택을 정했다.
- Task 사이의 의존 관계와 생성·실행 선행 조건을 정했다.

확정된 조건은 유지하고, 바꿀 필요가 있으면 별도로 논의한다. 실제 Task 생성은 3단계에서 한다.

생성 전에 확정하는 것은 Issue가 맡은 배정 사항이다. Task 안에서 사용자와 합의할 구체 설계·수행 순서·구현 방법·검증 절차까지 모두 먼저 정하도록 요구하지 않는다. 조사·설계 자체가 담당 결과라면 그 결론은 Task에서 만든다. 이미 채택한 결정은 배정의 확정 조건으로 전달한다.

배정은 [Task 입력 양식](<templates/task-input.md#assignment-body>)의 목적·기대 결과·이미 정해진 조건·Task에서 결정할 사항·완료 조건과 확인 방법으로 전달한다. Task 전체 활동을 표시할 복수 태그도 [태그 기준](<Task 공통 절차.md#tag-rules>)에 따라 함께 전달한다. 태그로 논의·결정 주체·실행 권한을 대신 정하지 않는다. 필요한 조건에는 결정의 적용 범위·근거와 선행 입력의 제공 담당/시점·미확보 시 제한을 적는다. Task에서 답을 정할 질문은 생성 후 논의 대상으로 남긴다.

제품 기능의 배정·검사는 [화면 기준](<../docs/details/operations/검증과 완료.md#screen-first>)을 따른다.

<a id="task-creation"></a>

### 3. Task 생성

- 준비 상태·Issue가 맡은 결정·배정·생성 선행 조건을 실제로 확인한다.
- Issue가 합의한 배정을 Task별 전달사항 파일로 확정하고 해당 배정 결정에 원본 경로·전달본 식별·확정 근거를 기록한다.
- 확정 전달사항과 Issue의 배정 기준 기록을 입력으로 [Task 본문 생성 지시서](<Task 생성 지시서.md#creation>)에 따라 본문을 생성하고 [등록 절차](<문서 관리.md#create>)에 따라 Task를 등록해 Issue에 연결한다. Task 본문에는 적용 전달본·식별·확정 근거와 Issue의 기준 기록을 참조하며 배정 원문을 따로 갱신하지 않는다. 정상 진행에는 실제 Task가 필요하다.
- Task 생성은 [기본 생성 범위](<../docs/작업 기록 체계.md#creation-scope>)에 따라 GitHub sub-issue 발급·부모 연결·등록 결과 확인까지 포함한다. 명시적으로 제한된 범위와 실제 미반영은 구별한다. 생성만 요청했다면 결과를 반환하고, Task 착수도 명시했다면 등록과 필수 준비를 확인한 뒤 해당 범위에서 이어간다.
- 생성 조건이 부족하면 미생성으로 둔다. 실행 조건만 부족하면 제한을 명시해 생성할 수 있지만, 해당 조건이 충족될 때까지 그 조건에 의존하는 실행은 허용하지 않는다. 생성 제한을 임의로 실행 제한으로 바꾸지 않는다.

원본 대조·기준 기록은 [전달사항 참조](<Task 공통 절차.md#assignment-record>)를, 배정 변경은 [전달사항 변경 절차](<Task 공통 절차.md#revision>)를 따른다.

생성 후 전체 계획 합의·공통 실행 준비는 [Task의 실행 전 전체 계획](<Task 공통 절차.md#sequence-rules>)을 따른다. Issue는 배정·의존·결과 대기·전체 수용을 관리하고, 각 Task의 실행 순서와 완료 체크는 해당 Task 계획으로 연결한다. 배정·의존 관계가 복잡하면 상세 Issue 계획을 연결한다. 생성 완료와 실행 조건 충족을 따로 판정한다.

**완료 조건**

- 필요한 Task를 실제로 생성하고 Issue에 연결했다.
- 생성 요청 범위에 포함된 GitHub sub-issue의 게시 명세·부모 관계·라벨·milestone과 로컬 Task의 번호·URL 대응을 확인했다. 요청에서 등록을 제한했다면 그 제한과 미반영을 남겼다.
- 각 Task의 확정 전달사항을 읽어 Issue 배정과 내용이 같은지, 원본 경로·전달본 식별·확정 근거 및 Task 본문 참조가 같은 전달본을 가리키는지 확인했다.
- 각 Task에 남은 실행 조건과 제한을 전달했다.

**결과 대기와 다음 단계**

3단계 완료 체크는 위 완료 조건으로 판단한다. 1·2단계와 이 조건들을 계속 충족하며 Task 결과를 기다리는 동안에는 다음과 같이 기록한다.

- 3단계 완료 체크를 유지하고, 현재 위치는 본문의 3단계로 둔다.
- 다음 행동은 허용된 결과 확인·보완 요청으로 적는다. 결과 준비 상태·근거·남은 실행 제한은 담당 Task로 연결한다.

필요한 Task의 결과·검증 근거가 준비되면 4단계로 진행한다.

<a id="step-4"></a>

<a id="completion-rules"></a>

### 4. 최종 검사

- 필요한 모든 Task의 실제 결과와 결과 사이의 연결을 Issue 전체 수용 조건별로 대조한다. [검증 기준](<../docs/details/operations/검증과 완료.md>)에 따라 자가검수와 [별도 검수](<../docs/details/operations/별도 검수.md>)를 거쳐 판정·근거·한계를 기록한다. 유효한 Task 검수 근거를 연결하고 결합 결과와 Issue 전체 조건을 확인한다.
- 결과가 부족하면 담당 Task에서 보완·재검증한다. Issue가 맡은 배정·전체 수용 기준에 새 결정이나 변경이 필요하면 2단계로, Task를 추가해야 하면 3단계로 돌아간다. 새 질문은 합의한 뒤 목록에 추가한다.
- 배정 변경은 [전달사항 변경 절차](<Task 공통 절차.md#revision>)를 따른다. 배정 안의 구체 설계·수행/검증 방법 등 상세 선택은 Task에서 합의하며 Issue가 맡은 결정이 바뀌지 않는 경우 2단계 복귀를 요구하지 않는다.

**완료 조건**

- 필수 결정과 확인에 미정·미확인·불충족이 없다.
- 전체 결과가 수용 조건을 충족했고, 수용 권한이 있는 주체가 이를 수용했다.
- 필수 반영·보존·정리 등 [종료 처리](<문서 관리.md#close>)를 마쳤다.

**완료 처리**

위 조건을 모두 충족하면 로컬에 수용 판단을 기록하고 상태를 ‘완료’로 바꾼다. 이후 허용된 범위에서 [GitHub 반영](<문서 관리.md#github-update>)을 수행해 해당 Issue를 닫고 상태·관계를 맞춘다.

미반영·실패·남은 종료 처리는 구분해 기록한다. GitHub 반영이 실패해도 로컬 수용 판단을 되돌리지 않으며, 전체 반영이나 종료가 끝났다고 보고하지 않는다.

취소하거나 미완료 상태로 인계할 때는 같은 종료 절차에 따라 구분해 기록하고, 자료·잔여·재개 조건·다음 행동을 남긴다. 준비를 보완한다는 이유로 본작업을 먼저 진행하거나 수행하지 않은 단계를 체크하지 않는다.

<a id="selection-rules"></a>

## 진행 중 확인

- 착수·재개·조건 변경·단계 전환·수용 전에 기록과 실제 상태를 대조한다.
- 현재 위치는 첫 미완료 단계를 기준으로 한다. 다만 [3단계의 조건](#task-creation)을 계속 충족하며 Task 결과를 기다리는 동안에는 3단계에 머문다.
- 실제 근거가 있을 때만 체크한다. 독립적으로 허용된 일을 진행할 때도 공통 제한을 지킨다. 막힘·현재 위치·다음 행동은 본문의 규칙 주석에 따라 Issue 본문에서만 갱신한다.
- 조건이 바뀌면 기존 결정·준비·생성된 Task에 미치는 영향을 확인하고, 다시 충족하지 못하게 된 항목의 체크를 해제한다. 영향을 확인하지 못했거나 필수 조건이 충족되지 않은 실행은 보류하고, 허용된 행동·보완 범위·근거를 남긴다. 영향 확인 전에는 관련 Task를 추가 생성하지 않는다.
