# Task 공통 절차

확정 전달사항으로 계획·수행·확인·종료한다. 작성·갱신은 실제 Task와 수행 기록의 주석을 따른다.

<a id="file-creation"></a>

## 최초 파일 작성

신규 Task는 [생성 지시서](<Task 생성 지시서.md>)와 [별도 계획용 본문 양식](templates/task-with-plan.md#body)을 사용한다. 이미 작성된 Task는 적용한 양식과 보호 기준을 따른다.

<a id="execution-creation"></a>

### 수행 기록 최초 생성

첫 할 일 착수 조건을 갖춘 때만 `artifacts/task-<실제 순번>-execution.md`를 만든다. [생성 양식](templates/task-execution.md#execution-body)의 머리말·파일 공통 주석·착수한 할 일 구역을 복사하고 본문에서 실제 수행 기록으로 연결한다. 종전 형식은 본문의 할 일과 수행 기록, 별도 계획 형식은 계획의 단계와 수행 기록을 각각 왕복 연결한다. 이후에는 실제 파일 머리말의 규칙·기록 기준을 따르고 할 일 구역 구조만 주석 없이 추가한다. 머리말·규칙 주석은 반복하지 않으며 미착수 구역·미발생 결과를 만들지 않는다.

<a id="agreement-rules"></a>

## 배정과 상태

<a id="assignment-record"></a>

Issue는 결과·범위·완료 조건·기존 결정/계약·제약·선행 입력·위임·사용자 확인 조건을 확정 전달한다. 원본 경로·전달본 식별·확정 근거는 Issue의 배정 기준 기록이 관리하고 Task는 같은 원본·기록을 대조한다. `r001`은 실제 초판 확정 때만 쓰며 이 관리 정보를 입력란에 반복하지 않는다.

<a id="body-structure"></a>

전달사항 원문은 원본에 두고 Task는 **현재 요약·전달사항 참조·계획과 합의·결과**에서 현재 계획·합의·상태·전체 결과를 관리한다. 과거 기준은 필요하면 해당 커밋으로 식별한다.

<a id="state-rules"></a>

### 상태와 전환

현재 요약의 `- 상태: 값` 한 줄에 실제 상태 하나를 쓴다. 신규·미착수만 예정이며 기존 활동·중단 상태를 우선한다. 재개·복구·이관이나 예시로 초기화·추론하지 않는다.

| 상태    | 의미                                                                 |
| ------- | -------------------------------------------------------------------- |
| 예정    | 허용된 활동 미착수. 막힘 해소 뒤에도 미착수면 예정.                  |
| 진행 중 | 허용된 계획·논의부터 수행·확인·보완·종료 확인까지 진행 중.           |
| 중단    | 다음 합의 행동이 구체 조건에 막히거나 추진을 멈춤. 미착수 때도 가능. |
| 완료    | [자기 수용과 필수 종료 처리](#completion-rules)를 충족함.            |
| 취소    | 목표 달성으로 처리하지 않고 작업을 닫음.                             |

검증·검수는 현재 위치에, 대기 이유·재개 조건은 막힌 조건에 둔다. 미정·부분 완료·검수 실패를 새 상태로 만들거나 부모/자식·GitHub에 자동 전파하지 않는다. 상태는 권한·준비·수용의 근거가 아니며 재개·부분 막힘은 [착수 확인](#start-check)을 따른다.

<a id="tag-rules"></a>

## 태그와 행동

Task와 각 할 일의 `- 태그:` 한 줄에 아래 태그 여러 개를 쉼표로 구분한다. 미정·미확인은 판별 상태이며 태그 종류가 아니다.

| 태그 | 행동과 조건                                                                                                              |
| ---- | ------------------------------------------------------------------------------------------------------------------------ |
| 조사 | 허용된 자료의 사실·근거·비교와 가설·미확인을 구별한다. 미위임 선택을 확정하지 않는다.                                    |
| 논의 | 근거·대안·영향·질문을 제시하고 실제 사용자 응답을 확인한다. 질문·무응답·AI 권고는 논의 완료나 합의가 아니다.             |
| 결정 | 지정 주체가 선택한다. 사용자 응답/합의 또는 AI에 명시 위임한 대상·범위·근거가 필요하다. 주체·위임이 불명확하면 확인한다. |
| 실행 | 허용·선행 조건과 필요한 논의·결정이 확인된 변경을 실제 대상에 반영한다.                                                  |
| 검수 | 실제 결과·행동·근거를 수용 기준에 대조하고 판정·한계·결함을 남긴다. 태그·체크만으로 이행을 판정하지 않는다.              |
| 커밋 | 실제 후보의 필수 자체·별도 검수·보완과 권한·실행 조건을 충족한 뒤 수행한다. 조건부 계획은 허용이 아니다.                 |

- 할 일 태그는 해당 행동을, Task 태그는 전체 활동을 요약한다. Task 태그에 할 일 태그를 포함하되 모든 할 일에 일괄 적용하지 않는다.
- 진행 AI가 배정·합의 안에서 계획과 태그를 맞춘다. 현재값은 Task에 두고 생성 입력·완료 행동의 태그를 보존한다. 완료는 실제 근거·체크로 구별한다.
- 종류·의미를 임의로 늘리지 않는다. 태그는 권한·위임·상태·GitHub 라벨을 만들거나 기존 의무를 없애지 못한다. 통상적 기록 갱신마다 실행 태그·불필요한 일을 추가하지 않는다.
- 복수 조건을 함께 적용하며 결정 위임으로 필수 논의를 생략하지 않는다. 논의·결정 근거가 없으면 해당 완료·선택 확정·의존 실행을 제한한다. 같은 응답·근거는 재사용하고 재승인을 요구하지 않는다.
- 불명확하면 확인 대상·시점을 남기되 그것만으로 본문 생성을 보류하지 않는다. 필수 조건은 [착수 확인](#start-check), 내용·태그 변경은 [계획 갱신](#plan-update)을 따른다.

<a id="separate-plan"></a>

## 별도 계획을 쓰는 Task

1. 계획을 처음 제시할 때 [계획 양식](templates/task-plan.md#body)으로 담당 Issue의 `artifacts/task-<순번>-plan.md`를 만들고 본문의 `상세 계획`에서 연결한다. 본문과 계획의 적용 전달본·식별을 대조한다.
2. 착수 전에 단계별 순서·선행 입력·완료 기준·검증·사용자 확인 지점과 순서 있는 세부 작업을 합의한다. 합의란에 `제안`을 쓰거나, 실제 합의가 있으면 `합의 — [실제 합의 근거](...)`로 담당 Task 본문의 합의 구역에 연결한다. 합의 구역에는 적용 전달본·실제 응답과 검증 도구로 계산한 계획 지문을 남긴다. 지문은 합의한 작업 범위·순서·완료 기준·확인 조건을 식별한다. 합의 표기, 단계 완료 체크, 수행 기록 링크처럼 진행만 갱신한 항목은 계산에서 제외한다. 단계의 `stage-…` ID는 유지하고 제목 번호와 세부 목록 순서로 실행 순서를 표시한다.
3. 단계 완료 체크는 계획에서 갱신한다. 실제 결과·세부 작업별 자가검수·단계 별도 검수와 필수 기록을 갖춘 단계만 체크하고 같은 Issue artifacts의 수행 기록 구역으로 연결한다. 수행 기록의 역방향 링크는 해당 계획 단계로 연결하고, 본문에는 수행 기록과 현재 단계 또는 담당 판단을 연결한다. 진행 메시지에 계획상 현재 위치와 다음 행동을 표시한다.
4. 계획·입력·조건 변경 시 실제 수행 ID와 근거를 보존하고 영향받는 순서·확인과 요약을 맞춘다. 전체 수용은 실제 결과와 전달본을 대조하고 판정·한계·잔여를 본문에 둔다.

승인할 계획 지문은 `python -B -X utf8 scripts/check-rule-comments.py --candidate work --plan-fingerprint <Task 상대 경로>`로 계산한다. 실제 합의를 확인한 뒤, 계획이 연결한 Task 합의 구역에 `- 합의 근거: <실제 응답 또는 그 기록>`과 `- 계획 지문: <SHA-256>`을 남긴다. 착수·재개 전에는 기록 검사와 실제 합의·권한 확인을 함께 수행한다.

<a id="task-format-migration"></a>

### 기존 정식 Task의 개별 전환

1. 사용자가 요청한 Task 경로·범위와 적용 전달본, 현재 상태·완료 내역, 검증 근거와 링크 사용처를 대조한다. 고정 기존 기록의 적용 경계는 [기록 체계](<../docs/작업 기록 체계.md#format-adoption>)를 따른다.
2. 보호 정책의 `taskPlanMigrations`에 그 Task의 정확한 경로와 담당 Task 또는 Issue에 기록한 사용자 승인 표식을 연결한다. 기존 보호 원문과 도입 시점 경로 목록을 보존한다.
3. 기존 상태·결정·완료 판정·근거와 할 일 식별을 보존한 채 별도 계획으로 옮긴다. 기존 작업 표식은 호환 표식으로 유지하고 실행 기록은 상세 계획의 새 단계 링크도 연결한다. 후보에서 이전 상태·체크·근거와 실제 참조를 대조한다.

<a id="sequence-rules"></a>

## 실행 전 전체 계획

<a id="boundary"></a>

첫 할 일 실행 전에 목표 달성부터 검증·검수·허용된 커밋·종료까지 전체 계획을 합의하고 공통 준비를 갖춘다. 계획 합의는 새 실행 권한이 아니다. 계획·논의를 위한 허용된 준비는 진행할 수 있다.

<a id="body-placement-proposal"></a>

종전 형식은 `### 전체 수행 계획` 아래 할 일별 `####` 행동 제목·태그·완료 체크·할 일·확인·수행 기록을 둔다. 별도 계획 형식은 [계획 파일의 단계](#separate-plan)를 사용한다. 결과·범위·선행 조건·기존 제약·위임된 판단·사용자 확인 시점·검증 방법·커밋 범위를 구별한다. 합의 사실·근거는 현재 합의에서 관리한다.

개수·순서는 목표·의존 관계에 맞춘다. 같은 결과·근거로 충족되는 행동은 묶고 검증·보완·기록까지 포함하되 명령·파일마다 나누거나 모든 행동 종류를 강제하지 않는다. 조사 후 정할 선택은 결정 시점·후속 계획 구체화 시점을 정하고 의존 실행 전에 확정한다. 제품 기능은 [화면 선행·화면을 통한 검증](<../docs/details/operations/검증과 완료.md#screen-first>)을 반영한다.

<a id="plan-update"></a>

## 수행과 갱신

<a id="start-check"></a>

착수·재개·주요 전환·조건 변경 때 해당 Task의 안내 주석과 실제 입력·권한·선행 결과·등록·브랜치 등 영향받는 준비를 확인한다. 허용된 활동을 시작·재개하면 진행 중으로 맞춘다. 사용자 확인 조건은 의존 실행 전에 확인하며 막힘 해소를 새 승인으로 해석하지 않는다.

별도 계획 형식은 계획 연결·적용 전달본·합의 근거·계획 지문을 대조한다. 계획이 없거나 제안 상태이거나 합의 근거·지문이 일치하지 않으면 그 합의에 의존하는 실행을 보류한다. 기록 오류는 실제 합의와 대조해 바로잡고, 합의 대상이 바뀌었으면 변경 범위를 다시 합의해 근거와 지문을 갱신한 뒤 재개한다. 진행 정보 갱신과 영향받지 않는 허용 행동은 계속할 수 있다. 종전 형식은 본문의 계획·합의와 실제 근거를 대조한다. 기록 검사는 저장된 근거와 참조를 확인하며, 진행 AI가 실제 사용자 응답·권한·행동 전제를 대조한다.

<a id="integrity-failure"></a>

부족·충돌에 의존하는 행동은 제한하고 원인·해소 조건을 남긴다. 전체 계획·공통 준비가 갖춰졌으면 이미 허용된 독립적인 일은 계속한다. 논의 태그·필요 시점 전의 미정·계획 보완만으로 전체를 중단하지 않는다.

<a id="judgment"></a>

AI는 합의한 목표·범위·완료 기준·동작/계약·권한·위임 안에서 방법을 판단하고 할 일을 추가·수정·삭제·재배열·분할·병합할 수 있다. 경계를 바꾸거나 필수 확인을 생략해야 하면 관련 실행 전에 논의한다. 합의 대상으로 기록한 범위·순서·완료 기준·확인 조건을 변경하는 조정에는 [계획·합의 대조](#start-check)를 적용한다. 그 조건을 유지하는 통상적인 조정은 기존 합의와 위임 안에서 처리한다.

논의 응답·새 사실·조건 변경이 영향을 주면 **다음 관련 행동 전에** 아래 항목을 함께 갱신한다. 중요한 변경 이유·근거를 남기되 응답마다 전면 재작성하거나 별도 변경 로그를 만들지 않는다.

| 영향           | 갱신                                                                                                                      |
| -------------- | ------------------------------------------------------------------------------------------------------------------------- |
| 합의·선택      | 현재 합의의 결정·이유·근거와 해결된 남은 결정. 의견·추가 조사를 선정/실행 허용으로 바꾸지 않는다.                         |
| 질문·계획      | 남은 결정의 질문·판단 기준·주체·시점, 할 일의 내용·태그·선행 관계·확인·연결과 Task 태그. 작은 보완은 기존 할 일에 묶는다. |
| 다음 행동·막힘 | 현재 요약의 위치·다음 행동·제한·해소 조건.                                                                                |
| 기존 결과      | 수행 사실·식별자·근거를 보존하고 영향받는 확인만 다시 한다.                                                               |

제안·미정은 확정과 구별한다. 현재 결론은 같은 항목에서 교체하고 상세 근거는 수행 기록에 둔다. [DB 논의 후 갱신 예시](examples/task-body-example-db-method.md#discussion-update-example)를 참고한다.

<a id="revision"></a>

### 전달사항 변경

배정 안의 현재 합의는 Task 본문에서 요약·참조한다. 배정된 결과·범위·기존 결정·완료 조건·권한이 바뀌면 Issue에서 내용·이유·영향을 합의할 때까지 의존 행동을 제한한다. 기존 전달본·개정 이유·합의를 보존하고 새 개정본과 Issue 기준 기록·Task 참조를 맞춘다. 기존 결과의 적용 전달본을 유지하며 필요한 부분만 보완·재검증한다.

<a id="decision-rules"></a>

<a id="recording-proposal"></a>

## 수행 기록

Task당 한 파일에 착수한 할 일 구역을 추가한다. 종전 형식은 본문 할 일, 별도 계획은 계획 단계와 왕복 연결한다. 규칙 주석은 파일 머리말에 한 번만 두고 할 일 구역에는 넣지 않는다. 식별자는 순서와 분리하며 실제 조치·확인 뒤 같은 구역에서 보완·갱신한다. 미착수 구역의 경로는 적용 형식의 계획에서만 예정으로 표시한다. 수행 기록 생성 전의 계획 논의는 Task 본문에서 관리하며 기록을 위해 미착수 할 일·구역을 만들지 않는다.

수행 예정은 종전 형식의 본문 또는 별도 계획 형식의 계획 파일에 둔다. 수행 기록은 **조치·판단 / 확인 / 잔여**로 쓴다. 파일 수정 없는 논의·결정과 세부 선택·대안/기각 이유·논의 조건·유보/철회 이유도 조치·판단에 담는다. 제안·미결·합의·철회와 결정의 적용 범위·주체·근거를 구별한다.

확인에는 대상·입력·적용 전달본·기준·방법·관찰·판정·근거·한계를 남긴다. 같은 단계 안의 세부 작업별 자가검수는 기존 `확인`에 대상과 판정을 짧게 남기고 필요한 근거를 연결한다. 해당 단계와 당시 계획·작업을 식별할 수 있게 하며, 순서·이름 변경 뒤에도 당시 근거의 연결을 보존한다. 논의·사용자 결정에는 필요한 실제 응답을, AI 결정에는 명시 위임 근거·범위와 실제 선택을 대조한다. 위임으로 필수 논의를 생략하지 않는다. 예정 방법은 참조하고 차이·실제 결과만 보완할 수 있다. 잔여는 해당 할 일의 미해결·재개 조건만 적는다.

후속 행동·검수·수용 판단·진행 조건에 필요한 결정은 Task의 현재 합의에 결론·핵심 이유·조건과 상세 기록 링크를 반영한다. 여러 할 일의 공통 결정은 처음 기록한 한 구역을 함께 참조한다. 여러 Task에 적용할 계약·기준은 담당 Issue·기준 문서의 변경 절차로 연결하며 수행 기록만으로 확정하지 않는다.

코드·diff·테스트 정의는 원본에서 관리하고 기록에 복사하지 않는다. 변경본을 검증했으면 버전·변경 범위와 필요한 커밋을 식별하고 대상이 달라지면 영향받는 확인을 다시 한다. 기존 근거를 참조하며 단순 확인마다 로그·증명 파일을 만들지 않는다. 재현·실패 분석에 필요한 원자료만 담당 artifacts에 보존한다. [작성 예시](examples/task-execution-example.md#execution-example)를 참고한다.

삭제·분할·병합해도 실제 수행·근거·원래 식별자·변경 이유·후속 연결을 보존한다. 태그 변경이 판정에 영향을 주면 당시 적용 태그·기준·변경 이유를 식별한다. 수행한 할 일을 본문에서 빼면 계획과 합의에 원래 표식·근거 연결을 남긴다. [기록 경계](<../docs/작업 기록 작성 기준.md#recording-boundary>)에 따라 필요한 실패 원인·근거는 보존하고 상세 과정 중복·명령별 로그·미발생 결과는 만들지 않는다. 실제 결과·필수 확인·보완·기록을 갖춘 할 일만 완료 표시한다.

<a id="commits"></a>

## 검수와 커밋

실제 행동·결과를 태그·배정·수용 기준과 대조한다. Task/할 일 태그의 포함 관계와 필요한 응답·지정 주체의 결정/명시 위임·선행 결과·실행/커밋 허용을 확인한다. 태그가 바뀌거나 빠져도 의무는 유지하며 근거가 없으면 해당 이행·완료는 미확인 또는 불충족이다.

[필수 별도 검수](<../docs/details/operations/별도 검수.md>)를 연결하고 커밋 전 실제 후보를 자체·별도 검수한다. 필수 결함·미확인을 해소하고 권한 안에서 [변경 목적별](<../docs/details/git/작업 커밋 기준.md#working-commits>) 변경과 수행 기록을 묶는다. 여러 할 일을 포함할 수 있으며 유효한 검수 근거는 재사용하고 달라진 영향만 확인한다.

<a id="completion-rules"></a>

## 수용·종료와 중단

전체 결과를 전달사항의 완료 조건과 대조하고 [자가·별도 검수](<../docs/details/operations/별도 검수.md>)를 거쳐 판정·근거·한계·잔여를 본문에 남긴다. 자기 수용과 필수 반영·확인·보존·정리 등 [종료 처리](<문서 관리.md#close>)를 충족해야 완료다. 할 일 체크·커밋·부모 완료는 이를 대신하지 않으며 부모 Issue의 수용과도 구별한다.

중단·전환·취소는 실제 상태·이유·영향·보존 결과·잔여·해소/재개 조건·다음 행동을 기존 요약·계획/결과에 남긴다. 취소도 잔여 처리·보존을 확인하며 필수 미충족은 미완료로 유지한다.

<a id="fingerprint-rule"></a>

과거 원문·지문은 당시 근거로 보존하고 현재값으로 갱신하지 않는다.
