# GitHub Issue 게시 양식

로컬 Issue를 GitHub issue에 반영하는 양식이다. [단위·상태 대응](<../../docs/작업 기록 체계.md#github>)과 [신규 등록](<../문서 관리.md#create>)·[갱신](<../문서 관리.md#github-update>) 절차를 따른다. 로컬 원본의 현재 계획·조건·판단과 실제 결과를 옮겨, 본문만으로 Issue의 진행과 수용 근거를 검토할 수 있게 작성한다. 원본 파일이 아직 원격에 없으면 로컬 경로를 적고 존재하지 않는 문서 링크를 만들지 않는다.

## 등록 정보

| 항목 | 값 |
|---|---|
| 대상 저장소 | 실제 등록할 저장소 |
| 원본 | 담당 `issue.md` 또는 [번호 발급 전 등록용 초안](<../문서 관리.md#create>) |
| milestone | 소속 Phase의 실제 milestone. 독립 Issue는 설정하지 않음 |
| 라벨 | `unit:issue`와 자신의 로컬 상태에 대응하는 [상태 라벨](<../../docs/GitHub 라벨 기준.md#labels>) |
| 담당자 | 실제로 지정된 경우에만 설정 |
| 상태·종료 사유 | [로컬 상태 대응](<../../docs/작업 기록 체계.md#github-state>) 적용 |

## 제목

```text
<로컬 Issue 제목>
```

## 본문

```markdown
## 현재 요약
- 상태: <로컬 상태>
- 현재 진행 위치: <Issue 전체에서 준비·수행·확인 중인 내용>
- 다음 판단·행동: <다음에 결정하거나 수행할 일>
- 막힌 조건·근거: <진행을 막는 구체 조건과 근거. 해당 시>

## 문제와 목표
<해결할 문제와 기대 결과>

## 범위
- 포함 범위: <이번 Issue가 해결할 범위>
- 제외 범위·제약: <범위 밖의 결과와 지켜야 할 제약>
- 기준 원천: <관련 요구·기준과 적용 내용>

## 수용 조건
- <충족해야 할 Issue 자체의 수용 조건>

## 해결 계획과 의존
- 준비·해결 계획: <문제를 해결할 접근과 수행 순서>
- Task 분해 방향: <나눌 결과·역할·선후 관계와 통합할 내용>
- 의존·착수 조건: <선행 자료·작업 및 시작에 필요한 조건>
- 예정 확인: <확인할 결과와 방법>

## 조건부 사항과 미정
- 조건부 사항: <적용 조건·기준 원천·확인 대상과 시점·현재 판단>
- 미정·제안·후속: <항목별 구분·결정 시점·관련 원천>

## 주요 결정
- <확인 가능한 날짜·논의한 문제·결정·이유·적용 조건과 근거>

## 수용 판단과 검증 근거
- <수용 조건별 실제 판정과 그 이유·근거>
- <수행한 통합 확인의 대상·입력·기준·방법과 실제 관찰>
- <미확인 사항·확인 범위와 한계>

## 결과와 미해결
- 종료 구분·실제 결과: <완료·취소·미완료 인계 판단과 수용 대비 결과>
- 미반영·미확인·남은 일: <해결하지 못한 범위와 그 영향>
- 다음 행동·재개 조건: <후속 처리와 필요한 조건>
- 취소 이유·부분 효과: <취소 시 이유와 실제 남은 결과·처리>

## 원본과 관련
- 원본: <담당 로컬 기록의 경로·링크 또는 번호 발급 전 등록용 초안의 출처>
- 관련 과제: <관련·의존 과제와 그 관계·이유. 보유와 구별>
```

[작성 시점](<../../docs/작업 기록 작성 기준.md#minimum>)에 맞춰 알려진 계획과 미정을 구별한다. 주요 결정·검증 결과·종료 구역은 실제 사건이 생겼을 때 포함하고, 수행하지 못한 필수 확인이나 진행을 막는 미해결은 현재 요약에 남긴다. 조건부 항목이 없으면 해당 줄·구역을 생략한다.

보유 Task는 실제 sub-issue 관계로 연결한다. 본문에는 Task 분해 이유·통합 계획과 실제 결과를 적고, Task별 상세 실행·상태 목록을 복제하지 않는다. 중요한 계획·판단·검증 결과는 본문에 직접 적고 원본 링크로 세부 근거를 연결한다.
