# Issue 생성 시 입력 양식

[Issue 파일 생성 지시서](<../Issue 생성 지시서.md>)

[입력 예시: Issue #42](../examples/issue-creation-input-example-42.md)

Phase 하위·독립 Issue에 같은 네 입력 구역을 사용한다. 생성 담당 AI는 이미 전달된 내용과 맥락을 재사용해 정리하며 사용자가 이 양식을 다시 채우도록 요구하지 않는다. 부모 Phase·소속 경로·실제 식별은 생성 맥락에서 확인한다.

각 구역에는 전달받은 내용을 적는다. 다음 경우에는 해당 표시를 쓴다.

- `없음`: 적용할 내용이 없음을 확인한 경우.
- `미정`: 아직 결정하지 않은 경우.
- `미확인`: 확인하지 못한 경우.

전달되지 않은 내용을 임의로 `없음`이나 확정된 값으로 채우지 않는다.

<과제가 끝난 뒤 달성할 상태나 남길 산출물. 정하지 않은 상세는 미정으로 표시>

## 이미 정해진 조건

입력을 전달할 때 이미 확정되어 이번 Issue가 따라야 하는 요구·제약·선택을 한 항목에 한 조건씩 적는다.

적용 범위는 조건이 적용되는 대상이나 부분을 알아볼 수 있게 적는다. 제안·미정 사항·단순한 현황 사실을 확정된 조건으로 쓰지 않는다.

- 조건: <반드시 지켜야 할 구체적인 내용>
  - 적용 범위: <이번 Issue의 어떤 대상·부분에 적용되는가>
  - 확정 근거: <원천의 해당 구역 링크 또는 사용자 합의 내용>

## Issue에서 결정할 사항

질문이 없음을 확인했으면 `없음 — 확인 근거`를 적는다. 전달된 질문이 없다는 사실만 확인했으면 `미확인 — 목록 확인 대상·필요 시점`을 적는다. 두 경우 모두 가짜 결정 질문을 만들지 않는다.

Issue 파일을 생성할 때 아직 답이 없고, 이번 Issue에서 Task를 분해·배정하기 전에 답을 확정하도록 맡긴 초기 질문을 한 항목에 하나씩 적는다.

조사·설계 자체를 Task에 맡길 때는 Issue에서 먼저 정할 배정 범위·판정 기준과 Task가 만들어야 할 조사·설계 결론을 구별한다. 예를 들어 두 저장 방식을 비교하도록 맡길 과제라면 조사 대상·비교 기준·담당 결과를 먼저 정하고, 비교 결론은 Task의 결과로 남긴다. 그 결론까지 초기 질문에 넣어 Task 배정 전에 확정하도록 요구하지 않는다.

DB 생성 방법을 Task에서 논의하도록 맡길 때도 대상·기존 제약과 논의가 남길 결과를 먼저 정한다. 후보 제안·권고안·최종 선정 중 어디까지 맡기는지와 결정 주체·수용 기준을 구별하며, 생성 방법 자체를 미리 선정하지 않는다. 실제 DB 생성이나 시험 실행의 허용 범위는 논의 배정과 구별한다. [가상 배정·전달사항 예시](../examples/task-creation-input-example-db-method.md#db-method-assignment-example)에서 이 구분을 확인한다.

전달받은 질문의 소속이 애매하면 원문·순서·미정을 유지해 사용자와 확인한다. AI가 질문을 임의로 삭제·재분류하거나 답을 대신 정하지 않는다. 기존 목록의 편집 제한과 전체 확정 조건은 [Issue의 논의·결정](<../Issue 공통 절차.md#step-2>)을 따른다.

결정 범위는 답을 정할 대상과 경계다. 그 범위 안의 내용을 AI가 스스로 결정해도 된다는 뜻은 아니다. Issue 파일을 생성하면서 질문의 답을 대신 작성하지 않는다.

- 결정할 사항: <Task 분해·배정 전에 이번 Issue에서 답을 확정할 초기 질문 하나>
  - 결정 범위: <답을 정해야 할 구체적인 대상과 경계>
  - 판단 기준: <결정할 때 충족하거나 비교해야 할 기준>
