# 작업 결과 검수

## 적용과 역할

일반 검수·리뷰는 공통 검수 구역을 사용한다. 커밋을 준비할 때는 커밋 전 확인 구역도 적용한다. [검증·완료 원칙](<../../../docs/details/operations/검증과 완료.md>)과 [별도 검수 조건](<../../../docs/details/operations/별도 검수.md>)을 따른다. 스킬 사용은 수정·커밋·외부 작업의 권한을 추가하지 않는다.

작성자는 자체 검수·지적 처리·최종 대조를 맡는다. 별도 에이전트는 검토자 역할로 읽기 전용 검수를 하며, 직접 수정·커밋하거나 다른 검수 에이전트를 재귀 호출하지 않는다. 필요한 실행 확인은 허용된 범위에서만 한다.

<a id="common-review"></a>
## 공통 검수

### 대상과 근거 확인

요청·합의·수용 조건, 적용 기준·원자료, 실제 대상과 비교 기준을 확인한다. 변경 검수라면 변경 전후와 필요한 주변 내용을 읽는다. 설계·초안은 현재 합의와 제약에 대조하며 구현·실제 동작의 확인과 구별한다. 작성자가 정한 파일 목록이나 요약도 검토 대상으로 삼고, 빠진 필수 결과·불필요한 파일을 먼저 찾는다.

| 관점 | 실제 수행할 확인 |
|---|---|
| 범위·필요성 | 필요한 결과의 누락, 무관한 변경·불필요 첨부·중복이 있는지 확인. 명시적 접근 제한이 있으면 실제 조회·비교 범위와 결과 설명의 일치도 확인 |
| 요구·정확성 | 요청·수용 조건을 결과가 충족하는지, 원자료와 다른 내용·근거 없는 주장이 있는지 대조 |
| 연결·영향 | 직접 사용처·참조·관련 정상 동작과 기존 사용자 변경에 미치는 영향 확인 |
| 검증 근거 | 필요한 확인을 실제 수행했는지, 근거의 대상·입력·기준이 현재에도 유효한지 확인 |
| 기록·상태 | 담당 기록과 필요한 부모 요약·등록·상태가 실제 결과와 일치하는지 확인 |
| 제출 일치 | 검수 이후 변경과 실제 제출 범위를 확인하고 달라진 영향 재확인 |
| skill·hook 변경 | [현황 관리 기준](<../../../docs/문서 관리 기준.md#skill-hook-inventory>)에 따라 실제 원천·등록·지정 의존과 해당 현황의 대응 및 마지막 확인 범위/근거를 대조. [후보 검사](<../../../harness/문서 관리.md#skill-hook-maintenance>) 통과와 설명·동작의 정확성은 구별 |

확인 방법은 이번 작업에 필요한 것만 선택한다. 코드는 관련 동작·회귀의 실행 근거, 문서는 의미·원천·역할·참조, 자료는 출처·버전·대응, 설정은 요청한 작성·적용 범위에 맞는 설정값·동작을 확인한다. 링크·형식 검사만으로 내용이나 실제 실행까지 통과시키지 않는다. 모든 작업에 새 테스트나 전수 검사를 만들지 않는다.

### 별도 검토자에게 전달할 내용

검토자에게 이 공통 구역과 해당하는 커밋 구역, 요청·수용 조건, 실제 대상·비교 기준·필요 원자료, 허용된 확인·실행과 접근 금지 범위를 전달한다. 대상 환경에서 자료를 읽을 수 있는지 확인하고, 작성자의 결론만으로 검토를 대신하지 않는다. 실제 확인 범위를 넓혀 보고하지 않는다.

### 반환과 판정

검토자는 다음을 간결하게 반환한다. 지적 수나 항목별 긴 보고서를 채우기 위한 작업은 하지 않는다.

- 실제 읽은 대상·비교 기준·핵심 원자료와 확인하지 못한 필수 범위.
- 지적별 위치·기대 기준·실제 문제·영향·수정 방향. 필수 결함과 선택적 개선을 구별한다.
- 수행한 확인·관찰 결과·한계 및 필수 조건의 충족·불충족·미확인 판단.

작성자는 반환 내용과 실제 결과를 다시 대조하고 지적의 반영 또는 반영하지 않은 근거를 확인한다. “이상 없음”만으로 통과시키거나 다수의 동의를 근거로 판정하지 않는다. 수정이 허용됐으면 필수 결함을 조치하고 달라진 영향만 재확인한다. 검토만 요청됐거나 해결할 수 없으면 지적·미확인을 반환한다. 필요한 확인과 지적 처리가 충족되면 끝내며 범위 밖 개선까지 수행하는 반복을 만들지 않는다.

현재 대상·입력·기준·관련 의존이 같아 유효한 검수 근거는 재사용한다. 검수 뒤 의미가 달라지면 영향을 받은 범위를 재검수한다. 이미 확인한 관찰·한계를 그대로 기록한 요약만 추가했다면 그 정확성을 자체 확인하며, 새로운 상태·수용·범위 판단이나 주장을 추가했다면 관련 검수를 다시 한다. 결과는 [기존 담당 기록](<../../../docs/작업 기록 작성 기준.md#minimum>)에 남기고 별도 검수 증명 파일을 만들지 않는다.

<a id="before-commit"></a>
## 커밋 전 확인 — 작성자

1. [커밋 기준](<../../../docs/details/git/작업 커밋 기준.md#working-commits>)에 따라 변경 목적과 후보를 정한다. HEAD 등 비교 기준, 실제 변경, 관련 미추적·미스테이징 파일과 필수 동반 변경을 확인한다. 관련 없는 사용자 변경·Git 제외 대상을 임의로 포함하지 않는다. 아직 커밋이 허용되지 않았으면 검수까지만 수행하며 검수만을 위해 스테이징을 강제하지 않는다.
   - Task 종료 결과를 제출할 때는 기존 수용 판단으로 정한 기대 상태를 인덱스와 대조한다. 저장소 루트에서 `python .agents/skills/review-work/scripts/check_task_status.py --task <담당 Task의 저장소 상대 경로> --expect-state "<기대 상태>"`를 한 번 실행한다. 같은 인덱스·기대 상태의 유효한 결과는 재사용한다. 불일치(종료값 1)·미확인(2)은 해당 상태 확인을 해결한 뒤 제출하며, 수용을 맞추려고 상태만 자동 변경하지 않는다. 독립 Issue·일반 질문·아직 스테이징하지 않는 리뷰에는 실행하지 않는다. 이 검사는 Task 상태만 대조하므로 부모·현황·GitHub와 검수·PR·종료 처리는 기존 절차로 확인한다.
2. 공통 구역으로 자체 검수한 뒤 별도 에이전트를 호출해 후보를 검수한다. 문서·단순 수정도 적용한다. 일부만 스테이징했으면 실제 인덱스 내용을 확인한다. 작업 폴더에서 얻은 실행 근거가 후보 밖 변경에 의존하는지 확인하고, 확인할 수 없으면 후보의 실행성은 미확인으로 남긴다.
3. 지적을 처리하고 변경된 영향의 검수 근거를 갱신한다. 커밋 직전에 실제 스테이징 차이와 검수한 후보를 다시 대조한다. 필수 결함·미확인 또는 필수 에이전트 호출 미수행이 남으면 정상 결과 커밋을 진행하지 않는다. 허용된 커밋 뒤에는 생성된 내용·메시지·부모와 남은 작업 트리를 [Git 절차](<../../../harness/Git 작업 절차.md#commit>)로 확인한다.

WIP도 자체·별도 검수를 수행한다. 제품의 미구현·미검증은 보존할 한계로 명시할 수 있지만 보존 후보 식별·기존 변경 보호·한계 기록·검수 수행의 미확인은 면제하지 않는다. 호출 실패를 이유로 WIP로 우회하지 않는다.

커밋이 생길 수 있는 부모 반영도 생성 전에 결합 결과를 확인할 수 있게 [Git 절차](<../../../harness/Git 작업 절차.md#start>)를 따른다. 새 커밋 없는 fast-forward나 기검수 결과의 통합은 유효한 근거를 재사용하며, 충돌 해결·의존 변경 등 달라진 영향은 확인한다. PR 통합은 최종 head·base에 대한 근거의 유효성을 확인하고 같은 이유로 새 검토자를 반복 호출하지 않는다.

이 스킬의 최초 구현·변경도 사용자 합의와 기존 유효 기준으로 검수한다. 변경 중인 스킬의 새 예외를 자기 검수의 면제 근거로 사용하지 않는다.
