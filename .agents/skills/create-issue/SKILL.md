# Issue 생성과 등록

## 적용과 원천

Phase 진행 AI가 넘긴 과제와 독립 요청을 받은 AI가 정리한 입력 모두에 사용한다. 부모 Phase가 실제로 배정한 과제인지 생성 근거를 확인한다. 현재 Phase가 있다는 이유만으로 귀속시키지 않는다. 소속 판단이 필요한 경우 관련 계획·요청을 먼저 읽고, 근거로 결정할 수 없는 부분만 확인한다.

다음 원천을 읽고 사용한다. 이 skill은 입력 확인·본문 작성·검증과 GitHub 등록을 연결하며, 생성 지시서는 그중 본문 작성 단계에 적용한다.

- [입력 양식](../../../harness/templates/issue-input.md): 공통 네 구역과 없음·미정·미확인의 의미. 이미 전달된 요청과 맥락을 재사용하며 사용자에게 양식을 다시 채우도록 요구하지 않는다.
- [생성 지시서](../../../harness/Issue%20생성%20지시서.md): 입력 반영·초기값·소속·링크 보정·작성 후 대조.
- [본문 양식](../../../harness/templates/issue.md): 공통 본문과 규칙 주석. 독립 Issue는 부모 Phase 행만 생략하고 생성 근거는 유지한다.
- [생성 기본 범위](../../../docs/작업%20기록%20체계.md#creation-scope)·[생성·등록 절차](../../../harness/문서%20관리.md#create)·[GitHub Issue 게시 양식](../../../harness/templates/github-issue.md): 전체 로컬 본문 검증부터 발급·정식 저장·연결 확인까지의 순서. 게시 명세는 [공통 작성 규칙](../../../harness/문서%20관리.md#github-projection)을 따른다.

두 유형은 같은 네 단계·다섯 상태·Task 배정·수용 절차를 사용한다. Phase 하위만 부모 보유 목록과 milestone에 연결한다. 독립 제품/하네스의 위치는 수정 파일이 아니라 작업 목적으로 구분한다.

## 입력 확인과 보완 요청

입력과 이미 확인한 맥락으로 기록할 대상·의도·기대 결과의 개요를 파악할 수 있는지 본다. 같은 정보가 다른 구역이나 연결된 원천에 있으면 재사용하고 빈칸만을 이유로 다시 요구하지 않는다. 과제의 필요성·우선순위나 해결 방법을 대신 심사하지 않는다.

핵심 내용을 새로 정하거나 중요한 해석 중 하나를 선택해야만 본문을 작성할 수 있을 때만 보완을 요청한다. 이때 본문을 생성하지 않고 다음을 간결하게 반환한다.

- 부족하거나 충돌한 항목.
- 그 정보가 생성 전에 필요한 이유.
- 사용자가 확인·보완할 내용.

논의할 선택의 답·상세 범위·구현 방법·판단 기준은 미정으로 남길 수 있다. 초기 질문 목록·조건의 세부 근거가 미확인이라는 이유만으로 반려하지 않는다. 충돌 자체를 논의 대상으로 전달받았다면 그 사실을 보존한다. 미정·미확인을 임의의 확정값이나 `없음`으로 바꾸고 질문을 새로 만들지 않는다.

보완 요청은 입력에 대한 반환이다. 새 Issue 상태를 만들거나 과제를 취소·종료하지 않는다.

## 생성과 본문 작성

출력 방식·소속·식별 정보·저장 위치는 요청 및 이미 확인한 맥락을 따른다. 기본 생성 요청은 본문 작성과 GitHub 등록까지 허용한 것으로 처리하고, 초안·본문만 작성하거나 외부 등록을 금지한 명시적 제한을 우선한다. 대화·가상 검토만 요청됐다면 파일을 쓰지 않는다. 저장 위치가 불명확하거나 기존 파일과 충돌하면 확인 없이 덮어쓰지 않는다.

입력이 충분하면 먼저 생성 지시서와 본문 양식으로 전체 로컬 본문을 작성·검증한다. 실제 번호가 없어도 내용·질문·불확실성·규칙 주석·초기값을 확인하고 번호·URL·정식 경로만 미발급으로 구분한다. 생성 중 결론·Task 배정·준비 성공·실행 결과를 만들지 않는다.

GitHub 등록이 요청 범위에 포함되면 검증한 본문에서 공통 작성 규칙과 게시 양식으로 작업 명세를 작성·대조한 뒤 발급한다. 실제 번호·URL로 정식 로컬 기록과 필요한 부모·현황 등록을 갖추고 최종 링크·식별·실제 게시 결과를 다시 확인한다. 발급 제한·실패·결과 불확실과 부분 반영은 생성·등록 절차에 따라 초안과 실제 발급 정보를 보존하며 중복 발급하지 않는다.

생성만 요청했다면 생성·등록 결과를 반환하고 Issue 본작업에는 착수하지 않는다. 같은 요청에서 착수도 명시했다면 등록과 필수 준비를 확인한 뒤 그 범위에서 이어가며 재승인받지 않는다. 생성 권한만으로 Task 생성·브랜치 조작·구현·DB 변경·커밋·push·PR을 진행하지 않는다.

## 확인과 반환

입력과 본문을 대조해 의미·질문·조건·미정/미확인의 보존, 양식·규칙 주석·링크·초기값을 확인한다. 질문이나 준비가 미확인인 채 생성했으면 그 확인 대상과 필요한 시점이 드러나는지 본다. 미발생 승인·결과·완료를 채우거나 생성만으로 다음 단계의 조건을 충족했다고 표시하지 않는다.

미정 사항의 확정 주체·시점과 그에 따른 제한은 입력·합의·담당 원천에서 확인한 범위만 기록한다. Issue의 배정 결정과 Task의 상세 설계·수행 방법·검증 절차 합의는 [논의·결정의 경계](../../../harness/Issue%20공통%20절차.md#step-2)를 따른다. 소관·시점이 불명확하면 관련 판단 전에 사용자와 확인할 대상으로 남긴다. 이를 근거 없이 Issue 생성·모든 후속 논의·Task 배정의 선행 조건으로 확대하지 않는다.

실제 작성 범위·파일 또는 초안 위치·GitHub 번호·URL과 등록/연결 확인 결과·미반영·남은 보완을 반환한다. 본문 작성과 기본 생성 범위 전체의 완료를 구별한다. 요약에서도 방법 자체의 결정과 담당·배정 범위의 결정, 확인된 제한과 남은 확인을 구별한다. 요약에서도 초기 질문 목록 확인(1단계 완료 전)과 답 확정(Task 분해·배정 전)을 구별하고 상세 위치를 연결한다. 요청이 본문 재작성을 금지하면 내용 대신 위치와 결과만 요약한다.

실제 신규 기록을 저장했으면 공통 주석 검사기의 작업 파일 검사로 자동 적용을 확인한다. 기존 기록의 예외 목록을 갱신하거나 생성 기록을 예외에 추가하지 않는다. 생성 후 진행은 실제 본문 주석과 공통 절차가 담당한다.

등록된 Issue에서 계획·합의를 요청하면 [issue-plan](../issue-plan/SKILL.md)으로 연결한다.

## 질문 없음과 목록 미확인

질문 없음이 확인된 입력은 사실·근거만 결정 구역에 남기고 예시 질문 구역을 생략한다. 질문 목록 미확인은 1단계 입력 확인에 두며 `결정 1`로 만들지 않는다. 기존 요청·답을 재사용하고 목록 확인을 불필요한 재승인으로 확대하지 않는다.
