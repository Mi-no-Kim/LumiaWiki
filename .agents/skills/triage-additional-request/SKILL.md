# 추가 요청의 작업 단위 판단

## 적용

기존 작업에 추가·변경 요청이 들어오면 새 요청의 첫 수정·등록·브랜치 전환 전에 적용한다. 판단에 필요한 조회는 먼저 할 수 있다. 작업이 중단·완료됐거나 미커밋 변경이 없어도 관련된 후속 변경이면 적용한다.

## 판단과 알림

1. 새 메시지가 조회·승인, 기존 지시의 명확화·정정, 기존 작업 보완, 추가 목표 중 무엇인지 구별한다. 단순 조회·승인에는 작업 분리나 전체 미커밋 조사를 강제하지 않는다. 명확화라도 실제 범위·수용 조건이 달라지면 그 영향을 확인한다.
2. 담당 기록의 목표·수용 조건과 실제 관련 변경을 읽고 [작업 단위 기준](<../../../docs/작업 기록 체계.md#ownership>)으로 소속을 판단한다. 같은 목표의 수용 보완인지, 같은 Issue 안의 별도 실행·수용 단위인지, 독립 목표인지 확인한다. 파일 위치·변경량·같은 파일을 수정한다는 이유로 단위를 정하지 않는다. 제품 작업에 필요한 하네스 보완과 독립 하네스 정비, 의존 관계와 부모 소유를 구별한다.
3. 정한 작업 단위 안에서 [변경 목적별 커밋](<../../../docs/details/git/작업 커밋 기준.md#working-commits>)을 별도로 판단한다. 새 Task·Issue가 필요하다는 판단과 지금 전환할 수 있다는 판단은 구별한다.
4. 분리가 필요하면 착수 전에 분리 수준·이유, 기존 변경의 보존 방법, 처리 순서와 필요한 복귀 조건을 짧게 알린다. 같은 작업의 단순 보완에는 긴 분리 보고를 만들지 않는다. 기존 허용 범위에서는 진행하고, 새 선택·권한이 필요한 부분만 확인한다.

## 보존과 전환

- 같은 파일에 변경이 섞였으면 실제 파일·스테이징·변경 출처와 의존을 먼저 확인한다. 판단만으로 commit·stash·reset하거나 기존 변경 전체를 다른 작업으로 옮기지 않는다. 미완성·미검수 작업을 전환을 위해 정상 완료로 포장하지 않는다.
- 다른 작업을 먼저 해야 하면 [전환 절차](<../../../harness/문서 관리.md#transition>)로 기존 상태·다음 작업·복귀 조건을 연결한다. 필요한 등록·번호·권한이 없으면 [등록 절차](<../../../harness/문서 관리.md#create>)에 따른 초안을 유지하며 가짜 기록을 만들지 않는다.
- 종료된 작업의 후속 요청은 [새 요구·수용 실패·기록 오류 판별](<../../../docs/작업 기록 작성 기준.md#close>)과 필요한 [브랜치 재개 기준](<../../../docs/details/git/브랜치 관리 기준.md#branch-resume>)을 따른다.

분리 판단은 실행 권한을 넓히지 않는다. 의미 있는 결정·전환은 기존 담당 기록에 남기고, 필요 없는 Task·Issue·커밋을 늘리지 않았는지도 확인한다.
