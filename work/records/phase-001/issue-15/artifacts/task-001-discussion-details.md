# Task 15-001 — 상세 논의와 확인 사례

[Task 본문](<../task-001.md#summary>)에서 분리한 등록 정보·검색·제작 관계의 상세다. 제품 규칙은 연결한 제품 문서를 따르며, 이 문서는 판단 조건·이유·미정과 후속 설계 입력을 보관한다.

<a id="registration-discussion"></a>
## 등록 정보 논의

- 현재 전제: P1에 시즌·버전 정의와 시즌 1·v1.0.0 초기 등록을 포함한다.
- 시즌·버전·지역의 합의한 규칙은 [공통 데이터 요구](<../../../../../docs/details/product/게임 데이터 변경 관리.md#season-information>)에, 능력치 종류 구분·중복 제한·백분율 값의 표현과 획득 방법·단일 조합법은 [아이템 요구](<../../../../../docs/details/product/아이템 탐색과 상세.md#stat-information>)에 반영했다. P1 포함 범위와 스킬의 텍스트 취급 범위는 [Phase 본문](<../../phase.md#agreed-data-scope>)에 반영했다.
- 자료는 사용자가 나중에 링크를 제공하고 원자료·변환 결과와 근거를 담당 Issue·Task에 보관한다. 단계의 제공·보류 조건은 [자료 준비 계획](<../../phase.md#input-workflow>)을, 기록·첨부 위치는 [공통 보관 기준](<../../../../../docs/작업 기록 체계.md#paths>)을 따른다. 서비스 DB의 출처 연결 구조는 이 결정만으로 확정하지 않는다.
- 사용자 요청에 따라 이후에는 관련 항목을 여러 묶음씩 제시한다. 실제 게임 자료 조사·확보·처리의 기존 보류 조건은 유지한다.
- 기존 Task의 범위 안에서 진행하며 새 작업 단위나 별도 목적의 커밋으로 분리하지 않는다.

### 등록 정보안과 남은 결정

아래는 기존 제품 요구를 바탕으로 P1의 구체 범위를 논의하기 위한 안이다. 최종 필드 목록이나 필수 여부를 확정한 것이 아니다.

| 묶음 | 등록 정보안 |
|---|---|
| 공통 식별·날짜 | 대상 연결용 내부 식별값과 사용자 지정 숫자 규칙을 유지하고 별도 코드 필드는 두지 않음. 시즌 시작일·종료일과 버전별 패치 적용 일시는 포함 |
| 버전 | 현재는 아이템 중심 관리. 변경된 패치에만 새 정보를 등록하고 다음 변경 전까지 사용하며 이력에서 유효 버전을 선택해 조회. 불편이 커질 때 정보별 독립 관리로 전환할 계획. 메이저·마이너 번호·정렬식·표시 규칙은 합의했으며 별도 적용 순서 필드는 두지 않음 |
| 아이템 기본 정보·분류 | 이름·종류·등급·장비 부위·이미지는 P1에 포함. 종류는 상하위 계층을 두고 목록은 입력하며 정함. 장비 아래 무기, 그 아래 무기 종류. 종류의 이름·상하위 관계는 변경 패치에 새 버전을 등록해 과거 구조 보존. 등급은 별도 정보로 이름·정렬 순서를 두고 목록은 입력하며 결정하고 이름·순서는 고정 |
| 능력치 | 이름의 ` (%)` 접미사로 백분율 종류를 구별하고 아이템별 같은 종류의 중복은 금지. 백분율 값은 5%를 5로 저장 |
| 아이템 스킬 | 한 아이템에 여러 스킬을 연결할 수 있음. 스킬 버전에는 대상·내부 이름·텍스트를 두고 JSON은 아이템스킬–아이템–게임 패치 버전 연결에 둠. P1은 저장과 텍스트 표시까지. JSON의 수식 참조·계수 저장 방향을 유지하며 실제 수식 계산·외부 조건 처리는 후속 |
| 제작·수량 | 한 아이템의 대체 조합법은 없음. 제작 1회에 두 재료를 각각 1개씩 소비하며 별도 필요 수량 필드는 두지 않음. 제작 결과 수량은 획득 수량과 별도 저장. 최대 중첩 수량을 포함. 개수 수량은 정수이며 허용 범위는 후속 |
| 지역·획득 | 지역 정렬용 숫자는 시작값·증가값 모두 10으로 합의. 획득 방법은 채집·사냥·획득(상자 획득)으로 구분하고 같은 아이템에 여러 방법을 연결할 수 있음. 구체적인 지역 순서·이름과 방법별 세부 대상·지역 연결 방식은 미정 |
| 배달 | 가능 여부·비용을 저장하고 현재 배달당 수량은 획득 수량과 공통 저장. 실제 차이가 발생하면 별도 항목으로 분리 |
| 출처·보존 | 나중에 제공받을 링크와 변환 결과는 담당 작업 기록·필요 첨부에 함께 보관. 서비스 DB의 출처 연결 구조는 미정 |

후속 설계·자료 확인으로 이어갈 항목은 다음과 같다.

- 메이저·마이너 번호의 허용 범위와 구체적인 지역 순서.
- 획득 방법별 세부 대상·조건과 지역 연결 방식은 명칭·구조의 후속 설계에 연결.
- 아이템 중심 버전의 구체적인 연결·키·재사용 방식과 향후 독립 관리 전환 방법. 스킬 실행 문법·함수의 세부는 기존 후속 범위를 유지.

<a id="version-strategy"></a>
### 현재 버전 관리·수량·분류와 전환 계획

확정한 규칙은 제품 원천을 따른다. 현재 선택 이유와 남은 결정은 다음과 같다.

- 현재는 아이템 중심 방식으로 시작한다. 아이템 귀속 정보에 변경이 생기면 새 아이템 버전을 기준으로 당시 구성을 보존한다. 조회는 이력에서 해당 게임 패치에 유효한 아이템 버전을 선택하며 현재값의 별도 사본은 두지 않는다. 특정 스킬 버전·게임 패치 직접 참조와 스킬 자체의 대상·버전 구조는 유지한다. 테이블 분리와 변경하지 않은 정보의 재사용 방식은 후속 설계에서 정한다.
- 정보별 독립 관리로 전환할 계획은 유지한다. 사용자는 읽기 빈도가 늘어날 때의 효율 개선을 기대하고 현재 방식의 불편을 예상해 이후 전환을 정했다. 전환 시점은 불편이 커질 때로 두며, 전환 대상·구체 시점·이관 및 검증 방법은 그때 실제 자료와 사용을 근거로 정한다. Task 005에서 이 조건을 후속 과제에 연결하며, 전환 전후에 과거 정보와 참조 정합성을 보존한다. 현재의 자료 입력·패치 축적을 진행하기 전에 독립 관리 구조를 완성하도록 요구하지 않는다.
- 최대 수량은 인벤토리 한 칸의 최대 중첩 개수로 확인했고 등록 정보에 포함한다. 저장 위치의 세부는 후속 설계에서 정한다.
- 고정 1+1 조합은 재료별 소비량을 1개로 두며 별도 필요 수량 필드는 생략한다. 목표 제작 개수에 따른 총 필요량은 계산할 값으로 구별한다.
- 종류 목록은 입력 때 정하고 계층은 지원한다. 종류의 이름·상하위 관계는 변경된 패치에 새 버전을 등록하고 다음 변경 전까지 사용해 과거 구조를 보존한다. 등급은 종류와 별도 정보로 이름·정렬 순서를 두고 목록은 입력하면서 정한다. 등급 자체의 이름·순서 변경은 없다는 전제다.
- SQL 재점검에서 `weapon_type`은 캐릭터의 사용 무기·무기 스킬 연결용 별도 대상으로 초기부터 두기로 했다. 아이템 종류 계층과 연결하며 구체 관계는 DB 설계 때 정한다. 정보 원천은 [분류 요구](<../../../../../docs/details/product/아이템 탐색과 상세.md#classification>)를 따른다.

### 스킬의 조건문·함수와 JSON — 현재 방향과 미정

스킬 버전과 연결별 JSON의 소유·역할은 [제품 원천](<../../../../../docs/details/product/게임 데이터 변경 관리.md#item-skills>)을 따른다. 같은 스킬의 표시 텍스트를 공유하면서 아이템·버전별 효과 차이를 JSON으로 표현하려는 요구다. 이전의 연결별 설명 저장 제안은 채택하지 않았다.

SQL 재점검에서 초기에는 내부 이름·텍스트를 한 스킬 버전에 함께 보존하고 스킬 대상과 특정 스킬 버전을 모두 직접 참조하기로 했다. 두 참조의 소속 일치 검사 방식은 DB 설계 때 정한다. 비교 근거는 [스킬 연결 검토](<task-001-sql-review.md#skill-reassessment>)에 있다.

- 텍스트의 함수는 캐릭터 능력치 등을 받아 계산한 결과를 표시할 수 있고 조건문은 외부 정보도 참조한다. 실제 수식은 표시 텍스트와 별도로 둔다. JSON은 단순 치환값에 한정하지 않고 효과·수식을 구조화해 같은 스킬 안의 차이도 제어한다.
- 확정: 수식 정의는 별도로 두고 JSON에는 참조할 수식과 계수를 지정한다. 구체적인 참조 형식·계산 처리 연결과 수식 정의의 버전 보존은 미정이다.
- 확정: 연결의 버전은 게임 패치 버전이며 아이템과 스킬의 연결은 스킬 대상·특정 스킬 버전·게임 패치를 함께 참조한다. 변경 패치에만 새 정보를 등록해 다음 변경 전까지 사용한다. 두 스킬 참조의 소속 일치 검사는 DB 설계 때 정하며, 현재 아이템 중심 방식에서의 구체적인 연결·키·테이블 구성은 후속 설계에서 정한다.
- 현재 표시 방향: 외부 정보가 없는 일반 아이템 상세는 우선 텍스트 형태로 보여준다. 조건별 문구·미제공 입력 처리, 내부 이름의 검색·표시 용도와 원문 보존은 후속 결정 사항이다.
- 문법·등록 함수·JSON 스키마와 검증 방식은 아직 선택하지 않았다. P1의 실행 범위는 아래 합의를 따른다. 후속 표현 체계의 완성을 P1 저장·표시의 선행 조건으로 삼지 않는다.

사용자 지시에 따라 수식 관련 구체 논의는 [딜량 계산기 작업](<../../../../../docs/details/product/딜량 계산기.md#pending>) 때까지 미룬다. 현재 SQL 비교나 P1 범위 논의에서 다시 요구하지 않는다.

P1 범위는 합의했다. 스킬 대상·버전·연결별 JSON의 저장과 텍스트 표시까지 지원하며 실제 수식 계산과 외부 조건 처리는 후속 단계에서 구현한다. 구체적인 저장·표시 방식은 이 경계 안에서 후속 설계·구현 과제로 구체화한다.

<a id="deferred-target-design"></a>
### 별도 관리 대상 — 명칭·구조 후속 설계

사냥 관련 대상은 별도 테이블로 관리하기로 했다. 명칭은 미정이며 제안 명칭을 채택하지 않는다. 세부 필드·관계·관리 대상 범위와 지역별 획득 조건의 표현은 후속 설계로 미룬다. 실제 테이블 생성은 이번 논의에 포함하지 않는다.

Task 005에서 해당 설계·구현 과제를 배정하고 관련 구현을 준비할 때 구체화한다. 명칭·구조 논의를 지금 반복하는 선행 조건으로 삼지 않는다. 전투 능력치·출현 시간·확률 등의 포함은 확정하지 않았다.

<a id="search-detail-discussion"></a>
## 검색·상세 범위 합의

사용자 응답에 따라 이름 검색, 옵션·부위 필터를 P1에 포함하고, 상세에는 제시한 기본 정보·능력치·스킬 설명·획득·배달 정보를 모두 표시하기로 했다. 미등록 정보는 비우고 검색 결과가 없을 때도 목록을 비우며 별도 안내 문구를 요구하지 않는다. 단계 범위와 확인할 결과는 [Phase 본문](<../../phase.md#agreed-search-detail-scope>)에 반영했다.

이름 검색의 일치 규칙, 옵션 필터의 세부 항목·입력 방식, 스킬 내부 이름의 검색·표시 용도는 이번 응답으로 확정하지 않으며 후속 설계에서 구체화한다. 제품 문서의 폭넓은 검색·필터 요구는 유지하고 이번에는 P1 포함 범위를 정한다. 제작 관계는 [SQL 참고에 따른 결정](<task-001-sql-review.md#legacy-sql-reference>), 기본 루트는 [합의한 기본 루트 범위](<#basic-route-discussion>)를 따른다.

기존 Task의 범위 보완으로 처리하며 별도 작업 단위나 목적별 커밋을 추가하지 않는다. 이번 반영은 로컬 계획·기록에 한하며 GitHub 게시물은 갱신하지 않았다. 실제 구현·동작 검증과 자료 작업은 수행하지 않았다.

자체 확인: 사용자 응답과 Phase의 검색·상세 범위, Task·부모 Issue·현황의 현재 요약 및 다음 행동을 대조했다. 연결한 구역과 변경 범위의 공백 검사를 확인했으며, 검색의 부분 일치나 옵션 세부 규칙을 임의 확정하지 않았고 기존 미커밋 변경을 유지했다. 확인 범위는 문서 반영이며 기능 동작 검증은 아니다.

<a id="crafting-details"></a>
### 제작 관계의 세부 조건과 예정 확인

Phase에 과도하게 적었던 다음 조건을 이 Task로 옮겼다. 제공 범위나 계산 의미를 삭제·변경한 것은 아니며, 후속 기능 설계의 입력으로 사용한다.

- 하위 조합법은 최하위 재료까지 재귀적으로 확인하고 연결된 재료의 상세로 이동한다. 직접 상위 제작 아이템 목록에서도 상세로 이동한다. 상위 관계의 여러 단계 동시 표시는 후속이다.
- 각 조합은 제작 1회에 재료 두 개를 각각 1개씩 소비하며 결과 수량을 표시한다. 같은 아이템이 두 재료 칸에 쓰이면 총 2개를 소비한다.
- 최하위 재료의 총 필요량은 반복 재료와 중간 재료의 생산 수량을 반영한다. 필요한 제작 횟수는 올림하고 남는 수량을 반영하며, 단순히 모든 경로의 개수만 더하지 않는다. 구체 알고리즘은 후속 기능 설계에서 정한다.
- 조회할 게임 패치의 유효한 조합법·재료 정보를 일치시킨다. 조합법이 없는 기본 재료와 조합법 미등록을 내부적으로 구별하고, 미등록을 필요 재료 0개로 계산하지 않는다. 화면의 미등록 값은 기존 합의대로 비워 둔다.
- 후속 구현에서 확인할 사례: 여러 단계 조합, 같은 재료의 반복, 여러 개를 생산하는 중간 재료와 잔여 수량, 직접 상위 목록·상세 이동, 버전별 관계와 미등록 상태. 화면 확인과 필요한 계산 결과 대조를 함께 수행한다. 현재 실제 실행 결과는 없다.
- `item_leaf_materials`의 채택·저장·계산 방식은 해당 기능 개발 때 실제 실험을 여러 차례 거쳐 결정한다. 현재 어느 방식으로도 확정하지 않으며, 후속 과제 배치 때 이 실험·결정 시점을 연결한다. 비교할 쟁점은 [SQL 재점검의 두 번째 묶음](<task-001-sql-review.md#reassessment>)을 따른다.

<a id="basic-route-discussion"></a>
## 기본 루트의 P1 범위 합의

사용자가 제안한 최소 범위를 선택했다. 제공 범위는 [Phase 본문](<../../phase.md#basic-route-scope>)을 따르며, 입력·결과와 후속 경계는 다음과 같다.

| 구분 | 합의와 후속 설계 입력 |
|---|---|
| 목표 | 제작할 장비를 직접 지정하고 전체·일부 부위를 모두 지원한다. 후보 장비 조합 탐색·상세 스탯 조건·캐릭터별 고정 장비 예외는 후속이다. |
| 조건 | 최대 방문 지역 수·최대 배달 횟수를 지정한다. 실제 기본값·입력 제약과 화면 조작은 후속 설계에서 정한다. |
| 계산 | 필요·생산 수량, 공통·잔여 재료, 버전별 최초 보유 구성을 반영한다. 최초 보유 구성의 실제 값은 자료 확인 때 정하며 임의의 값으로 가정하지 않는다. |
| 결과 | 지역 집합, 수집·배달할 재료와 수량, 배달 횟수, 장비 기본 능력치 요약을 제공한다. 지역 수·배달 횟수 기준 정렬과 결과 없음 안내를 지원한다. |

계산 경계는 기존 루트 요구를 따른다. 지역 총 출현 개수와 배달 비용은 루트 계산에 사용하지 않는다. 방문 순서 최적화나 사용자 임의 보유 수량 입력을 이번 합의로 추가하지 않는다. 세부 알고리즘·가공 데이터·캐시와 임시 아이템의 루트 취급은 해당 기능 개발 때 정하며 `item_leaf_materials`의 방식은 실제 실험 후 결정한다.

후속 구현에서 확인할 범위는 전체·일부 장비 지정, 지역·배달 한도, 반복 재료·제작 수율·잔여·최초 보유 구성 반영, 결과 정렬과 결과 없음이다. 화면 조작과 필요량·배달 횟수의 계산 결과 대조를 함께 수행한다. 현재 확인은 사용자 선택과 제품 요구·Phase·Task의 문서 반영이며 실제 자료 확인·구현·계산 실험은 수행하지 않았다.

<a id="preservation-discussion"></a>
## 보존·정정의 P1 최소 지원 합의

사용자가 제안한 최소 지원을 선택했다. 범위는 [Phase 본문](<../../phase.md#preservation-scope>)을 따른다.

- 제공 원자료와 변환 결과를 담당 기록·첨부에 보관하고 출처·기준 버전을 식별할 수 있게 연결한다. 서비스 DB의 출처 연결 테이블이나 전용 관리 화면을 이 합의로 확정하지 않는다.
- v1.0.0 등록 정보를 보존하고 후속 변경 때 기준 상태를 잃지 않도록 한다. 입력 오류 정정은 새로운 실제 게임 패치로 꾸미지 않는다.
- 초기 자료의 오류를 고쳐 검색·상세·제작 관계·루트의 관련 결과에 반영한다. 자료 수정·재등록 등 구체 수단과 정정 기록 방식은 사용자 지시대로 후속 설계 때 정한다.
- 전용 정정 화면·변경 항목 선택 적용/되돌리기·자동 영향 추적은 후속으로 둔다. 관련 결과의 일치를 확인하는 요구는 유지하며, 그 수단으로 자동 영향 추적 기능의 선행 구현을 요구하지 않는다.

이번 확인은 사용자 선택과 제품의 보존·정정 요구 및 Phase 범위의 문서 대조다. 실제 자료 처리·DB 수정·정정 실행이나 검증은 수행하지 않았다. 이후 사용자가 [최종 완료 조건](<../../phase.md#completion-criteria>) 여섯 항목을 확정했다.
