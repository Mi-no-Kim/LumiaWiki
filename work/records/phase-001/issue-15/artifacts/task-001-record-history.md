[Task 본문](<../task-001.md#summary>)에서 분리한 과거 정정·검수·전환 기록이다. 당시 수행·판단과 한계를 보존하며, 현재 진행 위치는 Task 본문을 따른다.

## Phase 기록 정리와 원인 확인

사용자가 Phase의 과도한 기록을 수정하고 원인·문제점·기존 작성 방식을 보고하도록 요청했다. 기존 Task의 기록 품질 보완으로 처리하며 새 작업 단위나 별도 목적의 커밋을 만들지 않는다.

**확인한 작성 방식과 영향**

| 기존 작성 | 문제와 이번 처리 |
|---|---|
| 등록 범위 아래에 백분율 저장값·정수 수량·스킬 필드·JSON 위치·등급 고정 규칙 등을 계속 추가 | 제품 원천의 규칙을 Phase에도 다시 관리했다. 서로 다르게 수정될 수 있으므로 Phase에는 등록 대상과 단계 경계만 남기고 제품 문서를 참조한다. |
| 검색·상세의 지원 목록을 적은 뒤 같은 내용을 다시 `확인할 결과`로 반복 | 범위 설명을 복제했으며 독립된 검증 근거도 아니었다. 중복 문장을 줄이고 Phase의 완료 조건과 Task의 예정 확인을 구별한다. |
| 제작 관계에 `같은 아이템이 두 재료 칸에 쓰이면 총 2개`, 제작 횟수 올림·잔여 수량·미등록을 0으로 계산하지 않는 조건을 기록 | 계산·예외 처리의 상세가 부모 문서의 범위와 섞였다. [제작 관계 상세](<task-001-discussion-details.md#crafting-details>)로 옮기고 Phase에는 하위·직접 상위 관계와 수량 확인의 제공 범위만 남긴다. |
| SQL을 참고한 위임 경위와 자식 Task의 다음 행동을 Phase에 기록 | 판단 근거와 상세 진행 위치의 소유가 중복됐다. SQL 원본·해석은 첨부와 이 Task에 두고 Phase의 다음 행동은 Issue 수준의 범위·수용 조건·실행 계획 확정으로 정리한다. |
| 채팅 첨부 경로만 남기며 `SQL의 별도 사본을 만들지 않는다`고 판단 | 원천의 중복 관리를 피하는 것과 제공 원본을 보관하는 것을 혼동했다. 요약만으로는 원본의 모든 필드·제약을 재확인할 수 없다. 앞서 담당 첨부에 원문을 보관하고 일치를 확인했다. |

**원인과 기준 적용의 오류**

- 직접 원인은 이 Task의 `Phase 본문에 반영한다`는 문장을 상세 내용까지 옮기는 방식으로 적용한 것이다. [기록 체계](<../../../../../docs/작업 기록 체계.md#ownership>)의 `자식 상세를 부모·현황에서 따로 관리`하지 않는다는 기준, [문서 기준](<../../../../../docs/문서 관리 기준.md#product-and-plan>)의 제품 요구·Phase·Task 역할을 함께 적용하지 못했다. 현행 지침이 상세 복제를 요구한 것은 아니다.
- 대화에서 항목을 결정할 때마다 Phase에 항목과 확인 문장을 추가해 현재 결론을 한 번 더 누적했다. 단계 범위·수용 조건의 변경인지, 기존 범위 안의 상세화인지 구별하지 않았다. 수정 횟수 자체가 아닌 문서의 소유와 기록 수준이 문제다.
- 앞선 자체 검수에서는 사용자 요구의 내용 보존·참조·공백 확인에 치우쳤다. 검수 기준에 포함된 파일별 필요성·중복·소유 경계를 충분히 대조하지 못했으므로, 당시 자체 확인 문장을 이번 기록 품질의 통과 근거로 재사용하지 않는다.
- 이번에는 기존 기준을 적용해 문서를 정리한다. 공용 규칙·스킬·양식을 새로 바꾸지 않으며, 내용 이동을 제품 요구 변경이나 Task·Phase 완료로 처리하지 않는다.

**수정 범위와 검증**

Phase의 등록·검색·제작 범위를 요약하고 필드 규칙의 중복·반복 확인 문장·첨부 보관 절차의 재서술을 줄였다. 옮긴 계산·누락 조건은 [제작 관계 상세](<task-001-discussion-details.md#crafting-details>)에 보존했다. 기존 참조 표식, 실제 자료 작업의 보류 조건, 과거 조사·계획 이력은 유지했다.

자체 확인 결과: 변경 전 내용과 제품·기록 기준을 대조해 등록 대상·검색·제작 범위와 후속 경계의 보존, 세부 조건의 이동, 부모·자식의 기록 역할을 확인했다. 두 변경 문서의 로컬 참조 39개의 파일·표식과 공백 검사를 통과했고, 보관 SQL은 채팅 첨부 원본과 해시가 일치했다. 확인 범위는 문서 정리와 원인 분석이며 제품 동작 검증은 수행하지 않았다. 기본 루트·보존·정정·최종 수용 조건은 기존 미완료로 유지하고, 커밋·GitHub 반영은 수행하지 않았다.

### 사용자 정정 요청에 따른 잘못된 기록의 처리

사용자가 잘못 작성한 Phase 기록의 삭제·정리를 명시적으로 요청한 범위에서 아래 정정을 수행했다. 이를 개선 초안에서 ‘기존 기록도 현재 필요성에 따라 삭제·요약한다’는 규칙으로 확대했던 것은 잘못이다. 후속 사용자 지적에 따라 그 일반화를 철회했다. 기존 기록은 보존하며, 앞으로 작성할 내용의 필요성 판단과 이미 잘못 작성한 내용의 정정을 구별한다.

| Phase의 항목 | 처리와 이유 |
|---|---|
| 2026-10-30 계획 등록·2026-11-05 역할 정리 및 사건 구역의 서문 | 이 Phase에 불필요하게 작성한 기록으로, 사용자가 지정한 삭제 대상이므로 정정했다. 정상적인 기존 기록 전반의 삭제 기준으로 사용하지 않는다. |
| 빈 관련 Issue 구역 | 삭제. 실제 관계나 다음 판단을 제공하지 않는다. |
| 공통 계획 변경 처리 | 삭제. 공용 절차를 되풀이하며 이 Phase 고유의 변경 조건을 제공하지 않는다. |
| 일반적인 예정 확인과 계획 등록을 마쳤다는 결과 문장 | 삭제. 목표·완료 조건·현재 요약과 중복되고 실제 검증·수용 판단을 담지 않는다. |
| 2026-11-01 입력 조사 표 | 원문과 조사 시점을 Task 004의 입력 근거로 이동. 해당 Task가 필요한 입력과 확인 범위를 구분할 때 사용하며 과거 관찰을 현재 확보 상태로 오해하지 않도록 한다. Phase에는 착수 때 필요한 입력과 담당 근거의 연결만 남긴다. |
| 목표·지원 범위·후속 경계·완료 조건·보유 Issue | 유지. 이 단계가 제공할 결과와 담당 과제·수용 판단을 정한다. |
| 실제 자료의 제공 방식·처리 보류·미정 | 유지. 자료 작업의 착수 권한과 선행 조건, 임시 변환과 상시 관리 기능의 경계를 제한한다. |

이 기록은 ‘필요한 과거 근거를 유지했다’는 앞선 자체 확인의 한계를 정정한다. 재발 방지 수정 계획은 사용자가 요청한 별도 하네스 개선으로 분리했다. 문제·목표·수정 대상·계획·수용 조건을 처음부터 다시 구성했고, 기존 기록 삭제 정책은 포함하지 않는다. 정식 번호가 없는 등록 대기 초안이며 이전 누적 수정 초안을 현행 등록안으로 사용하지 않는다.

독립 개선의 현재 판단·수정안·검증은 main 기준 로컬 브랜치 `codex/record-writing-isolation`의 `work/records/harness/record-writing-prevention/issue-draft.md`가 소유한다. 제품 브랜치에 그 상세를 복제하지 않는다. 기존 항목을 삭제·요약하는 일반 규칙과 Phase 002~007의 정리 실행 계획은 제거했다. 다른 Phase의 반복 문구는 작성 방식의 관찰 근거로만 사용하고 정정 권한을 확대하지 않는다. 이번 Phase 정정과 이미 보관한 원자료·조사 근거는 유지한다.

GitHub 등록은 자동 승인 검토가 공개 저장소에 내부 작업 기록·운영 문제와 경로를 포함한 구체 본문을 공개할 명시적 승인이 확인되지 않는다는 이유로 거부했다. 이후 저장소가 공개이며 현재 계정에 ADMIN 권한이 있음을 읽기 확인했다. 당시 우회 등록이나 재시도는 하지 않았다. 후속 독립 분리 요청에서 구체적인 두 이슈 본문의 공개 등록도 자동 승인 검토가 거부했고, 사용자에게 본문·목적지를 제시하자 당시에는 공개하지 않고 로컬 초안으로 유지하도록 선택했다. 이후 실패 분석 본문의 공개 등록과 실제 번호에 따른 경로 이동을 별도로 승인받아 Issue #26을 생성했다. 기존 기록 기준 개선 초안의 미등록 상태와 Phase 정리·로컬 근거 보존은 유지한다.

추가 정리 검증: 삭제한 구역으로 향하는 참조가 없는지 필요한 docs·harness·work 범위에서 확인했고, 변경한 세 기록의 로컬 참조 43개와 공백 검사를 통과했다. Task 004로 옮긴 조사 표는 변경 전 표와 내용이 일치하며 Task의 예정 상태와 자료 처리 보류를 유지했다. Phase의 나머지 내용은 단계의 목표·범위·착수 조건·수용 판단에 사용하는지 대조했다. 최종 제품 제출 후보 9개 파일은 별도 에이전트가 실제 인덱스로 재검수했고, 현재 결과의 상태 표현을 보완한 뒤 필수 결함이 없었다. 후보의 문서 참조 119개와 편집 문서 공백 검사, SQL의 원본 바이트 일치를 확인했다. 이 제품 기록 정정의 검증은 독립 개선의 기준 적용·운영 효과 판정과 구별하며, 해당 개선의 최신 결과는 별도 초안에서 관리한다.

### 독립 작업으로의 전환과 제품 논의 복귀

독립 개선을 제품 커밋 뒤에만 나눠 담았던 전체 결과 `7ab3360`은 `codex/local-record-split-preserved`에 보존하고, 이 제품 경로는 제품 커밋 `dfca1f5`에서 이어간다. 기준 개선은 main에서 직접 분기한 `codex/record-writing-isolation`의 커밋 `6588a548631d5541ef565fd1ab0e3b77495a37db`로 분리했다. 분리·최종 검수의 누락 원인과 수정 계획은 main 기준 독립 브랜치 `issue/26-recognition-compliance`의 [Issue #26](https://github.com/Mi-no-Kim/LumiaWiki/issues/26)에서 다룬다. 로컬 원본은 `work/records/harness/issue-26/issue.md`다. 두 과제를 제품 Issue의 자식으로 등록하지 않는다.

제품 논의 복귀 조건은 원래 결과·SQL·검증 근거 보존, 독립 경로의 실제 분리 확인과 실패 분석 초안의 검수다. 이 조건을 확인한 뒤 이 Task의 남은 기본 루트·보존·정정·완료 기준 논의를 이어간다. 제품 요구·Phase 범위·자료 처리 보류와 구현 미착수 상태는 유지한다.

별도 검수에서 이 제품 경로의 실제 Task 1개 후보와 main 기준 두 독립 작업의 분리·원래 결과 보존을 대조했다. 제품의 전환·복귀 연결과 미등록 한계, 문서 참조 19개·표식·공백 검사를 확인했고 필수 결함이 없었다. 독립 수정안의 구현·효과 검증과 제품 구현을 완료한 것으로 판정하지 않는다.

### 제품 논의 복귀

사용자가 별도 Task 26-001의 개선을 중단 상태로 남기고 원래 작업으로 복귀하도록 지시했다. Task 26-001은 미완료 보류이며 완료나 예방 효과 확인으로 처리하지 않는다. 처음에는 별도 작업 폴더의 기록만 갱신해 실제 브랜치 전환을 누락했다. 사용자 지적 후 현재 프로젝트 루트를 `issue/15-phase-planning`으로 실제 전환하고 이 Task의 기존 미커밋 변경을 복원했다. 중단한 하네스 변경은 `.tmp/task-26-paused-worktree`의 `task/26-001-cause-evidence`에 분리 보존했다. 이 Task의 기존 미커밋 변경과 SQL·합의·근거는 유지한다.

남은 기본 루트와 보존·정정·완료 기준 논의에서 이어간다. 별도 개선의 해결을 제품 논의의 선행 조건으로 두지 않으며, 실제 자료 조사·확보·처리 보류와 제품 구현 미착수의 경계는 유지한다.
