# Task 005 — 후속 Issue·Task 구성과 실행 순서

담당: [Task 005](<../task-005.md#summary>). 합의한 일곱 후속 Issue를 GitHub #42~#48로 실제 등록하고 Phase 001의 정식 Issue 파일로 옮겼다. 모두 예정 상태이며 Task는 생성하지 않았다. 기존 Task 구성 23개는 각 Issue의 윤곽으로만 유지한다. 실제 자료 작업 보류를 유지하며 정식화 결과의 제출·부모 통합은 Task 005에서 구분해 관리한다. 기존 [배정 요구 목록](<task-005-handoff-requirements.md>)을 유지한다.

별도 Issue로 두기로 합의한 두 작업은 테이블·관계와 저장·조회 코드를 만드는 개발, 그리고 실제 v1.0.0 원자료를 변환해 테이블에 값을 등록·교정하고 대조하는 자료 작업이다. 실제 수치·허용 범위·필수 내용에 의존하는 스키마/검증은 사용자 자료 확인 뒤 결정하며, 입력 부족을 임의 값으로 해결하지 않는다. 기본 DB 수정과 Java/Spring 교정 실행의 [주담당 배정](<../../issue-45/issue.md#ownership>)은 합의했다. 자료 Issue에서 필요에 따라 선행 DB 코드·기본 화면 등을 보완하고 관련 검증을 수행하는 재작업도 허용한다.

검색 목록·필터·미리보기와 개별 아이템 기본 상세는 한 Issue에서 다룬다. 제작 트리·상위 아이템 탐색·재료 수량 계산은 별도 Issue에서 다루되 같은 상세 페이지의 제작 구역으로 연결한다. 자료 등록 전에 준비할 기본 상세와 자료 등록 뒤 완성할 제작 기능의 수용 범위를 구분한다. 공통 시각 표현은 검색·기본 상세의 화면 설계 Task가 마련하고 제작·루트가 재사용한다. 기술 골격은 실행 기반이 맡는다.

<a id="sequence"></a>
## 합의한 실행 순서와 선행 결과

합의한 큰 순서는 실행 기반→DB 구조·저장/조회 코드와 등록 수단→자료 확인용 검색·기본 상세→실제 자료 등록·화면 대조→제작·루트 등 나머지 기능과 화면 완성→통합 확인이다. 실제 자료를 먼저 확인해 수치·스킬 설명·제작/획득 관계를 뒤늦게 발견하는 데 따른 재작업을 줄이려는 방향이다. 아래 필요한 선행 결과와 병행 범위를 따르며 실제 일정·개별 실행 절차는 담당 과제에서 구체화한다.

| 진행 위치 | 필요한 선행 결과 | 병행·보류 경계 |
|---|---|---|
| 실행 기반 먼저 | Task 001~004 합의와 Issue #15 종료 | 기반 초반에 골격·테스트 명령→최소 TDD hook 연결·검증. CI는 로컬 명령 준비 후 연결하고 기반 과제 완료 전에 실제 통과/실패 확인. 첫 제품 기능의 동작 구현은 hook 선행 조건 충족 뒤 |
| 데이터 기반과 공통 화면 준비 | 실행 기반 및 필요한 저장·조회 계약 | 데이터 관계 설계와 화면 디자인은 필요한 입력이 있으면 병행. 공통 화면 디자인을 검색·제작·루트가 재사용. 각 기능의 화면 검토→동작 구현→화면/내부 검증 순서 유지 |
| 검색·기본 상세 준비 | 필요한 데이터/API 계약과 공통 화면 | 전체 실제 자료 등록을 기다리지 않고 빈 상태·통제한 검증 입력으로 준비. 실제 자료 입력 전 검색·상세 확인 화면을 마련 |
| 실제 자료 등록·교정 | 사용자 자료 작업 보류 해제·제공 입력, 담당 저장/검증 설계·등록 수단과 확인용 검색·상세 | 제작·루트 등 나머지 기능의 완성보다 먼저 자료 등록·화면 대조를 진행. 테이블별로 진행하고 부족·충돌의 영향 범위만 보류 |
| 제작 관계·루트 개발 | 제작은 관계/수량 정보와 제작 화면, 루트는 장비·제작·획득/배달 정보와 루트 화면 | 합의한 순서에 따라 실제 등록 자료를 바탕으로 개발·검증. 자료 보류 중에는 허용된 준비와 통제한 입력의 실험을 할 수 있으나 모든 기능을 실제 자료 없이 먼저 완성하는 것을 기본 순서로 두지 않음 |
| P1 통합 확인 | 필요한 기능·실제 자료·각 과제의 검증 근거 | 기존 검사 결과를 재사용하고 실제 자료를 이용한 연결 확인·변경 영향·미확인 해소를 수행. 모든 검증을 처음부터 복제하는 과제로 만들지 않음 |

큰 실행 순서의 합의는 실제 자료 작업의 보류 해제를 뜻하지 않는다. 보류 해제는 별도 사용자 요청이 필요하며, 구체 일정·모든 준비 작업의 직렬 실행까지 확정하지 않았다. 구현 과제의 입력 부족은 영향을 받는 범위에서 판단한다.

## 확정한 Task 구성과 수용 경계

실행 환경 구축/DB 개발 분리, 제작/루트 분리와 P1 통합 확인의 별도 Issue 구성에 더해 제안한 Task 구성과 개별 수용 조건을 확정했다.

| 확정한 내용 | 합의 결과 |
|---|---|
| 각 Issue의 Task 구성 | 실행 기반·DB·자료·제작·루트는 각 4개, 검색·기본 상세는 3개로 총 23개 Task. 통합 확인은 Task 없이 직접 수행. 구성 윤곽이며 실제 Task는 미생성 |
| 기본 DB 수정과 복잡한 Java/Spring 교정의 책임 | 합의. DB Issue가 공통 저장·기본 수정·참조/캐시 일치 처리를 제공하고, 자료 Issue가 교정 실행·실패 복구와 실제 자료 수용을 담당. 자료 Issue에서 필요한 선행 코드·화면 수정과 관련 재검증도 수행 |
| 자료 Issue의 수용과 후속 제작·루트 검증의 관계 | 합의. 자료 Issue는 등록 자료·교정·기본 화면에서의 자료 확인까지 수용. 제작·루트 Issue가 각 계산의 정합성과 정정 반영을 확인하고 통합 Issue에서 전체 연결 확인 |

Task 구성과 각 Issue의 수용 조건은 연결한 계획서를 따른다. 각 문서의 남은 결정은 담당 과제에서 정할 상세 설계이며 이번 합의로 임의 확정하지 않는다. Task 005의 완료 조건 대조와 제출·통합 잔여는 [담당 기록](<../task-005.md#readiness>)에서 구분한다. 이번에는 Issue만 실제 등록하고 정식 기록을 만들었다. Task 생성·첫 착수 과제의 상세 실행 계획·구현은 수행하지 않는다.

## 기능 과제에 공통으로 적용할 기준

- 각 기능의 화면을 디자인·검토한 뒤 동작을 구현한다. 구현 전에 사용자 확인 목록을 공유하고 같은 사례를 TDD·자동 검사·AI 화면 조작·사용자 확인 안내에 연결한다. 실제 결과와 미확인은 구분한다.
- Task마다 맡은 기능의 자동 검사·화면 확인을 포함한다. 별도의 테스트 실행 Task를 일률적으로 추가하지 않으며 최종 통합 확인은 유효한 기존 근거를 재사용한다.
- Task 002의 기준 시안을 상세화하고 P1 범위·빈 상태·v1.0.0 표시를 유지한다. 등록 전 기본 화면은 통제한 입력으로 준비하고 제작·루트 완성은 실제 자료 등록·대조 뒤 진행한다.

## 문서 구성

- Task 본문: 목적·범위·상태·완료 조건과 현재 결정/다음 행동.
- 이 문서: 합의한 Issue 경계·실행 순서와 Task 구성. 상세 Task 표를 중복 보관하지 않고 연결.
- 정식 Issue 파일 7개: 합의한 목표·입력·수용 조건·의존 관계·남은 결정과 Task 구성 윤곽을 소유한다. 기존 일곱 계획서의 내용을 이관하고 현재 참조를 맞췄다.
- Task: 이번에는 생성하지 않는다. 합의한 제목·담당 결과·선후 관계를 Issue 안의 윤곽으로 보존하고 실제 파일·등록과 상세 완료/실행/검증 계획은 담당 Issue 준비 때 작성한다.
- 기존 두 묶음 안내: 정식 Issue로 탐색하는 링크만 유지한다.
- 배정 요구 목록: 기존 Task 005의 상세 인계 항목을 보존. 원천 기준은 Task 001~004와 docs를 계속 참조하고 같은 규칙을 새로 소유하지 않음.

등록한 Issue가 자기 계획과 이후 Task를 소유하고 이 문서는 구성·배정 근거를 연결한다. 실제 실행·검증 기록을 이 계획에 누적하지 않는다. 별도 검수 증명 파일·가짜 Issue 번호·첫 Issue의 상세 Task 계획은 만들지 않는다.
