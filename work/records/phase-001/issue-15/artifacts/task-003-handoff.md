# Task 003 — 공통 전제·의존 관계·상세 설계 인계

담당 기록: [Task 003](<../task-003.md#summary>). 기술 규칙의 원천은 [개발 기준](<../../../../../docs/개발 기준.md#current>)이며 이 문서는 이번 계획의 선행 관계·후속 담당·결정 시점을 관리한다.

<a id="current"></a>
## 최종 점검 판단

Task 001의 P1 범위·보존/참조 합의와 Task 002의 세 화면·흐름을 대조했다. 공통 기술·서버/데이터 표현의 미합의 선택은 남지 않았다. 아래 상세 미정은 담당·필요 입력·결정 시점에 연결되므로 Task 003 완료를 위해 임의 확정하지 않는다. 현재 실제 담당은 [후속 Issue #42~#48의 배정](<task-005-handoff-requirements.md#allocation>)에 연결했다. 아래 Task 003 당시의 인계 경로·미정 자체는 보존하며 실제 실행은 각 담당 Issue에서 준비한다.

<a id="dependencies"></a>
## 구현의 선행 관계

| 결과·단계 | 필요한 선행 결과와 확인 경계 |
|---|---|
| 기반 프로젝트·공통 실행 | 이 Task의 기술·버전·DB/환경·검사 기준 → 프로젝트 골격·테스트 명령 → 최소 TDD hook·포맷/검사 연결·실제 검증. 첫 기능의 동작 구현 전에 [착수 조건](<../task-003.md#tdd-automation-handoff>) 충족을 확인한다. |
| CI 구축·독립 실행 | 로컬 검사·테스트·빌드 명령과 잠금 파일/Wrapper 등 재현할 입력을 마련한 뒤 첫 기반 구축 과제에서 CI를 연결·검증한다. 해당 기반 과제 완료 전에 실제 CI 결과를 확인하고 후속 기능 PR 검증에 사용한다. 세부 담당·시점은 아래 CI 인계를 따른다. |
| 자료 저장·참조 | [공통 데이터 전제](<../../../../../docs/개발 기준.md#data-relations>) → 담당 DB 설계에서 테이블/키·버전 선택·일치 검사 결정 → Flyway·매핑·저장/조회 검증. 구체 범위·정밀도에 실제 자료가 필요한 컬럼은 입력 확인 전 임의 확정하지 않는다. |
| 확인용 검색·상세 | Task 002의 디자인·흐름과 공통 API/프런트 골격 → 빈 상태·통제한 검증 입력으로 화면 준비. DB/API 연동은 해당 저장·조회 계약을 정한 뒤 확인한다. 전체 실제 자료의 확보·등록 완료를 화면 준비의 선행 조건으로 삼지 않는다. |
| 실제 자료 등록·교정 | 사용자 보류 해제·자료 제공·출처/버전 확인과 담당 저장/검증 설계, 확인용 검색·상세가 준비된 뒤 등록 → 기존 화면에서 확인. Task 004는 이 방향과 사례의 계획이며 실제 확보·변환·등록이 아니다. |
| 제작 관계 | 아이템·조합 참조/수량의 저장·조회 계약과 전체 재귀 트리 디자인 → 순환·누락·반복/수율 사례 실험·검증 → 실제 등록 자료와 대조. 알고리즘 검증용 입력과 실제 원자료를 구분한다. |
| 기본 루트 | 장비·제작·획득/배달의 조회 계약과 지원 범위/최초 보유 입력 확인, 루트 디자인 → 계산 규칙·알고리즘/화면 검증 → 실제 등록 자료와 대조. 입력 변경만으로 재계산하지 않고 같은 조건의 결과임을 확인한다. |

이는 기술 의존 관계이며 모든 과제를 위 행 순서대로 직렬 실행하는 계획이 아니다. 화면·로직은 통제한 검증 입력으로 준비할 수 있고 실제 게임 자료에 대한 검증은 허용된 자료가 준비된 뒤 수행한다. Task 005에서 독립 수용 경계를 정할 때 계약·필요 입력을 연결하고 의존 순환을 만들지 않는다.
