# Task 005 — 후속 과제의 배정 요구 목록

담당: [Task 005](../task-005.md#summary). 기존 본문의 상세 인계 항목을 이곳으로 옮겨 보존한다. 이는 이미 정한 요구와 배정 책임이다. [합의한 Issue 경계·큰 순서](task-005-issue-outline.md)를 바탕으로 Task 구성·수용 조건의 세부 배정을 대조한다.

<a id="requirements"></a>

## 상세 인계와 배정할 필수 사항

- [Task 003의 TDD 기준](../task-003.md#tdd)에 따라 기반 구축에는 테스트 실행 환경을, 기능 과제에는 화면 설계 → 실패 테스트·최소 구현·통과·리팩터링 → 실제 화면 검증을 연결한다. 적용 범위·예외의 이유와 대표 검증 근거는 담당 Task의 검증 계획·기록에 포함한다.
- [TDD 자동화 인계](../task-003.md#tdd-automation-handoff)에 따라 첫 기반 구축 과제의 초반에 테스트 환경 구성 후 최소 hook을 연결·검증하도록 범위·수용 조건을 배정한다. 이를 첫 기능 동작 구현의 선행 조건으로 명시하고 등록 시 실제 과제를 [Phase 착수 조건](../../phase.md#tdd-readiness)에 연결한다.
- [공통 검사·포맷 인계](task-003-code-quality.md#handoff)에 따라 첫 기반 구축 과제에 TypeScript lint 호환 구성, 문서·일괄 포맷 명령, 파일 생성/수정 자동 포맷과 제출 후보 검사·실제 검증을 배정한다. TypeScript 병행과 포맷 방식은 Task 003의 채택 기준을 따른다.
- [CI 인계](task-003-handoff.md#handoff-decisions)에 따라 첫 기반 구축 Issue에 CI 도구·트리거·명령·영향 영역의 설계와 검사·테스트·빌드 독립 실행 연결·검증을 배정한다. 로컬 명령을 마련한 뒤 연결하고 해당 기반 과제 완료 전 실제 통과/실패 처리를 확인하도록 수용 조건에 명시한다. 실제 번호는 등록 시 연결하며 이번 Task 005에서 CI를 구현하지 않는다.
- [사용자 확인 목록](task-003-testing-and-tdd.md#user-checklist)에 따라 각 기능 과제의 동작 구현 전에 조작·기대 결과를 작성·공유하고, 구현 후 AI의 실제 검증 결과와 사용자 확인 절차·미확인을 구분해 전달하도록 실행·검증 계획에 연결한다. 같은 사례를 자동 테스트·브라우저 확인에 재사용한다.
- [프런트 공통 구성](<../../../../../docs/details/development/기술 구성.md#frontend-common>)의 Router·Query·스타일·SPA 골격과 기존 Vitest·React Testing Library 실행 환경은 기반 구축에, [기능별 프런트 동작 테스트](<../../../../../docs/details/development/테스트와 TDD.md#frontend-testing>)와 목록 복귀·스크롤·계산 버튼 흐름 검증은 해당 기능 과제에 배정한다.
- [이미지 보관·제공 기준](<../../../../../docs/개발 기준.md#images>)에 따라 정적 파일 제공·공통 URL 구성과 과거 파일 보존 검증을 해당 기반/조회·자료 과제에 배정한다. 실제 파일 규모·Git 취급은 자료 확인 시 정하고, [S3 후속 검토](<../../../../../docs/개발 기준.md#image-storage-followup>)는 이미지 업데이트/재배포 부담 또는 공개 배포 환경 결정 시 해당 이미지 제공·배포 설계에 연결한다. 현재 S3 구현을 필수로 추가하지 않는다.
- [능력치 수치 기준](<../../../../../docs/개발 기준.md#stat-numeric>)에 따라 해당 데이터/DB/API 과제에 NUMERIC·BigDecimal 저장·매핑·기본 합산·원본/캐시·전달 값 보존 검증을 배정한다. 실제 범위·소수 자릿수와 API/화면 표현은 자료 확인 후 스키마·검증 구현 전에 결정한다.
- [스킬 연결별 JSON 기준](<../../../../../docs/개발 기준.md#skill-json>)에 따라 담당 자료/스킬·DB·API 과제에 jsonb·JSON 트리 매핑과 문법·중복 키·값의 저장/읽기 보존 검증을 배정한다. 필수 키·값 범위는 해당 설계에서 정하고 수식 해석·실행 논의는 딜량 계산기까지 보류한다.
- [날짜·초 단위 시각 기준](<../../../../../docs/개발 기준.md#datetime>)에 따라 해당 데이터/DB·API 과제에 자료형·UTC·초 단위 정규화와 왕복/화면 표시 검증을 배정한다. 실제 값·시간대·미확인 값의 등록 허용은 자료 설계에서 스키마/검증 구현 전에 확인한다.
- [공통 내부 ID 기준](<../../../../../docs/details/development/공통 DB 모델.md#internal-identifiers>)에 따라 기반 데이터/DB·해당 API 과제에 자동 발급·Java 매핑·문자열 ID 전달과 값의 왕복 보존·참조 정합성 검증을 배정한다. 구체 테이블·키·제약은 해당 DB 설계에서 정한다.
- [서버 환경별 설정 기준](<../../../../../docs/개발 기준.md#server-profiles>)에 따라 첫 기반 구축 과제에 공통·로컬·테스트 YAML과 명시적 프로필 활성화·환경변수 전달·개발/테스트 DB 분리의 설정·실제 검증을 배정한다.
- [JPA 조회·응답 구성 기준](<../../../../../docs/개발 기준.md#jpa-query-boundary>)에 따라 기반 구축에는 `open-in-view=false` 설정을, 해당 기능 과제에는 서비스 트랜잭션 안의 조회·DTO 구성과 실제 응답 검증을 배정한다.
- [최소 로그 기준](<../../../../../docs/개발 기준.md#logging>)에 따라 기반 구축에는 기본 콘솔·수준 조정 설정을, 기능 과제에는 필요한 로그 작성 지점·진단 정보 확인을 배정한다. 파일 보관·중앙 수집·분석의 결정은 운영 환경을 정하는 배포·운영 설계에 연결한다.
- [API 공통 규칙·로컬 연결](<../../../../../docs/details/development/기술 구성.md#api-common>)에 따라 첫 기반 구축 과제에 프록시·[개발 기준의 공통 오류 처리](<../../../../../docs/개발 기준.md#error-handling>) 골격·실제 검증을 배정하고, 기능별 경로·DTO 필드·페이지 처리·오류 코드 목록은 해당 기능/API 설계에 배정한다.
- [Task 002의 확정 디자인 분담](../task-002.md#design-handoff)과 [남은 상세 결정](../task-002.md#handoff-decisions)을 공통/검색/상세·제작/루트 기능 과제에 배정한다. 검색 v2·상세 v1·루트 v1은 현재 기준 시안이며 세부 디자인은 각 담당 기능에서 구체화한다. 등록·정정 확인은 기존 화면을 재사용하고 전용 관리 화면을 선행 조건으로 추가하지 않는다.
- [Task 003의 최종 의존·인계](task-003-handoff.md#dependencies)에서 기반·저장/조회·확인용 화면·등록·제작·루트의 선행 관계와 [후속 미정](task-003-handoff.md#handoff-decisions)의 담당·입력·시점을 실제 과제에 배정한다. 배포 환경별 API 문서 노출·SPA fallback·운영 권한/로그/백업도 해당 환경 적용 전 결정할 담당으로 연결한다.
- 실행 순서와 다음 착수 Issue, 그 Issue를 준비하기 위해 충족할 조건을 정한다.
- [Task 004 자료 계획](task-004-data-plan.md#handoff)과 [검증 인계](task-004-verification-plan.md#evidence)의 입력 준비·등록/교정·확인 화면·대표 사례 V01~V12를 해당 자료/DB·조회·제작·루트·보존 과제의 범위·수용 조건에 배정한다. 테이블별 작업, Java/Spring 기본 교정과 다른 테이블에 영향이 전혀 없는 독립 DB 수정 예외, 전체 내부 검사·대표 화면 확인 및 화면에서 자료를 함께 대조하는 검증 B를 연결한다. 실제 자료 보류와 통제한 검증 입력/원자료의 구별을 유지한다.
- [Task 001의 이월 목록](task-001-discussion-details.md#handoff-decisions)의 각 P1 상세 결정을 담당 기능 묶음과 결정 시점에 배정한다. DB 관계·일치 검사·캐시 갱신, 자료/정정 수단, 루트·임시 아이템 취급과 재료 합산 실험을 누락하지 않는다. 독립 관리 전환은 후속 추적에 연결하고 수식은 딜량 계산기 작업 전의 선행 조건으로 두지 않는다.

## 사례와 후속 경계 배정

[Task 004 대표 사례](task-004-verification-plan.md#cases)의 V01·V02·V11·V12는 DB/자료와 필요한 기능 과제, V03·V04는 검색·상세, V05의 삭제/검색 노출 경계는 DB·검색/상세와 필요한 실제 자료 확인을 맡는 자료 Issue, V04·V06·V07·V11은 제작, V08~V10은 루트에 연결한다. 최종 통합은 각각의 실제 결과와 정정 영향·연결을 확인한다. 상세 실행 입력·주소·명령·검증 절차는 해당 과제를 준비할 때 정한다.

독립 정보 관리 전환·버전 선택기·이력/전용 관리 확장·수식은 기존 후속 경계를 유지한다. 실제 배포 환경·API 문서 노출·SPA fallback·관리 권한/로그 보관·백업과 이미지 저장소 전환 조건은 통합 확인 Issue가 필요한 자료 적용/후속 운영 과제에 연결하되 P1에 전체 공개 운영 기능을 추가하지 않는다.
