# Task 004 — 필요한 자료와 등록·교정 계획

담당: [Task 004](<../task-004.md#summary>). 이 문서는 입력 준비와 등록·교정 순서를 소유한다. 검증 사례와 수용 조건 대응은 [검증 계획](<task-004-verification-plan.md>)을 따른다.

<a id="direction-discussion"></a>
## 합의한 자료·교정·검증 방향

| 판단 | 합의한 방향 | 후속에서 정할 상세 |
|---|---|---|
| 자료 작업 단위 | 테이블별로 작업 단위를 정한다 | 구체 테이블·참조 관계에 따른 처리 순서와 등록 도구·트랜잭션/분할 크기 |
| 부족·충돌 자료 처리 | 영향받는 대상·관계/계산의 등록·수용은 보류하고 독립적으로 확인된 범위는 진행. 누락을 임의 값으로 메우지 않음 | 미확인 값의 등록 허용, 실제 참조·계산 의존 관계에 따른 영향 범위 |
| 교정 기본 방식 | Java·Spring을 사용해 교정하고 관련 테이블·원본/캐시·조회/계산 결과를 함께 반영·확인 | 교정 로직의 구체 구성·실행 진입점·반영 단위·실패 복구 |
| 직접 DB 수정의 예외 | 다른 테이블에 영향을 전혀 주지 않는 독립적인 수정에만 허용. 드문 경우의 이론적 예외이며 기본 작업 흐름으로 사용하지 않음 | 실제 사용 시 다른 테이블에 영향이 없는지 확인할 대상·근거 |
| 검증 B | 기계적으로 비교 가능한 전체 자료·관계는 내부 검사하고 대표 정상/실패/경계 흐름은 화면에서 확인. 자료 내용도 기존 화면에서 사용자와 함께 원자료에 대조 | 실제 입력에 맞는 검사 도구·대표 사례·화면 대조 범위 |

교정은 잘못된 자료와 관련 결과를 올바르게 고치는 작업이다. 원인 분석·분류나 변환 규칙 수정을 매 교정의 선행 절차로 요구하지 않으며, AI가 잘못 입력한 값도 기본 교정 방식으로 바로잡는다. 구체적인 수정 대상·전후 값·근거와 결과는 담당 기록에 남기고 입력 오류 정정을 새 게임 패치로 꾸미지 않는다. 매번 전체 테이블을 지우고 재등록하는 방식을 확정한 것은 아니다.

검증 B의 내부 검사는 등록 대상/건수·필수 정보·참조·중복·버전·원본/캐시와 자동 대조 가능한 값을 전체 범위에서 확인한다. 화면은 자료 확인에도 재사용하며 기능 동작 확인과 원자료 대조를 같은 흐름에서 수행한다. 모든 자료를 별도의 수작업 검사표에서 다시 건별 대조하는 절차를 추가하지 않는다. 대표 사례는 정보 종류·제작/수량 구조·획득 방법·주요 상태를 포함하도록 정하고 미확인·충돌 항목은 확인 대상으로 구분한다.

교정 뒤에는 변경한 값과 관련 관계/캐시·조회·계산 결과를 재확인한다. 공통 처리 로직을 변경했다면 그 로직의 영향을 받는 범위를 다시 검사한다. 기대값은 기능 출력만으로 만들지 않고 원자료·독립적인 계산 근거와 연결한다. 실제 자료 작업 보류, 사용자 자료 제공·AI 변환 지원·함께 교정하는 임시 방식, 등록 전 확인용 검색·상세 준비와 원자료/버전 보존은 유지한다.

<a id="input-status"></a>
## 현재 입력 상태와 보류 경계

현재 담당 기록에는 실제 v1.0.0 원자료의 제공 위치·버전 적합성·포함 정보가 확인돼 있지 않다. 이는 기록 기준의 미확인이며 자료가 어디에도 없다는 판단이 아니다. 이번에는 실제 자료 파일·웹·보존 영역을 조사하지 않았다. 사용자 제공 SQL은 설계 참고, Task 002의 시안 값은 예시이며 게임 수치 원자료로 수용하지 않는다.

실제 조사·확보·변환·등록은 사용자의 자료 작업 재개 요청 뒤 지정된 자료·허용 범위를 확인해 수행한다. 아래 목록은 그때 필요한 입력이며 지금 자료 제공이나 보류 해제를 요구하는 목록이 아니다.

## 필요한 자료·부족 입력

각 자료에 제공 위치, 출처, 기준 버전/시점, 포함 범위와 누락·해석 불확실성을 연결한다. 자료 간 충돌은 조용히 덮어쓰지 않고 담당 자료 기록에서 확인한다. 구체 파일 형식·변환 산출물·등록 수단은 후속 설계에서 정한다. 교정 방식은 위 합의를 따른다.

| 자료 종류 | 필요한 정보·확인할 의미 | 현재 부족 입력과 후속 연결 |
|---|---|---|
| 시즌·버전·지역 | 시즌 1·v1.0.0 대응, 시즌 표시 이름/고유 이름·기간, 별도 버전 이름·패치 적용 일시/시간대, 지역 목록·순서 | 실제 값·출처 미확인. 자료 담당이 확인하고 DB 담당이 번호 범위·미확인 값의 등록 허용을 스키마/검증 구현 전에 결정 |
| 아이템 기본·분류·이미지 | 이름·종류 계층·등급/순서·5부위·최대 중첩, 별도 무기 종류 연결, 이미지 원본/목록/규모·버전 대응, 검색 제외·게임 삭제의 의미 | 실제 목록·파일 미확인. 자료/이미지 담당이 확보·Git 취급·등록 방식을 허용된 확보 전 결정하고 과거 참조를 보존 |
| 능력치 | 종류·값·백분율 구분, 실제 범위·소수 자릿수, 같은 종류의 중복 여부 | 실제 수치 미확인. 자료→DB/API 담당이 정밀도·표현을 구현 전 결정. 원본/표시 캐시와 왕복 값 대조는 검증 계획에 연결 |
| 아이템 스킬 | 대상·내부 이름·설명 원문·특정 스킬 버전·게임 패치·연결별 JSON | 실제 텍스트/JSON 미확인. 필수 내용·값 범위와 참조 일치 검사 수단은 스킬/DB 담당이 저장 구현 전에 결정. 수식 실행 설계는 딜량 계산기까지 보류 |
| 제작 관계 | 재료 A/B와 결과 수량, 조합법 없는 기본 재료와 자료 누락의 구분, 버전별 관계, 필요한 임시 아이템 관계 | 실제 조합법 미확인. 제작 담당이 순환/누락을 확인하고 합산 방식 실험에 사용. 고정 1+1 소비 규칙을 유지 |
| 획득·배달 | 지역별 획득 가능 여부·방법·대상, 지역 총 출현 개수, 획득/배달당 수량·배달 가능 여부/비용 | 실제 목록·수치 미확인. 획득/DB 담당이 사냥 대상·지역 관계를 구현 전에 구체화. 출현 개수·비용은 보존하되 루트 계산에서 제외 |
| 최초 보유 구성 | 적용 버전·아이템/수량, 선택 무기군에 대응하는 시작 무기 | 실제 구성·버전 경계 미확인. 자료→루트 담당이 실제 자료 검증 전에 확인. 임의 기본 구성이나 사용자 자유 수량 입력으로 대체하지 않음 |
| 출처·교정 근거 | 제공 원자료·해석 설명·변환 결과와 대응, 오류 지적·수정 대상/기준 버전 | 실제 자료/오류 사례 미제공. 자료·보존 담당이 최초 등록/교정 전 기록 위치·Java/Spring 교정의 구체 실행 수단·DB 출처 연결 필요성을 결정 |

정보의 의미와 채택한 자료형은 [제품 데이터 요구](<../../../../../docs/details/product/게임 데이터 변경 관리.md>)·[아이템 요구](<../../../../../docs/details/product/아이템 탐색과 상세.md>)·[개발 기준](<../../../../../docs/개발 기준.md#data-relations>)이 소유한다. 이 표는 새 필드를 확정하는 스키마가 아니다.

<a id="workflow"></a>
## 등록·교정·확인의 순서

자료 작업 재개 뒤 테이블별로 대상·기준 버전·필요 참조와 부족/충돌 항목·영향 범위를 담당 기록에 연결한다. 참조나 계산이 부족 자료에 의존하면 해당 대상과 관련 결과의 등록·수용을 보류하고, 독립적으로 확인된 범위는 계속한다. 아래 표는 확인할 단계와 의존 관계이며 구체 처리 순서는 테이블 참조 관계에 맞춰 정한다. 부분 등록을 전체 자료·P1 완료로 판정하지 않는다. 자동 영향 추적 기능의 구현을 선행 조건으로 요구하지 않는다.

| 단계 | 준비 조건·할 일 | 다음 단계로 넘길 근거 |
|---|---|---|
| 1. 확인 기반 준비 | 담당 기능의 화면 디자인·검토 후 검색·상세를 빈 상태/통제한 검증 입력으로 준비. 저장·조회 계약과 내부 검사 환경도 마련 | 자료 입력 전에 확인용 검색·상세가 있어야 한다. 실제 전체 자료 확보는 화면 준비의 선행 조건이 아님. 첫 기능 구현의 테스트/hook 선행 조건은 [Phase](<../../phase.md#tdd-readiness>) 유지 |
| 2. 자료 재개·입력 확인 | 사용자 재개 요청 후 지정 위치·접근 범위·출처·버전/시점·해석·누락 확인 | 원자료와 담당 기록의 연결. 미확인 항목은 표시하고 의존하는 등록/수용 판단을 제한 |
| 3. 변환·교정 | 원자료를 보존하며 담당 과제에서 정한 형식으로 변환. 사용자 오류 지적과 자료 충돌을 확인·수정 | 원본 위치와 변환 결과·대응, 수정 이유/대상. 전용 상시 업로드·관리 화면을 도입한 것으로 처리하지 않음 |
| 4. 등록 전 검사 | 필수/허용 범위·날짜/시간대·수치·JSON·참조·제작 순환/누락을 담당 설계 기준으로 검사 | 문제와 미확인을 구분. 누락 자료를 0·임의 날짜·가짜 관계로 메우지 않음. 반영 단위·실패 시 부분 반영 확인/복구 수단은 등록 실행 전에 결정 |
| 5. DB 등록·조회 확인 | 의존 관계를 지켜 시즌/패치·대상/분류·버전별 정보/관계를 등록. 실제 순서는 DB 설계에서 확정 | 저장값·참조·유효 버전 조회와 검색·상세를 원자료에 대조. 버전 번호/정렬값과 내부 ID를 구별 |
| 6. 제작·루트 확인 | 해당 화면·기능과 필요한 실제 입력이 준비되면 관계·수량·기본 루트 결과 대조 | [검증 계획](<task-004-verification-plan.md#acceptance-map>)의 화면 조작과 내부 값 대조를 모두 수행. 계산용 예시 성공만으로 실제 자료 검증을 대체하지 않음 |
| 7. 오류 정정·재확인 | 잘못 입력한 기준 버전의 자료를 Java·Spring으로 교정하고 관련 테이블·원본/캐시·조회·계산을 재확인. 직접 DB 수정은 위 독립 수정 예외에 한함 | 게임 패치를 새로 만든 것으로 기록하지 않음. 정정 대상·이유·관련 결과·미해결을 담당 기록에 보존 |

등록 전의 검사는 구조·입력 정합성을 확인하며, 등록 뒤의 왕복·조회·화면 검증을 대신하지 않는다. 제작·루트는 계약과 통제한 입력으로 병행 준비할 수 있지만 실제 자료 수용에는 준비된 원자료와의 대조가 필요하다. 전용 정정 화면·자동 영향 추적·전체 기능 디자인 완료를 첫 자료 확인의 선행 조건으로 추가하지 않는다.

<a id="handoff"></a>
## 미정의 결정 시점과 Task 005 인계

Task 005가 위 표의 자료/DB·조회·제작·루트·보존 담당을 실제 과제에 배정한다. 실제 번호는 아직 발급하지 않는다.

- 자료 재개 때: 제공 위치·출처·버전·실제 값·포함/부족 범위를 확인한다. 형식·보관·이미지 규모에 따른 처리와 자료 충돌의 해결도 담당 자료 과제에서 정한다.
- 스키마·저장/전달 검증 구현 전: 수치 범위/정밀도·API 표현, 날짜/시간대와 미확인 허용, JSON 필수 내용, 키/참조·캐시 갱신·사냥/임시 아이템 관계를 결정한다. 실제 값 의존 부분은 자료 확인 뒤 정한다.
- 최초 등록·교정 실행 전: 변환/반영 단위·Java/Spring 교정의 구체 실행 수단·정정 기록·출처 연결·실패 복구를 결정한다. 원자료의 보존과 관련 결과 일치를 확인할 수 있어야 한다.
- 제작·루트 개발 때: 반복/수율/잔여·기본 재료/누락 구별과 `item_leaf_materials` 대안을 실제 실험으로 비교한다. 실험 입력·환경·반복 횟수·판정 기준은 담당 실행 계획에 둔다.
