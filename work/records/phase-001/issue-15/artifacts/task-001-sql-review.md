# Task 15-001 — 제공 SQL 대조와 설계 참고

[Task 본문](<../task-001.md#summary>)의 SQL 대조와 재검토 논의다. 아래 기존 검토는 당시 판단이며, 재검토 제안과 확정한 변경을 구별한다.

<a id="reassessment"></a>
## SQL과 기존 합의 재점검

- 사용자 요청: SQL과 기존 결정 어느 쪽도 정답으로 전제하지 않고 비교하며 결정한다. 초기 개발을 위해 의도적으로 단순하고 거친 방식을 선택할 수 있다.
- 비교할 내용: 제공할 결과, 초기 입력·구현 부담, 오류 가능성, 이후 변경 비용. 현재 제품 요구도 변경 논의의 대상이며, 변경 합의 전에는 기존 요구를 임의로 대체하지 않는다.
- 여덟 번째 묶음까지 원문·대상별 발췌·구조화한 게임 변경의 역할을 합의했다. 입력 오류 정정의 구체 기록 방식은 후속 설계 때 정한다. 수식 논의는 사용자 지시로 딜량 계산기 작업 때까지 미룬다. 앞선 기능 설계·DB 설계·실험으로 이월한 사항은 유지하며 이후 범위 논의는 [Task 본문](<../task-001.md#summary>)에서 이어간다. SQL 원본 수정·실행은 수행하지 않았다.

### 첫 묶음 — 버전 관리와 현재값 저장: 합의

| 선택 | SQL과 기존 합의의 비교 | 결정과 이유·대가 |
|---|---|---|
| 변경을 보존하는 단위 | SQL은 이름·능력치·조합법 등의 이력 테이블을 나누지만, 함께 갱신할지 변경된 정보만 갱신할지는 DDL만으로 알 수 없다. 기존 합의는 아이템 버전 기준으로 당시 구성을 보존하는 방향이었다. | 아이템 단위 보존을 선택했다. 초기에는 변경 없는 정보도 복사하는 단순 구현을 허용한다. 중복 저장을 감수하며, 테이블 분리·재사용의 구체 방식은 후속 설계에서 정한다. |
| 현재값 별도 보관 | SQL은 `item` 및 `item_stat`의 현재값과 `*_version` 이력을 함께 둘 수 있는 구조이며 갱신 절차는 SQL에 없다. | 이력에서 조회할 패치에 유효한 아이템 버전을 선택한다. 현재값의 별도 사본은 두지 않는다. 아이템 자체의 식별 대상은 유지한다. 제품 원천에도 반영했다. |
| 이후 독립 관리 전환 | 기존 합의는 정보별 독립 관리로 전환할 계획이다. | 전환 계획은 유지한다. 사용자는 읽기 빈도가 늘어날 때의 효율 개선을 기대하며, 기존 방식의 불편을 예상해 이후 전환으로 정했다. 시점은 불편이 커질 때로 표현한다. 단순히 전환 여부를 나중에 검토하는 후보로 바꾸지 않는다. 구체 대상·이관·검증 방법은 후속 설계에서 정한다. |

확인 범위: SQL 정의·제품 원천·상세 논의와 사용자 선택을 대조했다. 합의와 문서 반영의 확인이며, 실제 SQL 실행·조회 성능·전환 효과를 검증한 결과는 아니다.

| `item_leaf_materials` | 해당 기능을 만들 때 실제 실험을 여러 차례 거쳐 판단한다. 지금은 합산표를 채택하거나 생략하는 어느 쪽도 확정하지 않는다. 조합법으로 계산하는 방식과 합계를 저장하는 방식을 실제 입력으로 비교하고, 목표 수량·중간 생산 수량·잔여·정정 시 갱신과 반복 조회의 부담을 확인해 결정한다. 구체 실험 입력·횟수·환경과 판정은 해당 기능의 구현 계획·기록에서 정한다. 현재 실험 결과는 없다. |

사용자 선택과 제품 원천·Task의 진행 위치를 자체 대조했다. 확인 범위는 문서 반영이며 캐시 동기화나 재료 계산의 구현·실험 결과를 포함하지 않는다.

### 세 번째 묶음 — 아이템 스킬의 버전과 동시 참조: 합의

- 확인한 의미: 제공 SQL의 `special_stat`은 기존 논의의 아이템 스킬이다. `item_special_stat`과 그 이력은 아이템과 스킬의 연결을 나타낸다. 이 확인만으로 테이블 이름·최종 키·구조를 확정하지 않는다.
- 공통점: 한 아이템에 여러 스킬을 연결하고 연결별 JSON으로 차이를 표현하는 방향은 SQL과 기존 합의가 맞는다. 기존 합의의 수식 정의 별도 관리·JSON 참조와 P1의 저장·텍스트 표시 범위는 유지하며, 실행 문법·계산 구현을 지금 확정하지 않는다.

| 쟁점 | SQL의 구성과 기존 합의 | 결정과 남은 검토 |
|---|---|---|
| 스킬 버전의 단위 | SQL은 이름 이력과 설명·수식 이력을 나눈다. 기존 합의는 스킬 대상에 속한 버전에 내부 이름·텍스트를 함께 둔다. SQL만으로 두 이력을 어떤 단위로 갱신할지는 알 수 없다. | 사용자 선택에 따라 초기에는 이름·텍스트를 한 스킬 버전으로 함께 보존한다. 변경 없는 필드의 복사는 감수하며 수식 정의는 별도로 둔다. |
| 연결이 참조할 대상 | SQL의 `item_special_stat_version`은 `special_stat_id`와 게임 패치 `version_id`를 두며 특정 스킬 버전 행의 직접 참조는 없다. 기존 합의는 특정 스킬 버전과 게임 패치를 함께 참조한다. | 사용자 선택에 따라 스킬 대상과 특정 스킬 버전을 둘 다 직접 참조한다. 게임 패치 참조도 유지한다. 일치 검사 방식은 DB 설계 때 정한다. |

#### 스킬 대상·특정 스킬 버전 동시 참조

아이템과 스킬의 연결에 스킬 대상 참조와 특정 스킬 버전 참조를 함께 둔다. 대상 참조는 같은 스킬을 사용하는 아이템 검색·관계 탐색에 사용하고, 실제 표시·해석할 설명은 지정한 스킬 버전을 따른다. 게임 패치 참조는 이 둘과 별개의 기존 역할을 유지한다.

- 이점: 스킬 대상 기준의 관계 탐색에 버전 행을 거쳐 대상 식별값을 얻는 과정을 줄일 수 있고, 사용할 설명 버전도 명시한다. 조회 성능 향상을 측정한 결론은 아니다.
- 중복 조건: 지정한 스킬 버전이 속한 대상과 연결의 스킬 대상이 같아야 한다. 두 참조를 각각 존재 여부만 확인하면 다른 스킬의 버전을 잘못 연결할 수 있다. 두 값을 한 쌍으로 검사하는 DB 제약이나 등록·정정 시 검증 등 구체 강제 방식은 DB·키 설계 때 정한다.
- 두 참조를 함께 저장해도 공통 스킬 변경이 연결의 지정 버전을 자동 교체하지는 않는다. 대상별 최신 버전 조회와 지정 버전 표시는 구별한다.

동시 참조와 일치 조건은 합의했으며 구체 필드·제약·일치 검사 방식은 DB 설계 때 정한다. 사용자 선택을 제품 원천과 상세 논의에 반영해 대조했다. 확인 범위는 문서 반영이며 실제 실행·성능 비교는 수행하지 않았다.

사용자 선택을 제품 분류 요구·Phase 등록 범위와 상세 논의에 반영해 대조했다. 문서 반영의 확인이며 SQL 실행이나 캐릭터·무기 스킬 기능 구현은 수행하지 않았다.

### 여섯 번째 묶음 — 검색·삭제 플래그와 노출 규칙: 합의

| SQL의 항목 | 확인한 의미와 후속 검토 |
|---|---|
| `item.searchable` | 사용자는 일반 아이템 조합 외에 캐릭터 스킬 등과 관련된 조합법이 있으며, 이를 표시하기 위해 임시 아이템을 추가한다고 설명했다. 해당 임시 아이템을 검색에서 제외하는 용도다. 관계를 통한 조합 표시와 검색 목록의 노출은 구별한다. |
| `item.is_deleted` | 게임에서 삭제된 상태임을 사용자가 확인했다. 서비스 기록의 삭제·무효화가 아니다. 삭제 적용 패치와 삭제 전 존재 상태를 보존·조회할 구체 방식은 DB 설계 때 정한다. |

기존 요구는 현재 없는 아이템을 검색 목록 아래 별도 구역으로 제공하고 과거 정보·변경 이력을 보존하는 것이다. 사용자 설명을 제품 문서에 반영하고 기존 요구와 대조했다. SQL 원본 수정·DB 구현은 수행하지 않았다.

#### 합의한 노출 규칙

| 검색 가능 | 게임 내 상태 | 검색·표시 처리 |
|---|---|---|
| 가능 | 존재 | 현재 아이템 검색 목록에 표시 |
| 가능 | 삭제 | 과거 아이템 구역에 표시하고 과거 정보·이력으로 연결 |
| 제외 | 어느 상태든 | 일반 검색과 과거 아이템 검색 구역에서 제외하되 필요한 조합 관계의 표시는 유지 |

사용자가 위 노출 규칙을 선택했고 제품 원천에 반영했다. `searchable`은 화면 검색 노출을 위한 구분이며, 이 값만으로 루트 계산의 수집·제작 대상을 판정하지 않는다. 임시 아이템의 루트 계산 취급은 해당 기능을 만들 때 결정한다. 임시 아이템의 구체 구조·P1 적용 범위는 미정이다. 임시 노드를 표현하는 방식이 일반 아이템의 고정 1+1 소비량과 맞는지는 필요한 기능 설계 때 확인하며, 캐릭터 스킬 사용을 일반 재료 수집·제작으로 자동 간주하지 않는다. 이 설명으로 캐릭터 기능을 P1에 추가하지 않는다.

| 항목 | SQL과 기존 합의의 비교 | 결정과 후속 확인 |
|---|---|---|
| 시즌·버전 정보 | SQL은 시즌명·버전명·시각·정렬값을 둔다. 기존 합의는 시즌 번호·표시 이름·시즌명·시작/종료일, 버전 메이저/마이너 번호와 정렬식을 구별한다. | 이미 합의한 정보와 정렬식을 재승인받지 않는다. SQL의 누락된 항목과 구체 키·제약은 DB 설계에 연결한다. |
| 버전 이름 | SQL에는 `version_name`이 있고 사용자가 별도 버전 이름이 있음을 확인했다. 번호로 해석하는 표기·정렬 규칙과 이 이름의 보존은 별개다. | 버전 이름을 별도 정보로 유지한다. 번호에서 생성한 문자열로 대체하는 제안은 채택하지 않는다. 시즌 표시 이름과 고유 시즌명의 기존 구분은 유지하며 이번 응답으로 그 생성·저장 방식을 새로 정하지 않는다. |
| 패치 적용 시각과 현재 판정 | SQL은 버전의 `created_at`을 패치 반영 시각으로 설명하고 서버 시각과 비교해 현재/예정을 판정하는 방향이다. | 사용자 선택에 따라 게임의 현재/예정은 패치 적용 시각으로 판정한다. 서비스 공개·적용은 별개로 다루며 구체 방식과 자료 미준비 시 동작은 해당 기능의 후속 설계에서 정한다. |

사용자 확인·선택을 공통 버전 요구와 아이템 화면별 버전 선택의 미정에 반영해 대조했다. SQL 실행·날짜 자료 조사·자동 전환 검증은 수행하지 않았다.

### 여덟 번째 묶음 — 원문·변경 이력의 역할과 정정 설계 이월: 합의

| SQL의 항목 | 합의한 역할과 후속 확인 |
|---|---|
| `patch_note.raw_text` | 패치노트 전체 원문을 보관한다. 역할을 합의한 것이며 P1부터 이 테이블에 모두 입력할지는 아직 정하지 않았다. |
| `patch_note_fragment` | 사용자가 대상별 원문 발췌용임을 확인했다. 서비스용 요약과 구별한다. |
| `change_log` | 사용자가 구조화한 게임 변경 내용을 담는 용도임을 확인했다. 실제 상태는 아이템 버전에서 읽고, 이 로그가 상태 저장을 대체한다고 간주하지 않는다. |

기존 요구는 실제 게임 변경과 입력 오류 정정을 구별하는 것이다. 예를 들어 같은 패치의 공격력 10을 100으로 잘못 입력했다가 10으로 고치는 것은 새 게임 패치의 너프로 기록하지 않는다. P1 최소 지원은 [이후 합의한 보존·정정 범위](<../../phase.md#preservation-scope>)를 따르며 정정 사실의 보존·원문 연결·관련 캐시 갱신의 구체 방식은 후속 설계에서 정한다.

사용자가 세 역할을 확인했고 입력 오류 정정의 구체 기록 방식은 후속 설계 때 정하도록 선택했다. 역할 구분을 공통 데이터 요구에 반영해 대조했다. SQL은 `change_log`와 원문 발췌의 직접 연결이나 변경 전후 값·정정 구분을 명시하지 않으므로 구체 링크·필드 채택을 이번 역할 구분만으로 확정하지 않는다. 미정의 담당·시점은 [최종 인계 목록](<task-001-discussion-details.md#handoff-decisions>)에 연결했으며 SQL 실행·실제 자료 처리는 수행하지 않았다.

### 수식 논의는 딜량 계산기 작업으로 이월

사용자 지시로 수식의 역할·저장·버전·로컬 수정 등을 지금 논의하지 않는다. [딜량 계산기 작업](<../../../../../docs/details/product/딜량 계산기.md#pending>) 때 다시 다루며 그 전의 P1 등록·표시·범위 결정의 선행 조건으로 삼지 않는다. SQL 원본은 보존하고 이번 재점검에서 수식 설계를 채택하거나 배제하지 않는다.

## 제공받은 미완성 SQL의 활용과 제작 관계 결정

사용자가 이전에 작성하다 중단한 SQL을 제공하며 참고해서 적절히 진행하도록 설계 판단을 맡겼다. 기존 Task의 범위 안에서 제작 관계의 P1 범위를 정하고 후속 데이터 설계의 입력으로 정리한다. SQL 전체의 채택, DB 기술 선정이나 실제 생성·자료 작업 재개로 확대하지 않는다.

- 제공 원본 보관: [사용자 제공 미완성 SQL](<task-001-user-schema.sql>). 2026-11-09 채팅에 첨부된 `붙여넣은 텍스트.txt`의 `CREATE TABLE` 및 제약 정의를 내용 변경 없이 보관했다. 사용자가 이전에 작성하다 중단한 설계 참고 자료이며, 현행 확정 스키마나 실제 게임 수치 자료가 아니다. 아래 대조·해석은 원본과 구별한다.
- 제작 관계 선택: `item_recipe_version`의 두 재료 참조와 `create_count`, `item_leaf_materials`의 최하위 재료·합산 수량 구상을 활용한다. P1의 제공 범위는 [Phase 본문](<../../phase.md#crafting-scope>)에 요약하고, 수량·누락 처리와 확인할 사례는 [제작 관계 상세](<task-001-discussion-details.md#crafting-details>)에서 관리한다. 이는 사용자 위임에 따른 설계 선택이며 SQL만으로 화면 동작이 이미 정의돼 있었다고 판단하지 않는다.

## 현행 요구와 대조한 참고·조정 사항

| 제공안의 요소 | 활용·조정 방향과 후속 담당 |
|---|---|
| `item_type.parent_id`, `item_rank`, `stat_type` | 계층 종류·별도 등급·능력치 종류의 구상은 활용한다. 종류의 이름·상하위 관계 이력과 동일 아이템 버전의 같은 능력치 중복 금지는 보완해야 한다. 실제 키·유일 제약은 후속 데이터 설계에서 정한다. |
| `item`와 이름·이미지·능력치·기타 정보별 `*_version` | 제공안은 현재값과 정보별 이력을 함께 둔다. 현행 선택인 아이템 중심 버전 구성으로 조정하고 동일 패치의 정보를 일치시킨다. 독립 관리 전환은 기존 후속 조건을 유지한다. |
| `item.stat_json`과 `item_stat` | 같은 능력치를 두 곳에서 각각 수정하는 원천으로 두지 않는다. 검색·표시·계산이 같은 값을 사용하도록 원천과 가공 표현을 후속 데이터 설계에서 구분한다. JSON 컬럼 채택이나 자료형·소수 정밀도를 이번에 확정하지 않는다. |
| `item_recipe_version`, `item_leaf_materials` | 원본 조합 관계를 기준으로 필요량을 산출한다. 최하위 재료 합산을 저장한다면 재생성할 수 있는 가공 결과로 취급하고 버전·조합법·생산 수량의 변경이나 정정 때 갱신한다. 테이블 채택·갱신 방식과 중간 생산물 잔여 활용은 후속 계산 설계에서 다룬다. |
| `special_stat`, `item_special_stat` 및 이력 | 아이템별 연결과 JSON의 구상은 스킬 요구에 참고한다. 기존 명칭만으로 아이템 스킬과 같은 개념이라고 단정하지 않는다. 특정 스킬 버전과 게임 패치의 동시 참조, 연결별 JSON·별도 수식 참조는 현행 요구에 맞춰 보완한다. |
| `inventory_limit`, `create_count`, `delivery_acquire_count` | 최대 중첩 수량·제작 결과 수량·현재 공통 획득/배달당 수량의 구상은 활용한다. 제작 수량과 획득 수량은 구별하고 고정 1+1 조합의 재료별 소비량 필드는 추가하지 않는다. |
| `item_region_spawn`와 지역·연결 이력 | 획득 가능한 지역 연결에 참고한다. 채집·사냥·상자 획득의 구분과 후속 사냥 대상 연결은 추가 설계가 필요하다. 출현 수량은 제공받으면 원자료로 보존하되 루트 계산의 수량 제한에는 사용하지 않는다. 지도 좌표·이동 연결·하이퍼루프·키오스크를 P1 필수 기능으로 추가하지 않는다. |
| `season`, `version`, `region` | 시즌 번호·표시 이름/시즌명·시작/종료일, 버전 메이저/마이너 번호·확정 정렬식, 지역 정렬값을 현행 요구에 맞춰 보완한다. `created_at`의 주석만으로 최신 공개 버전 판정 규칙을 확정하지 않는다. |
| `searchable`, `is_deleted`, `change_log`, `patch_note` | 과거 아이템 조회·과거 상태와 원자료 보존의 참고로만 사용한다. 검색 제외·삭제 플래그로 과거 이력을 없애지 않는다. 패치 변경과 입력 오류 정정, 원문과 구조화 결과를 구별하는 방식은 후속 보존 설계로 연결한다. |
| `system_formula`와 캐릭터·특성·무기 스킬 | 후속 단계의 참고다. 수식의 현재값만 저장한다는 주석이나 IndexedDB 구상을 채택하지 않는다. 과거 재현·수식 버전 보존의 판단을 후속으로 유지하며 P1의 실제 수식 계산이나 캐릭터·특성 구현을 추가하지 않는다. |

실행 가능한 최종 DDL로 쓰기 전에는 조합의 양쪽 재료 누락·순환 참조, 버전·연결의 유일성, 필수 관계의 참조 제약과 갱신·삭제 정책을 후속 데이터 설계에서 확인해야 한다. 이번에는 제공안의 내용을 현행 요구와 대조했으며 SQL 실행·DB 연결·기술 선택·게임 수치 검증은 수행하지 않았다. GitHub 게시물도 갱신하지 않았다.

자체 검수: 제공 SQL과 아이템·루트·변경 관리 요구를 대조해 참고 가능한 요소와 현재 합의에 맞춰 보완할 요소를 구별했다. 제작 관계의 Phase 범위와 Task·Issue·현황의 다음 행동, 새 참조 표식 및 변경 범위의 공백 검사를 확인했다. 기존 미커밋 변경은 유지했다. 검수 결과는 설계·기록 반영에 한하며 SQL 실행 가능성이나 제품 기능의 완료를 판정하지 않는다.

원본 보관 보완: 처음에는 채팅 첨부 경로만 남겼으나 사용자 지적에 따라 위 첨부로 보관하고 참조를 교체했다. 제공 파일과 보관 파일의 SHA-256 일치를 확인했다. Git의 줄바꿈 자동 변환이 이 원문을 바꾸지 않도록 해당 첨부에만 `.gitattributes`의 `-text`를 적용했고, 커밋 후보의 바이트도 제공 파일과 일치했다. 원문 끝의 빈 줄은 보존하며 편집 문서의 공백 검사와 구별한다. 이번 수정은 원본 보관·참조에 한하며 Phase의 범위나 설계 선택은 변경하지 않았다.
