# Task 15-001 — 등록 대상·지원 기능·완료 기준 정하기

<a id="summary"></a>
## 현재 요약

- GitHub sub-issue: [Mi-no-Kim/LumiaWiki #21](https://github.com/Mi-no-Kim/LumiaWiki/issues/21)
- 상태: 진행 중
- 현재 진행 위치: 등록 정보의 주요 방향과 검색·상세 범위를 합의했고, 제공받은 미완성 SQL을 참고해 사용자 위임으로 제작 관계의 P1 범위를 구체화했다. SQL의 참고·조정 사항을 아래에 정리했으며 실제 DB 구조 확정·실행은 수행하지 않았다.
- 다음 행동: 기본 루트와 보존·정정·완료 기준을 구체화한다. 실제 테이블·키·제약과 가공 데이터 갱신 방식은 후속 구현 준비에 연결한다.

## 목적과 허용 범위 및 완료 조건

- 부모 Issue: [Issue #15](<issue.md#goal>)
- 목적: Phase 001에서 무엇을 등록·저장·조회하고 어떤 기능을 사용할 수 있어야 하는지 확정한다.
- 입력: [Phase 계획](<../phase.md#goal>), [아이템 정보 요구](<../../../../docs/details/product/아이템 탐색과 상세.md#item-information>), [루트 요구](<../../../../docs/details/product/루트 계산기.md#current>), [데이터 요구](<../../../../docs/details/product/게임 데이터 변경 관리.md#current>).
- 결과 반영: 합의한 P1 포함·후속 범위와 수용 조건은 Phase 본문에 요약한다. 정보별 규칙은 담당 제품 문서를 참조하고, 판단의 조건·이유·미정과 세부 설계·확인 사례는 이 Task에서 관리한다.

### 결정할 범위

| 항목 | 결정할 내용 |
|---|---|
| 등록 대상 | 시즌·버전·아이템과 능력치 종류·스킬 설명·조합법·지역·배달 등 어떤 정보를 P1에서 다룰지 |
| 등록 정보 | 대상별 의미·관계·필수·선택·후속 정보와 저장·조회 범위. 시즌·버전의 정렬 규칙과 시즌 1·v1.0.0 초기 등록·자료 연결 조건, 아이템 이름·분류·능력치, 재료와 수량, 획득 지역 등을 포함해 판단 |
| 검색·상세 | 지원할 검색 조건과 확인할 정보, P1에서 제공할 동작 |
| 제작 관계 | 하위 재료·상위 제작 아이템을 확인할 범위와 필요한 수량 표현 |
| 기본 루트 | 제작 목표 지정 방식, 지원 조건, 필수 결과 정보와 후속으로 남길 옵션 |
| 보존 | 원자료 연결, v1.0.0 기준 정보 보존과 입력 오류 정정에 필요한 최소 요구 |

시즌·버전의 정의와 구현은 Phase 001에 포함한다. 이 Task는 필요한 결과와 구현 범위를 정하며, DB 종류·접속 방식·환경 설정은 [Task 003](<task-003.md#goal>)에서 선택한다. 실제 자료 조사·확보·처리·등록과 기능 구현은 후속 P1 과제의 범위다.

### 완료 조건

- 등록 대상·필요 정보·관계·저장·조회 범위가 정리되어 있다.
- 시즌·버전의 정의·관계·정렬 규칙과 시즌 1·v1.0.0 초기 등록·자료 연결 요구가 포함되어 있다.
- 기능별 P1 포함 범위와 후속 범위가 합의되어 있고, “기본”·“최소”라는 표현에 구체적인 지원 동작이 연결되어 있다.
- Phase 수용 조건이 확인 가능한 결과로 작성되어 Phase 본문에 반영되어 있다.
- 남은 미정에는 필요한 입력과 결정 시점·담당 기능 묶음이 연결되어 있다. 실제 자료의 값이 없다는 이유만으로 알려진 요구의 범위 결정을 미루지 않는다.
- 합의된 제품 요구와 단계 범위가 일치하고, 제품 요구를 바꾸는 선택은 담당 제품 문서에 합의 후 반영되어 있다.

예정 검증은 제품 요구·Phase 본문·범위 목록을 대조해 시즌·버전과 관련 정보의 누락, 모호한 완료 조건, 기술 선택의 혼입이 없는지 확인하는 것이다. 실제 기능이 작동한다고 판정하는 단계는 아니다.

## 등록 정보 논의

- 현재 전제: P1에 시즌·버전 정의와 시즌 1·v1.0.0 초기 등록을 포함한다.
- 시즌·버전·지역의 합의한 규칙은 [공통 데이터 요구](<../../../../docs/details/product/게임 데이터 변경 관리.md#season-information>)에, 능력치 종류 구분·중복 제한·백분율 값의 표현과 획득 방법·단일 조합법은 [아이템 요구](<../../../../docs/details/product/아이템 탐색과 상세.md#stat-information>)에 반영했다. P1 포함 범위와 스킬의 텍스트 취급 범위는 [Phase 본문](<../phase.md#agreed-data-scope>)에 반영했다.
- 자료는 사용자가 나중에 링크를 제공하고 원자료·변환 결과와 근거를 담당 Issue·Task에 보관한다. 단계의 제공·보류 조건은 [자료 준비 계획](<../phase.md#input-workflow>)을, 기록·첨부 위치는 [공통 보관 기준](<../../../../docs/작업 기록 체계.md#paths>)을 따른다. 서비스 DB의 출처 연결 구조는 이 결정만으로 확정하지 않는다.
- 사용자 요청에 따라 이후에는 관련 항목을 여러 묶음씩 제시한다. 실제 게임 자료 조사·확보·처리의 기존 보류 조건은 유지한다.
- 기존 Task의 범위 안에서 진행하며 새 작업 단위나 별도 목적의 커밋으로 분리하지 않는다.

### 등록 정보안과 남은 결정

아래는 기존 제품 요구를 바탕으로 P1의 구체 범위를 논의하기 위한 안이다. 최종 필드 목록이나 필수 여부를 확정한 것이 아니다.

| 묶음 | 등록 정보안 |
|---|---|
| 공통 식별·날짜 | 대상 연결용 내부 식별값과 사용자 지정 숫자 규칙을 유지하고 별도 코드 필드는 두지 않음. 시즌 시작일·종료일과 버전별 패치 적용 일시는 포함 |
| 버전 | 현재는 아이템 중심 관리. 변경된 패치에만 새 정보를 등록하고 다음 변경 전까지 사용. 정보 입력·패치 이력 축적 후 독립 관리로 전환할 계획. 메이저·마이너 번호·정렬식·표시 규칙은 합의했으며 별도 적용 순서 필드는 두지 않음 |
| 아이템 기본 정보·분류 | 이름·종류·등급·장비 부위·이미지는 P1에 포함. 종류는 상하위 계층을 두고 목록은 입력하며 정함. 장비 아래 무기, 그 아래 무기 종류. 종류의 이름·상하위 관계는 변경 패치에 새 버전을 등록해 과거 구조 보존. 등급은 별도 정보로 이름·정렬 순서를 두고 목록은 입력하며 결정하고 이름·순서는 고정 |
| 능력치 | 이름의 ` (%)` 접미사로 백분율 종류를 구별하고 아이템별 같은 종류의 중복은 금지. 백분율 값은 5%를 5로 저장 |
| 아이템 스킬 | 한 아이템에 여러 스킬을 연결할 수 있음. 스킬 버전에는 대상·내부 이름·텍스트를 두고 JSON은 아이템스킬–아이템–게임 패치 버전 연결에 둠. P1은 저장과 텍스트 표시까지. JSON의 수식 참조·계수 저장 방향을 유지하며 실제 수식 계산·외부 조건 처리는 후속 |
| 제작·수량 | 한 아이템의 대체 조합법은 없음. 제작 1회에 두 재료를 각각 1개씩 소비하며 별도 필요 수량 필드는 두지 않음. 제작 결과 수량은 획득 수량과 별도 저장. 최대 중첩 수량을 포함. 개수 수량은 정수이며 허용 범위는 후속 |
| 지역·획득 | 지역 정렬용 숫자는 시작값·증가값 모두 10으로 합의. 획득 방법은 채집·사냥·획득(상자 획득)으로 구분하고 같은 아이템에 여러 방법을 연결할 수 있음. 구체적인 지역 순서·이름과 방법별 세부 대상·지역 연결 방식은 미정 |
| 배달 | 가능 여부·비용을 저장하고 현재 배달당 수량은 획득 수량과 공통 저장. 실제 차이가 발생하면 별도 항목으로 분리 |
| 출처·보존 | 나중에 제공받을 링크와 변환 결과는 담당 작업 기록·필요 첨부에 함께 보관. 서비스 DB의 출처 연결 구조는 미정 |

후속 설계·자료 확인으로 이어갈 항목은 다음과 같다.

- 메이저·마이너 번호의 허용 범위와 구체적인 지역 순서.
- 획득 방법별 세부 대상·조건과 지역 연결 방식은 명칭·구조의 후속 설계에 연결.
- 아이템 중심 버전의 구체적인 연결·키·재사용 방식과 향후 독립 관리 전환 방법. 스킬 실행 문법·함수의 세부는 기존 후속 범위를 유지.

<a id="version-strategy"></a>
### 현재 버전 관리·수량·분류와 전환 계획

확정한 규칙은 제품 원천을 따른다. 현재 선택 이유와 남은 결정은 다음과 같다.

- 현재는 아이템 중심 방식으로 시작한다. 아이템 귀속 정보에 변경이 생기면 새 아이템 버전을 기준으로 당시 구성을 보존한다. 특정 스킬 버전·게임 패치 직접 참조와 스킬 자체의 대상·버전 구조는 유지한다. 테이블 분리와 변경하지 않은 정보의 재사용 방식은 후속 설계에서 정한다.
- 정보를 모두 입력하고 패치 이력이 쌓인 뒤 정보별 독립 관리로 전환할 계획이다. 전환 대상·구체 시점·이관 및 검증 방법은 그때 실제 자료와 사용을 근거로 정한다. Task 005에서 이 조건을 후속 과제에 연결하며, 전환 전후에 과거 정보와 참조 정합성을 보존한다. 현재의 자료 입력·패치 축적을 진행하기 전에 독립 관리 구조를 완성하도록 요구하지 않는다.
- 최대 수량은 인벤토리 한 칸의 최대 중첩 개수로 확인했고 등록 정보에 포함한다. 저장 위치의 세부는 후속 설계에서 정한다.
- 고정 1+1 조합은 재료별 소비량을 1개로 두며 별도 필요 수량 필드는 생략한다. 목표 제작 개수에 따른 총 필요량은 계산할 값으로 구별한다.
- 종류 목록은 입력 때 정하고 계층은 지원한다. 종류의 이름·상하위 관계는 변경된 패치에 새 버전을 등록하고 다음 변경 전까지 사용해 과거 구조를 보존한다. 등급은 종류와 별도 정보로 이름·정렬 순서를 두고 목록은 입력하면서 정한다. 등급 자체의 이름·순서 변경은 없다는 전제다.

### 스킬의 조건문·함수와 JSON — 현재 방향과 미정

스킬 버전과 연결별 JSON의 소유·역할은 [제품 원천](<../../../../docs/details/product/게임 데이터 변경 관리.md#item-skills>)을 따른다. 같은 스킬의 표시 텍스트를 공유하면서 아이템·버전별 효과 차이를 JSON으로 표현하려는 요구다. 이전의 연결별 설명 저장 제안은 채택하지 않았다.

- 텍스트의 함수는 캐릭터 능력치 등을 받아 계산한 결과를 표시할 수 있고 조건문은 외부 정보도 참조한다. 실제 수식은 표시 텍스트와 별도로 둔다. JSON은 단순 치환값에 한정하지 않고 효과·수식을 구조화해 같은 스킬 안의 차이도 제어한다.
- 확정: 수식 정의는 별도로 두고 JSON에는 참조할 수식과 계수를 지정한다. 구체적인 참조 형식·계산 처리 연결과 수식 정의의 버전 보존은 미정이다.
- 확정: 연결의 버전은 게임 패치 버전이며 아이템은 특정 스킬 버전을 직접 참조하고 게임 패치 버전도 함께 참조한다. 변경 패치에만 새 정보를 등록해 다음 변경 전까지 사용한다. 현재 아이템 중심 방식에서의 구체적인 연결·키·테이블 구성은 후속 설계에서 정한다.
- 현재 표시 방향: 외부 정보가 없는 일반 아이템 상세는 우선 텍스트 형태로 보여준다. 조건별 문구·미제공 입력 처리, 내부 이름의 검색·표시 용도와 원문 보존은 후속 결정 사항이다.
- 문법·등록 함수·JSON 스키마와 검증 방식은 아직 선택하지 않았다. P1의 실행 범위는 아래 합의를 따른다. 후속 표현 체계의 완성을 P1 저장·표시의 선행 조건으로 삼지 않는다.

### 제작 관계의 세부 조건과 예정 확인

Phase에 과도하게 적었던 다음 조건을 이 Task로 옮겼다. 제공 범위나 계산 의미를 삭제·변경한 것은 아니며, 후속 기능 설계의 입력으로 사용한다.

- 하위 조합법은 최하위 재료까지 재귀적으로 확인하고 연결된 재료의 상세로 이동한다. 직접 상위 제작 아이템 목록에서도 상세로 이동한다. 상위 관계의 여러 단계 동시 표시는 후속이다.
- 각 조합은 제작 1회에 재료 두 개를 각각 1개씩 소비하며 결과 수량을 표시한다. 같은 아이템이 두 재료 칸에 쓰이면 총 2개를 소비한다.
- 최하위 재료의 총 필요량은 반복 재료와 중간 재료의 생산 수량을 반영한다. 필요한 제작 횟수는 올림하고 남는 수량을 반영하며, 단순히 모든 경로의 개수만 더하지 않는다. 구체 알고리즘은 후속 기능 설계에서 정한다.
- 조회할 게임 패치의 유효한 조합법·재료 정보를 일치시킨다. 조합법이 없는 기본 재료와 조합법 미등록을 내부적으로 구별하고, 미등록을 필요 재료 0개로 계산하지 않는다. 화면의 미등록 값은 기존 합의대로 비워 둔다.
- 후속 구현에서 확인할 사례: 여러 단계 조합, 같은 재료의 반복, 여러 개를 생산하는 중간 재료와 잔여 수량, 직접 상위 목록·상세 이동, 버전별 관계와 미등록 상태. 화면 확인과 필요한 계산 결과 대조를 함께 수행한다. 현재 실제 실행 결과는 없다.

**원인과 기준 적용의 오류**

- 직접 원인은 이 Task의 `Phase 본문에 반영한다`는 문장을 상세 내용까지 옮기는 방식으로 적용한 것이다. [기록 체계](<../../../../docs/작업 기록 체계.md#ownership>)의 `자식 상세를 부모·현황에서 따로 관리`하지 않는다는 기준, [문서 기준](<../../../../docs/문서 관리 기준.md#product-and-plan>)의 제품 요구·Phase·Task 역할을 함께 적용하지 못했다. 현행 지침이 상세 복제를 요구한 것은 아니다.
- 대화에서 항목을 결정할 때마다 Phase에 항목과 확인 문장을 추가해 현재 결론을 한 번 더 누적했다. 단계 범위·수용 조건의 변경인지, 기존 범위 안의 상세화인지 구별하지 않았다. 수정 횟수 자체가 아닌 문서의 소유와 기록 수준이 문제다.
- 앞선 자체 검수에서는 사용자 요구의 내용 보존·참조·공백 확인에 치우쳤다. 검수 기준에 포함된 파일별 필요성·중복·소유 경계를 충분히 대조하지 못했으므로, 당시 자체 확인 문장을 이번 기록 품질의 통과 근거로 재사용하지 않는다.
- 이번에는 기존 기준을 적용해 문서를 정리한다. 공용 규칙·스킬·양식을 새로 바꾸지 않으며, 내용 이동을 제품 요구 변경이나 Task·Phase 완료로 처리하지 않는다.

**수정 범위와 검증**

Phase의 등록·검색·제작 범위를 요약하고 필드 규칙의 중복·반복 확인 문장·첨부 보관 절차의 재서술을 줄였다. 옮긴 계산·누락 조건은 위 세부 구역에 보존했다. 기존 참조 표식, 실제 자료 작업의 보류 조건, 과거 조사·계획 이력은 유지했다.

자체 확인 결과: 변경 전 내용과 제품·기록 기준을 대조해 등록 대상·검색·제작 범위와 후속 경계의 보존, 세부 조건의 이동, 부모·자식의 기록 역할을 확인했다. 두 변경 문서의 로컬 참조 39개의 파일·표식과 공백 검사를 통과했고, 보관 SQL은 채팅 첨부 원본과 해시가 일치했다. 확인 범위는 문서 정리와 원인 분석이며 제품 동작 검증은 수행하지 않았다. 기본 루트·보존·정정·최종 수용 조건은 기존 미완료로 유지하고, 커밋·GitHub 반영은 수행하지 않았다.

### 사용자 정정 요청에 따른 잘못된 기록의 처리

사용자가 잘못 작성한 Phase 기록의 삭제·정리를 명시적으로 요청한 범위에서 아래 정정을 수행했다. 이를 개선 초안에서 ‘기존 기록도 현재 필요성에 따라 삭제·요약한다’는 규칙으로 확대했던 것은 잘못이다. 후속 사용자 지적에 따라 그 일반화를 철회했다. 기존 기록은 보존하며, 앞으로 작성할 내용의 필요성 판단과 이미 잘못 작성한 내용의 정정을 구별한다.

| Phase의 항목 | 처리와 이유 |
|---|---|

독립 개선의 현재 판단·수정안·검증은 main 기준 로컬 브랜치 `codex/record-writing-isolation`의 `work/records/harness/record-writing-prevention/issue-draft.md`가 소유한다. 제품 브랜치에 그 상세를 복제하지 않는다. 기존 항목을 삭제·요약하는 일반 규칙과 Phase 002~007의 정리 실행 계획은 제거했다. 다른 Phase의 반복 문구는 작성 방식의 관찰 근거로만 사용하고 정정 권한을 확대하지 않는다. 이번 Phase 정정과 이미 보관한 원자료·조사 근거는 유지한다.

GitHub 등록은 자동 승인 검토가 공개 저장소에 내부 작업 기록·운영 문제와 경로를 포함한 구체 본문을 공개할 명시적 승인이 확인되지 않는다는 이유로 거부했다. 이후 저장소가 공개이며 현재 계정에 ADMIN 권한이 있음을 읽기 확인했다. 당시 우회 등록이나 재시도는 하지 않았다. 후속 독립 분리 요청에서 구체적인 두 이슈 본문의 공개 등록도 자동 승인 검토가 거부했고, 사용자에게 본문·목적지를 제시하자 공개하지 않고 로컬 초안으로 유지하도록 선택했다. 원격 이슈는 생성하지 않으며 Phase 정리와 로컬 계획·근거를 보존한다.

추가 정리 검증: 삭제한 구역으로 향하는 참조가 없는지 필요한 docs·harness·work 범위에서 확인했고, 변경한 세 기록의 로컬 참조 43개와 공백 검사를 통과했다. Task 004로 옮긴 조사 표는 변경 전 표와 내용이 일치하며 Task의 예정 상태와 자료 처리 보류를 유지했다. Phase의 나머지 내용은 단계의 목표·범위·착수 조건·수용 판단에 사용하는지 대조했다. 최종 제품 제출 후보 9개 파일은 별도 에이전트가 실제 인덱스로 재검수했고, 현재 결과의 상태 표현을 보완한 뒤 필수 결함이 없었다. 후보의 문서 참조 119개와 편집 문서 공백 검사, SQL의 원본 바이트 일치를 확인했다. 이 제품 기록 정정의 검증은 독립 개선의 기준 적용·운영 효과 판정과 구별하며, 해당 개선의 최신 결과는 별도 초안에서 관리한다.
