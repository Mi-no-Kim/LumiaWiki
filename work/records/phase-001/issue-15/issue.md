<a id="goal"></a>
## 문제와 목표 및 수용 조건

### 문제와 목표

Phase 001에는 단계 목표와 검토용 완료 조건이 있지만, 등록 정보·구조, 최소 화면·제작 관계·루트 범위와 구현 과제가 아직 정해지지 않았다. 이를 구체화하고 후속 Issue의 목표·수용 조건·의존 관계와 Task 윤곽을 정해 다음 과제를 준비할 수 있게 한다.

### 범위와 제약

- Phase 001의 최소 완성 범위, 후속으로 남길 기능과 수용 조건을 정한다.
- 사용 흐름·핵심 계산 규칙과 데이터·기술·자료 등록의 공통 전제를 과제 분해에 필요한 수준까지 정하고, 화면 디자인을 담당할 과제를 정한다.
- [화면 디자인 선행과 검증 기준](<../../../../docs/details/operations/검증과 완료.md#screen-first>)을 적용해 후속 Issue·Task에도 디자인 → 동작 구현 → 화면이 있는 상태의 검증 순서를 반영한다.
- 후속 Issue별 목표·범위·수용 조건·의존 관계와 실행 순서를 정한다.
- 각 Issue의 Task 윤곽과 선후 관계를 정한다. 상세 Task의 범위·완료 조건·실행·검증 계획은 해당 Issue를 준비할 때 구체화한다.
- 제품 요구를 바꾸는 선택은 기존 요구와 구별해 논의하고, 합의된 변경은 담당 제품 문서에 반영한다.
- 이번 Issue에서는 화면 목록·사용 흐름·디자인 담당 범위까지 정하고, 실제 화면 디자인은 각 기능 Issue에서 동작 구현보다 먼저 수행한다. 기능 동작 구현과 실제 게임 자료의 조사·확보·변환·DB 등록은 포함하지 않는다. 자료 작업은 [기존 보류 조건](<../phase.md#input-workflow>)을 유지한다.
- 각 Phase의 첫 Issue를 같은 방식으로 두자는 제안 중, 이번에는 Phase 001만 구체화한다.

### 이 Issue의 수용 조건

- Phase 001의 최소 완성 범위와 후속 범위가 합의되어 담당 Phase 본문에 반영되어 있다.
- Phase 수용 조건별 확인 대상과 방법이 정해져 있다.
- 과제 분해에 필요한 주요 설계와 선택 이유가 정리되어 있다.
- 화면 목록·사용 흐름·디자인 담당 범위와 후속 과제의 화면 디자인·동작 구현·화면 검증 선행 관계가 정리되어 있다.
- 후속 Issue의 목표·수용 조건·의존 관계와 실행 순서가 정해져 있다.
- Issue별 Task 윤곽과 선후 관계가 정리되고, 상세 실행·검증 계획을 구체화할 담당 Issue가 연결되어 있다.
- 남은 미정은 결정할 과제·시점·착수에 미치는 영향과 연결되어 있다.

## 해결 계획과 의존

### Task 분해 방향 — 제안

아래 5개를 이번 Issue의 Task 구성안으로 검토한다. 순서는 실행 순서 제안이며 아직 발급한 Task 번호가 아니다.

| 순서 | Task 구성안 | 결과·완료 조건 |
|---|---|---|
| 1 | Phase 001 최소 완성 범위·수용 조건 정하기 | 등록 자료·검색·상세·제작 관계·기본 루트·보존 기반의 포함/후속 범위와 단계 수용 조건을 합의해 Phase 본문에 반영한다. |
| 2 | 화면 목록·사용 흐름·디자인 범위 정하기 | 필요한 화면 목록과 핵심 입력·출력·이동 흐름, 각 기능 Issue에서 디자인할 범위를 정한다. 실제 화면 디자인은 담당 기능 Issue에서 동작 구현보다 먼저 수행한다. |
| 3 | 공통 전제·의존 관계 정리하기 | 데이터 관계·식별·버전 보존과 기술 구성 중 먼저 정할 공통 사항을 가려내고, 구체 DB·API·알고리즘 등 세부 설계를 담당할 후속 과제와 연결한다. |
| 4 | 자료 등록·검증 방향 정하기 | 필요한 자료와 확인·변환·교정·등록의 큰 순서, 확인용 페이지의 선행 관계, 화면을 통한 기능 검증과 내부 정합성 확인의 방향을 정한다. 실제 자료 처리는 보류를 유지한다. |
| 5 | 후속 Issue·Task 윤곽과 실행 순서 정하기 | 후속 Issue별 목표·범위·수용 조건·대상 화면·Task 윤곽·의존 관계와 실행 순서를 정하고, 다음 착수 Issue를 선택한다. |

1 → 2 → 3 → 4 → 5 순으로 진행하는 안이다. 뒤 단계에서 앞선 선택에 문제가 드러나면 영향을 받는 결정으로 돌아간다. 이번 Issue에서는 과제 분해에 필요한 설계를 정하고, 실제 자료에 따른 세부 설계·동작 구현은 담당 후속 과제로 연결한다.

구성을 합의한 뒤 이 Issue 바로 아래에 실제 Task 문서와 보유 목록을 갖춘다. 이번 Issue는 후속 Issue의 Task 윤곽까지 정하고, 모든 후속 Issue의 상세 Task는 각 Issue를 준비할 때 정한다.

### 의존과 예정 확인

- 현재 제품 요구와 Phase 계획으로 설계 논의를 진행한다.
- 실제 자료가 필요한 판단은 필요한 입력과 결정 시점을 명시하고, 자료 없이 확정한 것으로 처리하지 않는다.
- 합의할 범위를 제품 요구·다른 Phase의 경계와 대조한다.
- 후속 과제의 누락·중복·의존 관계와 다음 Issue의 착수 가능성을 확인한다.
- 로컬 Phase·Issue·Task가 각자의 범위와 판단을 소유하고, GitHub는 로컬 내용을 기준으로 반영한다.

## 미정·제안과 결정 시점

### 최소 완성 범위 — 미합의 제안

| 영역 | 제안 |
|---|---|
| 기준 자료 | 확정한 v1.0.0 아이템 전체와 제작·획득 관련 자료 등록 |
| 검색·상세 | 이름 부분 검색·장비 부위 필터, 기본 정보·능력치·스킬 설명과 획득·배달 보조 정보 |
| 제작 관계 | 하위 조합법과 수량의 재귀 표시, 바로 위 제작 아이템 목록과 이동 |
| 기본 루트 | 직접 지정한 전체·일부 장비의 지역 집합과 배달 계산. 필요·생산 수량, 공통·잔여 재료, 최초 보유 구성 반영 |
| 루트 조건·결과 | 최대 지역 수·배달 횟수 지정, 수집·배달 재료와 수량, 장비 기본 능력치 요약, 지역 수·배달 횟수 정렬과 결과 없음 안내 |
| 보존 기반 | 원자료 연결, 기준 버전 보존과 입력 오류 정정 방법 |

현재 목록은 논의를 이어가기 위한 제안이며 Phase의 확정 범위로 채택한 것이 아니다. 상세 필터·후보 장비 조합 탐색·캐릭터 예외 등 후속 범위와의 경계는 범위 논의에서 맞춘다. 버전별 최초 보유 구성 등 미제공 게임 사실은 자료를 확인한 뒤 정한다.

- 이번 Issue의 Task 구성: 최소 완성 범위 결정에 앞서 현재 논의에서 정한다.
- 최소 범위·수용 조건: Task 구성을 정한 뒤 첫 Task에서 결정한다.
- 데이터·기술·계산 규칙과 자료 등록·검증 방식: 위 설계 순서에 따라 필요한 선택을 구체화한다.
- 후속 Issue·Task 윤곽과 첫 착수 대상: 주요 설계·의존 관계를 정리한 뒤 결정한다.
