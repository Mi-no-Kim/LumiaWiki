<a id="goal"></a>
## 목표와 범위 및 수용 조건

아래는 합의한 단계 범위와 수용 조건이다. 기능별 상세 설계·검증 입력은 담당 과제에서 이 조건을 기준으로 구체화한다.

**공동 목표/기대 결과**

시즌 1·버전 1.0.0의 아이템 정보를 DB에 등록하고, 조회·제작 관계·기본 루트 계산을 통해 자료가 실제로 작동하는 상태를 만든다.

**P1 포함 범위**

아래 등록·검색·상세·제작 관계·기본 루트 계산과 보존·정정의 최소 지원을 포함한다. 담당 과제와 결정 시점을 정리한 [이월 목록](<issue-15/artifacts/task-001-discussion-details.md#handoff-decisions>)을 후속 설계에 사용한다.

<a id="agreed-data-scope"></a>
### 합의한 등록 범위

- 시즌·버전·지역과 시즌 1·v1.0.0의 아이템 기본 정보·분류·능력치·스킬·조합·획득·배달 정보를 등록한다. 정보 항목과 규칙은 [아이템 요구](<../../../docs/details/product/아이템 탐색과 상세.md#item-information>)와 [공통 데이터 요구](<../../../docs/details/product/게임 데이터 변경 관리.md#season-information>)를 따른다.
- 무기 종류는 초기부터 별도 대상으로 두고 아이템 종류 계층과 연결한다. 역할과 DB 설계로 넘긴 관계의 세부는 [분류 요구](<../../../docs/details/product/아이템 탐색과 상세.md#classification>)를 따르며, 캐릭터·무기 스킬 기능 자체를 P1에 추가하는 결정은 아니다.
- 아이템 중심 버전 관리로 기준 자료와 과거 상태를 보존한다. 독립 관리 전환 조건과 별도 사냥 대상의 후속 설계는 [담당 Task](<issue-15/task-001.md#version-strategy>)에서 연결한다.
- 아이템 스킬은 대상·버전·연결별 JSON의 저장과 설명 텍스트 표시까지 지원한다. 수식 계산과 외부 조건 처리는 후속 단계로 둔다.

<a id="agreed-search-detail-scope"></a>
### 합의한 검색·상세 범위

- 자료 입력 전에 이름 검색과 옵션·장비 부위 필터, 개별 상세 페이지를 마련한다. 상세에는 기본 정보·능력치·스킬 설명·획득·배달 정보를 모두 표시한다.
- 미등록 정보와 검색 결과 없음은 빈 상태로 둔다. 세부 일치 규칙·필터 구성과 화면 설계의 미정은 [담당 Task](<issue-15/task-001.md#search-detail-discussion>)에서 관리한다.
- P1의 개별 아이템 페이지는 v1.0.0 정보만 표시한다. 버전 선택기는 후속으로 두며 제품의 과거 버전 조회 요구와 기준 정보 보존은 유지한다.

<a id="crafting-scope"></a>
### 제작 관계의 P1 범위

- 하위 조합법을 최하위 재료까지 확인하고, 직접 상위 제작 아이템 목록과 재료·제작 아이템의 상세 이동을 제공한다. 제작 1회의 재료·결과 수량과 최하위 재료의 총 필요량을 확인할 수 있게 한다.
- 상위 관계의 여러 단계 동시 표시는 후속으로 둔다. 범위 선택의 근거, 생산 수량·반복 재료·미등록 자료의 처리와 확인 사례는 [담당 Task](<issue-15/task-001.md#crafting-details>)에서 관리한다.

<a id="basic-route-scope"></a>
### 합의한 기본 루트 범위

- 제작할 장비를 직접 지정하고 전체·일부 부위의 계산을 모두 지원한다. 결과는 방문 순서가 아닌 지역 집합으로 다룬다.
- 최대 방문 지역 수·최대 배달 횟수를 지정한다. 필요·생산 수량과 공통·잔여 재료, 버전별 최초 보유 구성을 반영한다.
- 지역 집합, 수집·배달할 재료와 수량, 배달 횟수, 장비 기본 능력치 요약을 제공한다. 지역 수·배달 횟수 기준 정렬과 결과 없음 안내를 지원한다.
- 후보 장비 조합 탐색·상세 스탯 조건·캐릭터별 고정 장비 예외는 후속으로 둔다. 최초 보유 구성의 실제 값은 자료 확인 때 정한다.
- 수량·계산 경계는 [루트 요구](<../../../docs/details/product/루트 계산기.md#constraints>), 합의 조건과 확인할 사례는 [담당 상세 논의](<issue-15/artifacts/task-001-discussion-details.md#basic-route-discussion>)를 따른다.

<a id="preservation-scope"></a>
### 합의한 보존·정정의 최소 지원

- 제공 원자료·변환 결과를 담당 기록과 첨부에 보관하고 출처·기준 버전을 식별할 수 있게 연결한다. v1.0.0 등록 정보를 보존하며 후속 변경에도 당시 상태를 유지한다.
- 입력 오류를 고쳐 검색·상세·제작 관계·루트의 관련 결과에 반영할 수 있게 한다. 구체 수정 수단과 정정 기록 방식은 후속 설계 때 정한다.
- 전용 정정 화면·변경 항목 선택 적용/되돌리기·자동 영향 추적은 후속으로 두며 P1의 선행 조건으로 삼지 않는다. 합의 조건은 [담당 상세 논의](<issue-15/artifacts/task-001-discussion-details.md#preservation-discussion>)를 따른다.

<a id="completion-criteria"></a>
### 합의한 최종 완료 조건

| 영역 | 확인할 결과 |
|---|---|
| 기준 자료 | 확정한 v1.0.0 등록 대상·정보·관계가 DB에 등록돼 있고 원자료·출처·기준 버전과 대응을 확인할 수 있다. |
| 검색·상세 | 화면에서 이름 검색·옵션/부위 필터와 상세를 조작해 등록값·관계, 합의한 빈 상태·검색 노출 규칙을 확인한다. |
| 제작 관계 | 하위 전체·직접 상위 관계와 상세 이동이 작동하고, 재료·생산 수량 및 최하위 재료 필요량이 원본 조합법과 일치한다. |
| 기본 루트 | 전체·일부 장비 지정과 지역/배달 한도에 따라 합의한 결과·정렬·결과 없음 처리가 작동하며 수량·잔여·최초 보유 구성과 배달 횟수가 입력 자료에 맞는다. |
| 보존·정정 | 기준 정보·원자료를 보존하고 입력 오류를 고친 뒤 관련 조회·계산 결과가 수정한 자료와 일치한다. 실제 게임 변경과 정정을 구별한다. |
| 검증·후속 경계 | 화면 조작과 필요한 내부 값 대조의 근거를 남기고, P1 필수 범위에 미해결·미확인이 없다. 후속 범위와 이월한 결정의 담당·시점이 연결돼 있다. |

실제 v1.0.0 자료로 정상 동작을 확인하며 빈 상태·입력 오류 등 필요한 변형 상황의 검증 입력은 실제 원자료와 구별한다. 사용자가 위 여섯 항목을 P1 완료 조건으로 확정했다. 현재는 범위·수용 조건의 합의이며 기능 구현·검증은 아직 수행하지 않았다.

<a id="plan"></a>
## 계획과 주요 의존

범위·수용 조건과 후속 실행 계획을 먼저 정하고, 실제 자료 등록과 기능 구현으로 이어간다. 자료 제공·검증 준비는 아래 착수 조건을 따른다.

Task 005에서 합의한 큰 순서는 실행 기반·DB 저장/조회 준비→자료 확인용 검색·기본 상세→실제 자료 등록·화면 대조→제작·루트 등 나머지 기능·화면 완성→통합 확인이다. DB 코드 개발과 실제 자료 등록·교정은 별도 Issue로 두며 일곱 Issue의 경계·Task 구성·수용 조건과 필요한 선행 결과는 [합의한 실행 계획](<issue-15/artifacts/task-005-issue-outline.md#issues>)을 따른다. 실제 자료 작업 보류는 유지한다.

<a id="tdd-readiness"></a>
### 첫 기능 구현 전 테스트·TDD 자동화 준비

- [Task 003](<issue-15/task-003.md#tdd-automation-handoff>)에서 TDD 규칙과 최소 hook 검사·예외·근거·비용 기준을 정한다.
- [Task 005](<issue-15/task-005.md#goal>)가 테스트 환경·최소 TDD hook 연결·실제 동작 검증을 [Issue #42 실행·개발·검증 기반](<issue-42/issue.md#foundation>)의 필수 범위·수용 조건으로 배정했다. 실제 hook 구현·검증은 등록한 [Task 42-002](<issue-42/task-002.md#summary>)(GitHub #51)가 맡는다. 현재는 예정이며 실제 구현·검증은 미수행이다.
- 계획 Issue #15의 종료 후 첫 기반 구축 과제 초반, 프로젝트 골격과 테스트 실행 명령을 마련한 직후 hook을 연결·검증한다. 이 결과는 해당 기반 과제의 필수 완료 조건이다.
- 첫 제품 기능의 동작 구현은 위 자동화 연결·검증이 완료된 뒤 시작한다. 미완료·미확인이면 기능 구현의 선행 조건이 충족되지 않은 것으로 처리한다.

현재는 배정·순서·완료 기준을 정한 상태이며 실제 hook 구현·동작 확인을 완료한 것은 아니다. 제품 기능의 화면 설계 선행·화면을 통한 검증 기준은 함께 유지한다.

<a id="input-workflow"></a>
### 자료 확보·임시 변환 계획

실제 자료는 사용자가 제공한다. 웹사이트·엑셀 등 자료와 해석 방법을 채팅으로 제공받고 AI가 변환을 도우며, 사용자가 지적한 오류를 함께 교정하는 임시 방식이다. 특정 자료 형식·전체 상태/변경 자료 중 하나나 입력 화면의 직접 타이핑으로 한정하지 않는다.

이 임시 작업을 서비스의 상시 업로드·관리 화면이나 영구 운영 절차로 확정하지 않는다. 변환 산출물 형식·검증 방법·서비스 DB 반영과 정식 운영으로의 전환은 미정이다. 실제 자료 확보·처리는 사용자 보류 요청이 유지되고 있으므로 재개 요청 뒤 제공 위치·출처·버전과 허용 범위를 확인한다. 실제 자료 없이도 범위·설계 논의는 진행할 수 있다.

<a id="input-readiness"></a>
### 자료 등록의 입력 준비

실제 자료의 제공 위치·출처·기준 버전과 포함 항목은 자료 작업 재개 시 확인한다. 기존 조사 범위와 부족 입력은 [자료 계획 Task의 조사 근거](<issue-15/task-004.md#inherited-input-survey>)에서 확인한다.

<a id="entry-decisions"></a>
### Phase 진입 또는 Issue에서 정할 사항

- 합의한 등록 범위와 실제 제공 자료의 대응, 필요한 테이블·관계·식별 방식.
- 검색·상세·제작 관계의 P1 범위는 위 본문을 따른다. 화면·조작 방식은 [Task 002](<issue-15/task-002.md#goal>)와 후속 기능 설계에서 정한다.
- 기본 루트의 화면·입력 조작·결과 표현 상세와 계산 알고리즘. 지원 범위는 위 합의한 기본 루트 범위를 따른다.
- 자료 정정·검증 방법과 버전 연결의 구체 구현.
