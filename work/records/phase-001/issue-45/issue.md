<a id="acceptance"></a>

### 합의한 수용 조건

- P1 기준 자료의 등록 대상·필수 정보·관계와 출처/버전의 대응을 확인한다. 부족·충돌은 영향 범위를 구분하고 임의 값으로 메우지 않는다. 필수 자료의 미해결을 남긴 채 전체 자료 등록 완료로 판정하지 않는다.
- Java/Spring 교정으로 관련 테이블·원본/캐시 및 검색·기본 상세가 수정한 자료와 일치한다. 입력 오류 정정을 새 게임 패치로 꾸미지 않고 원자료·정정 대상/전후 값·근거를 보존한다. 실패 복구도 확인한다.
- 검증 B에 따라 기계적으로 대조 가능한 전체 등록 정보·관계를 내부 검사하고 자료 내용은 기존 화면에서 함께 확인한다. 실제 자료와 통제한 검증 입력을 구분한다.

입력 확인 Task는 보류 해제 뒤 DB/화면 개발에 필요한 자료를 먼저 전달할 수 있다. 실제 등록은 확인용 검색·기본 상세 준비 뒤 수행한다. 등록과 화면 대조·교정은 테이블별 진행에 맞춰 이어가며 아이템별 작은 묶음 절차를 요구하지 않는다.

이 Issue의 수용 범위는 등록 자료·교정 처리·기본 화면에서의 자료 확인까지로 합의했다. 이후 제작·루트 계산의 정합성과 정정 반영은 각 기능 Issue에서 확인하고 전체 연결은 통합 확인 Issue가 맡는다. 자료 Issue의 완료가 아직 구현하지 않은 제작·루트 기능의 완료를 기다리도록 만들지 않는다.

<a id="ownership"></a>

## 합의한 책임 배정과 선행 결과의 보완

DB Issue는 공통 저장·기본 수정·참조/캐시 일치를, 자료 Issue는 테이블별 등록과 관련 변경을 함께 처리하는 Java/Spring 교정 실행·실패 복구 및 실제 자료 수용을 주로 맡는 것으로 합의했다.

실제 자료를 다루며 앞서 구현한 DB 구조·저장/조회·API·기본 화면을 보완하는 재작업은 감수한다. 필요한 보완은 자료 Issue의 Task 범위에 포함해 수행하고 관련 값·참조·캐시·화면과 기존 동작을 재확인한다. Issue별 주담당을 나눴다는 이유로 이전 코드의 수정을 막지 않으며, 실제 자료에 맞게 필요한 수정 내용·근거·영향과 결과를 담당 기록에 연결한다.

상세 배정은 [기존 요구 목록](../issue-15/artifacts/task-005-handoff-requirements.md)과 [Task 004 인계](../issue-15/artifacts/task-004-data-plan.md#handoff)를 대조한다. 수치·정밀도/API 표현·이미지 Git 취급·미확인 값 허용 등 실제 입력 의존 미정은 필요한 담당 Task에서 구현/등록 전에 정한다.

<a id="pending"></a>

## Task 선후 관계와 남은 결정

- 입력 확인→등록/교정 수단 준비→실제 등록·화면 대조/교정의 큰 순서다. 등록과 화면 대조·교정은 테이블별 진행에 맞춰 이어가며 아이템별 작은 묶음 반복을 강제하지 않는다.
- 등록용 형식·이미지 Git 취급/참조 보존·반영 단위·Java/Spring 교정 실행 경로·정정 기록·실패 복구는 실제 적용 전에 결정한다.
- 기본 화면에서의 자료 확인까지를 이 Issue가 수용하고 제작·루트 계산 정합성은 각 기능 Issue, 전체 연결은 통합 확인 Issue가 맡는다.
