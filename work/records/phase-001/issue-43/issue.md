### Task 구성 윤곽

Task는 아직 생성하지 않았다. 아래 표는 합의한 구성 윤곽이며 실제 Task 등록·파일 작성과 상세 실행/검증 계획은 이 Issue를 준비할 때 진행한다.

| Task 제목 윤곽 | 만들 결과·다음 작업과의 관계 |
|---|---|
| 공통 식별·시즌/패치·지역·분류 | 테이블·키·제약과 Java 매핑, 시즌/버전 정렬·종류 계층·등급·별도 무기 종류의 저장 관계 |
| 아이템·능력치·스킬 저장/조회 | 기본 정보·능력치 원본/표시 캐시·스킬 대상/버전·연결 JSON의 저장·조회. 수치·JSON·시각·ID 전달은 기존 기준 적용 |
| 제작·획득·배달 관계 저장/조회 | 두 재료·생산 수량·기본 재료/자료 누락 구별, 지역/방법·사냥 대상·획득/배달 수량·노출/삭제·임시 아이템 관계의 필요한 저장/조회 |
| 유효 버전 조회·참조 일치·갱신 처리 | 같은 게임 패치의 유효 정보 선택·스킬 대상/버전 일치 검사·원본/캐시 갱신과 기본 수정 처리. 기능별 검색·트리·루트 동작은 각 기능 Issue로 연결 |

<a id="acceptance"></a>
### 합의한 수용 조건

- 시즌 1·v1.0.0을 포함한 합의 모델을 저장·조회할 수 있고 식별값·정렬값·관계가 구별된다. 스키마와 Java/API 값 왕복이 채택 기준을 충족한다. 실제 게임 자료 전체 등록은 자료 Issue가 담당한다.
- 조회 패치의 유효한 이력을 선택하고 과거 상태를 보존한다. 종류 계층·스킬 동시 참조·삭제 전 상태·노출 구분·필요 참조의 일치를 확인하며 현재값의 별도 원본 사본을 전제하지 않는다.
- 기본 수정과 원본/캐시 갱신이 일치하고 검색·제작·루트가 사용할 저장/조회 결과와 인터페이스가 준비된다. 수식 실행·버전 선택기 등 후속 기능은 추가하지 않는다.

실제 수치 범위·소수 정밀도·미확인 날짜 허용·JSON 필수 내용 등 자료 의존 결정은 구현 전에 제공 자료를 확인한다. 자료 Issue의 입력 확인 결과가 필요한 부분은 그 결과를 받되, 자료 Issue 전체 완료를 선행 조건으로 삼지 않는다. 현재 보류 중인 자료를 조사하거나 값을 가정하지 않는다.

## Task 선후 관계와 남은 결정

- 공통 식별·시즌/패치·지역·분류 관계를 먼저 마련한 뒤 아이템과 관련 정보의 저장/조회를 연결한다. 이력·참조·캐시 일치 조건은 각 관계 설계부터 함께 반영하고 마지막 Task에서 유효 버전 조회·갱신 처리를 연결한다.
- 테이블·키·제약·사냥 대상·임시 아이템 관계, 수치 범위/정밀도·API 표현·JSON 필수 내용·미확인 값 허용은 필요한 입력을 받아 구현 전에 결정한다.
- [합의한 주담당 배정](<../issue-45/issue.md#ownership>)에 따라 기본 수정 처리는 이 Issue가 제공하며 자료 Issue에서 필요한 선행 코드 보완도 수행할 수 있다.
