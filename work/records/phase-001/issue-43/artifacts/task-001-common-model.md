# Task 43-001 — 공통 6개 표·키·참조 검사

<a id="current"></a>

공통 필드/필수값·관계 개수·키/IDENTITY·DB 검사를 구체화할 때. 담당 상태·수용 판단은 [Task 43-001](../task-001.md#summary), 전체 길잡이는 [설계 안내](task-001-shared-version-references.md#summary)를 따른다. 아래 채택·비채택·미정을 구별하며 실제 자료·DB 작업과 구현 파일 생성은 계속 보류한다.

현재 저장 규칙은 [공통 DB 모델](<../../../../../docs/details/development/공통 DB 모델.md#current>)과 [8개 표 구조](../../../../../db/model/table-layout.md#current)·N1~N5를 따른다. 사용자 확인의 메이저/마이너 각각 0~99 CHECK·패치 정렬 UNIQUE와 D1 NULL 등록·D2 중복 금지를 적용한다. 실제 제약별 이름·정확한 환경은 초안에서 제시하며 실제 목록/값은 자료 재개 뒤 확인한다. F1~F3는 키·참조 검사의 결론과 비교 근거다.

## 공통 6개 표 저장 계약 — 확정 규칙과 미정

대상은 public.season·game_patch·region·item_category·item_grade·weapon_type과 지도 2개 표다. M1~M3·8개 표 저장 구조·N1~N5와 번호 각각 0~99 CHECK/패치 정렬 UNIQUE를 채택했다. D1 NULL 등록·D2 중복 금지·D3 필수 일대일 FK·D4 지속 지역/작업용 이름과 지도 이력을 유지한다. 실제 목록/값·제약별 이름/정확한 환경과 최종 DDL은 미완성이며 실제 자료·DB 작업과 구현 파일 생성은 보류한다.

표의 합의·M 채택은 확정 규칙, 보류는 자료·의미 확인이 필요한 항목이다. 자료형이 확정돼도 NULL/등록 허용이나 최종 배치는 D 항목으로 남을 수 있다. 보류는 NULL 허용을 뜻하지 않는다.

### 기존 합의 — 다시 선택하지 않는 범위

| 범위                | 유지할 계약                                                                                                                                                                                                              |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 여섯 내부 키        | 모두 `id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY`. NOT NULL/유일성과 Java Long·API ID 문자열 경계를 유지. PK 보호의 여섯 대상/함수/trigger·오류/권한 계약도 유지                                                 |
| 업무 키·핵심 필수값 | season의 `season_number` UNIQUE/NOT NULL, game_patch의 `(season_id, major_no, minor_no)` UNIQUE와 세 열 NOT NULL. 내부 ID와 업무 번호/정렬값은 별개                                                                      |
| 시즌·패치·지역 규칙 | 시즌 번호 1부터, 시즌 정렬값은 시즌 번호+9. 패치 정렬값은 시즌 정렬값×10000+메이저×100+마이너. 메이저 패치의 마이너 0·초기 표기/값과 별도 version_name을 유지. 지역 정렬값은 10부터 10단위                               |
| 날짜·일시 | 시즌 날짜 DATE/LocalDate, 적용 시점 timestamptz(0)/Instant·UTC·초 미만 절삭. D1의 5개 메타정보 NULL 등록을 허용하고 임의 날짜/자정으로 보완하지 않음 |
| 종류와 등급         | 종류는 버전 없는 현재 이름/계층, parent 0~1개의 트리 모음·깊이 미고정. 확인된 루트만 parent_id NULL, 일반 부모 FK/자기 부모 금지 CHECK. 등급 이름/순서는 관리자 판단·기본 검사로 수정, 같은 대상 오류는 같은 ID에서 정정 |
| 참조·갱신 | 일반 FK 비지연·삭제 RESTRICT·ON UPDATE NO ACTION, Spring 업무/DB 무결성 분담과 검토된 예외 쓰기. 무기 종류의 category_id 필수 FK + UNIQUE·N3~N5 계약 적용 |

근거는 [시즌/패치·지역 요구](../../../../../docs/details/product/게임 데이터 변경 관리.md#season-information), [분류·등급·별도 무기 종류](../../../../../docs/details/product/아이템 탐색과 상세.md#classification), [일시 기준](../../../../../docs/개발 기준.md#datetime), [키 계약](#f1-keys), [F3 필수값](#f3-null)을 따른다. 종류의 버전 제외를 지역이나 다른 자료에 확대하지 않는다.

### 채택 필드·자료형·필수값과 계속 유보하는 NULL/배치

여섯 표 모두 위 공통 `id`를 포함한다. 아래에 id를 반복하지 않는다. 새 필드명/자료형/지정 필수값은 **M1로 함께 확정한 계약**이며 같은 선택을 다시 요구하지 않는다. 업무 번호·정렬값·문자열에 0/빈 문자열 등의 기본값을 자동 부여하지 않는 M1 계약을 유지한다. 실제 0인 패치 번호는 명시 입력하며 미확인과 구별한다.

#### season

| 필드          | 자료형 초안     | NULL/필수        | 상태·의미                                                                                                                |
| ------------- | --------------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------ |
| season_number | INTEGER M1 채택 | NOT NULL 합의    | UNIQUE 합의. 1부터 시작하는 의미는 합의, DB 하한 CHECK는 M2 채택. INTEGER 물리 범위의 채택과 게임에서 허용할 상한은 구별 |
| display_name  | TEXT M1 채택    | NOT NULL M1 채택 | 표시 이름. 시즌명과 구별해 저장하며 번호를 조합한 문자열로 자동 대체하지 않는 M1 안                                      |
| season_name   | TEXT M1 채택    | NULL 허용 D1          | 별도의 실제 시즌명. 표시 이름/시즌 번호를 미확인 값의 대체로 저장하지 않음                                               |
| sort_order    | BIGINT M1 채택  | NOT NULL M1 채택 | 번호와 별도 정렬 필드로 저장하는 M2 안. 시즌 번호+9의 단일 행 CHECK 채택                                                 |
| start_date    | DATE 합의       | NULL 허용 D1          | 실제 시작일. 시간/시간대를 덧붙이지 않음                                                                                 |
| end_date      | DATE 합의       | NULL 허용 D1          | 실제 종료일. NULL 허용. NULL만으로 진행 중/해당 없음 판정하지 않으며 추가 구분은 별도 확인                                                  |

#### game_patch

| 필드         | 자료형 초안         | NULL/필수        | 상태·의미                                                                                  |
| ------------ | ------------------- | ---------------- | ------------------------------------------------------------------------------------------ |
| season_id    | BIGINT              | NOT NULL 합의    | season.id 일반 FK·비지연/참조 중 RESTRICT. 별도 시즌 번호를 FK 대신 저장하지 않음          |
| major_no | INTEGER M1 채택 | NOT NULL 합의 | 0~99 CHECK. 사용자 확인의 번호 범위 |
| minor_no | INTEGER M1 채택 | NOT NULL 합의 | 0~99 CHECK. 실제 0도 명시 입력하며 누락을 기본 0으로 숨기지 않음 |
| version_name | TEXT M1 채택        | NULL 허용 D1          | 기존 요구의 별도 패치 이름. `시즌.메이저.마이너` 표기를 이름으로 대체하지 않음             |
| sort_order | BIGINT M1 채택 | NOT NULL M1 채택 | 기존 식으로 계산·검증해 저장, UNIQUE. 메이저/마이너는 각각 0~99 |
| applied_at   | timestamptz(0) 합의 | NULL 허용 D1          | 초 미만 절삭 후 저장. 미확인이면 현재/예정도 미확인. NULL 등록 허용. 명시 조회와 현재/예정 판정을 구별하며 DTO/API는 별도   |

기존 업무 UNIQUE는 `(season_id, major_no, minor_no)`다. 표기 문자열은 별도 업무 키/이름/코드 열을 추가하지 않고 번호로 구성하는 안이다. `applied_at`의 자료형 정밀도 변환에 초 미만 절삭을 맡기지 않는다. DB에 도착하기 전 정규화와 예외 쓰기의 같은 규칙 준수는 구현/검증 대상이며 이 초안으로 실제 실행을 확인한 것은 아니다.

#### region — 지속 ID·작업용 이름과 지도 이력

| 필드                            | 자료형 초안    | NULL/필수        | 상태·의미                                                                        |
| ------------------------------- | -------------- | ---------------- | -------------------------------------------------------------------------------- |
| region_map_member.name | TEXT | NOT NULL | 해당 지도 구성의 공개 지역 이름. 같은 구성 안 UNIQUE |
| region_map_member.sort_order | BIGINT | NOT NULL | 해당 지도 구성의 순서. 10 이상·10의 배수, 같은 구성 안 UNIQUE |
| region.display_name | TEXT | NOT NULL | 작업용 표시 이름. 빈값 금지·region 목록 안 UNIQUE, 공개 이름과 자동 동기화하지 않음 |

region은 시즌 사이 동일 ID를 유지한다. 등장·공개 이름·순서는 region_map_version/region_map_member에 저장한다. 작업용 display_name은 업무 UPDATE로 수정할 수 있고, 수정만으로 지도 새 버전·과거 구성·획득 참조를 바꾸지 않는다. 적용 구간과 전체 열/키는 [지역 저장 계약](../../../../../db/model/region-layout.md#current)을 따른다.

### M1~M3 확정 — 이유와 비채택 비교 대안

| 묶음                             | 확정·이유                                                                                                                                                                                                                                                                     | 비채택 비교 대안·부담                                                                                                                                                                                                                                 |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| M1. 기본 필드·자료형·추가 필수값 | **위 필드명/의미와 INTEGER 업무 번호·BIGINT 정렬값·TEXT 이름을 사용**. display_name 및 지역/종류/등급/무기 종류의 name, 정렬 필드는 NOT NULL로 채택. 자료형과 입력 누락을 구별하고 의미 없는 문자열 길이 상한을 피함. 업무 값의 기본 0/빈 문자열과 자동 이름 대체는 두지 않음 | 이름/정렬도 NULL을 허용한 불완전 원본, 길이를 고정한 VARCHAR(n), 업무 숫자/정렬의 다른 정수 자료형. 전자는 조회/완성 판정이 늘고 후자는 실제 길이/범위 근거가 필요. D1의 실제 이름/날짜와 D4 지역 배치는 M1로 자동 확정하지 않음                      |
| M2. 정렬 저장·단일 행 검사       | **정렬값을 별도 저장하고 Spring에서 기존 식으로 계산/검증**. 시즌 식·번호 하한·지역 10단위·확인된 날짜의 역전·이름 빈값에 아래 최소 CHECK를 채택. 저장된 정렬값을 조회에 사용하고 단일 행의 오류를 DB에서도 드러내기 쉬움                                                     | 읽을 때 JOIN/식으로 계산하거나 가능한 열에 생성 열 사용. 중복 저장/갱신 부담은 줄지만 조회·정렬/인덱스 계약이 달라짐. patch는 다른 season 행이 필요해 동일 행 생성 열만으로 해결할 수 없음. 다른 행 참조 CHECK/추가 업무 trigger를 자동 채택하지 않음 |
| M3. 종류 이름 범위·보조 인덱스   | **같은 부모 아래 이름 중복 금지, 루트끼리도 같은 이름 중복 금지**로 채택. 서로 다른 부모의 같은 이름은 허용. 전체 이름 UNIQUE보다 트리의 문맥을 유지하기 쉬움. 필요시 parent_id 조회 인덱스를 우선 후보로 두고 확정 PK/UNIQUE와 같은 인덱스를 중복 생성하지 않음              | 이름 전역 UNIQUE, 또는 ID만 구별하고 이름 중복을 허용. 전역은 다른 가지의 동명도 제한하고 무제약은 같은 가지의 동명 구별/표시 규칙이 필요. M3 범위는 확정. 실제 동명 충돌은 입력/교정 계약에서 반환하며 실제 자료에 중복이 없다는 진술은 아님         |

M1의 INTEGER/BIGINT도 물리 범위를 갖는 채택 자료형이며 실제 게임 번호/순서의 업무 허용 상한을 확인한 것은 아니다. BIGINT 정렬값을 ID로 취급하거나 API의 모든 Long을 문자열로 바꾸지 않는다. 이름에 TEXT를 쓰는 안은 자동 trim/대소문자 변환/Unicode 정규화·공백 병합을 허용한 것이 아니다. [정수 자료형](https://www.postgresql.org/docs/18/datatype-numeric.html) · [문자열 자료형](https://www.postgresql.org/docs/18/datatype-character.html)

#### M2의 채택 CHECK/저장 책임

| 대상                  | 확정한 검사/책임                                                                                                                             | 보장하지 않는 것                                                                                                                                                              |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| season.season_number  | `season_number >= 1`                                                                                                                         | 실제 최댓값·빈 번호 없는 연속 등록을 정하지 않음                                                                                                                              |
| season.sort_order     | `sort_order = season_number::bigint + 9`                                                                                                     | 시즌 번호 교정 시 참조 패치의 재계산·동시 변경 처리는 별도 변경 계약                                                                                                          |
| game_patch 번호 | major_no BETWEEN 0 AND 99 AND minor_no BETWEEN 0 AND 99 | 사용자 확인의 범위를 CHECK로 검사하고 패치 정렬값 UNIQUE 적용. 실제 제약 생성은 보류 |

### 검토/검증과 다음 행동

M1~M3를 저장·검증 계약으로 사용한다. D1~D4의 입력 확인에도 자료 보류가 적용된다. D1~D4는 최초 구동 B1~B3 구현의 선행 조건이 아니다.

후속 검증은 기존 001/004 사례를 보완한다. 현재는 실행하지 않았다.

1. 필드별 합의 NOT NULL과 M 채택/계속 유보를 구별하고 누락·0·빈 이름·미확인 값을 서로 대체하지 않음. 두 시즌 이름/별도 패치 이름·날짜/시점의 왕복과 초 미만 사전 절삭을 확인.
2. 시즌/패치 업무 중복·확정 FK/자기 부모·번호 하한/시즌 식/지역 간격/기간 역전과 CHECK의 NULL 경계를 검증. M1~M3·D1 NULL 등록·D2-N 중복 금지와 D2-P 검토 기준을 기대 결과에 반영하고 실제 입력·물리 미정을 임의로 채우지 않음.
3. 루트/형제/다른 부모의 동명과 비교 방식, PK/UNIQUE/parent 인덱스의 실제 배치/중복을 검증. 자기 부모 검사를 긴 순환/동시성 통과로 확대하지 않음.
4. W 선택에 맞는 다중/누락/비무기 분류 연결과 region의 선택한 시즌/이력 의미를 검증. 선택하지 않은 열/표를 함께 만들지 않음.
5. patch 정렬 계산·부모 시즌/번호 정정의 관련 영향·오류/롤백을 다음 변경 계약과 연결. 실제 목록/범위를 확인한 결과와 합성 입력의 구조 검증을 구별.

남은 범위는 **실제 입력과 D1~D4의 물리/조회 상세**다. 확정한 NULL 등록·중복 금지와 번호/정렬 검토 기준을 다시 선택하지 않는다. 전체 6개 표의 최종 DDL은 아직 승인/완성되지 않았다. 기존 Task의 계획/미정 소유를 유지하며 실제 구현·자료·DB 작업 보류를 해제하지 않는다.

### F1 — 내부 ID PK·업무 UNIQUE·ALWAYS 채택

| F1-U. 업무상 중복 방지   | 시즌은 UNIQUE `season_number`, 패치는 UNIQUE `(season_id, major_no, minor_no)` — 채택 | 서비스/도구만의 업무 중복 검사는 비채택. 확정한 UNIQUE와 F3 핵심 NOT NULL을 유지. 실제 제약명·그 밖의 NULL/미확인 보관 정책은 별도 확인                     |
| F1-I. IDENTITY 입력 옵션 | ALWAYS — 채택. 일반 입력에서 직접 지정한 ID를 실수로 수용하는 일을 줄임               | BY DEFAULT는 비채택 비교안. 명시 ID 입력을 기본 허용하지 않는 ALWAYS를 채택하되 #45의 이관/복원 예외 절차는 별도 확인                                       |

PK는 한 행의 내부 식별, 업무 UNIQUE는 같은 시즌/패치 표기의 중복 방지, FK는 다른 행의 참조 검사라는 역할이다. 확정한 구성은 두 종류의 키를 분리하고 ID는 번호·정렬값·종류명으로 계산하지 않는다. 같은 메이저/마이너라도 시즌이 다르면 위 패치 업무 키는 다른 조합이다. 종류명·등급명·무기명·지역명에 전역 UNIQUE를 함께 넣는 선택은 아니다.

IDENTITY와 PK/UNIQUE·NOT NULL의 역할을 구별한다. 기본 UNIQUE는 NULL이 포함된 조합을 별도로 다룬다. 핵심 NOT NULL/루트 NULL과 일반 FK 비지연·참조 중 DELETE RESTRICT를 적용한다. 나머지 NULL/입력 보관·복합 참조·제약 배치·패치 정렬값 UNIQUE·번호 상한은 담당 미정이다. [IDENTITY](https://www.postgresql.org/docs/18/ddl-identity-columns.html) · [PK·UNIQUE와 NULL](https://www.postgresql.org/docs/18/ddl-constraints.html#DDL-CONSTRAINTS-UNIQUE-CONSTRAINTS)

#### ALWAYS와 BY DEFAULT의 동작 차이

아래는 다른 제약을 만족한다는 전제의 PostgreSQL 동작 비교이며 실행한 결과가 아니다. `42`는 설명용 내부 ID다. 두 옵션 모두 ID를 생략하거나 DEFAULT로 주면 같은 종류의 자동 발급을 사용하며, 조회·참조 모델을 바꾸는 옵션은 아니다.

| 입력/조작                                     | ALWAYS                                                  | BY DEFAULT                                           |
| --------------------------------------------- | ------------------------------------------------------- | ---------------------------------------------------- |
| INSERT에서 ID 생략 또는 DEFAULT               | DB 자동 발급                                            | DB 자동 발급                                         |
| 보통 INSERT에서 ID 42 지정                    | 오류                                                    | 지정한 42 사용                                       |
| INSERT에 OVERRIDING SYSTEM VALUE와 ID 42 지정 | 명시적으로 42 사용                                      | 42 사용                                              |
| INSERT에 OVERRIDING USER VALUE와 ID 42 지정   | 지정 ID를 무시하고 자동 발급                            | 지정 ID를 무시하고 자동 발급                         |
| ID에 명시 NULL 입력                           | NOT NULL 규칙에 따라 오류. 자동 발급 요청이 아님        | 동일                                                 |
| UPDATE로 ID를 다른 숫자로 변경                | DEFAULT 외의 직접 변경은 오류                           | IDENTITY 규칙상 허용. PK/FK 등 다른 제약은 별도 적용 |
| UPDATE에서 ID = DEFAULT                       | 새 자동 발급 값으로 바뀔 수 있음. 다른 제약은 별도 적용 | 동일                                                 |
| COPY FROM의 입력 열에 ID가 포함되고 값을 제공 | 입력 ID 사용                                            | 입력 ID 사용                                         |

일반 INSERT의 override 규칙은 [INSERT 문서](https://www.postgresql.org/docs/18/sql-insert.html), UPDATE의 차이는 [CREATE TABLE의 IDENTITY 규칙](https://www.postgresql.org/docs/18/sql-createtable.html)과 [UPDATE DEFAULT](https://www.postgresql.org/docs/18/sql-update.html)를 따른다. COPY FROM은 IDENTITY 옵션과 관계없이 입력 ID를 사용하며, ID 열을 입력 목록에서 제외하면 그 열은 기본값을 사용한다. 따라서 ALWAYS를 복원·대량 입력까지 막는 보안 장치로 해석하지 않는다. [COPY FROM의 IDENTITY 처리](https://www.postgresql.org/docs/18/sql-copy.html)

ALWAYS도 ID를 절대로 바꿀 수 없게 하는 옵션은 아니다. PK의 불변성·쓰기 권한·ID 필드를 일반 수정에서 제외하는 계약은 F3·F4의 검사/갱신 설계와 구별한다. 이 비교는 가능한 SQL 동작을 설명하며 기존 ID를 일반 업무 수정으로 바꾸자는 제안이 아니다.

#### 채택 이유와 등록·복원 경계

내부 ID PK와 업무 UNIQUE를 구별하고 ID는 ALWAYS로 발급한다. 일반 저장에서 ID를 생략하면 DB가 발급하고, 명시 ID를 실수로 포함한 INSERT는 오류로 드러난다. 입력 실수의 조기 확인이 목적이며 조회 성능의 우열은 측정하지 않았다.

BY DEFAULT 조합 F1-B는 비채택 비교안이다. 내부 ID를 직접 지정해 유지하는 입력을 일상 쓰기에 포함하려는 경우의 대안으로 비교했다. 두 안 모두 의도적인 ID 보존 입력은 가능하다. 예외 입력이 가능하다는 사실과 그 경로를 평상시 허용할지는 다른 선택이다. 아직 복원/등록 수단이나 SQL override·COPY 사용을 채택/허용한 것은 아니다.

| 상황                         | 제안하는 구분·남은 확인                                                                                                                       |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| 보통 신규 등록               | 확정한 자동 발급 방식에 따라 보통 신규 입력은 ID 생략/DEFAULT를 사용. 실제 입력 형식·반환 ID 연결은 #45의 등록 수단 설계에서 확인             |
| 기존 ID를 유지하는 이관/복원 | 관계 참조와 ID 보존 필요, 명시 입력 경로, 시퀀스 상태를 함께 확인. ALWAYS라서 복원 불가라고 판단하지 않음                                     |
| 일부 행을 명시 ID로 입력     | 입력 ID가 커졌다고 자동 발급 시퀀스도 그 최대값에 맞춰졌다고 가정하지 않음. 실제 정합성 확인/보정은 별도 절차                                 |
| 전체 백업 복원               | pg_dump는 표 자료와 시퀀스 값도 다루므로 행만 수동 입력한 경우와 구별. 실제 덤프 범위·복원 대상·부분 복원의 잔여 참조·발급 상태를 확인해야 함 |

위의 시퀀스 정합성 주의는 명시 ID 입력과 시퀀스 발급이 다른 경로라는 공식 동작에서 따르는 설계 판단이다. 실제 보정 명령을 지금 정하거나 실행하지 않는다. [시퀀스 함수](https://www.postgresql.org/docs/18/functions-sequence.html) · [pg_dump의 자료/시퀀스 범위](https://www.postgresql.org/docs/18/app-pgdump.html)

자동 발급 번호에는 롤백·충돌 등의 이유로 빈 번호가 생길 수 있다. ID를 빈틈없는 수량·정렬로 사용하지 않으며, 시퀀스 상태 변경이 행 자료와 동일하게 롤백된다고 가정하지 않는다. 임의의 `MAX(id)` 보정식을 공통 정답으로 채택하지 않고 빈 표·동시 쓰기·실제 발급 상태와 복원 범위에 맞춰 후속 확인한다. [시퀀스와 롤백](https://www.postgresql.org/docs/18/functions-sequence.html)

물리 제약 배치·업무 허용 범위·나머지 유일성/NULL·복합 참조와 실제 구현 수단은 미정이다. 일반 참조/삭제 규칙은 [F3](#f3-rules), 복원/시퀀스 보정은 [조건부 예외](task-001-pending.md#conditional-exceptions)를 따른다. 실제 자료·DB 작업은 보류한다.

<a id="f3-rules"></a>

### F3 — 참조·NULL/필수값·삭제·고정 규칙 상세 검토

F3의 확정 범위는 일반 FK NOT DEFERRABLE·참조 중 ON DELETE RESTRICT, 핵심 NOT NULL·확인된 루트 부모 NULL과 등급의 관리자 판단/기본 검사다. 나머지 추가 검사·복합 제약은 담당 미정이다. 키/ALWAYS와 관계 개수는 F1/F2를 따르며 실제 자료·DB·구현 작업은 보류한다.

#### 유지할 합의와 새 결정의 경계

| 기존 합의·근거                                                                                                                                                                                                                                                      | 확정 규칙·미정                                                                                                                             |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| F1의 공통 대상 단일 ID PK·ALWAYS, 시즌/패치 업무 UNIQUE. | K-D와 F2-A·F2-B의 현재 분류, 부모 0~1개인 순환 없는 트리 모음, 완성 버전당 종류 1개. <a id="f3-reference"></a>

#### F3-R — 참조 존재와 대상/버전의 소속 검사

일반 공통 참조의 존재는 DB FK로 지연 없이 검사한다. 서비스 사전 검사는 입력 오류를 설명하는 보완 수단이다. 실제 FK/저장 경로는 미구현이며 이 제약이 권한이나 관리자 우회를 해결하지는 않는다.

| 검사 대상                          | 추천 후보                                                                                                     | 대안·한계와 담당                                                                                                                                |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| 시즌·종류·부모 등 공통 대상 참조   | 일반 FK를 NOT DEFERRABLE로 검사 — 채택. 실제 FK 열/이름과 선택 범위 밖 필수값은 각 행 계약에서 확인           | 서비스 검사만 두는 안은 다른 쓰기 도구도 같은 계약을 지켜야 함. 일괄 참조 재배치가 필요하면 해당 FK에만 지연 검사를 비교. 공통 001·각 저장 Task |
| 재료/스킬의 대상 ID + 지정 버전 ID | 관계가 존재하면 두 ID를 같은 대상의 짝으로 검사하는 복합 FK 후보. 참조 쪽 대상/버전 조합의 유일성도 함께 설계 | 두 단일 FK만으로 소속 일치가 보장되지 않음. trigger/공통 함수 검사 대안과 실제 PK/UNIQUE는 002·003, 결합 확인 004                               |
| 선택 관계와 반쪽 NULL              | 관계가 존재하는 완성 행의 필수 ID 쌍은 NOT NULL 후보. 선택 관계 부재를 행 부재로 둘지 저장 배치에서 비교      | 두 값 모두 NULL인 선택 열을 쓰면 MATCH FULL 후보도 가능. 관계 없음과 대상 미확인을 같은 상태로 취급하지 않음. 저장 형태·미확인 등록은 미정      |
| 종류의 자기 부모·긴 순환           | 자기 부모는 F4-S2로 같은 행 CHECK 채택. 긴 순환은 조상 경로 검사와 F4의 동시 변경 계약으로 확인               | 단일 부모 열·self FK·자기 부모 CHECK만으로 전체 순환 방지를 통과시키지 않음. 검사 자체가 순환 입력에서도 종료해야 함                            |
| 스킬 연결의 소속 패치              | R3대로 소속 아이템 버전 기준 패치인지 확인하는 구체 제약/공통 쓰기 검사 후보                                  | 지정 스킬 버전의 기준 패치까지 같게 강제하지 않음. 재료의 Q 정합성도 대상/버전 소속 검사만으로 대체하지 않음. 002·003·004                       |

복합 FK의 기본 MATCH SIMPLE은 구성 열 중 NULL이 있으면 참조 검사를 건너뛸 수 있다. MATCH FULL은 반쪽 NULL을 막지만 둘 다 NULL이면 참조가 없는 상태를 허용하므로 필수 관계의 NOT NULL을 대신하지 않는다. [PostgreSQL FK의 NULL 규칙](https://www.postgresql.org/docs/18/sql-createtable.html)

<a id="f3-timing"></a>

#### 비지연 검사·지연 검사와 이 계약의 뜻

트랜잭션은 여러 SQL 변경을 한 묶음으로 확정(COMMIT)하거나 취소하는 단위다. **선택한 비지연 FK 검사**는 각 SQL 명령이 끝날 때 참조 조건을 만족해야 한다. **지연 검사**는 지연 가능한 제약을 실제 지연 모드로 사용해 검사를 트랜잭션 끝까지 미룰 수 있는 비교 방식이다.

다음은 실제 자료가 아닌 설명용 사례다. 시즌 S가 아직 없고, 이를 참조하는 패치 P를 저장하려 한다. 각 단계는 서로 다른 SQL 명령이며 한 트랜잭션 안에서 수행한다고 가정한다.

| 단계                          | 선택한 비지연 FK                                                   | 비교용 실제 지연 검사                                  |
| ----------------------------- | ------------------------------------------------------------------ | ------------------------------------------------------ |
| 1. S를 참조하는 P를 먼저 저장 | 이 SQL에서 참조 오류. 다음 SQL에 S를 넣을 예정이어도 통과하지 않음 | 검사 시점까지 일시적으로 허용                          |
| 2. 뒤의 SQL로 S 저장          | 앞 명령이 실패했으므로 이 순서로 저장을 완료하지 못함              | 이제 참조가 맞음                                       |
| 3. COMMIT                     | 이 순서는 실패. S를 먼저, P를 다음 SQL로 넣는 순서를 사용          | 최종 참조가 맞으면 성공. S가 끝까지 없으면 COMMIT 실패 |

S를 먼저 저장하고 같은 트랜잭션에서 P를 다음 SQL로 저장하면 두 방식 모두 마지막에 한 번 COMMIT할 수 있다. 비지연 검사가 SQL마다 따로 COMMIT해야 한다는 뜻은 아니다.

DEFERRABLE은 검사를 미룰 수 있다는 뜻이며 그것만으로 항상 커밋까지 미뤄지는 것은 아니다. INITIALLY IMMEDIATE는 처음에는 명령마다 검사한다. 확정한 NOT DEFERRABLE FK는 뒤에서 지연 모드로 바꿔 임시 참조 오류를 허용하는 계약이 아니다. [PostgreSQL 검사 시점](https://www.postgresql.org/docs/18/sql-createtable.html)

RESTRICT는 별도의 삭제 규칙이다. 이미 P가 S를 참조한다면 S의 삭제를 거부한다. 참조 중인 대상과 과거 관계를 보존하는 정책이며 실제 게임 삭제/검색 제외와 구별한다. [PostgreSQL 삭제 제한](https://www.postgresql.org/docs/18/ddl-constraints.html#DDL-CONSTRAINTS-FK)

<a id="f3-null"></a>

#### F3-N — 필수값과 NULL의 의미

기준 원본에는 핵심 필수 번호·참조가 확인된 행을 저장한다. 확인된 최상위 종류의 부모 없음은 parent_id NULL로 표현한다. 핵심값이 미확인인 행은 선등록하지 않는다. 미확인 입력의 보관 위치·임시 표·등록 상태 필드는 미정이다.

| 항목                                         | 추천 후보/유보                                                                                                   | 새로 결정할 범위                                                                                                             |
| -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 공통 대상 내부 ID                            | F1 PK/IDENTITY의 NOT NULL·유일성은 이미 확정한 키의 성질                                                         | 확정 규칙. ID 불변성은 별도 고정 규칙                                                                                        |
| 시즌 번호, 패치의 시즌 ID·메이저/마이너 번호 | 기준 행의 NOT NULL — 채택. F1 업무 UNIQUE와 함께 식별을 완성                                                     | 미확인 필수 번호를 가진 행은 기준 원본에 선등록하지 않음. 보관/처리는 별도 정책. 0이 실제 번호인 경우와 미확인 대체값을 구별 |
| 완성된 아이템 버전의 종류 ID                 | NOT NULL로 F2-B의 종류 1개를 표현 — 채택                                                                         | 종류 미확인 행의 기준 원본 선등록은 허용하지 않음. 보관/처리 위치는 미정이며 실제 DDL은 002와 확인                           |
| 종류의 부모                                  | 확인된 최상위는 parent_id NULL, 자식은 유효 부모 ID 사용 — 채택                                                  | NULL은 확인된 부모 없음만 뜻함. 미확인/생략된 부모를 기본값으로 루트 처리하지 않음                                           |
| 시즌 기간·패치 적용 일시                     | 미확인을 임의 날짜/자정/현재 시각으로 채우지 않는 기존 원칙 유지. 실제 등록 시 NULL 허용은 필드별 유보           | 날짜가 모두 확인된 경우의 기간 순서 검사도 의미/입력과 대조. 진행 중·해당 없음·미확인을 먼저 구별                            |
| 종류/시즌/패치 이름, 지역·등급·무기 종류 값  | M1 추가 필수값/TEXT·정렬 자료형과 M3 종류 이름 범위는 채택. 그 밖의 실제 이름 NULL/유일성·길이/업무 상한은 D1/D2 | 실제 값/명명 의미·미확인 사례가 필요한 부분은 #45 보류 해제 뒤 확인                                                          |

핵심 필수 참조를 NULL로 둔 미완성 행의 기준 원본 선등록은 비채택 비교안이다. 입력 보존에는 유연하지만 미완성 판정·조회 제외·확정 전환을 추가 설계해야 한다. 확정한 안은 완성 구성과 미확인 입력의 의미를 구별하며, 미확인 입력 자체의 보관/처리 위치는 아직 정하지 않았다. 후속 M1의 추가 필수값은 유지하며 실제 시즌명/패치명·날짜의 5개 메타정보 NULL 등록은 D1으로 허용한다.

NULL이라는 값만으로 그것이 확인된 루트인지 누락인지 DB가 알아낼 수는 없다. 루트 사실 확인은 입력 계약에서 별도로 수행해야 한다. FK·CHECK만으로 필수값을 대신하지 않으며 CHECK의 NULL 결과도 제약을 통과할 수 있다. [CHECK와 NOT NULL](https://www.postgresql.org/docs/18/ddl-constraints.html#DDL-CONSTRAINTS-NOT-NULL)

<a id="f3-delete"></a>

#### F3-D — 참조 중 삭제와 게임 삭제의 구별

일반 FK는 비지연 검사이며 참조 중인 공통 대상 행의 삭제는 ON DELETE RESTRICT로 거부한다. 시즌/패치·종류·등급·무기 종류·지역에 적용하고 후속 귀속 행 전체의 삭제 정책은 별도로 정한다.

| 대안                                          | 동작·추천 판단                                                                                            | 남은 조건                                                                                                   |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| FK NOT DEFERRABLE + ON DELETE RESTRICT — 채택 | 중간에 참조가 끊기는 변경을 일찍 드러내고 참조 중인 대상을 삭제하지 못하게 함                             | 참조 재배치가 필요한 경우 저장 순서를 맞춰야 함. 미참조 행 삭제 허용·병합·ID 교체는 별도 정책               |
| 지연 가능한 FK + ON DELETE NO ACTION          | 일반 기본안으로는 비채택 비교. 필요한 특수 관계가 생기면 트랜잭션 끝 검사 전 참조 재배치 흐름을 별도 제안 | 지연 범위·검사 시점·수정 순서·실패/재시도와 F4 계약이 필요. NO ACTION이 참조 검사를 하지 않는다는 뜻은 아님 |
| ON DELETE CASCADE/SET NULL                    | 공유 대상의 기본안으로 추천하지 않음. 자동 삭제나 참조 해제가 과거 구성 또는 루트 의미를 바꿀 수 있음     | 일부 소유 관계에서는 별도 검토 가능하나 002·003의 소유/보존 계약으로 판단. 모든 삭제에 일괄 적용하지 않음   |

RESTRICT는 참조 중 삭제를 지연 검사로 미룰 수 없고, 지연 가능한 NO ACTION은 최종 검사까지 관계를 맞추는 흐름과 비교할 수 있다. [PostgreSQL 삭제 동작](https://www.postgresql.org/docs/18/ddl-constraints.html#DDL-CONSTRAINTS-FK) · [검사 지연의 조건](https://www.postgresql.org/docs/18/sql-createtable.html)

게임에서 아이템이 삭제되거나 검색에서 제외되는 처리는 이 물리 DELETE 후보와 별개다. 과거 정보와 필요한 제작 참조를 지우는 허용으로 확대하지 않는다. RESTRICT가 미참조 행의 삭제까지 금지하는 규칙은 아니므로 미참조 공통 행·종류 병합/폐기·키 재배치의 허용은 따로 확인한다. 이 문서는 실제 DELETE·정정·복원 작업의 승인이 아니다.

참조 ID의 ON UPDATE 동작도 별도 미정이다. F4-S3에서 확정한 정책대로 보통 갱신은 기존 공통 PK 값을 유지하고, 예외적인 키 재배치는 별도 계약으로 확인한다. ID 변경을 연쇄 전파하는 ON UPDATE CASCADE를 자동 선택하지 않는다.

#### F3-F — PK 보호와 관리자에 의한 속성 수정

공통 PK 값의 일반 변경은 AFTER UPDATE 행 trigger와 Spring 검사로 거부한다. 등급 이름·순서의 수정은 PK 보호와 구별하며 [관리자 판단과 기본 검사](task-001-updates.md#grade-change-explanation)를 적용한다.

| 필드/상황                    | 현재 계약                                                                                                     | 남은 확인                                                                                             |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| 공통 대상 PK                 | 실제 PK 값 변경은 P1-A로 거부. 같은 값 재대입은 거부하지 않음. N/E/R·F/I의 정의/오류/권한·본문/설치 설계 유지 | 구현 SQL/버전 배치·요청/예외 연결·역할별 권한. 새 행의 ID 보존 복원과 기존 PK 값 변경은 구별          |
| 등급 이름·표시 순서          | 지정 관리자가 원자료와 영향으로 판단해 수정. 코드는 기본 입력/DB 검사. 같은 대상의 오입력은 같은 ID에서 고침  | 목록 안 동명·동순위 금지(D2-N). 실제 값/충돌·수정 근거는 #45. 별도 교정 판별/전용 guard는 요구하지 않음 |
| 종류 이름·부모               | K-D의 현재 기준 갱신과 단일 부모·비순환·참조 검사 유지                                                        | 긴 순환·동시 부모 변경의 국소 수단                                                                    |
| 시즌/패치의 번호·정렬·일시   | 업무 UNIQUE는 모든 속성의 불변 선언이 아님                                                                    | 실제 수정 범위와 필요한 종속 정렬 재계산/롤백                                                         |
| 아이템 자체의 소속 종류 변경 | 실제 게임 변경이면 아이템 버전에 당시 소속 ID 보존                                                            | 현재 종류 이름 수정과 아이템의 과거 소속 변경을 혼동하지 않음                                         |

PK guard의 값 비교는 OLD/NEW의 실제 차이로 검사하는 채택 계약을 따른다. 등급 이름/순서의 차이로 수정 목적을 판별하는 규칙을 추가하지 않는다.

#### 행 밖의 검사·미정 입력과 후속 검증

시즌 정렬식처럼 같은 행 안의 관계는 CHECK 후보지만, 패치 정렬식은 시즌 값을 읽으므로 단순 CHECK로 다른 표의 값을 지속 보장한다고 처리하지 않는다. 저장/계산 위치·번호 범위와 F4 갱신 계약을 먼저 확인한다. 날짜·이름·지역/무기 종류 대응·선택 관계·미확인 등록의 실제 사실 입력은 #45 보류 해제 뒤 확인하며 값을 가정하지 않는다.

| 미정                                                                   | 담당·필요 입력                                                                   | 결정 시점과 현재 제한                                                                                                         |
| ---------------------------------------------------------------------- | -------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| F3-R·F3-D의 일반 FK/검사 시점·공통 대상 삭제                           | 001이 후보 준비, 002·003·004와 대상/소유/이력 계약 대조. 사용자 삭제/재배치 의도 | 해당 FK/삭제 구현 전. 일반 FK 비지연·참조 중 RESTRICT는 채택. 구체 제약명/소유 관계를 맞추며 미참조 삭제는 자동 허용하지 않음 |
| F3-N 채택 핵심 NOT NULL/루트 NULL의 실제 배치·그 밖의 NULL/미확인 처리 | 001·002·004, 확정한 핵심 필수값/루트 의미와 실제 필드값·미확인 사례 #45          | 해당 DDL/등록 구현 전. 채택 핵심값을 재선택하지 않고 날짜/이름·그 밖의 NULL·보관/처리는 별도 확인                             |

| 등급 일반 변경·오입력 정정                  | 관리자가 원자료·수정 영향을 판단하고 기본 입력/DB 제약을 검사. 실제 자료 수정/근거는 #45 준비 뒤              |
| 자기 부모·긴 순환·동시 부모 변경            | 같은 행 제약과 그래프/경쟁 조건 검증을 구별. F4 수단 선택 전에는 동시성을 수용 판정하지 않음                  |

확정한 범위는 관련 Task 실행/검증 계획에 반영하고 다른 기존 계획·미정 표를 보존한다. 남은 guard/복합 검사·F4의 수단은 선택 뒤 검증을 구체화한다. 문서 검토이며 SQL·동시성·데이터 입력 검사를 실행한 결과가 아니다. 새 결정은 사용자 응답 전 확정하지 않고 실제 자료·DB 작업 보류를 유지한다.

**정렬 범위의 남은 선행 조건:** 기존 식에서 메이저 1·마이너 100과 메이저 2·마이너 0은 같은 시즌에서 같은 정렬값이 된다. 이는 실제 게임 번호가 아니라 수식의 설명용 입력이다. 번호 허용 범위를 확인하기 전 정렬값 UNIQUE나 `minor < 100` 같은 상한을 확정하지 않는다. 범위가 식의 충돌을 허용한다면 그 문제를 먼저 사용자에게 반환하며 ID나 임의 순번으로 덮지 않는다. 패치 정렬값에 의존하는 조회의 완전한 수용도 그 확인 전에는 판정하지 않는다.
