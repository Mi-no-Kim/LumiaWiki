# Task 43-001 — 업무 갱신·교정·동시성

<a id="current"></a>

Spring/DB/Python 분담과 업무 트랜잭션, 등급 관리자 수정, 필요한 국소 동시성을 검토할 때. 담당 상태·수용 판단은 [Task 43-001](../task-001.md#summary), 전체 길잡이는 [설계 안내](task-001-shared-version-references.md#summary)를 따른다. 아래 채택·비채택·미정을 구별하며 공통 8개 표의 구현·검증·로컬 적용은 [생성 결과](task-001-creation.md#current)를 따른다. 실제 자료 작업은 계속 보류한다.

현재 갱신 규칙은 [DB 갱신과 보호](<../../../../../docs/details/development/DB 갱신과 보호.md#current>)와 이 문서 상단 최소 계약을 따른다. 경로 비교는 선택 이유이며 비채택 공용 함수/추가 보호를 현재 구현 조건으로 확대하지 않는다.

## 변경·교정 최소 계약 — 관리자 판단과 기본 검사

지정 관리자가 원자료와 영향을 확인해 등급을 수정하고 코드는 기본 입력·DB 검사를 적용한다. 프로그램은 일반 변경과 오입력 교정을 별도의 허용·차단 기능으로 판별하지 않는다.

조회 중심 위키와 지정 관리자의 수동 입력/정정 범위에 맞춘 계약이다. 기존 M1~M3·키/FK/기본 검사·PK 보호·Spring/DB 분담을 유지하며 최초 구동은 B1과 B2/B3를 따른다. D1~D4와 공통 8개 표는 확정·구현·검증/적용했다. 정확한 실행 범위는 [생성 결과](task-001-creation.md#current)를 따르며 실제 자료 작업은 계속 보류한다.

### 반영한 최소 범위와 초기 필수에서 제외한 것

| 구분               | 현재 취급                                                                                                                                                                                                |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 업무 변경 단위     | 업무 변경 하나와 필요한 종속 값은 Spring 서비스 트랜잭션 하나로 처리. 실패한 업무를 부분 커밋/성공으로 표시하지 않음. SQL/행마다 나눠 커밋하는 방식을 기본으로 두지 않음                                 |
| 기본 정합성        | 이미 합의한 PK/FK/UNIQUE/NOT NULL/CHECK·PK 보호와 입력 검사 유지                                                                                                                                         |
| 종류 부모 변경     | 순환 검사와 갱신을 같은 업무 범위에서 처리. 동시성 보호도 실제 충돌이 문제가 되는 이 범위에 한정해 작은 안으로 검토                                                                                      |
| 등급 의미          | 지정 관리자가 원자료와 영향에 따라 수정 이유를 판단. 코드는 기본 입력·DB 검사 적용. 교정/변경 자동 판별·별도 교정 플래그/예외 경로 없음                                                                  |
| 초기 필수에서 제외 | 공통 자료 전체 advisory lock/고정 키, 모든 쓰기의 기대 원본 전수 비교·새 행 버전 열, 읽기 격리 수준의 일괄 강화, 교정 기록용 신규 DB 장부, 공통 SQL 30초·상세 멱등/재시도·결과 판정 체계를 도입하지 않음 |

### 필요한 동시성 범위

종류의 긴 순환/동시 부모 변경이라는 제품 불변식은 유지한다. 같은 트랜잭션에 검사/갱신을 넣는 것만으로 서로 다른 행의 동시 변경까지 안전하다고 주장하지 않는다. 실제 부모 변경을 구현할 때 해당 범위의 직렬화/잠금 등 작은 안을 비교하며 공통 6개 표 전체 쓰기 잠금이나 전역 격리 정책을 먼저 요구하지 않는다.

종류 부모 변경은 L-A의 item_category SHARE ROW EXCLUSIVE 잠금 뒤 최신 트리를 검사/수정한다. 여러 SQL 조회의 일관성은 해당 조회에서 검토하며 전역 advisory 잠금·고정 키·전체 격리 강화는 초기 범위에 두지 않는다. 구체 잠금 순서와 N4의 대기/실패는 [확정 갱신 계약](../../../../../db/model/writes-and-checks.md#catalog-locking)을 따른다.

### 등급 수정은 관리자가 판단한다

코드는 값의 전후 차이만 알 수 있고 그 이유가 입력 오류의 정정인지 실제 게임 변경인지는 알 수 없다. 지정 관리자가 원자료와 영향을 확인해 판단하고, 코드는 관리자 접근·필수값·허용 값·기존 참조/DB 제약을 검사한다. 교정 플래그의 진위를 검증하거나 일반 수정과 교정을 별도 진입점·권한·trigger로 구별하는 기능은 만들지 않는다.

| 상황                                | 현재 처리 원칙                                                                                                                            |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| 같은 등급 이름/순서의 오입력        | 관리자가 같은 등급 ID의 값을 수정하고 필요한 이유/근거를 기존 작업 기록에 남김. 새 게임 패치나 새 등급을 만들어 오류를 꾸미지 않음        |
| 개별 아이템의 등급이 실제로 변경    | 공유 등급 이름을 바꾸는 대신 002의 아이템 버전으로 소속 등급 변경을 보존                                                                  |
| 게임의 등급명/체계 자체가 실제 변경 | 관리자가 실제 변경임을 확인하고 과거 표시 영향·기존 이력 요구를 검토. 현재 선택만으로 과거 전체 덮어쓰기나 등급 버전 도입을 확정하지 않음 |

관리자 판단은 무조건 덮어써도 된다는 뜻이 아니다. 같은 등급을 참조하는 과거/현재 아이템에 미치는 영향을 확인하고, 실제 자료 수정은 #45의 허용 범위에서 진행한다. 별도 승인 단계·등급 전용 API/guard·신규 교정 DB 장부는 초기 구현 조건으로 추가하지 않는다. 실제 등급 목록·정렬·중복 허용은 D2로 남긴다.

### 실패·예외와 후속 확인

업무 트랜잭션 실패 시 해당 업무 변경을 롤백하고 미실행/실패를 성공으로 보고하지 않는 기본 경계를 유지한다. 시퀀스 소모/외부 응답까지 모두 되돌린다는 보장이나 상세한 자동 재시도·복구 시스템을 추가하지 않는다. 실제 오류/부분 반영이 관찰되면 허용 범위에서 상태를 확인하고 필요한 복구를 검토하는 기존 절차를 따른다.

서비스 밖 예외 쓰기는 기존 S1대로 대상/이유·검사·동시 변경 통제·실패/복구가 검토된 작업이어야 한다. FK RESTRICT·PK 보호를 우회하거나 미참조 행 삭제를 자동 허용한 것은 아니다. 추가 역할/권한·삭제/복원·새 API의 실제 선택은 해당 필요가 생길 때 다룬다.

후속 검증은 기존 001/004의 업무 저장/조회·중간 실패/롤백, FK/UNIQUE/필수값·PK 보호, 종류 순환/부모 변경과 등급 일반 변경/정정 사례에 연결한다. 철회한 전역 잠금·고정 키·공통 시간 제한·신규 교정 장부를 필수 테스트 대상으로 추가하지 않는다. 실제 동작 검증은 아직 하지 않았다.

담당은 001이 최소 업무 계약/필요한 국소 보호안을 준비하고 004가 결합 동작을 확인한다. 실제 자료의 근거/교정 기록·수단과 실행/복구는 #45 준비에서 다룬다. 후속 미정의 담당/입력/결정 시점을 유지하며 이 계약을 실제 자료 작업 재개나 부모 Issue 완료로 확대하지 않는다.

## F4 — Spring 중심 역할 분담의 채택과 후속 미정

Spring 중심 역할 분담과 공통 8개 표의 서비스/DB 수단은 확정/구현했다. #43의 일반 갱신은 Java/Spring을 기본 처리 경로로 둔다. Python에는 적합성이 확인된 개별 작업만 배정한다. 구체 역할을 미리 만들거나 별도 일반 DB 갱신 도구로 전제하지 않는다. 실제 자료 작업 보류는 유지한다.

| 담당          | 확정한 역할                                                  | 별도로 확인할 것                                                                     |
| ------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------ |
| Spring 서비스 | 업무 규칙·트랜잭션·갱신 순서·오류/응답 처리                  | 구체 업무 단위·API·일반 수정/교정 계약·잠금/격리·실패 처리                           |
| DB            | PK·UNIQUE·FK·NOT NULL 등 무결성 검사. F1~F3의 채택 정책 유지 | 추가 CHECK/복합 검사·고정 필드 보호·함수/trigger의 필요성과 권한 강제                |
| Python        | 적합성이 확인된 개별 작업만 선별 배정                        | 담당할 일·선택 이유·입출력·Spring/DB와의 연결·검증 방법을 먼저 제시하고 새 결정 확인 |

동일한 업무 규칙을 공용 DB 함수에 병렬 구현하는 방식을 기본으로 두지 않는다. 추가 DB 검사와 도구 간 연결은 위 역할을 기준으로 검토하며, Python의 직접 DB 갱신이나 서비스 호출 방식을 아직 선택하지 않았다. 구현 기준은 [갱신 역할 분담](<../../../../../docs/details/development/DB 갱신과 보호.md#update-role-boundary>)에 연결한다. 종류 이름/부모 변경과 등급 교정은 책임 구분의 사례이며, 실제 #45 자료 처리 파이프라인·도구 배정까지 결정한 것은 아니다.

아래는 **복합 갱신 규칙의 위치와 외부 도구 진입점**을 비교한 안이다. 현재 채택 기준은 위의 Spring 중심 역할 분담이며, 각 비교안에 포함된 Python의 직접 쓰기나 서비스 일괄 통합까지 함께 채택하지 않았다. 기본 PK/UNIQUE/FK/NOT NULL은 DB가 검사하고 추가 guard는 별도 확인한다.

| 트랜잭션의 책임  | Java/Python 호출자가 한 업무 작업의 범위를 열고 함수 호출들을 포함. 함수 안에서 중간 COMMIT하지 않는 후보 | 서버 서비스가 요청의 업무 단위를 묶음. 여러 API 호출을 한 DB 트랜잭션으로 자동 취급하지 않음 | 각 호출자가 DML 묶음을 열고 trigger는 그 변경에 참여. 제각각인 도구의 묶음 범위를 맞춰야 함   |
| 등급 교정의 구별 | 일반 수정과 구별한 교정 역할의 호출 계약 후보                                                             | 구별한 서비스 업무 동작/입력 계약 후보                                                       | 같은 UPDATE의 값 차이만으로 교정 목적을 알 수 없으므로 추가 교정/권한 계약 필요               |
| 기존 JPA와 연결  | JPA 조회를 유지할 수 있으며 함수 수정 뒤 재조회/이미 읽은 값의 일치도 검증                                | Java 업무 코드와 기존 서비스 구성을 함께 추적하기 쉬움                                       | 일반 저장 방식은 유지하기 쉽지만 trigger의 추가 동작과 오류를 같이 추적해야 함                |
| 주된 부담        | SQL 업무 로직·호출 계약을 함께 관리. 원시 DML 우회가 자동 차단되지는 않음                                 | 외부 도구의 서비스 의존·오류/일괄 요청 계약이 필요. 직접 DB 수정 가능성과 조정               | 직접 SQL의 유연성은 있으나 변경 시점·일괄 작업·동시성·교정 예외를 trigger와 함께 더 설계/검증 |

종류의 부모를 바꾸는 동일 작업을 예로 들면, A는 Java/Python이 같은 부모 변경 역할의 함수를 호출하고, B는 같은 서비스 업무 동작으로 요청하고, C는 두 도구가 UPDATE를 실행하면 지정한 시점에 DB trigger가 규칙을 검사하는 흐름이다. A에서도 Spring 서비스는 트랜잭션과 응답 구성을 맡는다. 어느 안이든 실제 SQL에 적용되는 F3의 비지연 FK를 커밋 지연 검사로 바꾸는 선택은 아니다.

### 현재 역할 분담의 이유와 비교안의 조건

일반 갱신의 기준은 Spring 서비스 중심·DB 무결성 검사·Python 선별 배정이다. 업무 흐름은 Spring에서 관리하고 DB 제약은 쓰기 경로와 관계없이 적용한다. Python은 적합성이 확인된 개별 작업만 담당한다. 성능 검증은 미수행이다.

**F4-A**는 독립 DB 갱신 도구들이 같은 SQL 업무 계약을 사용해야 할 때의 비교안으로 남긴다. Python의 독립 쓰기를 전제로 한 공용 함수 중심안을 현재 기본 경로로 적용하지 않는다.

**F4-B**는 모든 일반 쓰기를 Spring에 모으고 Python도 서비스의 소비자로 두려는 경우의 대안이다. 이미 있는 Java 서비스·오류/DTO 구조를 중심으로 규칙을 관리하기 쉽다. 필요한 등록/교정/일괄 서비스의 실제 경로와 요청 단위는 새 선택이며 지금 만들어진 API로 안내하지 않는다.

**F4-C**는 일반 테이블 DML을 여러 도구의 정상 갱신 방식으로 유지해야 하는 요구가 있을 때의 대안이다. 단순 행 검사에는 잘 맞을 수 있으나, 부모 관계의 순환과 여러 행·여러 트랜잭션 변경은 trigger가 있다는 사실만으로 해결되지 않는다. 교정 목적도 별도 계약이 필요하다. C를 택해도 일부 복합 동작이나 교정에 공용 함수가 필요한지 따로 비교할 수 있다.

### 함수·서비스·trigger의 실제 책임 경계

| ---------------- | ------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| DB 함수와 커밋   | A는 함수가 호출자의 트랜잭션에 참여하는 방식으로 제안. 호출자는 성공 시 커밋하고 실패 시 업무 단위를 롤백           | 트랜잭션 제어를 할 수 있는 procedure/CALL 방식까지 함께 채택하지 않음. 함수/호출자 인터페이스와 업무 묶음 크기는 미정                               |

| trigger의 실행   | 행마다 또는 SQL 문장마다 실행하는 형태가 달라 여러 행 변경의 검사 시점을 함께 설계                                  | 행/문장 trigger·실행 순서·고정 필드/교정 예외·권한을 아직 선택하지 않음                                                                             |

함수/프로시저의 트랜잭션 제어 차이는 [PostgreSQL 트랜잭션 관리](https://www.postgresql.org/docs/18/plpgsql-transactions.html), 함수 실행 권한의 기본 동작은 [CREATE FUNCTION](https://www.postgresql.org/docs/18/sql-createfunction.html)에 대조했다. Spring 서비스 경계와 기본 예외 롤백 범위는 [Spring Data JPA 트랜잭션](https://docs.spring.io/spring-data/jpa/reference/jpa/transactions.html)·[Spring 롤백 규칙](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/rolling-back.html), trigger 실행 단위는 [PostgreSQL CREATE TRIGGER](https://www.postgresql.org/docs/18/sql-createtrigger.html)를 따른다. 여기서 제안하는 역할 분담과 선호도는 해당 동작 및 프로젝트 조건에서 도출한 설계 판단이다.

서비스 밖 직접 SQL을 허용할 때는 그 경로에도 같은 참조·교정·동시성 조건이 성립해야 한다. Spring을 기본 처리 경로로 정한 사실만으로 실제 DB 권한 강제·관리/복원 예외까지 결정하지 않는다. 직접 DML 허용/차단과 추가 DB 검사 범위는 필요한 사례와 함께 별도로 확인받는다.

### 서비스 밖 직접 SQL과 추가 DB 검사 — 공통 수단 확정·개별 예외 확인

F4-S1-A·S2-A·S3-A는 세 확정했다. Spring 중심 역할 분담·Python 선별 배정과 F1~F3·K-D의 기존 합의를 유지한다. [개발 기준의 채택 범위](<../../../../../docs/details/development/DB 갱신과 보호.md#outside-service-sql>)에 반영하며 구현·권한 변경·자료/DB 작업의 허용으로 확대하지 않는다.

**범위:** 서비스 안의 JPA·직접 작성 SQL은 Spring의 업무 처리 경로에 포함한다. 여기서 서비스 밖 SQL은 DB 관리 도구·콘솔·별도 스크립트 등이 서비스의 업무 처리를 거치지 않고 실행하는 명령이다. 자료를 바꾸지 않는 조회와 INSERT/UPDATE/DELETE 등 쓰기를 구별한다. 변경 함수를 호출하는 조회문·COPY 등의 우회 형태도 실제 효과가 쓰기라면 같은 범위로 검토한다. 도구가 Python이라는 이유만으로 쓰기 권한이나 역할을 부여하지 않는다.

| 기존 합의                                                         | 확정 규칙·미정                                                                           |
| ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Spring이 업무 규칙·트랜잭션·갱신 순서, DB가 기본 무결성 검사 담당 | 서비스 밖 쓰기를 어떤 용도로 허용할지와 추가 DB 검사 수단                                |
| 종류는 부모 0~1개인 비순환 트리 모음, 확인된 루트 부모만 NULL     | 자기 부모 금지 DB CHECK는 S2 채택. 긴 순환/동시성·미확인 부모의 의미는 별도              |
| 내부 ID PK·ALWAYS와 지정 업무 UNIQUE                              | 기존 공통 행의 PK 값 일반 변경 금지는 S3 채택. 실제 보호·복원/UPDATE 수단은 별도         |
| 등급 이름/순서 수정의 관리자 판단·기본 검사                       | 등급 전용 보호 수단은 추가하지 않음. 실제 자료 수정과 필요한 근거는 #45                  |
| 일반 FK NOT DEFERRABLE·참조 중 DELETE RESTRICT·지정 NOT NULL      | 추가 CHECK·복합 FK·UPDATE 정책·권한을 자동 채택하지 않음                                 |
| 공용 SQL/Flyway 구조 변경 이력과 #45의 실제 자료 등록·교정 실행   | 임시 SQL로 스키마를 우회 변경하거나 일반 자료 교정 수단을 새로 정한 것으로 확대하지 않음 |

#### F4-S1 — 서비스 밖 쓰기의 허용 목적

| 후보                                              | 허용 범위·추천 이유                                                                                                                                                                                            | 부담·대안의 영향                                                                                                                                |
| ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| S1-결론: 조회와 검토된 예외 쓰기                  | 자료를 바꾸지 않는 조회를 허용하며, 일반 등록/수정은 Spring에서 수행. 서비스로 처리하기 어려운 교정·이관 등의 직접 쓰기는 대상·이유·필수 검사·동시 변경 통제·실패/복구를 사전에 검토한 작업 단위만 예외로 검토 | Spring의 업무 규칙을 기본으로 유지하면서 필요한 정비 가능성을 남김. 예외마다 영향·검증을 준비할 책임이 생김                                     |
| S1-B 비채택 비교: 조회만, 자료 쓰기는 모두 Spring | 조회 외 직접 자료 쓰기 예외를 두지 않고 교정도 합의한 Spring 업무 경로로 처리                                                                                                                                  | 일반 쓰기 경계가 단순. 일회성 정비에도 필요한 서비스 동작을 먼저 마련해야 함                                                                    |

서비스 밖 SQL은 조회와 개별 검토된 예외 쓰기를 허용한다(S1-A). 실제 SQL·대상 행·도구·교정 실행은 별도 범위 확인이 필요하다. 전체 복구·TRUNCATE/대량 제거·제약 해제·계정/권한·스키마 변경은 포괄 승인하지 않는다. 백업/구조 변경 기준과 #45의 자료 보류 조건을 따른다.

서비스의 업무 규칙을 거치지 않은 쓰기는 DB의 기본 제약이 통과해도 업무 정합성이 검증된 것이 아니다. 예외 작업의 경우 서비스가 맡던 영향 범위·과거 구성/원본·캐시 일치·교정 의미와 동시 변경 통제의 확인 방법이 필요하다. 관련 조건이 미정이면 그 쓰기를 실행·수용하지 않는다. 구체 잠금·격리·정비 중 쓰기 통제 방식은 아래 기존 후보와 연결하되 선택하지 않는다.

#### F4-S2 — 자기 부모 금지 DB CHECK 채택

종류의 자기 부모 참조는 DB CHECK로도 거부한다(S2-A). Spring은 업무 입력/오류를 처리하고 DB는 잘못된 행의 저장을 막는다. 서비스 검사만 사용하는 비교 대안은 DB 제약 수가 적지만 서비스 밖 쓰기의 별도 검증 부담이 크다.

확인된 루트의 부모 NULL과 다른 종류를 가리키는 정상 부모는 허용하고 자기 부모는 거부하는 기준이다. NULL이 미확인 부모인지 확인된 루트인지는 DB가 이 조건만으로 알아낼 수 없으므로 입력 계약을 유지한다. 자기 부모 CHECK와 FK만으로 A→B→C→A 같은 긴 순환이나 동시 A→B/B→A를 막았다고 판정하지 않는다. CHECK는 검사 행 밖의 자료에 의존하는 전체 그래프 정합성의 보장 수단으로 쓰지 않는다. [PostgreSQL CHECK·FK의 범위](https://www.postgresql.org/docs/18/ddl-constraints.html)

#### F4-S3 — 기존 공통 PK 값의 일반 변경 금지 정책 채택

기존 공통 행의 PK 값은 일반 UPDATE로 변경하지 않는다(S3-A). 식별값을 유지하고 이름·번호 같은 업무 값의 오입력은 해당 수정 계약으로 처리해 참조 영향을 좁힌다. 키 변경/참조 재배치는 별도 영향·실패 계약이 필요한 비교 대안이다. 후속 버전/연결 행의 키 배치는 담당 Task에서 결정한다.

PK는 유일성·NOT NULL의 역할이며 불변성까지 뜻하지 않는다. ALWAYS도 기존 행의 ID를 영구 고정하지 않는다. 예를 들어 identity 열에 DEFAULT를 대입하는 UPDATE는 시퀀스의 새 값을 사용하므로, 참조/중복 제약이 허용하는 경우 ID가 달라질 수 있다. [PostgreSQL PK](https://www.postgresql.org/docs/18/ddl-constraints.html#DDL-CONSTRAINTS-PRIMARY-KEYS) · [UPDATE의 DEFAULT](https://www.postgresql.org/docs/18/sql-update.html)

공통 PK의 일반 변경은 AFTER UPDATE 행 trigger의 실제 값 비교와 Spring 검사로 거부한다. 이름/대상·오류·함수 권한은 N/E/R을, 일반 FK의 ON UPDATE는 NO ACTION을 따른다. 실제 DDL/권한 적용·DB 검증은 [생성 결과](task-001-creation.md#verification)를 따르며 복원/시퀀스 보정은 필요 시점에 확인한다. 이름/부모와 같은 ID의 등급 교정은 PK 변경과 구별한다.

### 경로 선택과 별개로 남는 동시성 후보

L-A의 필요한 표/행 잠금과 최신 상태 재검사를 적용한다. 아래 SERIALIZABLE·재시도는 비교 대안이며 초기 채택안이 아니다. 실제 동시성 검증은 생성 승인 뒤 수행한다.

종류 부모 변경은 SHARE ROW EXCLUSIVE 표 잠금 뒤 검사/수정한다. 일반 SELECT를 막지 않지만 관련 쓰기는 대기할 수 있다. 필요한 업무와 고정 순서는 [L-A 계약](../../../../../db/model/writes-and-checks.md#catalog-locking)을 따르며 실제 DB 검증을 수행한 것으로 표시하지 않는다.

제안 순서는 `트랜잭션 시작 → 공통 구조 잠금 → 현재 조상 경로/참조·기대 상태 재검사 → 변경 → 성공 시 커밋, 실패 시 전체 롤백`이다. 읽은 뒤 나중에 잠그거나 바꾸는 두 단계를 허용하지 않는다. 대상 하나의 행 잠금만으로 서로 다른 두 종류의 동시 부모 변경이 안전하다고 가정하지 않는다. 격리 수준의 추천 후보는 READ COMMITTED와 잠금 획득 이후 시작하는 최신 조상 조회의 조합이다. 잠금을 기다리기 전 고정된 오래된 스냅샷을 검사에 재사용하지 않아야 하므로 함수/호출자 SQL의 스냅샷 경계도 동시성 검증 대상으로 둔다. 다른 격리 수준의 재시도/스냅샷 처리, 대기·타임아웃·일괄 변경/정정 경계는 별도 구현 전 선택으로 남긴다. [PostgreSQL 격리 수준](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-READ-COMMITTED)

이 쓰기 경계는 모든 종류 갱신 경로가 따라야 성립한다. 별도 직접 UPDATE를 허용한다면 같은 검사·직렬화가 강제되는 방식으로 재검토해야 하며 표 잠금 하나가 우회 쓰기까지 검증해 주지는 않는다. 단순 이름/계층 변경은 같은 종류 ID를 갱신하고 K-D대로 아이템·재료·스킬 연결을 새로 만들지 않는다. 등급 고정 필드와 시즌/패치의 번호·정렬 정정은 각 규칙에 따라 별도 검사하며 실제 정정 실행/복구는 #45의 범위를 유지한다.

현재 분류를 읽는 요청에서 이름·계층이 일관되도록 읽기 단위도 004와 대조한다. 캐시·비동기 이벤트·일괄 전파 도구를 후보로 추가하지 않는다. 함수/trigger 이름·입력/결과·예외 매핑과 API/직접 확인 경로는 구현 전에 별도 제시한다.
