# Task 43-001 — 공통 PK 보호

<a id="current"></a>

PK 불변 정책·trigger 본문·이름/오류/함수 권한·원자 설치를 구현할 때. 담당 상태·수용 판단은 [Task 43-001](../task-001.md#summary), 전체 길잡이는 [설계 안내](task-001-shared-version-references.md#summary)를 따른다. 아래 채택·비채택·미정을 구별하며 공통 구현·검증·적용 상태는 [생성 결과](task-001-creation.md#current)를 따르며 실제 자료 작업은 계속 보류한다.

현재 PK 보호는 [DB 갱신과 보호](<../../../../../docs/details/development/DB 갱신과 보호.md#pk-update-protection>)를 따른다. 아래는 확정 계약과 비교 대안이다. 복원/키 재배치 절차는 [필요 시점](task-001-pending.md#conditional-exceptions)에 확인한다.

## 실제 PK 보호 수단과 권한 경계 — P1 방식·P2 목표 채택

공통 PK의 일반 변경은 AFTER UPDATE 행 trigger와 Spring 서비스 검사로 거부한다(P1-A). 업무·조회·예외 정비·구조 변경의 권한 목적은 구분한다(P2-A). 공통 8개 표와 실제 역할/권한·trigger·SQL 적용/검증은 [생성 결과](task-001-creation.md#current)를 따른다.

### 확정 규칙과 후보

| 기존 합의·근거                                                                                  | 확정 범위·미정                                                                                         |
| ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |

### F4-P1 — 세 보호 수단의 비교

| 항목                  | DB trigger                                                 | 열별 UPDATE 권한                                                         | Spring 서비스 검사                                                         |
| --------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| 검사 기준             | OLD/NEW의 실제 PK 값 차이를 검사해 오류로 거부             | 해당 계정이 PK 열을 UPDATE 명령의 대상으로 삼을 수 없게 제한             | 요청/업무 동작에서 ID 변경을 받지 않거나 발견해 거부                       |
| 서비스 밖 쓰기        | trigger가 활성화된 일반 UPDATE에도 동일 검사               | 실제 유효 권한에 따라 같은 열 제한                                       | 해당 서비스 경로를 거친 경우에 적용. 직접 SQL의 보호 수단은 별도 필요      |
| 같은 PK 값 재대입     | 값이 같으면 PK 변경 오류를 내지 않는 후보                  | PK 열을 명령에 포함하면 같은 값이어도 권한 오류가 날 수 있음             | 실제 요청 계약과 수정 SQL 생성 방식을 맞춰야 함                            |
| ALWAYS의 DEFAULT 변경 | 실제 값이 달라지면 참조 유무와 무관하게 거부하는 후보      | PK 열 UPDATE 권한이 없으면 명령 단계에서 거부                            | 서비스 밖 SQL에는 적용되지 않음                                            |
| 권한 조건·한계        | 소유자/슈퍼유저의 정의 변경·해제까지 막는 보호 경계는 아님 | 테이블 전체 UPDATE·상속/다른 역할·PUBLIC 등 유효 권한을 함께 제한해야 함 | DB 권한을 줄이거나 다른 쓰기 도구를 통제한 것으로 볼 수 없음               |
| 관리 부담             | 검사 함수·대상 표·오류 매핑과 실제 실행 범위 검증          | 열 추가/변경 때 허용 열 목록·ORM/일괄 SQL·권한 상속을 함께 유지          | API/업무 오류를 표현하기 쉬움. DB 밖 경로를 추가하면 보장 범위를 다시 확인 |

**P1-A 확정: 일반 행 AFTER UPDATE trigger의 실제 값 비교 + Spring 서비스 검사.** Spring은 허용된 업무 속성만 갱신하고 입력 오류를 처리하며, DB는 S3의 PK 값 변경 금지를 검사하는 조합이다. 조회·정정·갱신 순서를 DB에 다시 구현하는 안은 아니다. 대안 P1-B는 열별 UPDATE 권한 + 서비스 검사, P1-C는 서비스 검사만 적용하는 방식이다. P1-B는 실제 권한 분리를 전제로 PK 열의 명령 사용을 좁히며, P1-C는 직접 SQL 예외의 별도 검증 부담이 가장 크다. P1-A는 채택했으며 P1-B·P1-C는 비채택 비교안이다. 열별 권한의 추가 적용 여부는 실제 권한 설계에서 별도 확인한다.

**Spring으로 가능한데 trigger를 추천한 이유:** PK 변경 금지는 Spring 서비스로 구현할 수 있다. 선택의 기준은 쓰기 경로다. 현재 S1은 검토된 서비스 밖 쓰기를 허용하므로 그 경로에서는 서비스 검사가 실행되지 않는다. 예를 들어 관리 도구가 참조 없는 공통 행의 ID를 DEFAULT로 바꾸면 Spring의 검사는 거치지 않으며, PK/ALWAYS만으로 영구 불변을 보장하지도 않는다. 좁은 PK 값 비교를 DB에 두면 trigger가 활성화된 일반 UPDATE에도 같은 제한을 적용할 수 있다.

모든 쓰기를 Spring으로 통일한다면 서비스 검사만 사용하는 대안도 가능하다. 직접 SQL 예외가 있으면 그 경로의 PK 불변 검증을 별도로 보장해야 한다. 현재 계약은 S1의 직접 쓰기 예외와 P1-A의 좁은 PK 보호다.

trigger에는 SQL 로직·오류 매핑·검증과 구조 관리 비용이 추가된다. 따라서 전체 업무 규칙을 옮기기보다 현재의 직접 쓰기 예외에서도 유지할 좁은 상태 조건에 한해 추천한다. 소유자/슈퍼유저의 해제 능력과 실제 역할 경계는 P2의 구체화 대상이며, trigger를 모든 권한에 대한 절대 보호로 설명하지 않는다.

보호 방식·이름/대상·오류·함수 권한·본문/초기 설치는 P1/N/E/R/F/I를 따른다. 실제 마이그레이션 배치·요청/예외 연결·역할별 권한 적용은 구현 전에 확인한다.

| 세부 후보                                       | 추천 이유·보장 범위                                                                                      | 유보·대안                                                                                               |
| ----------------------------------------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| 일반 AFTER UPDATE, 행마다 실제 이전/새 PK 비교  | UPDATE와 BEFORE trigger 처리 뒤의 값을 비교해 변경이면 오류. 값이 같은 갱신과 정상 업무 속성 수정은 유지 | BEFORE 검사도 가능하지만 이후 다른 BEFORE trigger의 값 변경까지 보장하려면 순서/범위를 추가 관리해야 함 |
| UPDATE 전체를 대상으로 두고 실제 값 차이로 판정 | 명령의 SET 목록에 PK가 있는지만 검사하지 않고, 다른 BEFORE trigger에서 값이 바뀌는 사례도 검증           | UPDATE OF PK만으로 실행 여부를 정하는 대안은 SET 목록 밖 값 변경을 놓칠 수 있어 기본 추천에서 제외      |
| 변경 시 명시적 오류                             | PK를 원래 값으로 조용히 되돌리거나 행을 건너뛰어 성공처럼 처리하지 않음                                  | 실제 오류 식별·서비스 매핑은 구현 전 별도 확인                                                          |
| 커밋까지 지연하지 않는 일반 trigger             | 해당 SQL의 오류로 드러내는 후보. 일반 FK의 기존 비지연 기준도 유지                                       | 지연 가능한 constraint trigger를 함께 선택하지 않음. 업무 단위/예외 catch·롤백 계약은 별도              |
| PK 값 비교에 필요한 범위만 수행                 | 다른 표 조회나 권한 상승을 필요로 하지 않는 검사 후보                                                    | SECURITY DEFINER·추가 권한을 자동 도입하지 않음. 실제 함수 실행/소유 권한은 P2 구체화 때 확인           |

AFTER trigger가 보는 변경과 UPDATE OF의 실행 조건은 [PostgreSQL CREATE TRIGGER](https://www.postgresql.org/docs/18/sql-createtrigger.html)·[변경의 가시성](https://www.postgresql.org/docs/18/trigger-datachanges.html)에 대조했다. trigger의 오류는 해당 SQL과 trigger 변경을 같은 트랜잭션에서 되돌리지만, 전체 Spring 업무 단위의 롤백은 별도 예외/트랜잭션 계약으로 확인한다. [trigger 실행](https://www.postgresql.org/docs/18/trigger-definition.html)

열별 권한은 실제 PK 값 비교와 의미가 다르다. 권한은 특정 열을 수정 대상으로 사용할 수 있는지를 정한다. 테이블 전체 UPDATE 권한을 유지한 채 PK 열의 권한만 회수하는 것으로는 차단되지 않는다. 직접 부여·상속·PUBLIC·소유자 권한을 합쳐 검사해야 한다. [PostgreSQL GRANT](https://www.postgresql.org/docs/18/sql-grant.html)

### F4-P2 — 권한 목적의 경계

**P2-A 확정: 아래 네 목적의 권한 경계를 목표로 두고 실제 역할/계정과 적용 시점은 따로 확인.** P2-B의 권한 구조 선택 유보는 비채택 비교안이다. 채택 이유는 일상 갱신/조회와 구조 변경의 능력을 구별하려는 것이다. 이는 네 개의 로그인 계정이나 특정 역할 이름을 지금 만드는 결정이 아니다. [개발 기준의 목표 경계](<../../../../../docs/details/development/DB 갱신과 보호.md#db-privilege-boundary>)에 연결한다.

| 권한 목적(목표 채택) | 허용할 능력·용도                             | 일반 용도로 부여하지 않을 능력·남은 확인                                                                                                |
| -------------------- | -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| Spring 업무 처리     | 승인한 표의 필요한 조회·등록·업무 속성 갱신  | 소유권·슈퍼유저·구조/trigger 변경·TRUNCATE는 업무 권한으로 두지 않는 목표. DELETE·추가 함수 실행 등은 해당 정책/계약에 따라 별도 결정   |
| 조회                 | 자료를 바꾸지 않는 합의한 조회               | 쓰기/구조 변경과 자료를 바꾸는 함수의 간접 권한까지 함께 확인                                                                           |
| 예외 정비            | S1의 개별 계획에서 합의한 대상·목적의 쓰기   | PK 보호 해제·소유권·구조 변경을 정비 권한에 자동 포함하지 않음. 같은 PK의 오입력 교정과 참조/캐시·실패 계약은 #45와 대조                |
| 구조 변경/Flyway     | 승인한 공용 SQL 이력과 보호 장치의 정의 관리 | 강한 권한을 일상 앱/조회/정비가 상속하거나 SET ROLE로 얻는 경계를 검토. 구조 변경 능력이 있는 주체까지 trigger로 막았다고 보장하지 않음 |

확정한 목표는 최소한의 능력을 목적별로 구별한다. 소유자는 정의 변경 능력과 권한 재부여 능력을 가지므로 일반 역할의 열별 권한 제한과 같은 수준으로 취급하지 않는다. [PostgreSQL 권한·소유자](https://www.postgresql.org/docs/18/ddl-priv.html)

공용 개발 계정으로 trigger 동작을 확인하는 것과 비소유 업무 계정의 구조 변경 차단을 검증하는 것은 다르다. 목적별 권한의 실제 수용에는 역할 분리·상속/소유권·적용 시점에 맞는 검증이 필요하다.

또한 앱과 같은 DB 계정으로 실행한 직접 SQL을 DB가 Spring 요청과 구별해 주는 것은 아니다. P2는 계정의 능력 경계에 관한 채택 목표이며, S1의 서비스 경로/예외 계획과 업무 규칙은 계속 필요하다. Python은 적합한 개별 역할을 승인받은 뒤 필요한 연결/능력을 검토하며 지금 일반 쓰기 권한을 배정하지 않는다.

| ------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 일반 업무 속성 갱신·PK에 같은 값 재대입                             | S3의 실제 PK 값 변경 금지와 수단별 열 권한의 차이를 확인. 정상 종류명/부모 대상 변경·같은 ID의 교정은 해당 계약 유지                |
| 참조 없는 행의 PK DEFAULT 변경·참조 있는 행의 변경                  | PK 보호/참조 검사 중 실제 거부 위치와 선택한 오류 매핑을 확인. 참조 없는 행도 S3대로 거부하며 ID의 빈틈 없는 연속성을 요구하지 않음 |
| SET 목록에 PK 없음·다른 BEFORE trigger가 PK 값을 바꾸는 검사 입력   | P1-A가 최종 값 변경도 거부하는지 확인. 이는 향후 격리 검증용 사례이며 제품에 다른 trigger를 추가하는 결정이 아님                    |
| 여러 행 갱신·중간 오류·서비스 catch/롤백                            | 해당 SQL의 부분 반영과 별도 업무 단위의 롤백/오류 계약을 구별해 확인                                                                |
| 서비스 밖 예외 쓰기·열별 권한·상속/PUBLIC의 더 넓은 권한            | 선택한 보호 수단과 실제 유효 권한으로 보장 범위를 확인. DB 연결 성공이나 역할 이름만으로 권한 검증을 통과시키지 않음                |
| 업무/조회/정비의 구조·trigger 변경 시도, 구조 관리 주체의 수행 범위 | 선택한 실제 권한 아래에서 허용/거부를 확인. 소유자/슈퍼유저까지 불변 보장을 확대한 것으로 판정하지 않음                             |
| 명시 ID 복원 INSERT·삭제/재등록·TRUNCATE                            | 일반 UPDATE 보호와 구별하고 별도 계약/권한·보류 조건을 확인. PK guard 하나로 이 경로까지 전부 차단됐다고 주장하지 않음              |

P1/P2·N/E/R·F/I·O/C/T의 보호·오류·본문/설치·소유/접속 계약을 따른다. 구체 GRANT·최초 준비/기존 이관·정비 우회와 실제 적용은 해당 범위에서 확인한다. 실제 SQL·DB/API·권한·자료/복원·동시성 검증은 미수행이다.

## P1의 이름·대상·오류·함수 권한 — 계약 채택·실제 적용 미수행

함수/trigger 이름·대상·오류·함수 권한은 아래 확정 계약과 [현재 기준](<../../../../../docs/details/development/DB 갱신과 보호.md#pk-guard-contract>)을 따른다. 실제 DB 배치·설치/검증은 [생성 결과](task-001-creation.md#current), 실제 자료 작업은 보류다.

### 기존 합의와 확인한 현재 기반

| 유지할 합의·확인한 기반                                                                   | 확정 범위                                                                                        |
| ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 기존 공통 행의 실제 PK 값 변경을 일반 AFTER UPDATE 행 trigger + Spring 검사로 오류 거부   | 함수/trigger·스키마 이름, 대상 표/PK 열, 오류 식별과 함수 권한                                   |
| 같은 PK 값 재대입·정상 속성 수정은 PK 변경 오류로 거부하지 않음                           | 비교는 실제 이전/새 값 기준. 전체 UPDATE의 행 검사라는 기존 의미 유지                            |
| Task 43-001의 공통 대상은 시즌·패치·지역·종류·등급·별도 무기 종류                         | 해당 대상의 물리 표/열 명칭을 제안. 지역의 시즌 연결·분류 대응·다른 열/제약은 함께 확정하지 않음 |
| 내부 ID 단일 PK·ALWAYS, 일반 FK·NOT NULL과 S1~S3 유지                                     | PK 외 필드·참조 열·정렬값을 이 trigger로 고정하지 않음                                           |
| P2 목적별 권한 목표, 현재 로컬 앱/Flyway 공용 계정                                        | 함수의 소유/실행·설치 권한 계약을 비교. 실제 역할/계정·상속/분리 적용 시점은 별도                |
| 현재 backend에는 공통 API/개발용 기반만 있고 공통 자료 표·guard·업무 갱신 API 구현은 없음 | 아래 후보를 기존 API/표의 실제 주소나 실행 성공으로 설명하지 않음                                |
| 기존 입력 거부는 400 API_INPUT_INVALID, 예상 밖 실패는 500 API_INTERNAL_ERROR             | DB 오류 식별과 요청 원인에 따른 매핑을 구별. 새 공개 API 오류를 자동 추가하지 않음               |

오류 기반은 [ApiFailure](../../../../../backend/src/main/java/io/github/minokim/lumiawiki/common/api/ApiFailure.java)·[ApiExceptionAdvice](../../../../../backend/src/main/java/io/github/minokim/lumiawiki/common/api/ApiExceptionAdvice.java)와 [공통 HTTP/오류 기준](../../../../../docs/details/development/기술 구성.md)에 대조했다. 현재 예상 밖 오류 처리는 내부 메시지·원인·요청값을 응답/로그에 그대로 내보내지 않는 구성을 사용한다. 원인 체인을 내부에서 식별하더라도 그 내용을 노출하도록 바꾸는 결정은 하지 않는다.

### P1-N — 함수·trigger와 대상 이름

**N-A 확정:** `public.reject_common_pk_update()` 공용 함수 한 개를 사용하고, 각 표에는 `trg_<table>_reject_pk_update`를 붙인다. 아래 여섯 표의 공통 PK 열은 `id`다. 함수는 인자 없는 trigger용 함수로 해당 행의 이전/새 `id`만 검사한다. 다른 표 조회·동적 SQL·대상 표 자동 검색을 기본으로 추가하지 않는다.

| 공통 대상      | 표/PK 열 계약             | AFTER UPDATE 행 trigger 이름 계약    |
| -------------- | ------------------------- | ------------------------------------ |
| 시즌           | `public.season.id`        | `trg_season_reject_pk_update`        |
| 게임 패치      | `public.game_patch.id`    | `trg_game_patch_reject_pk_update`    |
| 지역           | `public.region.id`        | `trg_region_reject_pk_update`        |
| 아이템 종류    | `public.item_category.id` | `trg_item_category_reject_pk_update` |
| 아이템 등급    | `public.item_grade.id`    | `trg_item_grade_reject_pk_update`    |
| 별도 무기 종류 | `public.weapon_type.id`   | `trg_weapon_type_reject_pk_update`   |

보호 범위는 위 여섯 대상의 내부 PK다. 종류 parent_id·아이템 종류 참조·업무 번호/정렬값은 보호 대상 PK와 구별한다. 지역의 시즌/이력 배치와 무기 종류 대응 등 나머지 관계는 담당 미정이며 보호를 모든 표/필드로 자동 확대하지 않는다.

| 대안                                  | 이유·부담                                                                                                                                                   |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| N-결론: 공용 함수 하나 + 표별 trigger | 같은 PK 열/규칙을 한 곳에서 유지하고 trigger 이름으로 설치 대상을 확인하기 쉬움. 각 대상에 `id` PK가 실제로 존재하는지 검증 필요                            |
| N-B 비채택 비교: 표별 함수            | 예를 들어 `public.reject_season_pk_update()`처럼 각 표의 다른 PK 표현에 맞추기 쉬움. 현재 같은 규칙을 여섯 함수에 반복 관리하게 됨                          |
| 별도 함수 스키마                      | 구조/권한을 별도 공간에 모을 수 있지만 새 스키마·탐색/설치 권한과 소유 정책을 추가 설계해야 함. 필요성 선택 전 `app_private` 등의 새 스키마를 도입하지 않음 |

`public`·여섯 표의 `id`·공용 함수명·표별 trigger명은 N-A의 채택 계약이다. 표별 함수·별도 함수 스키마는 비채택 비교안이다. 실제 표의 나머지 DDL이나 기존 DB의 이름 충돌 여부까지 수용한 것은 아니다. 구현 전 확정한 배치와 함수가 읽는 열을 대조하고 이름/형식이 다른 표에 그대로 붙이지 않는다.

### P1-E — DB 오류 식별과 Spring 응답

**E-A 확정:** 이 guard가 실제로 오류를 내는 경우 전용 SQLSTATE `LW001`을 사용한다. 이는 PostgreSQL 표준 코드가 아닌 애플리케이션 전용 계약이며 DB 메시지는 값/SQL을 포함하지 않는 고정 문구 `Common primary key cannot be changed.`다. 문구를 파싱해 오류를 판별하지 않는다.

| 발생 단계                                                      | 채택 매핑 계약                    | 이유·한계                                                                                                                      |
| -------------------------------------------------------------- | --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| PK guard가 실제 값 변경을 발견                                 | SQLSTATE `LW001` + 고정 DB 메시지 | 다른 CHECK·FK·일반 RAISE와 구분할 수 있는 기계 식별자. 원래/새 ID 값을 메시지에 넣지 않음                                      |
| Spring이 요청 계약에서 식별자 변경 시도를 명시적으로 확인      | 기존 400 `API_INPUT_INVALID`      | 현재 잘못된 입력 분류를 재사용. 실제 입력 필드·DTO·수정 API는 해당 계약에서 확인하며 존재하지 않는 ID 수정 API를 만들지 않음   |
| 서비스 검사를 지나 저장/flush/커밋에서 예상 밖 guard 오류 발생 | 기존 500 `API_INTERNAL_ERROR`     | 요청 잘못임이 입증되지 않은 DB 실패를 사용자 오류로 일괄 전환하지 않음. 원본 예외를 ApiFailure의 안전한 메시지로 포장하지 않음 |
| 관리 도구의 직접 SQL                                           | DB의 SQLSTATE/고정 메시지         | HTTP 응답으로 꾸미지 않음. 실제 예외 작업은 S1 계획·권한·보류 조건을 따름                                                      |

기본 RAISE 오류는 `P0001`이므로 다른 사용자 정의 실패와 같은 값이 될 수 있다. PostgreSQL은 `00000`을 제외한 다섯 자리 숫자/대문자 SQLSTATE를 별도로 지정할 수 있으므로 `LW001`은 E-A의 문법상 유효한 전용 코드다. [PostgreSQL RAISE와 오류 코드](https://www.postgresql.org/docs/18/plpgsql-errors-and-messages.html)

`LW001`은 **이 guard가 실행되어 거부했음을 식별하는 코드**다. FK·중복·NOT NULL 등의 검사가 먼저 거부하면 다른 코드가 나올 수 있다. PK 변경 시도라는 이유만으로 모든 실패가 항상 `LW001`이라고 가정하거나 다른 무결성 오류를 PK 오류로 매핑하지 않는다. 원인 식별이 필요한 처리/검증은 SQLSTATE와 JDBC 원인/연결 예외를 확인하는 계약으로 구체화하며, 한 종류의 Spring/Hibernate 바깥 예외 클래스나 영문 메시지에만 의존하지 않는다.

| 대안                                                                                 | 매핑·영향                                                                                                                                                             |
| ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| E-결론: 전용 `LW001` + 서비스 입력 400/예상 밖 DB 500                                | DB 구분은 명확하게 하고 기존 공개 오류 형식/코드를 유지. 실제 요청 원인의 확인이 필요                                                                                 |
| E-B 비채택 비교: `23514` 등 범용 무결성 코드 + 추가 guard 식별 계약                  | 기존 CHECK 오류 분류와 연결하기 쉬우나 자기 부모 CHECK 등과 구별할 식별자를 더 설계해야 함. 코드만 보고 모두 PK 오류로 처리할 수 없음                                 |
| E-C 비채택 비교: 전용 `LW001`의 DB 거부도 409와 새 `API_IDENTIFIER_IMMUTABLE`로 응답 | 불변 거부를 항상 업무 충돌로 노출하는 새 계약. 실제로 서버 갱신 로직이 잘못된 경우까지 사용자 오류로 보일 수 있고 새 API 코드/소비자 계약이 필요해 현재 추천하지 않음 |

E-A에는 SQLSTATE·SQL·표/열·ID·내부 예외를 HTTP 응답에 추가하거나 현재 안전한 로그 정책을 확대하는 선택을 포함하지 않는다. 필요하다면 안전한 진단 필드를 별도 검토한다. 기존 ProblemDetail의 `code`·`requestId`·합의한 입력 오류 형식과 정상 자료/트랜잭션의 보존 조건은 유지한다.

### P1-R — 함수의 실행·정의 권한

함수는 SECURITY INVOKER이고 소유/정의·trigger 설치는 구조 변경 주체가 담당한다. 새 함수의 PUBLIC EXECUTE는 회수하며 일반 업무/조회/정비에는 정의 변경·trigger 설치/해제 능력을 부여하지 않는다. 일반 DML 역할에 직접 함수 EXECUTE도 미리 추가하지 않는다. 실제 소유/설치·업무 역할은 [O-A·C-A·T-A](task-001-bootstrap-contract.md#f4-pk-role-binding)를 따르고 구체 GRANT/기존 이관은 별도 확인한다.

| 확정한 함수 권한 계약                                                                 | 추천 이유·남은 확인                                                                                                           |
| ------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `SECURITY INVOKER`                                                                    | 호출 주체의 권한으로 실행. 이전/새 행 값 비교만 하므로 소유자 권한 상승을 도입할 이유가 없음                                  |
| 함수의 탐색 경로는 `pg_catalog`로 고정                                                | 사용자 행의 PK 비교와 시스템 기능만 필요한 계약에 맞춤. 다른 표/함수를 읽도록 범위를 넓히면 별도 재검토                       |
| 소유·CREATE/REPLACE·설치/해제는 구조 관리 주체                                        | 실제 소유자 역할과 Flyway 실행 주체의 연결·스키마 권한·상속은 P2의 구체 역할 설계에서 확인                                    |
| 새 함수의 `PUBLIC EXECUTE` 회수, 설치 주체에 필요한 함수 EXECUTE·대상 표 TRIGGER 보유 | 불필요한 기본 공개 권한을 줄이며 설치에 필요한 능력을 구별. 기존 다른 함수 전체 권한을 일괄 회수하는 안은 아님                |
| 일반 업무/정비는 승인한 표의 DML 능력으로 동작                                        | 함수 EXECUTE와 UPDATE/정의 변경 권한을 같은 것으로 취급하지 않음. 직접 SQL도 활성 guard를 거치며 실제 부여 범위는 역할별 확인 |

함수의 기본 실행 권한은 호출자 기준이고 새 함수에는 기본 `PUBLIC EXECUTE`가 부여된다. [PostgreSQL CREATE FUNCTION](https://www.postgresql.org/docs/18/sql-createfunction.html) trigger 생성/교체에는 대상 표의 TRIGGER와 함수 EXECUTE가 필요하다. [CREATE TRIGGER](https://www.postgresql.org/docs/18/sql-createtrigger.html)

PostgreSQL 18 소스에서는 생성 경로의 `ACL_EXECUTE` 검사와 실행 경로 `ExecCallTriggerFunc`를 구별해 확인했다. 실행 경로에서 같은 EXECUTE 검사를 다시 하지 않는 구현을 근거로, 일반 DML 역할에 직접 함수 EXECUTE를 미리 부여하지 않는 계약을 도출했고 확정으로 기록했다. 이는 소스에 근거한 설계 판단이며 **권한 검증을 실행한 결과는 아니다.** 실제 적용 전 비소유자 역할의 UPDATE가 guard를 실행하는지 격리 검증한다. [PostgreSQL 18 trigger 구현](https://raw.githubusercontent.com/postgres/postgres/REL_18_STABLE/src/backend/commands/trigger.c)

R-B는 비채택 비교안으로 INVOKER·PUBLIC 회수를 유지하면서 업무/정비 역할에도 해당 함수 EXECUTE를 명시적으로 부여하는 대안이다. 권한 목록을 직접 드러내지만 현재 값 비교 동작에 필요하지 않은 범위를 늘린다. 함수 권한 선택을 역할 설계까지 유보하는 비교안도 비채택이다. 소유/설치·업무 역할과 적용 시점은 후속 O-A·C-A·T-A를 따르며 구체 권한/준비/기존 이관·실행은 별도다. `SECURITY DEFINER`는 현재 검사에 추가 접근 능력이 필요하지 않고 권한/탐색 경로 검토 부담이 늘어 기본 추천에서 제외한다.

R-A 계약을 채택했지만 현재 공용 개발 계정을 변경하거나 계정·역할·GRANT를 실행하지 않는다. 소유자/슈퍼유저의 정의 변경까지 PK guard가 막는다고 보장하지 않으며 역할 상속·간접 권한·분리 시점과 실제 검증은 별도다. 권한 검증 결과가 계약의 가정과 다르면 추가 능력을 임의 부여하지 않고 필요한 변경을 다시 제시한다.

### P1-F — 비교를 공용 함수 안에 두는 본문

**F-A 확정:** PL/pgSQL 함수 안에서 `OLD.id IS DISTINCT FROM NEW.id`를 비교하고 변경 때만 기존 오류를 낸다. 정상 경로는 `RETURN NEW`로 마친다. 각 trigger에는 WHEN을 반복하지 않는다. 같은 값 재대입·정상 속성 수정은 통과하고 실제 값 변경은 거부하는 기존 의미를 한 함수에 유지하는 채택 설계다.

아래 정의문은 확정한 F-A 본문과 I-A 최초 CREATE 형식을 표현했다. 실제 실행 파일·표 DDL·버전/역할 배치는 별도로 확인한다.

```sql
-- 채택한 문서 설계: 구현 SQL 파일이 아니며 실행하지 않음.
CREATE FUNCTION public.reject_common_pk_update()
RETURNS trigger
LANGUAGE plpgsql
SECURITY INVOKER
SET search_path = pg_catalog
AS $pk_guard$
BEGIN
    IF OLD.id IS DISTINCT FROM NEW.id THEN
        RAISE EXCEPTION USING
            ERRCODE = 'LW001',
            MESSAGE = 'Common primary key cannot be changed.';
    END IF;

    RETURN NEW;
END;
$pk_guard$;

REVOKE EXECUTE
ON FUNCTION public.reject_common_pk_update()
FROM PUBLIC;
```

이 코드에는 다른 표 조회·동적 SQL·트랜잭션 제어·행 수정·무시/자동 교정 경로가 없다. 정확한 표/열과 AFTER UPDATE 행 호출은 설치 DDL·검증에서 맞춘다. 별도 이벤트 검사나 새 오설치 오류 코드를 함수에 추가하는 선택도 하지 않았다.

| 대안                                                    | 장점·부담                                                                                                                     |
| ------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| F-결론: 함수 안에서 비교, WHEN 없음                     | 비교 규칙을 한 곳에서 유지하고 설치문에 WHEN을 빠뜨려도 정상 UPDATE를 무조건 오류로 만들지 않음. 매 UPDATE 행에서 함수를 호출 |
| F-B 비채택 비교: 표별 WHEN에서 비교, 함수는 오류만 발생 | 값 변경 행만 함수에 진입. 여섯 설치문에 비교 조건을 유지해야 하며 WHEN 누락/변경 때 정상 갱신의 거부 가능성까지 검증 필요     |
| F-C 비채택 비교: WHEN과 함수 양쪽에서 비교              | 함수 진입을 줄이면서 본문 방어도 유지. 같은 조건을 두 위치에서 관리하는 부담이 있어 현재 측정 없이 기본으로 추가하지 않음     |

`IS DISTINCT FROM`은 NULL도 비교 가능한 값으로 다루며, 정상 NOT NULL PK에서는 일반 부등 비교와 같은 변경 판정을 한다. 이 구문으로 NOT NULL 정책을 바꾸지 않는다. [PostgreSQL 비교 연산](https://www.postgresql.org/docs/18/functions-comparison.html) AFTER 행 trigger의 반환값은 무시되므로 `RETURN NULL`도 가능한 대안이다. 확정한 `RETURN NEW`는 값을 고쳐 저장하려는 것이 아니라 정상 종료를 나타내는 본문 표현이며 거부는 RAISE로 수행한다. [PL/pgSQL trigger 반환](https://www.postgresql.org/docs/18/plpgsql-trigger.html)

### P1-I — 초기 설치 단위·순서·충돌 처리

**I-A 확정:** 최초 공용 함수 생성과 PUBLIC 회수를 같은 마이그레이션 트랜잭션에 두고, 각 보호 표의 생성과 그 표의 trigger 부착도 같은 마이그레이션 트랜잭션에 둔다. 공용 함수는 첫 trigger보다 먼저 한 번 생성한다. 같은 파일/트랜잭션에서 여러 표를 함께 만들 수 있으며, 한 표당 한 파일을 강제하지 않는다.

1. O-A의 소유/설치 주체 lumia_migrator와 T-A의 최초 P1 설치 전 분리를 따른다. 구체 권한·전체 표 DDL·마이그레이션 배치·최초 준비/기존 이관은 먼저 확인해야 한다. 문서 SQL에 미승인 OWNER/GRANT/SET ROLE 문을 추가하지 않는다.
2. 공용 함수의 최초 CREATE와 PUBLIC EXECUTE 회수를 같은 설치 단위에서 수행한다. 구조 변경 주체가 함수 소유/설치 능력을 갖는 전제이며 실제 역할 연결은 별도 확인한다.
3. 보호 표의 승인된 CREATE TABLE 뒤, 해당 표/키 계약을 대조하고 같은 설치 단위에 아래 해당 CREATE TRIGGER를 둔다. 코드 모음의 나열 순서로 전체 표의 생성 의존 순서를 정하지 않는다.
4. Flyway가 관리하는 트랜잭션 안에 배치하고 SQL 파일 안에 별도 BEGIN/COMMIT을 추가하지 않는다. 이 계획에 맞는 유효한 트랜잭션 설정·원자성은 격리 검증으로 확인한다. group/mixed/비트랜잭션 실행 같은 새 설정을 추가하지 않는다.

아래는 배치할 여섯 정적 설치문을 모은 설계안이다. 표의 전체 DDL·역할 설정을 생략한 문장 모음이며, 지금 실행할 수 있는 완결된 마이그레이션 파일로 제공하지 않는다. 확정한 F-A대로 WHEN과 UPDATE OF를 넣지 않았고 실제 AFTER UPDATE 행 비교를 유지한다.

```sql
-- 채택한 문서 설계: 각 문장은 해당 표 생성과 같은 설치 단위에 배치.
CREATE TRIGGER trg_season_reject_pk_update
AFTER UPDATE ON public.season
FOR EACH ROW
EXECUTE FUNCTION public.reject_common_pk_update();

CREATE TRIGGER trg_game_patch_reject_pk_update
AFTER UPDATE ON public.game_patch
FOR EACH ROW
EXECUTE FUNCTION public.reject_common_pk_update();

CREATE TRIGGER trg_region_reject_pk_update
AFTER UPDATE ON public.region
FOR EACH ROW
EXECUTE FUNCTION public.reject_common_pk_update();

CREATE TRIGGER trg_item_category_reject_pk_update
AFTER UPDATE ON public.item_category
FOR EACH ROW
EXECUTE FUNCTION public.reject_common_pk_update();

CREATE TRIGGER trg_item_grade_reject_pk_update
AFTER UPDATE ON public.item_grade
FOR EACH ROW
EXECUTE FUNCTION public.reject_common_pk_update();

CREATE TRIGGER trg_weapon_type_reject_pk_update
AFTER UPDATE ON public.weapon_type
FOR EACH ROW
EXECUTE FUNCTION public.reject_common_pk_update();
```

초기안은 새 일반 표를 승인한 CREATE TABLE로 만드는 경로를 전제로 한다. `id`의 BIGINT·ALWAYS·단일 PK·NOT NULL과 여섯 대상의 실제 배치를 표 DDL 및 격리 검증에서 확인한다. 함수가 일반 record를 받는다는 이유로 trigger 생성만 성공하면 PK 열/형식도 검증됐다고 보지 않는다. 별도 catalog 검사 DO 블록이나 검사 helper 함수를 설치 DDL에 추가하는 안은 현재 제안에 포함하지 않고, 위 조건을 테스트/수용 확인에 연결한다.

실제 기존 표·다른 형태의 객체·분할 표를 대상으로 해야 한다면 이 신규 일반 표 초기안을 그대로 적용하지 않고 배치/검증을 다시 제시한다. 이름 충돌은 plain CREATE에서 드러내고 자동 교체·DROP·IF EXISTS/IF NOT EXISTS로 건너뛰지 않는다. 반복 적용 여부는 Flyway 이력으로 관리하고 수동 SQL을 임의 재실행해 상태를 맞추는 안을 추가하지 않는다.

| -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| I-결론: 함수/회수 원자 설치, 표/자기 trigger 원자 설치, 충돌 시 중단 | 새 표가 보호 없이 커밋되는 구간을 피하고 미확인 동명 정의를 덮지 않음. 실제 표 DDL과 함수 선행 의존·트랜잭션 확인 필요                            |
| I-B 비채택 비교: 여섯 표가 만들어진 뒤 guard 전용 마이그레이션       | 보호 설치를 한 곳에 모으기 쉬움. 그 전에 커밋된 표의 쓰기를 어떻게 통제할지와 기존 표의 실제 형상 확인이 추가로 필요                              |
| 기존 정의를 OR REPLACE·DROP/재생성으로 맞추는 초기안                 | 재실행 편의는 있지만 동명 객체의 예상 밖 정의/소유·설정 차이를 숨길 수 있어 첫 설치 기본으로 추천하지 않음. 필요하면 별도 변경/복구 계약으로 검토 |

Flyway의 기본은 migration별 트랜잭션이며 실행 조건/설정에 따라 비트랜잭션 예외가 있으므로 실제 적용 방식은 검증해야 한다. I-A의 실패 수용 조건은 **실패한 표 설치 단위가 롤백되어 새 표만 보호 없이 남지 않는 것**이다. 이전에 성공한 함수 등 다른 migration까지 전부 되돌아갔다고 가정하지 않는다. [Flyway migration 트랜잭션](https://documentation.red-gate.com/flyway/flyway-concepts/migrations/migration-transaction-handling)

CREATE OR REPLACE 등은 이미 있는 정의를 교체하는 수단이므로 최초 plain CREATE 제안과 구별한다. 향후 수정은 당시의 이력·소유/권한·호출 대상을 확인한 별도 변경으로 검토하고, 기존 성공 이력 수정·repair·자동 삭제를 정하지 않는다. [CREATE FUNCTION](https://www.postgresql.org/docs/18/sql-createfunction.html) · [CREATE TRIGGER](https://www.postgresql.org/docs/18/sql-createtrigger.html)
