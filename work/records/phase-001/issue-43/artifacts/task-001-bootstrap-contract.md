# Task 43-001 — 최초 준비의 역할·권한·비밀값

<a id="current"></a>

소유/업무 계정 분리와 최초 역할/권한 SQL·비밀값 전달·인용/로그 보호의 결정 근거를 확인할 때. 담당 상태·수용 판단은 [Task 43-001](../task-001.md#summary), 전체 길잡이는 [설계 안내](task-001-shared-version-references.md#summary)를 따른다. 아래 채택·비채택·미정을 구별하며 최초 구동 구현과 격리 검증은 [검증 기록](task-001-bootstrap-verification.md#results)을 따른다. 실제 자료·기존 개발 DB/볼륨과 공통 도메인 표 구현은 보류한다.

역할/권한/비밀값은 [로컬 DB 최초 구동 기준](<../../../../../docs/details/development/로컬 DB 최초 구동.md#current>), 실행 흐름과 설정은 [최초 구동 상세](task-001-startup.md#current)를 따른다. 아래는 O/C/T·C-S-F/V/R/G/Q/L/E의 확정 계약과 비교 대안이다.

## P1의 실제 소유·설치 역할·권한 연결·분리 시점 — O-A·C-A·T-A 설계 채택

소유/설치와 업무 계정을 분리하고 Spring/Flyway는 각 목적의 접속을 사용한다(O-A/C-A). 역할 분리는 최초 P1 설치 전에 준비하며(T-A), 빈 DB의 두 역할/최소 권한 준비는 Compose 최초 초기화에서 자동 수행한다(C-S-A). 새 환경용 구현과 격리 역할/권한 검증은 수행했으며 기존 개발 DB의 실제 이관은 보류한다.

### 확정 규칙과 미정

### P1-O — 누가 소유하고 누가 설치할까

| 대안 — A 확정, B 비채택 비교안                                 | 실제 역할·권한 연결 후보                                                                                                                                                                                                                | 이유·부담                                                                                                                                                                                                                  |
| -------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **O-결론: 소유·설치 로그인 역할 하나 + 업무 로그인 역할 하나** | `lumia_migrator LOGIN`이 공용 함수·여섯 공통 표와 그 표에 종속된 IDENTITY 시퀀스를 소유하고 Flyway 설치도 수행. `lumia_app LOGIN`은 비소유 업무 접속. 두 역할 사이 멤버십 없음                                                          | 현재 한 개의 로컬 Spring/Flyway 실행 흐름에서 소유자와 실행 주체를 바로 맞출 수 있음. SET ROLE/연결 초기화가 추가되지 않음. 추후 설치 계정을 교체하면 대상 객체의 소유 이관 검토가 필요                                    |
| O-B 비채택 비교: 로그인 불가 소유 역할 + 설치/업무 로그인 역할 | `lumia_owner NOLOGIN`이 위 객체를 소유. `lumia_migrator LOGIN`에 owner 멤버십을 `INHERIT FALSE·SET TRUE·ADMIN FALSE`로 주고, Flyway의 각 필요한 연결에서 DDL/관리 표 생성 전 `SET ROLE lumia_owner`. app에는 해당 멤버십/간접 경로 없음 | 소유 이름을 고정하고 설치 로그인 교체를 분리하기 쉬움. 연결별 역할 전환·Flyway 버전별 동작·실패/재연결을 추가 설계/검증해야 함. migrator는 SET ROLE로 소유자 능력을 쓸 수 있어 설치자 자체를 무권한으로 만드는 방식은 아님 |

**O-A 채택 이유:** P1의 핵심은 일반 업무 접속을 객체 소유자와 분리하는 것이다. 설치 계정 교체나 여러 설치 주체가 아직 필요한 것으로 확인되지 않아, 현재는 추가 소유 역할/전환 수단의 관리 부담을 줄이는 편이 맞다. O-B가 필요해지는 조건은 설치 로그인 교체 빈도·복수 설치 주체·소유 이름 유지 요구다. O-A를 택해도 O-B 전환은 자동 예약하지 않는다.

아래는 **O-A로 확정한 권한 연결 원칙**이며 실제 GRANT 목록/실행문은 아니다.

| 주체 계약                                | 확정한 소유·설치 연결                                                                                                                                                      | 허용하지 않을 능력·남길 경계                                                                                                                                                                         |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 초기 관리자 — 현재 이름 `lumiawiki` 유지 | 허용된 재개 뒤 역할 생성·필요한 최초 권한 연결을 담당. 일반 앱/Flyway 접속에서 제외                                                                                        | 기존 관리자 역할/DB/스키마를 자동 삭제·이름 변경·소유 이전하지 않음. 관리자 비밀값을 앱 실행에 전달하지 않음                                                                                         |
| `lumia_migrator`                         | DB CONNECT, public USAGE/CREATE와 필요한 언어 사용 능력. 직접 만든 공용 함수/표의 소유자로 함수 EXECUTE·표 TRIGGER 등 설치 능력 보유. 새 Flyway 관리 표도 같은 주체가 관리 | NOSUPERUSER·NOCREATEDB·NOCREATEROLE·NOREPLICATION·NOBYPASSRLS. DB나 public 스키마 전체의 소유자가 될 필요는 없음. 소유 객체의 정의 변경 능력은 보유하므로 guard가 이 주체까지 막는다고 보장하지 않음 |
| `lumia_app`                              | DB CONNECT·public USAGE 및 승인한 업무의 대상 표/열 DML만 부여                                                                                                             | 같은 비관리 속성, 객체 소유·구조 관리 역할의 직접/간접 멤버십·SET ROLE 경로·유효 public CREATE·표 TRIGGER·TRUNCATE·권한 재부여 능력 없음. PK guard 함수의 직접 EXECUTE는 R-A대로 선부여하지 않음     |
| 조회·예외 정비 목적                      | P2 목적 경계를 유지. 첫 필요 작업의 대상/범위·계정·입력·동시 변경 통제·실패/복구 계약을 먼저 검토                                                                          | 상시 reader/maintainer 역할을 자동 생성하거나 앱/초기 관리자 계정을 정비 도구의 기본 접속으로 배정하지 않음. 실제 역할 수/이름은 해당 작업 전 별도 확인                                              |

업무 DML의 실제 표/열·SELECT/INSERT/UPDATE/DELETE·시퀀스 권한은 승인한 저장/조회 업무와 함께 별도 확인한다. 여섯 보호 대상이라는 이유로 여섯 표 전체 CRUD나 모든 현재/미래 public 표의 DML을 일괄 부여하지 않는다. Flyway 관리 표의 쓰기, 미참조 행 삭제, 시퀀스 setval/명시 ID 복원, DEFAULT PRIVILEGES도 함께 확정하지 않는다. 실제 유효 권한은 직접 GRANT뿐 아니라 PUBLIC·상속·SET ROLE 경로까지 대조해야 한다.

객체 소유자는 보통 생성문을 실행한 역할이고 구조 변경 능력이 소유권에 연결된다. O-B에서는 SET ROLE 후 생성한 객체가 전환한 역할의 소유가 된다. 이는 PostgreSQL의 권한/역할 동작이며 O-A 채택 이유는 현재 P1 규모에 따른 설계 판단이다. [객체 소유와 권한](https://www.postgresql.org/docs/18/ddl-priv.html) · [멤버십의 INHERIT/SET 구별](https://www.postgresql.org/docs/18/role-membership.html) · [역할 속성](https://www.postgresql.org/docs/18/sql-createrole.html)

trigger마다 독립 로그인/소유 역할을 추가하는 안은 아니다. 표 소유와 함수 소유를 연결해 생성/변경 능력을 관리한다. 설치에 필요한 권한은 [CREATE TRIGGER](https://www.postgresql.org/docs/18/sql-createtrigger.html)와 R-A 계약을 유지하고, PUBLIC EXECUTE 회수 뒤 비소유 DML 동작은 재개 후 격리 검증으로 확인한다.

### P1-C — 초기 관리자·Flyway·업무 접속을 어떻게 연결할까

| 대안 — A 확정, B 비채택 비교안                                            | 접속·비밀값 연결 후보                                                                                                                                       | 이유·부담                                                                                                                                                                                          |
| ------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **C-결론: 로컬 Spring 시작 시 Flyway 유지 + 별도 자격 증명의 datasource** | 일반 JPA/서비스는 `lumia_app`, Spring Boot 자동 Flyway만 `lumia_migrator`로 접속. `spring.datasource`와 `spring.flyway.url/user/password`를 명시적으로 나눔 | 기존 Boot 시작 시 마이그레이션 방식을 유지하고 업무 커넥션은 비소유자로 동작. 같은 Spring 프로세스가 두 비밀값을 보유하므로 프로세스 전체에서 설치 능력을 제거하는 경계는 아님                     |
| C-B 비채택 비교: 별도 마이그레이션 실행 뒤 업무 앱 시작                   | 구조 변경 실행에만 migrator 비밀값 공급, 업무 실행은 app 비밀값만 공급하고 Flyway 비활성                                                                    | 업무 프로세스가 설치 비밀값을 보유하지 않음. 별도 실행 경로·순서·실패/재시작·테스트/CI 계약이 필요하며 기존 시작 방식과의 변경을 먼저 확인해야 함. CLI 등 특정 새 도구를 여기서 자동 선택하지 않음 |

C-A 채택은 **#43의 로컬 개발 적용**에 한정한다. 현재 Spring Boot는 Flyway 별도 url/user를 지정하면 전용 datasource를 구성할 수 있다. O-A에는 SET ROLE 초기화가 필요 없으며 O-B는 비채택 비교안이다. 운영/배포의 별도 실행·비밀값 공급은 아직 정하지 않는다. [Spring Boot Flyway datasource](https://docs.spring.io/spring-boot/how-to/data-initialization.html)

C-A로 확정한 환경변수 이름·매핑은 다음과 같다. 개인 값은 요청하거나 문서에 기록하지 않는다.

| 목적           | 채택 키                                           | 연결 대상 계약                                                                  |
| -------------- | ------------------------------------------------- | ------------------------------------------------------------------------------- |
| 최초 DB 관리자 | `DB_BOOTSTRAP_USERNAME` / `DB_BOOTSTRAP_PASSWORD` | Compose의 POSTGRES_USER / POSTGRES_PASSWORD. 현재 초기 계정 이름 lumiawiki 유지 |
| 일반 업무      | `DB_APP_USERNAME` / `DB_APP_PASSWORD`             | spring.datasource.username/password → lumia_app                                 |
| 구조 변경      | `DB_FLYWAY_USERNAME` / `DB_FLYWAY_PASSWORD`       | spring.flyway.user/password → lumia_migrator                                    |

DB_HOST/PORT/NAME은 같은 로컬 DB를 가리킨다. Flyway url/user/password를 모두 명시하고 필수값 누락을 실행 입력 단계에서 거부해 주 datasource의 자격 증명으로 암묵적으로 대체되지 않게 한다. Spring 개발 실행에는 app/Flyway 쌍만 전달하고 bootstrap 쌍은 전달하지 않는 계약이다. 실제 설정·환경변수 로더·예제·검증/CI의 수정 범위는 구현 전에 별도 대조하며 지금 변경하지 않는다.

현재 DB_USERNAME만 lumia_app으로 바꾸면 Compose POSTGRES_USER까지 바뀐다. 공식 이미지는 이 값을 **빈 볼륨에서 초기 슈퍼유저 생성에 사용**하므로, 업무 역할을 슈퍼유저로 만드는 연결을 유지한 채 이름만 나누어서는 P2 목적을 달성하지 못한다. 반대로 기존 볼륨은 환경변수 수정만으로 역할/소유/비밀번호가 변경되지 않는다. [공식 이미지의 초기화 변수](https://hub.docker.com/_/postgres)

### C-A의 새 환경 준비 — C-S-A 자동화 방향 채택

C-A는 Spring과 Flyway의 접속 분리, C-S-A는 새 DB의 최초 준비 자동화다. migrator는 NOCREATEROLE이므로 첫 접속 전에 초기 관리자가 두 역할과 최소 접속/설치 권한을 준비한다.

새 로컬 환경의 목표 흐름은 환경값 준비 → DB 시작/최초 역할 준비 → Spring 시작 시 migrator로 구조 설치 → app으로 업무 실행이다. 최초 역할 준비는 C-S-A로 방향을 채택했으며 아래에 비채택 대안과 이유/부담을 남긴다. 기존에 필요한 개인 환경값 입력·Docker/JDK 준비까지 없어지는 것은 아니며 실제 실행 명령/성공은 아직 제공하지 않는다.

| 최초 준비 — C-S-A 확정, C-S-B 비채택 비교안                          | 새 환경에서 사용자가 할 일                                                                                                       | 이유·부담                                                                                                                                                |
| -------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **C-S-결론: Compose의 새 DB 최초 초기화에 역할/최소 권한 준비 연결** | 개인 환경값 준비 후 DB와 서버 시작. 성공한 새 DB 최초 생성에는 역할 생성용 수동 SQL이나 별도 초기 설정 명령을 추가하지 않는 목표 | 현재 로컬 Compose 흐름에 맞고 반복적인 수동 권한 설정을 줄임. 초기화에 필요한 비밀값 공급·역할/권한 충돌·중간 실패/복구·테스트의 별도 경로를 설계해야 함 |
| C-S-B 비채택 비교: DB 시작 뒤 별도 최초 설정 명령                    | 개인 환경값 준비 → DB 시작 → 초기 관리 목적의 설정 명령 1회 → 서버 시작                                                          | 초기 관리자 작업을 명시적으로 분리하고 실행 결과를 확인하기 쉬움. 새 환경마다 별도 명령 단계가 추가되며 대상 판별/재실행/실패 복구 계약도 필요           |

C-S-A 채택은 최초 준비의 자동화 방향에 한정한다. 구현 파일/명령·비밀값 전달 수단·재실행/복구를 미리 확정하지 않는다. 초기 관리자 준비는 역할·승인한 최초 권한에 한정하고, 공통 표/함수/trigger의 구조 DDL과 승인한 표별 업무 권한은 Flyway 담당 범위로 구별한다. 전체 public의 업무 권한·DEFAULT PRIVILEGES를 자동 추가하거나 실제 게임 자료를 넣는 안은 아니다.

공식 이미지의 최초 초기화 스크립트는 **빈 데이터 디렉터리에서만 실행**된다. 기존 볼륨의 소유/권한 이관에는 그대로 적용되지 않고, 최초 실행 중 실패한 뒤 재시작한다고 나머지 스크립트가 자동 재실행된다고 보장할 수도 없다. 기존 DB나 실패한 환경을 새 환경으로 만들기 위해 볼륨을 삭제하지 않는다. 대상 확인·통제된 복구는 별도 검토한다. [공식 이미지의 초기화 스크립트 조건](https://hub.docker.com/_/postgres)

001은 초기 준비 입력·기존 Compose/실행·테스트 계약을 대조하고 004는 권한 결합을 검증한다. 파일/전달/실패는 F/V/R, 최소 권한은 G, 인용/로그는 Q/L/E와 B2/B3를 따른다. 실제 본문·마운트·개별 복구/기존 DB 이관은 해당 구현/실행 전에 확인한다.

### P1-T — 언제 분리를 적용할까

기존 `flyway_schema_history`나 공용 계정 소유 객체가 있으면 필요한 대상과 새 소유/접근을 별도로 제시한다. DB/public 스키마 전체 소유 이관, REASSIGN OWNED 일괄 실행, 역할 삭제·비밀번호 변경·볼륨 초기화를 자동 포함하지 않는다. 역할 생성/최초 권한 연결은 구조 마이그레이션 로그인 자체에 CREATEROLE을 주어 해결하지 않고 초기 관리 목적에서 분리해 준비하는 계약이다. 구체 부트스트랩/이관 실행 수단·SQL·파일·단계별 실패 복구는 실제 적용 전에 별도 확인한다.

### C-S-F — 파일 배치와 실행 단위

| 대안 — A 확정, B 비채택 비교안           | 채택/비채택 원천/연결                                                                                                                                                                                                             | 이유·부담                                                                                                          |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| **F-결론: 쉘 진입 파일 + 별도 보조 SQL** | `db/bootstrap/10-prepare-roles.sh`를 `/docker-entrypoint-initdb.d/10-prepare-roles.sh`에 읽기 전용 마운트. `db/bootstrap/sql/prepare-roles.sql`은 `/opt/lumia-bootstrap/prepare-roles.sql`에 읽기 전용 마운트하고 쉘이 한 번 호출 | 입력/실행 오류 처리는 쉘, 고정 역할/권한 문장은 SQL로 구별해 검토하기 쉬움. 마운트 두 개와 경로 대응을 관리해야 함 |
| F-B 비채택 비교: 단일 쉘에 SQL 포함      | `db/bootstrap/10-prepare-roles.sh` 한 개만 같은 초기화 위치에 읽기 전용 마운트. 고정 SQL 입력을 파일 내부에서 준비해 한 psql 실행으로 전달                                                                                        | 파일/마운트 수가 적음. 쉘과 SQL의 인용·비밀값 처리·수정 검토가 한 파일에 섞임                                      |

F-A의 역할 준비 SQL은 **자동 실행 디렉터리 밖**에 둔다. 공식 entrypoint는 초기화 디렉터리의 `.sql`을 자체 실행하므로 쉘에서 다시 부를 SQL까지 그곳에 함께 두면 두 번 실행될 수 있다. 파일 하나씩 명시적으로 마운트해 자동 검색/폴더 전체 실행을 기본으로 넓히지 않는 계약이다. `.sh`는 실행 권한에 따라 실행되거나 현재 셸에 읽혀 처리되므로 Windows 체크아웃/마운트의 실행 비트만 가정하지 않고 두 경우의 정상/실패 전파를 검증한다. [공식 entrypoint의 파일 처리](https://raw.githubusercontent.com/docker-library/postgres/master/docker-entrypoint.sh)

bootstrap 쉘/SQL은 UTF-8·BOM 없음·LF로 관리한다. .gitattributes는 해당 파일 패턴에만 적용한다. 쉘/SQL·마운트 구현과 LF/소싱 호환은 격리 실행으로 확인한다.

F-A는 **역할/최초 권한 준비 원천만** `db/bootstrap/`에 두는 채택 계약이다. `db/migration/`은 기존 Flyway 구조/보호 장치와 승인한 표별 업무 권한의 원천으로 유지하고 두 곳에 같은 SQL을 복사하거나 bootstrap SQL을 backend Flyway 리소스에 포함하지 않는다. DB·시즌·종류·아이템 자료를 초기 준비 스크립트에 넣는 선택도 아니다.

| **V-결론: 기존 개인 `.env` + 대상별 명시 환경변수 전달**                         | 개인 값은 Git 제외 루트 `.env` 한 곳에서 관리. Compose `environment`에 필요한 키만 명시하고 DB 초기화에는 bootstrap·app·Flyway 쌍, Spring에는 app·Flyway 쌍만 전달                                      | 확정한 C-A 변수 이름/매핑과 현재 개인 환경값 준비 흐름을 유지. 컨테이너 환경을 조회할 수 있는 주체와 프로세스의 환경에는 비밀값이 남을 수 있음                                 |
| V-B 비채택 비교: DB 컨테이너는 Compose secrets 파일, Spring에는 필요한 값만 연결 | Git 제외 개인 비밀 파일을 서비스별 secrets로 마운트. bootstrap은 이미지의 POSTGRES_PASSWORD_FILE, app/Flyway는 초기화 파일에서 읽음. 호스트 Spring 실행기는 필요한 파일을 읽어 기존 C-A 환경변수로 전달 | DB 컨테이너 환경 설정에 평문 비밀번호를 직접 넣는 노출을 줄임. 파일 위치/제외/접근권한과 호스트 실행기의 파일 읽기를 추가 설계해야 하며 개인 값의 중복 원천을 만들지 않아야 함 |

V-A 채택 이유는 현재 **로컬 개발**의 합의한 `.env` 흐름과 변경량을 기준으로 한 설계 판단이다. Docker 문서는 비밀값에 secrets 사용을 권장하므로 컨테이너 환경 노출을 줄이는 것이 우선이면 V-B가 더 맞다. Compose secrets는 컨테이너에 파일로 전달하며 로컬 파일 권한/배포를 대신 관리하거나 환경·메모리·로그의 모든 노출을 없애는 장치는 아니다. 운영의 비밀값 공급은 이 선택에 포함하지 않는다. [Compose 환경변수](https://docs.docker.com/compose/how-tos/environment-variables/set-environment-variables/) · [Compose secrets](https://docs.docker.com/compose/how-tos/use-secrets/)

| V-A 채택 전달 경계·후속 미정   | 제안 내용                                                                                                                                                                                                                                |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| DB 컨테이너/최초 준비          | DB_BOOTSTRAP_USERNAME/PASSWORD는 POSTGRES_USER/PASSWORD로 연결. 두 역할 생성에 필요한 DB_APP_USERNAME/PASSWORD·DB_FLYWAY_USERNAME/PASSWORD도 명시 전달. 이미지가 사용자 정의 APP/FLYWAY 변수를 알아서 역할로 만드는 것으로 설명하지 않음 |
| Spring/Gradle/Java             | DB_HOST/PORT/NAME과 app/Flyway 쌍만 DB 연결 입력으로 선택. bootstrap·기타 관리자 DB 비밀값을 통째로 상속하지 않음. PATH/JAVA_HOME 등 필요한 일반 실행 환경의 보존 방식은 런처 구체화 때 대조                                             |
| 프런트·Git·첨부                | 개인 DB 비밀값 전달/기록 없음. `.env.example`에는 키와 자리표시자만 두고 실제 `.env` 자동 생성/덮어쓰기를 하지 않음                                                                                                                      |
| psql/SQL 입력·출력 — 후속 미정 | 비밀번호를 명령행 인자·셸 문자열 치환·생성 SQL 파일에 삽입하지 않는 방향. psql의 환경값 읽기와 식별자/문자열 인용을 검토하고 입력 누락은 역할 쓰기 전에 거부. 셸 추적·환경 출력·SQL echo를 쓰지 않고 단계/오류 분류만 남기는 후보        |

psql은 `\getenv`로 환경값을 읽을 수 있다. 이것만으로 SQL 인용이나 모든 오류 로그가 안전해지는 것은 아니다. PostgreSQL의 실패 문장/SQL 로그에 비밀값이 포함될 수 있으므로 **비밀값이 포함되는 SQL의 인용·클라이언트/서버 로그 처리와 검증 계약을 구현 전 별도로 확인**한다. V 선택은 전달 수단/범위이며 특정 로그 설정값·오류 가리기·진단 코드까지 자동 채택하지 않는다. [psql 환경값 읽기/인용](https://www.postgresql.org/docs/18/app-psql.html) · [PostgreSQL 로그의 비밀값 노출 조건](https://www.postgresql.org/docs/18/runtime-config-logging.html)

### C-S-R — 실패 단위와 복구

| 대안 — A 확정, B 비채택 비교안                                         | 채택/비채택 실패/복구                                                                                                                                                                                 | 이유·부담                                                                                                                                                           |
| ---------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **R-결론: 최초 역할 준비 한 트랜잭션·실패 시 중단 + 검토한 명시 복구** | 두 역할 생성과 승인할 최초 권한 준비를 한 psql 트랜잭션으로 묶고 SQL 오류 시 롤백/실패 종료. 기존 역할 충돌은 임의 skip/ALTER/비밀번호 교체 없이 중단. 실제 상태 확인 뒤 필요한 복구 계획을 별도 확인 | 새로 준비하는 두 역할/권한의 부분 반영을 줄이고 현재 초기 전용 범위를 유지. 실패 후에는 역할 준비 단위와 남은 DB 디렉터리를 구별해 확인해야 함                      |
| R-B 비채택 비교: 상태 확인 후 명시 재실행 가능한 초기 설정기           | 재실행 시 이미 맞는 초기 준비 결과는 재사용하고 승인한 누락만 보완. 예상 밖 기존 역할/권한은 중단. 일반 재시작에서 자동 변경하는 안은 아님                                                            | 반복 복구의 수동 판단을 줄일 수 있음. 기존 역할이 이 초기 준비의 결과인지 식별할 근거, 허용 상태/권한 보완/비밀번호 검증·완료 판정과 재실행 계약을 추가 설계해야 함 |

R-A는 psql의 `--single-transaction`·`ON_ERROR_STOP`와 사용자 초기화 파일을 읽지 않는 실행을 사용해 **역할/최초 권한 준비 SQL 단위**를 원자적으로 처리하는 설계 계약이다. 해당 입력에 별도 BEGIN/COMMIT을 중복하지 않고 오류를 성공으로 바꾸지 않는다. F-B처럼 표준입력으로 SQL을 넣더라도 단일 트랜잭션 옵션의 파일/명령 입력 조건에 맞게 실행 단위를 구성해야 한다. 이 내용은 Flyway의 I-A 트랜잭션과 서로 다른 준비 단계다. [psql 트랜잭션·실패 종료](https://www.postgresql.org/docs/18/app-psql.html)

**롤백 범위의 한계:** 공식 이미지의 initdb·초기 관리자·POSTGRES_DB 준비는 사용자 초기화 파일보다 앞선다. 역할 준비 SQL이 실패해도 그 앞의 DB 디렉터리/DB까지 없어지는 것이 아니다. 연결 끊김/프로세스 중단이 커밋 근처에 발생하면 클라이언트 오류만으로 커밋 여부를 단정하지 않고 실제 역할/권한 상태를 확인한다. 비어 있지 않은 데이터 디렉터리는 재시작 시 최초 준비 파일을 다시 실행하지 않을 수 있으므로 단순 재시작을 복구 성공으로 판정하지 않는다.

| R-A의 실패 지점/확인 결과                              | 제안하는 다음 행동 — 실행 미승인                                                                                                                 |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| 역할 쓰기 전 값 누락·잘못된 이름/대상·선행 상태 충돌   | 역할 준비 중단. 값 자체를 출력하지 않고 필요한 키/단계만 식별. 새 역할/권한을 일부 만들고 다음 단계로 넘어가지 않음                              |
| 역할 생성·최초 GRANT 중 SQL 오류                       | 해당 트랜잭션 롤백/실패 종료. 남은 PGDATA를 보존하고 DB가 완전히 새 상태라고 가정하지 않음                                                       |
| 실제 상태 확인 결과 두 역할/권한이 모두 미생성         | 재개 허용과 대상/검사/실패 복구를 갖춘 **명시적 역할 준비 재실행 계획**을 확인받음. 컨테이너 재시작·PG_VERSION 삭제로 초기화를 강제하지 않음     |
| 두 역할·권한이 모두 기대 상태와 일치                   | 비소유 app/설치 migrator의 실제 접속·유효 권한/필요 설치 능력을 읽기/접속 검사로 확인. 확인된 준비를 다시 만들거나 비밀번호를 임의 교체하지 않음 |
| 일부 존재·예상 밖 권한/멤버십·출처 불명·커밋 여부 불명 | 자동 보완하지 않고 현황과 대상별 교정/이관·실패 복구안을 제시. 실제 수정은 확인받은 개별 범위에서만 수행                                         |

역할 준비 실패/미확인 상태에서는 운영 절차로 후속 Flyway/업무 시작을 보류하고 상태 확인/명시 복구 뒤 진행한다. pg_isready는 초기 역할/권한 준비 완료를 증명하지 않는다. 기동은 최초 설치/격리 검증과 Spring/Flyway/JPA 기본 오류 처리를 사용한다. Compose health만으로 모든 독립 서버 실행을 차단하거나 전체 권한을 검증하지 않는다. [pg_isready 검사 범위](https://www.postgresql.org/docs/18/app-pg-isready.html)

현재 권한/이관·볼륨 보존 합의를 유지한다. PGDATA/볼륨 삭제·PG_VERSION 수정·역할 삭제·비밀번호/기존 권한 자동 교체·전체 소유권 이관을 복구의 기본 동작에 넣지 않는다. 별도 완료 표식 파일/DB 표·초기화 상태 버전·사용자 정의 entrypoint도 자동 채택하지 않는다. 이 중 필요해지는 수단은 이유와 대안을 다시 제시한다.

## C-S-A 최초 준비의 최소 권한 목록 — G-D-A·G-S-A 설계 채택

최초 직접 권한과 대상 DB/public의 PUBLIC 회수는 G-D-A/G-S-A를 따른다. 최초 권한은 격리 DB에서 검증한다. 업무 권한·이관은 해당 범위에서 확인하며 실제 .env·기존 DB/ACL 조회·자료 작업은 보류한다.

### 확정 규칙과 미정

| 유지할 합의                                                                                                           | 확정 범위·미정                                                                                                                |
| --------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| 초기 관리자 lumiawiki가 최초 두 역할/권한 준비. migrator/app에 슈퍼유저·DB/역할 생성 능력과 서로의 멤버십을 주지 않음 | 기존 초기 관리자가 가진 능력을 사용. 새 provisioning 역할이나 CREATEROLE 위임은 제안하지 않음                                 |
| O-A: migrator가 공용 함수/여섯 표·종속 시퀀스를 소유/설치, app은 비소유 업무                                          | 처음 연결에 필요한 DB/스키마/언어 권한과 나중에 소유자로 얻는 설치 능력을 구별                                                |
| C-S-F-A/V-A/R-A: 최초 준비 파일/전달 범위·한 트랜잭션/실패 중단·명시 복구                                             | 확정한 최초 GRANT/REVOKE도 역할 준비와 같은 트랜잭션에 포함. 실제 SQL 구문/인용·비밀 로그는 별도                              |
| 일반 업무 표/열 DML과 시퀀스·DEFAULT PRIVILEGES는 별도 확인                                                           | 최초 준비에서 app의 업무 권한을 미리 일괄 부여하지 않음. 이 목록은 첫 준비 단계의 범위                                        |
| R-A 함수 계약: 설치자는 함수 EXECUTE·표 TRIGGER 필요, app에는 직접 함수 EXECUTE 선부여하지 않음                       | 함수/표 생성 전 부트스트랩에서 없는 객체에 권한을 주지 않음. 생성 뒤 migrator 소유 능력·PUBLIC EXECUTE 회수는 Flyway I-A 단계 |

기준은 [채택 역할/접속 계약](<../../../../../docs/details/development/로컬 DB 최초 구동.md#pk-guard-role-install>)·[최초 준비 계약](<../../../../../docs/details/development/로컬 DB 최초 구동.md#bootstrap-files-values-recovery>)이다. 현재 [Flyway 설정](../../../../../backend/src/main/resources/application.yaml)은 리소스 위치만 지정했고 확정한 권한/스키마 준비를 구현한 상태가 아니다. O/C/T·C-S-A·F/V/R을 재선택하거나 실제 적용으로 보고하지 않는다.

### 최소 권한의 의미와 직접 부여 목록

DB의 `CONNECT`는 접속 허가, 스키마의 `USAGE`는 그 안의 객체 이름을 찾아 사용하는 허가다. `USAGE`만으로 표의 자료를 SELECT/UPDATE할 수는 없다. **DB의 CREATE**는 새 스키마 등 DB 수준 생성, **스키마 public의 CREATE**는 그 안에 표/함수 등을 만드는 능력이라 서로 다르다. migrator에는 후자만 필요하다는 현재 배치를 기준으로 한다. [PostgreSQL 권한 의미](https://www.postgresql.org/docs/18/ddl-priv.html)

아래는 G-D-A/G-S-A의 최초 직접 권한과 PUBLIC 회수 범위다. 역할/ACL의 유효 권한은 격리 DB에서 검증했다. WITH GRANT OPTION이나 ADMIN OPTION은 추가하지 않는다.

| 대상                    | lumia_app 직접 부여 계약     | lumia_migrator 직접 부여 계약    | 최초 준비의 한계                                                                                                                     |
| ----------------------- | ---------------------------- | -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| DB `lumiawiki`          | CONNECT                      | CONNECT                          | DB CREATE·TEMPORARY는 직접 부여하지 않음. PUBLIC의 CONNECT/TEMPORARY/CREATE도 G-D-A로 회수                                           |
| 스키마 `public`         | USAGE                        | USAGE, CREATE                    | DB/public 소유 이전 없음. PUBLIC의 USAGE/CREATE도 G-S-A로 회수. app의 유효 CREATE는 허용하지 않음                                    |
| 언어 `plpgsql`          | 별도 직접 GRANT 없음         | USAGE                            | 함수 정의에 필요한 언어 사용을 명시. 기존 언어/시스템 스키마/자료형의 PUBLIC 권한은 그대로 유지하는 계약                             |
| 표/열·시퀀스·guard 함수 | 최초 준비에서 직접 부여 없음 | 아직 없는 객체에 직접 GRANT 없음 | 구조 생성 뒤 소유자 능력과 승인한 업무 권한을 Flyway에서 구별. 전체 public 표/시퀀스/함수 GRANT나 DEFAULT PRIVILEGES를 추가하지 않음 |

PL/pgSQL은 기본 설치 언어지만 실제 대상 DB에 없으면 이를 자동 설치하거나 migrator에 DB CREATE/슈퍼유저를 주지 않는다. 함수 정의에는 언어와 입출력 자료형의 USAGE도 필요하므로 기본 자료형/시스템 접근을 일괄 회수하는 안은 아니다. [PL/pgSQL 기본 설치](https://www.postgresql.org/docs/18/plpgsql-overview.html) · [함수 정의 권한](https://www.postgresql.org/docs/18/sql-createfunction.html)

public 스키마·기본 언어가 존재하고 선택한 최초 권한으로 필요한 구조 설치가 가능하다는 조건을 재개 뒤 확인한다. 새 스키마/확장 설치를 최초 준비 범위에 추가하지 않는다. Flyway가 다른 스키마를 생성하려 하면 권한을 넓혀 해결하지 않고 대상/설정을 다시 확인한다. Flyway의 스키마 자동 생성 제어는 가능하지만 **default-schema/schemas/create-schemas의 실제 설정은 이 목록으로 자동 확정하지 않는다.** [Flyway 스키마 생성 설정](https://documentation.red-gate.com/flyway/reference/configuration/flyway-namespace/flyway-create-schemas-setting)

### 직접 GRANT와 실제 유효 권한의 차이

`PUBLIC`은 현재와 앞으로의 모든 역할에 적용된다. 실제 권한에는 직접 GRANT뿐 아니라 멤버십과 PUBLIC 경로가 합쳐지므로, app에 TEMPORARY를 직접 주지 않았다는 이유만으로 임시 표 생성이 차단되지는 않는다. 같은 이유로 app에 대한 직접 REVOKE만으로 PUBLIC의 권한을 없앨 수 없다. 소유자 능력도 별도로 대조한다. [GRANT·PUBLIC·소유 권한](https://www.postgresql.org/docs/18/sql-grant.html)

새 DB는 기본 PUBLIC CONNECT/TEMPORARY가 있고 public 스키마도 기본 PUBLIC USAGE를 가진다. 일반 새 스키마의 기본 권한과 public 스키마의 기본 설정을 혼동하지 않는다. 현재 DB의 실제 ACL을 확인한 결론은 아니며, 아래 회수는 **G-D-A·G-S-A로 확정한 설계 정책**이다. 실제 ACL 조회/회수 완료를 뜻하지 않는다. [DB 기본 공개 권한](https://www.postgresql.org/docs/18/ddl-priv.html) · [public 스키마 기본 USAGE](https://www.postgresql.org/docs/18/ddl-schemas.html)

### C-S-G-D — 대상 DB의 PUBLIC 권한

| 대안 — A 확정, B 비채택 비교안                                               | `lumiawiki` DB의 채택/비채택 범위                                                                                     | 이유·부담                                                                                                                                                                      |
| ---------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **D-결론: PUBLIC CONNECT·TEMPORARY·CREATE 회수 + 두 역할에 CONNECT 명시**    | 위 세 DB 권한을 PUBLIC에서 회수하고 app/migrator에 CONNECT만 직접 부여. 초기 관리자의 기존 소유/슈퍼유저 능력은 유지  | 대상 DB의 일반 접속자를 명시하고 현재 필요가 확인되지 않은 임시 표/새 스키마 생성을 열지 않음. 나중에 조회/정비 계정이나 TEMP 필요 업무가 생기면 해당 권한을 따로 확인해야 함  |
| D-B 비채택 비교: 기본 PUBLIC CONNECT·TEMPORARY 유지 + 두 역할의 CONNECT 명시 | DB PUBLIC CREATE는 없어야 하며 예상 밖 부여가 있으면 중단/확인. app/migrator는 기본 공개 경로로 TEMPORARY도 사용 가능 | 기존 PostgreSQL 사용 흐름과 향후 임시 표 사용의 제약이 적음. 새 역할에도 대상 DB 접속/임시 표 능력이 자동 적용되므로 두 역할만의 직접 권한 목록이 전체 능력 목록이 되지는 않음 |

D-A 채택 이유는 최초 준비에 필요한 기능만 여는 목적 때문이다. TEMPORARY는 임시 표 생성 권한이며, 기존 공통 표/trigger를 변경하는 능력과는 구별한다. 이 제한이 Flyway/후속 업무에 필요한 능력과 충돌하면 격리 검증 근거와 필요 범위를 제시하고 다시 확인받는다. 임시 표 권한을 자동 추가하지 않는다.

대상은 **새로 준비할 lumiawiki DB 한 곳**이다. postgres/template 등 다른 DB·인증/HBA·다른 클러스터 역할의 권한을 함께 변경하지 않는다. 역할은 클러스터 공통이므로 D-A만으로 다른 DB 접속까지 차단됐다고 설명하지 않는다. 기존 환경에 이 회수를 자동 적용하는 선택도 아니다.

### C-S-G-S — public 스키마의 PUBLIC 권한과 명시 부여

| 대안 — A 확정, B 비채택 비교안                                    | `lumiawiki.public`의 채택/비채택 범위                                                                                                                                 | 이유·부담                                                                                                                              |
| ----------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| **S-결론: PUBLIC USAGE·CREATE 회수 + 필요한 역할에 명시 부여**    | PUBLIC의 USAGE/CREATE 회수, app에 USAGE, migrator에 USAGE/CREATE. migrator에는 plpgsql USAGE도 명시하며 언어/시스템 스키마/기본 자료형의 기존 PUBLIC 권한은 그대로 둠 | 프로젝트 스키마의 사용/생성 주체가 직접 목록과 맞음. 새 조회/정비 역할이나 public의 확장 객체 소비자가 생기면 USAGE를 따로 연결해야 함 |
| S-B 비채택 비교: PUBLIC USAGE 유지·CREATE만 회수 + 같은 직접 부여 | public의 이름/객체 사용은 기본 공개 경로로 유지하고 생성은 migrator에만 허용. app/migrator 직접 권한과 migrator의 언어 USAGE는 S-A와 같음                             | public을 쓰는 향후 소비자의 설정이 적음. 접속 가능한 다른 역할도 스키마 USAGE를 가지며 실제 자료 접근은 여전히 별도 객체 권한이 필요   |

두 안 모두 app의 유효 public CREATE 금지라는 기존 O-A를 유지한다. schema USAGE와 함수 EXECUTE·표 SELECT/UPDATE를 하나로 취급하지 않는다. 언어 USAGE의 기본 PUBLIC 경로를 유지하므로 app에 plpgsql USAGE를 직접 주지 않더라도 유효 언어 사용 능력은 남을 수 있다. 언어 USAGE만으로 public에 함수를 만들 수 있는 것은 아니다. 채택 범위를 시스템 전체 권한 회수로 확대하지 않는다.

### 소유·설치 능력과 후속 업무 권한

| 단계/대상                        | 처리 규칙·한계                                                                                                                                                                                       |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 초기 관리자                      | 이미 확정한 초기 관리자가 CREATE ROLE·대상 DB/스키마·언어 권한 준비를 담당. 그 능력을 새 migrator/app에 위임하지 않음                                                                                |
| 새 공용 함수·여섯 표·종속 시퀀스 | migrator가 직접 생성해 소유. 소유자는 기본 객체 권한을 가지므로 자신이 만든 표의 TRIGGER·함수 EXECUTE를 위해 별도의 자기 대상 GRANT나 관리자 역할 상속을 추가할 필요가 없음                          |
| guard 설치와 PUBLIC EXECUTE 회수 | 함수/표가 생기는 Flyway I-A 단계에서 R-A 권한 계약 적용. PUBLIC EXECUTE 회수는 migrator 소유자 권한까지 회수하는 안이 아니며 app의 직접 EXECUTE 선부여 없음 유지                                     |
| 신규 Flyway 관리 표              | 실제 생성 주체/스키마와 소유를 대조. app에 관리 표 DML을 주거나 전체 public 표 DML로 우회하지 않음. 기존 관리 표 소유가 다르면 T-A의 대상별 이관 확인                                                |
| app 업무 표/열·시퀀스            | 최초 준비에서는 아직 없는 업무 객체의 권한을 미리 주지 않음. 실제 저장/조회/삭제·ID/복원 계약에 필요한 객체/열/능력은 각 업무/DDL에서 별도 확인. 시퀀스 setval·전체 시퀀스 권한도 자동 포함하지 않음 |

소유자에게는 기본 객체 권한이 있고 trigger 생성에는 표 TRIGGER·함수 EXECUTE가 필요하다. 이는 소유와 별도 GRANT의 차이를 설명한 것이며 설치/비소유자 실행을 실제 검증한 결과가 아니다. [소유자 기본 권한](https://www.postgresql.org/docs/18/sql-grant.html) · [trigger 설치 권한](https://www.postgresql.org/docs/18/sql-createtrigger.html)

| app의 스키마/DB 생성·임시 표·미승인 DML·관리 표/guard 정의 시도 | public/DB CREATE 및 미승인 객체 DML/구조 변경은 거부. TEMP는 G-D-A대로 거부되는지 확인하고, 아직 업무 DML 미부여인 상태를 업무 갱신 가능 상태로 보고하지 않음         |
| PUBLIC 회수 범위와 후속 승인 역할                               | 선택한 범위에서만 회수. public USAGE가 없는 경우와 표 권한 없는 경우를 구별. 다른 DB·시스템/언어 권한을 임의 회수하거나 테스트용 제3 역할을 운영 역할로 등록하지 않음 |
| 역할 준비 중 오류·커밋 불명·기존 ACL 충돌                       | R-A대로 역할/최초 GRANT·선택한 PUBLIC 회수를 한 단위로 검증. 롤백 후 선행 DB/스키마와 원래 ACL이 남는 사실을 구별. 실패 후 자동 교체/복구 없음                        |

최초 준비 능력과 기본 공개 권한을 구별한다. 현재 DB·역할/ACL·Flyway·함수/trigger·HBA·게임 자료의 조회/실행은 미수행이며 새로운 선택은 사용자 확인 후 확정한다.

## C-S-A 최초 권한 SQL의 인용·비밀 로그 — Q-A·L-A·E-A 설계 채택

SQL 인용·로그 제어 범위·진단 정보는 Q-A/L-A/E-A를 따른다. 구체 로그값 8개·SCRAM·고정 진단·파일/환경 연결과 기동은 [B1~B3](task-001-startup.md#f4-bootstrap-integrated)를 따른다. SQL·출력·정상/실패 검증은 격리 DB에서 수행했다. 개인 비밀값·기존 개발 DB/볼륨과 자료 작업·현재 환경 이관/사건 복구는 수행하지 않았다.

### 확정 규칙과 미정

### C-S-Q — 환경값과 SQL 인용

| 대안 — A 확정, B 비채택 비교안                             | 처리 후보                                                                                                                                                 | 추천 이유·부담                                                                                                     |
| ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| **Q-결론: psql 환경값 읽기 + 정적 SQL의 전용 인용**        | 보조 SQL이 `\getenv`로 환경값을 읽고 DB/역할 이름은 `:"name"`, 비밀번호는 `:'password'` 형태로 사용. 권한 키워드·public/plpgsql·PUBLIC은 고정 구문으로 둠 | 현재 두 역할과 정해진 GRANT/REVOKE를 직접 대조하기 쉬움. psql 치환의 적용 위치·누락/인코딩·로그 제어를 확인해야 함 |
| Q-B 비채택 비교: format의 식별자/문자열 인용 + 생성문 실행 | 인용한 입력으로 `format`의 `%I`/`%L`을 사용해 고정 템플릿의 명령을 만들고 `\gexec` 등으로 실행. 출력/파일로 SQL을 내보내지 않는 설계가 필요               | 처리 대상이 많아 명령 목록을 행으로 관리할 때 유리. 현재는 값→생성 SQL→실행의 단계와 검토/오류·로그 경로가 늘어남  |

Q-A로 확정한 입력/구문 경계는 다음과 같다. 이는 인용 방식의 계약이며 완결된 실행 SQL 파일이 아니다.

| 입력/구문       | 채택 방식/후속 미정                                                                                                                                                                            |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| DB/역할 식별자  | `:"db_name"`, `:"app_user"`, `:"migrator_user"`처럼 식별자로 인용. 값은 확정한 lumiawiki/lumia_app/lumia_migrator와 대조하고 임의 이름 변경을 허용하는 새 계약으로 해석하지 않음               |
| 비밀번호 문자열 | `:'app_password'`, `:'migrator_password'`처럼 문자열로 인용. 직접 작은따옴표를 붙이거나 원문 `:password` 치환을 하지 않음                                                                      |
| PUBLIC과 권한   | PUBLIC은 모든 역할을 뜻하는 SQL 키워드로 고정. 스키마 이름 public과 구별. 권한 이름/명령문을 환경값으로 받지 않음                                                                              |
| 셸→psql 전달    | 비밀번호를 `psql -v password=...` 같은 명령행 인자·비밀번호 포함 연결 URI·eval/envsubst·셸 문자열 치환으로 SQL에 끼워 넣지 않는 방향. 보조 SQL 원천에는 값 대신 변수 참조만 둠                 |
| 치환 위치/누락  | psql 치환이 안 되는 따옴표/달러 인용 본문 안에 변수를 넣지 않음. 기존 누락/빈 값/예제 값 검사를 유지하고 미정의 변수를 과거/기본값으로 대체하지 않음. 역할 쓰기 전에 필수값·승인한 이름을 확인 |

psql은 식별자/문자열용 인용을 지원하고, 이미 인용된 SQL 본문 안에서는 변수 치환을 하지 않는다. `\getenv`는 환경변수가 없을 때 기존 psql 변수 값을 바꾸지 않으므로 누락 확인을 생략할 근거가 되지 않는다. NUL은 psql 변수/환경값으로 정상 전달할 수 있는 입력이 아니며, 인코딩·비밀번호 길이/개행/제어문자 정책을 편의상 새로 제한하거나 변환하지 않는다. 이 정책과 Node/Compose/셸/psql 간 값 보존의 구체 검사는 구현 전에 별도 확인한다. [psql 변수와 SQL 인용](https://www.postgresql.org/docs/18/app-psql.html)

**인용은 로그 비노출을 뜻하지 않는다.** Q-A와 Q-B 모두 비밀번호 값이 SQL 처리 구간에 들어가며, 원문 SQL을 실행한다면 서버 처리/활동 조회에도 일시적으로 존재할 수 있다. 클라이언트에서 암호화된 비밀번호 표현을 만들어 보내는 방식은 그 노출을 줄이는 별도 대안이지만, 생성/입력 수단·저장 암호화 정책·검증값 취급을 자동 채택하지 않는다. 암호화된 표현도 로그에 마음대로 남길 정보로 취급하지 않는다. [클라이언트 비밀번호 변환의 목적](https://www.postgresql.org/docs/18/libpq-misc.html)

### C-S-L — 서버 로그 제어 범위

| 대안 — A 확정, B 비채택 비교안                                          | 처리 후보                                                                                                                                                             | 추천 이유·부담                                                                                                                                                    |
| ----------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **L-결론: 최초 준비 트랜잭션에 한정한 로그 제어·확인 후 비밀 SQL 실행** | 초기 관리자 연결에서 비밀값을 SQL에 보내기 전에 필요한 로그 설정을 SET LOCAL로 맞추고 값/조건 확인. 실패/미확인은 역할 생성 전 중단. 커밋/롤백 뒤 세션 기본 설정 복원 | DB 전체·업무 연결의 로그 정책을 바꾸지 않고 최초 준비 구간에 한정. 이 구간의 일반 SQL/오류 본문 진단이 줄어들며 구체 설정·출력 처리 검증이 필요                   |
| L-B 비채택 비교: 사전 준비된 로그 조건을 검사만 하고 진행               | 최초 준비가 요구하는 로그 조건은 관리된 실행 환경에서 미리 준비. 스크립트는 확인만 하고 맞지 않으면 중단하며 자체 SET을 하지 않음                                     | 기존 로그 관리 정책을 중앙에서 유지하는 환경에 적합. 현재 로컬에는 그 프로파일/공급이 없어 별도 설계가 필요하며, DB 전역 로그 설정 변경을 자동 승인하는 안은 아님 |

L-A의 채택 순서는 **단일 트랜잭션 시작 → 비밀값 없는 설정/상태 확인 → 로그 조건 적용/재확인 → 비밀값을 쓰는 역할 SQL 및 승인한 권한 처리 → 커밋**이다. 설정 실패/미확인 시 R-A대로 중단하며, 로그 제어를 위해 app/migrator에 SET·슈퍼유저 능력을 추가하지 않는다. [SET LOCAL의 트랜잭션 범위](https://www.postgresql.org/docs/18/sql-set.html)

로그 설정은 아래 8개 값과 L-A의 트랜잭션 범위·사전 확인/중단 조건을 따른다. 변경 전 표본 비율 0 확인·SET LOCAL 적용/재확인·고정 진단은 [B2](task-001-startup.md#f4-bootstrap-integrated)에 정의한다. 검사 SQL과 로그의 정상/거부 동작은 격리 검증했다.

| 경로                         | B2 채택 설정값                                                                                               | 확인할 목적/한계                                                                                                        |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------- |
| 일반 SQL·실행 시간·표본 로그 | log_statement=none, log_min_duration_statement=-1, log_min_duration_sample=-1, log_transaction_sample_rate=0 | SQL 문장 전체/일부 표본이 다른 경로로 남지 않게 검토. log_statement 하나만 껐다고 모든 경로가 닫힌 것으로 판정하지 않음 |
| 실패 SQL 문장                | log_min_error_statement=PANIC                                                                                | 일반 실패 SQL을 기록하지 않도록 B2에서 채택. PANIC 수준까지 완전 무기록이라는 뜻은 아님                                 |
| 일반 서버 오류 본문          | log_min_messages=PANIC                                                                                       | 비밀값이 오류 본문에 포함되는 일반 로그도 제한하는 B2 채택값. 이 준비 구간의 오류 진단 손실을 E와 함께 비교             |
| 바인딩 값 로그               | log_parameter_max_length=0, log_parameter_max_length_on_error=0                                              | B2로 확정한 바인딩 값 설정. SQL에 들어간 문자열 리터럴을 이 값으로 가릴 수 있다고 설명하지 않음                         |

일반 로그·실패 문장·바인딩 값은 별도 설정이다. 특히 log_statement=none이나 바인딩 값 길이 0만으로 실패 SQL/원문 리터럴 노출을 막았다고 볼 수 없다. [PostgreSQL 로그 설정](https://www.postgresql.org/docs/18/runtime-config-logging.html)

L-A의 후속 수용 범위는 선택한 표준 PostgreSQL/psql 실행의 정상·예상 SQL 오류/연결 실패에서 값이 원문 로그에 남지 않는지 검증하는 것이다. PANIC·추가 감사/추적 확장·관리자의 환경/활동 조회·메모리/덤프·외부 수집기는 자동으로 제어됐다고 보장하지 않는다. 그런 경로가 있거나 설정 조건을 확인할 수 없으면 비밀 SQL 실행 전에 조건을 반환해 별도 검토한다. 기존 V-A의 환경 조회 권한자 노출 한계도 유지한다.

### C-S-E — 셸/psql 출력과 진단 정보량

| 대안 — A 확정, B 비채택 비교안                | 표시/보관 후보                                                                                                                                                                              | 추천 이유·부담                                                                                                     |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| **E-결론: 고정 단계·결과·psql 종료값만 공개** | 셸/psql의 원문 stdout/stderr·SQL/값을 콘솔/로그/첨부/임시 파일로 남기지 않고 검토한 고정 단계/실패 분류와 종료값으로만 보고. 원문에 마스킹 정규식을 적용해 그대로 전달하는 방식은 쓰지 않음 | 새 두 역할 준비에는 비밀값이 섞일 필드를 최소화하기 쉬움. 실패 원인 상세가 줄어 사전 검사와 합성 입력 재현이 중요  |
| E-B 비채택 비교: 검증된 SQLSTATE만 추가       | E-A 제한을 유지하면서 구조화된 DB 코드로 확실히 식별한 SQLSTATE만 추가. 원문 오류/DETAIL/HINT/CONTEXT/SQL·입력값은 표시하지 않고 코드를 확정 못하면 고정 실패로 반환                        | 무결성/권한 등 실패 구별에 유리. 서버 오류/연결/클라이언트 오류의 코드 수집·허용 형식·출력 경로 검증이 추가로 필요 |

E-A의 진단 형식은 stage=role_prepare result=failed psql_exit=3과 같은 고정 필드/단계·허용 종료값·unknown 처리다. [B2](task-001-startup.md#f4-bootstrap-integrated)를 따르며 실제 고정 출력/실패 종료는 격리 검증했다. 공개 API 오류나 PK guard SQLSTATE에 자동 매핑하지 않는다.

psql은 SQL echo/출력 로그 옵션을 가지며 quiet 모드만으로 오류가 사라지지 않는다. 사용자 psqlrc·셸 추적/환경 출력·SQL echo·클라이언트 추적/출력 파일을 쓰지 않는 구체 실행을 대조한다. E-B 검토에 사용할 수 있는 SQLSTATE verbosity도 코드가 없으면 TERSE와 같이 원문 주 메시지로 되돌아갈 수 있으므로, 그 모드만 켜고 stderr를 그대로 출력하는 안은 아니다. [psql 출력/오류 옵션](https://www.postgresql.org/docs/18/app-psql.html) · [SQLSTATE 오류 형식과 fallback](https://www.postgresql.org/docs/18/libpq-control.html)

쉘의 원문 출력은 환경값 검사/psql 연결 전부터 관리해야 하고, DB 로그는 L의 별도 제어가 필요하다. 셸이 psql stderr를 버린다고 DB 로그가 없어지지 않으며 DB 로그를 제한해도 셸 추적/명령행/기존 개인 파일 노출은 해결되지 않는다. 원문 오류를 개인 파일에 따로 보관하는 예외나 실제 비밀값을 이용한 진단은 이 제안에 포함하지 않는다.
