<a id="goal"></a>
## 문제와 목표 및 수용 조건

번호만으로는 브랜치 목록에서 작업 목적을 구별하기 어려워 Phase·Issue·Task 이름에 짧은 작업명을 붙인다.

- 범위: [Git 기준](<../../../../docs/Git 작업 기준.md#current>)의 이름·작업명 작성·병합 후 재개 예시, [Git 절차](<../../../../harness/Git 작업 절차.md#start>)의 이름 기준 연결과 이 담당 기록.
- 제외: 문서 분할, 추가 요청 판단 skill, 저장소 설정, 과거 기록 개명, PR 병합.
- 수용 조건: 번호·계층·분기·병합 방식과 커밋·PR 식별 형식을 유지하면서 세 단계 신규·재개 이름에 작업 목적을 표시한다. 과거 숫자 전용 이름의 재개도 새 형식과 충돌하지 않아야 한다.
- 제출 조건: 분할 변경과 분리해 자체·별도 검수, 관련 참조와 실제 제출 범위 확인을 마친다.

<a id="plan"></a>
## 해결 계획과 의존

<a id="activity"></a>
## 주요 논의와 판정 근거

### 2026-11-07 — 이름 변경의 독립 제출

- 사용자는 Phase·Issue·Task 모두에 작업명을 붙이고 재개 시 이름을 유지하는 방향을 승인했다. 상세 제목·상태 변경만으로 브랜치를 개명하지 않는다.
- 이름 변경과 문서 분할은 각각 별도 Issue·커밋·PR로 구분하며 병합하지 않고 PR 생성까지만 수행한다.
- 추가 요청의 목적·분리 판단 규칙은 사용자가 향후 하네스 skill로 다룰 예정이므로 이번 변경에 포함하지 않는다.
- 문서 분할을 마친 로컬 결과는 보존한 채 이름 변경만 먼저 제출한다. 두 독립 Issue 모두 main에서 분기하고 main으로 PR을 만든다.

## 결과와 미해결
