## 명령별 역할과 공용 절차 확정

- 할 일: [Task 본문](../task-002.md#work-pending-plan)

- 조치·판단: [r002](task-002-assignment-r002.md)와 [단계 계획](task-002-plan.md#stage-contract)을 적용한다. 승인된 공통 진행 방식은 [합의](task-002-plan.md#command-agreement)를 따른다. 요청 의도·실제 상태에 따른 명령 선택, 명시 범위 우선, 결과 보고·재개 전환은 공용 절차에 둔다. 단위별 준비·기록·수용은 기존 Issue·Task 공통 절차를 참조한다. 생성·등록·검수는 기존 스킬을 진입점으로 두고 필요한 참조만 연결한다.
- 확인: 세부 작업별 자가검수를 수행했다.
  1. 두 선행 결과와 r002·사용자 승인 근거를 대조했다. 종전 형식인 87-002는 본문 단계 체크와 수행 기록을 사용하고, 신규 형식은 실제 별도 계획·합의 근거·지문과 기록 연결을 사용한다.
  2. Issue 명령 세 개를 [Issue 공통 절차](<../../../../../harness/Issue 공통 절차.md>)와 대조했다. 공통 입력은 대상 Issue, 요청 범위·권한, 담당 본문이다. `issue-plan`은 기존 결정·배정·전체 수용을 읽고 제안 또는 실제 합의를 기록한다. `issue-run`은 현재 단계의 Issue 행동을 진행하고 하위 발급은 승인된 `create-task` 경로로 연결하며 결과가 부족하면 대기 위치와 다음 확인을 남긴다. `issue-resume`은 하위 상태·의존·마지막 결과와 승인 범위를 대조해 실행·대기·확인을 반환한다. 하위 작업의 실행과 자기 수용은 Task가 소유한다.
  3. Task 명령 세 개를 [Task 공통 절차](<../../../../../harness/Task 공통 절차.md>)와 대조했다. 공통 입력은 실제 Task, 부모의 확정 전달본·요청 범위·기존 권한이다. `task-plan`은 양식별 계획 원본과 사용자 합의를 관리하고 신규 형식의 확정 지문을 기록한다. `task-run`은 공통 준비와 현재 계획을 확인하고 다음 승인 행동을 실행해 실제 결과·검수·체크를 담당 원본에 남긴다. `task-resume`은 계획·워크트리·마지막 실행과 검수 근거·권한을 대조하고 유효한 다음 행동이 있으면 `run`으로 연결한다. 합의·권한·필수 근거의 부족과 계류 결과는 의존 행동의 제한으로 기록한다.
  4. 역할 분담과 연결 범위를 [공용 절차](<../../../../../harness/공용 절차.md>) 및 기존 생성·검수의 적용 범위와 대조했다. Issue·Task의 최초 계획은 생성 결과에서 안내하고, 진행·검수는 실제 입력과 기록 원천을 참조한다. GitHub 등록·종료와 커밋의 실행 권한은 해당 행동별 기준을 사용한다.
  - 별도 검수: 여섯 명령의 입력·역할·권한·기록 원천·대기 조건과 4개 자가검수 근거를 r002·부모 배정·공통 절차에 직접 대조했다. 기존 r001과 보호 주석이 유지됐으며 필수 결함이 없었다. 실제 스킬 호출은 3단계 확인 범위다.
- 잔여: 없음.

## 여섯 스킬과 진행·재개 절차 연결

- 할 일: [Task 본문](../task-002.md#work-skill-linkage)
- 조치·판단: 검수한 역할에 따라 여섯 스킬을 추가하고 공용 절차, 기존 생성·검수 스킬 및 현황을 연결한다.
- 확인: 구현 후보의 세부 작업을 자가검수했다.

  - 별도 검수: Issue 준비·생성 미완료와 3단계 하위 결과 대기 조건을 구분하도록 두 Issue 스킬을 보완했다. 단위별 권한과 기록 경계, 여섯 스킬과 기존 세 스킬의 링크·의존·지문·현황이 일치했다. 생성 후 계획 연결은 create-issue의 결과 반환 구역에 뒀다.
- 잔여: 없음.

## 명령과 진행·재개 사례 검증

- 할 일: [Task 본문](../task-002.md#work-command-validation)
- 조치·판단: [검증 계획](task-002-plan.md#stage-validation)에 따라 실제 후보의 형식과 정상·보류·재개 사례를 대조했다.
- 확인: 실제 후보와 대표 사례를 세부 작업별로 자가검수했다.
  1. 여섯 스킬의 이름·본문 링크·앵커·의존과 스킬·훅 현황 검사, 실제 작업 후보의 기록 규칙 검사가 통과했다. 보호 주석·계획 지문 회귀 29건과 현황의 CandidateTests 31건이 통과했다. 확정 전달본의 필수 내용·참조 누락을 검출하고, 정상 생성 경로의 내용 확인을 기존 생성 스킬과 대조했다.
  2. 여섯 스킬을 읽기 전용 Codex 실행에 명시 입력으로 전달했다. 처음에는 이 계정에서 구성된 기본 모델을 지원하지 않아 거절됐다. 지원 목록의 기본 모델을 검증 실행에만 지정한 뒤 완료했고, Issue 논의와 결과 대기, 별도 검수 누락에 따른 완료 보류, 두 Task 형식과 재개 판정이 계획과 일치했다. 연결 문서 읽기 도구가 실패해 이 실행은 첨부 스킬만 적용했다.
  3. 별도의 평가 에이전트가 스킬·로컬 절차를 직접 읽고 여섯 모의 사례를 재현했다. 두 승인 행동의 연속 진행, 한 단계로 지정한 범위에서 멈춤, 다음 행동의 전제가 부족할 때 허용된 독립 확인의 계속을 별도로 대조했다. 합의에 포함된 계획 내용 변경은 지문을 바꾸고 체크만 갱신하면 지문이 유지되는 것을 회귀에서 확인했다. Issue 결과 대기는 3단계 생성 완료 이후에만 적용했다. 미승인 외부 발급은 보류하고, Issue 본문의 미결정과 다음 승인 확인을 반환했다. 옆 주제를 조회한 뒤 계획·권한·다음 행동이 유효한 사례는 같은 Task의 run으로, 작업 폴더나 외부 결과가 불명확한 사례는 resume으로 판정했다. Task 본문은 위치·막힘·다음 행동, 수행 기록은 검증·복구 근거를 담당했다.
  4. 외부 결과가 불명확한 모의 사례에서 결과 조회를 우선했다. 성공은 결과 재사용, 계류·미확인은 중복 실행 보류, 부분 반영은 허용된 복구, 미실행은 권한·실행 전제 대조로 판정했다. 보고·저장 위치는 모의 응답에서 대조했다. 실제 저장의 구조·체크·왕복 링크는 임시 저장소의 신규 양식 회귀와 이 Task의 종전 양식 본문·실제 2/4단계 수행 기록에서 대조했다. 외부 상태 변경·실제 컨텍스트 압축은 이 검증에 포함되지 않았다. 스킬 작성기 보조 검사에는 PyYAML이 없어 Codex 인식 검사와 직접 구조 검사로 대신했다.
  - 별도 검수: 권한이 없는 외부 발급 보류, 다른 주제에서 돌아올 때 run과 resume의 구분, 모의 판정과 실제 저장 증거의 범위를 대조했다. 3단계 완료를 막는 항목이 없었다.
- 잔여: 없음.

### 87-003에서 사용할 입력

- [여섯 스킬 원천과 확인 범위](<../../../../../harness/스킬 현황.md#current>) 및 [공용 진행·재개 절차](<../../../../../harness/공용 절차.md#operation-commands>)를 사용한다. 승인된 연속 진행, 명시 범위로 멈춤, 상태 대조 후 같은 단위의 실행 복귀를 구분한다.
- Issue는 본문의 3단계 결과 대기와 하위 Task의 실제 결과를 대조한다. Task는 형식별 실제 계획·체크·합의와 마지막 실행·검수 근거를 복원한다. 신규 형식의 계획 원본과 지문, 기존 형식의 본문과 수행 기록을 함께 시범 입력에 포함한다.
