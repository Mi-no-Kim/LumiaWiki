<a id="command-agreement"></a>

## 진행·재개 방식 합의

- `run`은 대상·다음 행동·권한을 짧게 확인한다. 사용자 요청에 명시된 단계·파일·행동 범위를 우선 적용하고, 그 안에서 같은 작업 단위의 승인된 다음 행동을 연속 수행한다. 필수 검수나 결과 대기가 미해결이거나 새 합의·권한이 필요하면 그 조건에 의존하는 행동을 보류한다.
- `resume`은 기록과 실제 상태·마지막 검수·권한을 대조한다. 다른 주제에서 돌아와도 다음 행동과 권한이 명확하면 `run`으로 이어가고, 상태 또는 실행 결과가 불명확하면 `resume`에서 먼저 대조한다. 이어갈 행동과 권한이 확인되면 같은 `run` 절차를 사용한다. 중단된 외부 작업은 실행 여부·부분 반영부터 조회한다.
- 근거: `run`과 `resume`의 진입 기준 제안에 사용자가 “그러면 되겠네”라고 응답했다. 연속 진행의 기본값은 “승인된 범위에서 연속 진행으로 하면 될 것 같아. 명시적인 범위가 있다면 그걸 따르고”라는 응답으로 정했다. 적용 범위는 두 명령의 진입과 같은 단위 안의 진행 방식이다.

## 1. 명령별 역할과 공용 절차 확정

1. 개정 배정과 두 선행 결과를 대조한다. 여섯 명령에 대해 필수 입력, 담당 원본과 기록할 내용, 실행 범위, 보류·대기 조건, 반환할 결과를 정리한다.
2. Issue의 `plan`은 배정·의존 관계·전체 수용 기준, `run`은 허용된 Issue 행동·Task 생성 절차 연결·결과 대기와 전체 수용, `resume`은 하위 결과와 선행 관계 복원을 맡는다. 하위 Task 내부 실행·검증·체크 갱신은 해당 Task 절차와 권한을 따른다.
3. Task의 `plan`은 배정 범위의 단계·완료 기준과 실제 합의 기록, `run`은 승인된 Task 실행·검수 연결과 상태 갱신, `resume`은 실제 변경·마지막 확인·유효한 승인 대조를 맡는다. 계획 합의와 실행 권한을 구별하고 대상이 모호하면 의존 행동 전에 확인한다.
4. [공용 절차](<../../../../../harness/공용 절차.md>)와 Issue·Task 공통 절차 중 공통 진입·진행·완료의 적용 위치를 정한다. 생성은 `create-issue`·`create-task`, 검수는 `review-work`에 연결한다. 새 책임·권한이나 기준이 필요한 결정은 구현 전에 합의한다.

**완료 기준과 확인** 여섯 명령에서 대상·필수 역할·권한·기록 위치·다음 행동을 해당 원천과 대조할 수 있다.

<a id="stage-skills"></a>

## 2. 여섯 스킬과 진행·재개 절차 연결

1. `$issue-plan`, `$issue-run`, `$issue-resume`, `$task-plan`, `$task-run`, `$task-resume`을 만들고 1단계에서 확인한 공용 절차와 단위별 원천을 참조한다.
2. 신규 Task는 별도 계획·확정 전달본·실제 합의 근거·자동 계산한 지문을 확인하고, 기존 Task는 본문 계획·합의·단계 체크를 확인한다. 단계 체크는 형식별 원본에서 관리한다. Task 본문·계획·수행 기록과 Issue의 배정·결과 대기를 해당 원본에 남긴다.
3. 세부 작업 완료 전에는 자가검수한다. Task 각 단계 완료 및 Task·Issue 종료 전에는 자가검수와 서브에이전트 검수를 실제 결과·수용 기준에 연결한다. 세부 작업별 판정은 기존 수행 기록에 짧게 남기고, 유효한 검수 근거는 영향 범위에서 재사용한다.
4. 생성 경로에서 확정 전달본의 필수 내용과 본문 요약을 대조하고, 검수 경로에서 실제 적용 계획과 근거를 찾을 수 있게 한다. 영향받는 스킬 원천·등록·조건·의존을 [스킬 현황](<../../../../../harness/스킬 현황.md>)과 맞춘다.

**완료 기준과 확인** 여섯 정의와 스킬 현황이 일치하고 두 Task 형식 및 Issue의 생성·계획·실행·재개·검수가 담당 기록에 연결된다.

<a id="stage-validation"></a>

## 3. 명령과 진행·재개 사례 검증

1. 스킬 형식·등록·참조·현황 지문과 보호 주석·기록 검사를 수행한다. 생성 본문과 확정 전달본의 정상 대응, 필수 내용이나 참조가 빠진 사례를 비교한다.
2. Issue와 Task에서 `plan`의 합의 대기와 `run`의 승인된 연속 진행을 검증한다. 명시한 한 단계까지만 실행하는 요청, 미승인 외부 행동, Issue가 하위 결과를 기다리는 중 하위 실행 권한이 없는 사례를 확인한다.
3. 신규 Task에서 계획 내용 변경과 진행 체크만 갱신한 경우를 대조하고, 합의 근거 또는 필수 검수 근거가 빠졌을 때 영향받는 처리가 보류되는지 확인한다. 기존 Task는 본문 계획과 체크를 사용하며, Issue 전체 수용은 결합된 하위 결과와 별도 검수 근거로 판단하는지 확인한다.
4. 잠시 다른 주제를 다룬 뒤의 `run` 복귀와 실제 상태가 달라져 `resume`이 필요한 경우를 비교한다. 외부 결과가 불분명하면 기존 결과를 먼저 조회한다. 성공이 확인되면 기존 결과를 사용하고, 계류 중이거나 여전히 미확인이면 중복 실행을 보류하고, 부분 반영이면 복구 절차로 연결하고, 미실행이 확인되면 기존 권한·실행 전제를 대조한 뒤 진행하는지 검증한다. 발급 등은 검증용 입력을 사용하고 실제 명시 호출·재현·형식 검사의 관찰과 한계를 구별한다.

**완료 기준과 확인** 개정 배정의 수용 조건별 실제 수행·관찰·판정·한계를 담당 수행 기록에서 찾을 수 있다.

<a id="stage-review"></a>

## 4. 결과 검수와 87-003에 전달

1. 실제 후보와 개정 배정 전체를 자체·서브에이전트 검수하고 지적의 영향 범위에 해당하는 검증을 다시 수행한다.
2. 87-003에 명령·기록 위치·확인된 재개 사례·남은 검증과 87-002 결과를 전달한다. 실제 컨텍스트 압축과 자동 훅 적용 여부는 87-003에서 판단한다.
3. Task 자기 수용과 부모의 수용을 구별하고 허용된 제출·통합·종료 절차를 확인한다. 실제 결과와 판정·한계에 맞춰 Task 및 관련 조회 기록을 갱신한다.

**완료 기준과 확인** Task 수용과 제출·반영 상태, 87-003의 재개 입력과 검수 근거를 추적할 수 있다.
