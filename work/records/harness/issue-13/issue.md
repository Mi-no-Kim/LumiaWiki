<a id="goal"></a>
## 문제와 목표 및 수용 조건

추가 요청을 기존 작업에 섞기 전에 목적·수용 조건으로 작업 단위와 커밋 구성을 판단하고, 커밋 전에 실제 결과를 자체·별도 에이전트가 구체적으로 검수하도록 한다. 스킬 이름이나 ‘검수’라는 단어만으로 행동을 추측하지 않도록 확인할 대상·근거·판정·재확인을 명시한다.

- 범위: [추가 요청 판단](<../../../../.agents/skills/triage-additional-request/SKILL.md>), [작업 결과 검수](<../../../../.agents/skills/review-work/SKILL.md>)와 AGENTS·기존 기준·절차의 필수 연결. 시험 중 발견된 첫 전체 Git 조회의 보존 영역 제외 누락도 같은 구현의 보완으로 포함한다.
- 제외: 훅·새 실행 프로그램·검수 증명 첨부·제품 변경·보존 영역 접근·push·PR·병합. 기존의 명시적 보존 접근 허용 예외는 유지한다.
- 기준: [작업 단위](<../../../../docs/작업 기록 체계.md#ownership>), [검증과 완료](<../../../../docs/details/operations/검증과 완료.md>), [별도 검수](<../../../../docs/details/operations/별도 검수.md>), [커밋](<../../../../docs/details/git/작업 커밋 기준.md#working-commits>)과 [보존 경계](<../../../../docs/문서 관리 기준.md#harness-design-boundary>).

수용 조건은 다음과 같다.

1. 추가 요청은 첫 수정·등록·전환 전에 작업 단위를 판단하고, 그 안에서 커밋 단위를 따로 판단한다. 필요한 분리를 알리며 기존 변경·권한을 보호한다.
2. 검수는 범위·필요성, 요구·정확성, 연결·영향, 검증 근거, 기록·상태, 제출 일치를 실제 원자료와 대조한다. 새 작업 결과의 커밋에는 자체·별도 에이전트 검수가 적용된다.
3. 일반 리뷰와 커밋 특화 확인을 구별하고, 기존 기준의 전문·새 양식·불필요한 승인·작업 단위·반복 검수를 늘리지 않는다.
4. 새 대화에서 두 필수 연결과 단순 조회의 범위를 확인한다. 관찰된 첫 경로 조회부터 보존 영역을 제외하며 실제 명령과 최종 설명을 대조한다.
5. 담당 Issue·기록·로컬 브랜치를 갖추고, 구현·문서·기록을 같은 변경 목적의 최종 커밋 후보로 준비·검수한다. 실제 커밋 실행·결과 확인은 승인된 다음 행동으로 구별한다.

## 해결 계획과 의존

두 스킬의 공통 목표는 추가 요청과 커밋 준비 시 AI가 기존 작업 기준을 실행하는 흐름을 갖추는 것이다. 각 스킬은 역할을 분리하고, 기준의 판정 원칙·스킬의 수행 행동·AGENTS와 절차의 호출 연결을 구별한다. 보존 경계 수정은 이 흐름의 시험에서 확인한 누락을 보완하며 별도 목표의 작업으로 확대하지 않는다.

이미 대화에서 수행한 구현·검수·시험의 유효한 근거를 재사용하고, 이번 등록·담당 기록·실제 커밋 후보처럼 달라진 부분을 추가 확인한다. Task나 가짜 Phase를 만들지 않는다. 최종 수용 판단·상태·기록을 커밋 전에 갖추며 문서 정리만을 위한 별도 커밋 단계는 두지 않는다.

## 수용 판단과 검증 근거

### 대표 상황과 문구 적용

다음은 별도 에이전트가 실제 스킬 본문을 읽고 제공된 모의 입력에 적용한 9개 상황이다. 실제 제품·GitHub 변경을 실행한 시험과 구별한다.

| 입력 상황 | 확인한 판단 |
|---|---|
| 현재 기능의 테스트 실행에 필요한 workflow 보완 | 같은 제품 작업에 포함 가능하며 파일 위치만으로 독립 하네스 Issue를 만들지 않음 |
| 저장소 전체 문서 게시 자동화를 먼저 요청 | 독립 목표로 분리하고 기존 변경 보존·처리 순서·복귀 조건을 착수 전에 판단 |
| 상태만 질문 | 필요한 조회로 답하고 새 Task·전수 조사·검수를 강제하지 않음 |
| 같은 Issue의 독립 태그 필터 구현 | 별도 Task 여부를 수용 단위로 판단하며 같은 파일을 수정한다는 이유로 합치지 않음 |
| 커밋 후보에 필요한 미스테이징 의존 변경이 없음 | 작업 폴더의 실행 성공을 후보의 성공으로 쓰지 않고 누락된 동반 변경을 지적 |
| 본문과 중복인 API 출력 JSON의 사용처가 없음 | 작성자 파일 목록도 검토하며 링크 통과만으로 첨부 필요성을 인정하지 않음 |
| 원자료 접근 불가·필수 에이전트 호출 실패 | 미확인을 반환하고 WIP로 필수 검수를 우회하지 않음 |
| 관찰 요약 추가와 새 완료·동작 주장 추가 | 충실한 요약의 자체 확인과 의미가 달라진 부분의 재검수를 구별 |
| 기검수 결과의 통합과 충돌 해결로 코드 변경 | 근거의 유효성을 확인해 재사용하고 달라진 동작·의존을 재검수 |

의존 변경 누락의 위험은 메모리 안의 작은 실행 예시로도 확인했다. `query.py`가 `rules.normalize`를 가져오지만 후보의 `rules`에는 함수가 없으면 ImportError가 발생했고, 작업 폴더에만 함수가 있는 경우는 실행됐다. 실제 저장소에 시험 파일·커밋을 만들지는 않았다.

### 새 대화의 필수 연결과 보존 경계

요청문·통과 조건을 자체·별도 검수해 답변 항목의 과도한 안내를 제거했다. 스킬 이름·평가표를 주지 않고 아래 새 대화를 실행했다. 대화 제목·ID는 로컬 앱에서 원래 실행을 찾는 단서이며 공개 GitHub 근거 링크가 아니다.

| 대화와 입력 | 실제 관찰·판정 |
|---|---|
| 읽기 전용 확인 1 — 검색 작업의 모의 맥락 뒤 게시 자동화 추가 요청. `01a1b5bf-dc30-74e1-ae07-3f0b3c81a444` | 추가 요청 스킬 본문을 실제 읽고 독립 Issue·변경 목적별 커밋과 기존 변경 보호를 판단. 구체적인 복귀 조건과 실제 보존·전환 실행은 미검증 |
| 읽기 전용 확인 2 — 실제 미커밋 변경의 커밋 준비 여부. `01a1b5c1-1616-7fa0-8e56-653e78a39905` | 검수 스킬 조회·실제 서브에이전트 호출·결과 대조를 확인. 최초 `git status`에는 보존 영역 제외가 없어서 접근 경계 준수는 실패로 판정. 보존 본문을 실제 열었다고 단정할 증거는 없음 |
| 읽기 전용 확인 3 — 미커밋 파일 이름만 조회. `01a1b5c3-5ca9-7203-bb11-8351c9fc7b92` | 보존 영역을 제외하고 파일 목록만 반환. 내용 검수·불필요한 위임·새 기록으로 확대하지 않음 |
| 읽기 전용 확인 4 — 두 구절 보완 후 2번과 같은 요청. `01a1b5d3-c4d7-75d3-be1c-3179fac6904f` | 첫 Git 상태 조회부터 두 보존 영역을 제외했고 후속 전체 차이·상태 조회도 동일 경계를 적용. 자체·별도 검수와 결과 대조를 수행. 시험 전후 기존 11개 파일·목록·스테이징·HEAD·브랜치 동일 |

재시험은 저장소 루트에서 다음 명령으로 시작했다.

```powershell
git --no-optional-locks status --short --untracked-files=all -- . ':(exclude)harness-design' ':(exclude).harness-state'
```

직접 원인은 기존 경계를 첫 조회 명령에 적용하지 않은 것이며, 내부 판단의 이유는 추정과 구별했다. AGENTS의 첫 조회 적용 문장과 검수 스킬의 실제 조회 범위·결과 설명 대조 구절만 보완했다. 출력에 보존 경로가 없거나 파일 변경이 없다는 이유만으로 접근 준수를 판정하지 않는다.

확인 가능한 활동 기록에서는 실제 위임·원자료 조회·검수 완료·주 진행 에이전트의 결과 대조를 관찰했다. 위임 입력 전문의 모든 전달 항목까지 확인된 것은 아니다. 지침 적용의 관찰을 완전한 접근 통제나 지속적인 재발 방지 보장으로 확대하지 않는다.

이번 정식화의 커밋 준비 중에도 주 진행 에이전트의 보조 인덱스 조회 일부(`git diff --cached --raw`, `git diff --cached --name-only`)에 경로 제외가 빠진 것을 최종 자체 대조에서 확인했다. 이 실행의 범위 구성은 미준수로 기록하며, 출력에 보존 경로가 없거나 내용 열람 증거가 없다는 이유로 준수로 바꾸지 않는다. 이후 조회는 허용 경로·명시적 제외를 적용한다. 별도 새 대화에서 첫 조회를 준수한 결과와 이번 적용 누락을 구별하며, 문구·스킬 연결만으로 모든 실행을 강제할 수 없다는 실제 운영 한계로 남긴다. 훅은 사용자 제외 범위에 따라 추가하지 않는다.

### 형식·참조·필수성·최종 후보

- 두 스킬의 번들 형식 검사를 통과했다. 필요한 YAML 해석기는 임시 위치에서 사용 후 정리했고 저장소·전역 Python 설정을 변경하지 않았다.
- 담당 기록 추가 전 11개 문서의 내부 링크 110개·표식·변경 형식 검사를 통과했다. 최종 기록을 포함한 후보의 검사·수용 판단은 아래 최종 검수에서 확인한다.
- 구현·최소 보완의 자체·별도 검수 지적 중 Git 제외 대상 보호 문구 누락은 복원했고, 검토 전용 요청은 미해결·미확인을 반환할 수 있도록 명확화했다. 두 구절 보완의 재검수에서도 남은 필수 지적이 없었다.
- 작업 단위·커밋 단위 구분과 실제 후보·원자료 대조는 필요하다. 모든 커밋·WIP의 별도 검수는 사용자 합의에 따른 강화 정책이며 작은 수정에도 호출 비용이 든다. 단순 조회·승인에 전체 조사·새 작업을 강제하지 않고 유효 근거 재사용·변경 영향 재검수·범위 밖 권고 분리로 반복을 제한한다.
- 이번 정식화의 최종 자체·별도 검수에서 HEAD `4740a711218e1772dda3cd1d437453cbe392eef3` 대비 실제 인덱스의 12개 파일과 작업 파일의 일치, 내부 링크 117개·변경 형식, 기준·절차의 일관성·최소성, 실제 Issue의 원본 경로·라벨·관계를 확인했다. 수용 조건 5의 자기 완료와 실제 커밋 성공을 혼동할 수 있는 문구를 수정해 재확인했고 남은 필수 지적은 없다. 완료 판단 뒤 기록 반영에 따른 최종 후보 일치는 커밋 직전에 다시 확인한다.
