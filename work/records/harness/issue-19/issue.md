- 제목: 작업 기록 기준 간소화
- 실제 GitHub Issue: [Mi-no-Kim/LumiaWiki #19](https://github.com/Mi-no-Kim/LumiaWiki/issues/19)
- 상태: 완료
- 현재 진행 위치: 기록 범위의 주원천과 관련 기준·절차를 정리하고 사례 대조와 실제 제출 후보의 자체·별도 검수를 마쳤다.
- 다음 판단/행동: 정리 결과를 반영하고 Issue #15의 Task 구성 논의로 복귀한다.

<a id="goal"></a>
## 문제와 목표 및 수용 조건

작은 결정 조정과 AI 제안 수정을 변경 이력으로 남기게 하는 포괄적인 기록 의무를 좁힌다. 현재 안의 갱신으로 충분한 일은 해당 내용을 갱신하고, 당시 사실이 필요한 실행·실패·부분 반영·복구와 유효한 승인·검증 근거는 보존한다.

### 범위

- [작업 기록 작성 기준](<../../../../docs/작업 기록 작성 기준.md#recording-boundary>)을 주원천으로 현재 안 갱신과 이력 보존의 경계를 정한다.
- [문서 참조와 변경 기준](<../../../../docs/문서 참조와 변경 기준.md#correction>), [관찰과 개선 기준](<../../../../docs/details/operations/관찰과 개선.md>), [문서 관리 절차](<../../../../harness/문서 관리.md#update>)를 같은 경계에 맞춘다.
- 정상 등록·확인은 담당 위치의 정보와 필요한 최종 근거로 충분하면 별도 사건 로그를 만들지 않는다.
- 라벨 확장·생성·정의 변경과 Phase 001의 제품 설계·Task 확정은 각각 별도 범위다.

### 수용 조건

- 작은 결정 조정과 AI 제안 수정은 현재 안 갱신으로 처리하며 별도 이력을 요구하지 않는다.
- 실제 실패·부분 반영·복구에 필요한 당시 사실과 유효한 승인·검증 근거를 보존한다.
- 관련 기준·절차가 같은 경계를 사용하고 정상 등록·확인마다 사건 로그를 요구하지 않는다.
- 아래 두 사례로 기록 경계를 대조하고 자체·별도 검수 및 문서 연결 확인을 마친다.
- 로컬 독립 Issue를 원본으로 GitHub의 내용·상태·독립 관계를 맞춘다.

<a id="plan"></a>
## 해결 계획과 의존

Issue #15의 현재 구성안 보존 → 기존 기준·절차 최소 수정 → 사례 대조·별도 검수 → 독립 반영 → 제품 Task 구성 논의 복귀 순으로 직접 수행한다.

<a id="verification"></a>
## 수용 판단과 검증 근거

| 대조 사례 | 기대 결과 |
|---|---|
| AI 제안의 항목을 수정하거나 작은 결정의 범위를 조정 | 현재 결론·미정·다음 행동만 갱신하고 이전 안·번복·정정 이력을 추가하지 않는다. |
| 실제 반영이 실패하거나 일부만 반영돼 정정·복구 | 당시 관찰·반영 범위·원인과 복구에 필요한 근거를 보존한다. 없던 승인·성공을 추가하거나 실제 검증 결과를 덮어쓰지 않는다. |

위 두 사례를 기준·절차의 실제 문구와 대조했고, 자체·별도 검수에서 필수 지적이 없음을 확인했다. 정상 등록·확인도 담당 위치와 최종 근거로 충분하면 별도 사건 로그를 요구하지 않는다. 제출 후보 5개 파일의 범위·상대참조·표식·패치 검사를 통과했다.

<a id="result"></a>
## 결과와 미해결

현재 안 갱신과 필요한 사실 이력 보존의 경계를 공통 기준에 반영하고 관련 절차를 맞췄다. 라벨 확장은 별도 범위로 유지한다. 장기적인 운영 효과는 후속 사용에서 확인하며, Issue #15의 기존 Task 구성 논의를 이어간다.
