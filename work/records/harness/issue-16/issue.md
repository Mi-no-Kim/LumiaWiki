# 화면 디자인 선행과 화면 기반 기능 검증 기준 정립

<a id="summary"></a>

## 현재 요약

- 제목: 화면 디자인 선행과 화면 기반 기능 검증 기준 정립
- 실제 GitHub Issue: [Mi-no-Kim/LumiaWiki #16](https://github.com/Mi-no-Kim/LumiaWiki/issues/16)
- 상태: 완료
- 현재 진행 위치: 공통 기준·절차·양식과 독립 담당 기록을 분리하고 실제 제출 후보의 자체·별도 검수를 마쳤다.
- 다음 판단/행동: 정리 결과를 반영하고 Issue #15의 Task 구성 논의로 복귀한다.

<a id="goal"></a>

## 문제와 목표 및 수용 조건

Phase 001 설계 Issue #15에 함께 반영했던 공통 화면 규칙의 관리 책임을 독립 과제로 분리한다. 사용자가 정한 원칙은 제품 기능의 동작 구현 전에 화면 디자인을 하고, 검증도 화면이 있는 상태에서 하는 것을 기본으로 한다는 것이다.

### 범위

- [공통 기준](<../../../../docs/details/operations/검증과 완료.md#screen-first>) 한곳에 원칙을 두고 [운영 기준 안내](<../../../../docs/하네스 운영 기준.md#current>)와 [설계·계획 절차](<../../../../harness/작업별 절차.md#planning>)를 연결한다.
- 로컬 및 GitHub Issue·Task 양식에 화면 위치, 디자인·구현 선후 관계, 화면에서 검증할 흐름을 연결하도록 한다.
- Phase 001의 범위·Task 확정과 제품 화면 제작·기능 구현은 각각 담당 제품 과제에서 진행한다.

### 수용 조건

- 동작 구현 전 화면 디자인과 화면이 있는 상태의 기능 검증이 공통 기준에 명시되어 있다.
- 절차·양식이 동일 기준을 사용하며 디자인 검토와 실제 동작 검증을 구별한다.
- 이번 Issue가 규칙 정비의 범위·수용·결과를 소유하고, Issue #15는 적용 관계만 관리한다.
- 실제 제출 후보의 자체·별도 검수와 문서 연결 확인을 마치고 로컬·GitHub의 내용·상태·원본 연결을 맞춘다.

<a id="plan"></a>

## 해결 계획과 의존

기존 변경 보존 → 공통 규칙 7개 문서 분리 → 담당 기록 정리 → 자체·별도 검수 → 원격 반영 확인 순으로 진행한다. 작고 하나의 수용 결과를 가진 기준 정비이므로 이 Issue에서 직접 수행한다.

## 수용 판단과 검증 근거

- 사용자의 화면 선행 원칙과 공통 기준·절차·양식을 대조했고, 실제 인덱스 8개 파일의 자체·별도 검수에서 필수 결함이 없음을 확인했다. 문서 연결·표식·패치 검사도 통과했다.
- 제출 후보에는 공통 규칙 7개 문서와 이 기록만 포함한다. Phase 등록 정보와 Issue #15의 제품 설계는 별도 변경으로 구별했다.

## 결과와 미해결

화면 디자인 선행·화면 기반 기능 검증 기준과 절차·양식 연결을 독립 하네스 Issue로 정리했다. 제품 화면 제작과 기능 동작의 검증은 후속 제품 과제에서 수행한다. Issue #15에서는 공통 규칙의 적용 관계를 연결하고 미합의 Task 구성 논의부터 재개한다.
