## Java 배치와 의존 규칙 결정

- 할 일: [Task 계획](../task-001.md#work-layout)

- 조치·판단: r001과 보완 계획을 사용한다. 실행 근거는 사용자의 `진행해줘`다. 부모 `94babc10`에서 Task 브랜치를 생성했다. Git 참조 `72c27a11`의 앱 루트·`common/api`·`dev`·테스트 소스와 빌드 설정을 조사했다. r001의 상세 설계 위임으로 기존 스캔 루트와 프로필 경계를 보존하고 업무 모듈별 역할 패키지와 명시적 공개 타입을 정했다. 모듈·`dev`·공유 픽스처에서 공유하는 기술 타입을 계약으로 한정하고 `common`의 역방향 업무 의존을 금지한다. 기존 앱·공용 구성 테스트의 공용 빈 조립을 보존한다.
- 확인: 참조 커밋의 `LumiawikiApiApplication`은 기본 스캔의 루트다. `FoundationController`와 `FoundationService`는 `local`·`test` 프로필에 한정되며 `FoundationService`가 `ApiFailure`를 참조한다. 로컬 main과 Task 기준 트리에는 추적된 `backend/`가 없다.
- 잔여: 없음.

## 공통 검사 입력과 승인 기준 설계

- 할 일: [Task 계획](../task-001.md#work-input)

- 조치·판단: [입력 규격](<../../../../../docs/details/development/Java 작성과 관리.md#input>)을 UTF-8 JSON으로 정했다. 후보 비교와 두 검사에서의 판독에 같은 정책 원천을 사용한다. 실제 후보와 별도로 확인한 Task 범위·승인 원천·효력을 대조한다. 초기 공개 HTTP 목록과 이후 개정 근거를 표현할 수 있게 하되 실제 최초 목록은 후속 승인 범위에 둔다.
- 확인: 실제 정책은 새 업무 모듈이나 실제 승인 목록을 등록하지 않는다. 가상 입력으로 기존 허용, 정확한 위임, 무승인 확대, 만료와 판독 실패를 구별했다. HTTP의 승인된 빈 초기 목록, 삭제 승인과 미확인 목록을 구별했다. [예시](task-001-policy-cases.json)

## 검수·기록·인계

- 할 일: [Task 계획](../task-001.md#work-review)

- 조치·판단: r001의 세 완료 조건과 실제 문서·입력을 자체 대조했다. 별도 검수에서 HTTP 목록 수준 근거와 삭제 승인, 실제 후보에 연결된 Task 승인 범위, `common` 소비자 범위의 불일치를 지적받아 보완했고 같은 검토자가 해소를 재확인했다.
- 확인: 기준 `94babc10`의 로컬 변경본을 확인했다. 산출물 SHA-256 접두어는 규칙 `A7FB9BDB4769`, 정책 `858C2ECF9600`, 사례 `7F53D85D9885`다. Python으로 JSON 중복 키·버전·참조와 문서에서 정한 기대 판정 18건(통과 7, 위반 8, 미확인 2, 적용 대상 없음 1)을 대조했다. 기록 주석·상태의 작업 트리 검사, 변경 기록 검사, 로컬 문서 링크 33개와 구조 문서의 공백 확인을 마쳤다. Issue 본문의 기존 작성 분량은 경고 기준을 넘는다. 전달본·나머지 Task·백업 8개는 착수 전 지문과 일치한다. 이 확인은 로컬 입력 규격과 예시에 적용된다.
- 제출 범위: 사용자의 재검수 후 진행 요청을 로컬 제출까지 적용한다. 부모 Issue와 배정·Task 등록이 기준 커밋에 없어, 규칙과 Task 결과의 승인·배정 근거 링크가 제출 후보에서도 해석되도록 필요한 기존 Issue 기록을 함께 보존한다.
- 잔여: 부모 브랜치 반영은 Issue에서, 훅·Spring 매핑·CI 실행 결과는 후속 배정에서 확인한다.
