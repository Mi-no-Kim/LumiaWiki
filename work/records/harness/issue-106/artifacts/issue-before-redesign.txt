<a id="purpose"></a>

#### 목적

Spring 백엔드 파일을 생성·수정·이동·삭제할 때 파일의 위치·이름·책임을 일관되게 판단하고 규칙 위반을 작업 중에 발견할 수 있도록, 저장소의 작성 규칙과 자동 검사 훅을 마련한다.

<a id="expected-results"></a>

#### 기대 결과

승인된 적용 범위와 예외, 정상·위반 예시가 포함된 작성 규칙, 선택한 훅의 등록과 사용자에게 보이는 검사 결과가 남는다. [첫 적용 범위](#decision-1) 안의 세부 경계와 구조, 자동 검사 시점·강제 수준과 도구는 조사·비교 후 결정한다.

#### 이미 정해진 조건

- 조건: Phase에 속하지 않는 독립 Issue로 진행한다.
  - 적용 범위: 작업 소속과 GitHub 등록
  - 확정 근거: 사용자 요청

- 대상·입력: 사용자의 [요청](#purpose), [코드 품질 기준](<../../../../docs/details/development/코드 품질.md>)과 [훅 현황](<../../../../harness/hook 현황.md>). 적용 파일·예시는 1단계에서 현재 소스와 초기 질문을 대조한다. <a id="decision-1"></a>

### 결정 1

- [ ] 결정할 사항: 어떤 Spring 파일과 변경에 규칙을 적용할까?
  - 결정 범위: 운영·테스트 Java, Spring 설정 YAML, SQL/Flyway와 Gradle 설정의 포함 여부를 정하고 신규·수정·이동·삭제, 생성 산출물·기존 파일의 처리 범위를 정한다.
  - 판단 기준: 팀이 실제 변경 대상과 예외를 경로·파일 유형으로 식별할 수 있는지, 기초 저장소와 Phase 백엔드에 모두 적용 가능한지 비교한다.
  - 결정 내용: 첫 적용은 운영·테스트 Java 파일의 생성·이동을 대상으로 하며, 경로·패키지·이름을 검사한다. 기존 파일의 일괄 정리는 별도로 판단한다. Spring 설정 YAML, SQL/Flyway, Gradle 파일은 첫 적용 범위에서 제외한다. 기존 Java 파일의 일반 수정·삭제와 생성 산출물의 처리 방식은 미정이다.
  - 결정 이유·근거: 운영·테스트 Java 파일의 생성·이동부터 검사하는 선택지에 사용자가 “java부터.”로 답했다. 기존 파일까지 일괄 적용하는 결정은 별도로 판단하도록 남겼다.

- [ ] 결정할 사항: 파일 배치·이름·책임과 생성 절차를 어디까지 표준화할까?
  - 결정 범위: 기능별, 계층별, 기능 내부 계층을 두는 배치와 공통 코드·테스트 위치를 비교한다. 문서와 예시를 통한 생성, 템플릿 또는 생성 명령을 제공하는 방식의 범위를 정한다.
  - 판단 기준: 현재 Spring 컴포넌트 스캔과 기존 패키지에 맞는지, 파일을 찾기 쉬운지, 상용구 감소가 템플릿 유지 비용에 비해 충분한지 비교한다.
  - 하위 질문
    - 모듈 간에 어떤 타입과 계약을 공개하며, 공개 경계는 어디에 둘까?
    - `dto`·`mapper` 같은 추가 역할 패키지는 어떤 경우에 만들고, 소유 업무 안의 어디에 배치할까?
    - `common`·`dev`·테스트 픽스처에는 어떤 Java 코드를 배치하고, 업무 모듈에 둘 코드와 어떻게 구분할까?
