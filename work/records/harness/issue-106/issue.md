<a id="task-execution-conditions"></a>

#### 위임·승인 및 실행 조건

- 위임 범위: 합의한 적용 범위와 강제 수준 안에서 검사 도구, 입력 데이터 형식, 오류 메시지와 재실행 방법, 검증용 코드의 구현을 정한다.
- 사전 승인: 최초 공개 HTTP API 목록과 공통 허용 경로·모듈 경계·예외의 범위 변경에는 프로젝트 결정권자 또는 명시적으로 위임받은 승인권자의 근거를 연결한다. 같은 후보에서 기준이나 승인 기록도 바꾸면 승인된 원천에 대조한다.
- Phase 1 원격 CI: 통합 검증 Task의 실행 선행 조건이다. Issue 등록 저장소에서 결합 후보를 검증하는 브랜치와 이벤트를 확인한다. 워크플로 조건에 맞는 승인된 `issue/` 검증 브랜치의 push를 우선 검토한다. 수행 전에 실제 원격 저장소·브랜치·실행 주체와 브랜치 생성·push, 실행 결과·로그 조회 및 필요한 재실행·정리의 권한 범위를 확인한다. 권한이나 실행 경로가 미확인이면 원격 CI를 미확인으로 남기고 이에 의존하는 검증과 병합을 보류한다.

  - 결정 범위: 경로·패키지·이름 검사의 추가 변경 유형과 생성 산출물 처리, 기존 파일 일괄 정리 여부를 정한다. TDD 훅은 기존 Java 파일의 어떤 변경에 어떤 테스트 근거를 요구하고, 어떤 예외를 허용할지 정한다. 실행 시점과 강제 수준은 [결정 4](#decision-4)에서 정한다.
  - 판단 기준: 개발자가 변경 유형별 경로·이름 검사 조건과 필요한 테스트 실행 기록을 식별하고, 내용 수정의 동작 변화가 승인된 작업 범위와 일치하는지 확인할 수 있어야 한다.
  - 결정 내용: 경로·패키지·이름 검사의 첫 적용은 운영·테스트 Java 파일의 생성·이동이다. Spring 설정 YAML, SQL/Flyway, Gradle 파일은 첫 경로·이름 검사 범위에서 제외한다. 기존 Java의 내용 수정과 동작을 제거하는 삭제는 승인된 Task 범위·동작 검증에 포함한다. 운영 코드와 테스트의 변경분을 승인 범위에 대조하고, 유지할 동작은 관련 회귀 테스트로 확인한다. 자동 생성 파일과 기존 파일 일괄 정리는 별도 검토로 둔다.
  - 결정 이유·근거: Java 파일을 생성하거나 이동할 때 위치·패키지·이름을 새로 정한다. 기존 파일의 내용 수정이나 삭제도 공개 동작을 바꿀 수 있으므로 승인 범위와 회귀 테스트를 확인한다. 자동 생성 파일과 기존 파일 일괄 정리는 처리 방식과 영향 범위를 따로 검토한다. 테스트 판정은 Phase 1의 TDD 검사 시점과 예외 기준을 따른다(`72c27a1:docs/details/development/TDD hook.md`).
  - 합의한 TDD 적용
    - **Red** — 운영 Java의 동작을 바꿀 때, 구현 변경 전에 테스트를 실행해 의도한 기대 동작에서 실패한 결과를 기록한다. 환경 오류나 테스트 미실행은 Red로 인정하지 않는다.
    - **Green** — 구현 수정 후 같은 테스트와 관련 기존 테스트를 실행해 통과 결과를 기록한다.
    - 동작을 유지하는 순수 리팩터링은 예외 근거를 남기고 변경 전후에 같은 관련 테스트를 실행해 통과를 확인한다.

### 결정 2

- [x] 결정할 사항: 파일 배치·이름·책임과 생성 절차를 어디까지 표준화할까?
  - 결정 범위: 큰 업무 단위로 묶는 DDD 방향을 전제로, 모듈 경계와 공개 범위에 대해 작성·관리 규칙이 다뤄야 할 원칙과 문서·예시 외에 제공할 생성 지원 범위를 정한다.
  - 판단 기준: 업무 모듈의 소유 범위와 공개 계약을 규칙과 예시에서 식별할 수 있어야 한다.
  - Task 검토 후보: 실제 업무 기능을 모듈로 묶는 기준, 모듈 내부 계층 및 패키지·테스트 배치안, Spring 컴포넌트 스캔 영향, 필요시 템플릿·생성 명령의 유지 비용을 검토한다.
  - Task 검토 후보의 하위 질문
    - 모듈 간에 어떤 타입과 계약을 공개하며, 공개 경계는 어디에 둘까?
    - `dto`·`mapper` 같은 추가 역할 패키지는 어떤 경우에 만들고, 소유 업무 안의 어디에 배치할까?
    - `common`·`dev`·테스트 픽스처에는 어떤 Java 코드를 배치하고, 업무 모듈에 둘 코드와 어떻게 구분할까?
  - 결정 내용: 큰 업무 단위로 묶고, 각 모듈이 소유하는 기능·데이터와 공개 계약을 작성·관리 규칙에 명시한다. 다른 업무 모듈은 해당 모듈의 공개 계약을 통해서만 접근한다. 필요한 경우 소유 모듈이 특정 사용 사례에 맞춘 공개 계약을 제공할 수 있다. 예를 들어 피해량 계산에 필요한 아이템 데이터를 한 번에 조회하는 계약을 아이템 모듈에 둔다. 구체적인 모듈·패키지 배치와 `common`의 허용 의존 범위는 Task에서 설계한다.
  - 파일 생성 지원: 첫 버전은 작성 규칙과 정상·위반·예외 예시를 제공한다. 운영 Java와 대응 테스트 한 쌍의 경로·패키지·클래스 이름·소유 모듈을 제시한다. 위반 예시에는 경로·패키지 불일치와 다른 모듈의 내부 타입 참조의 수정 방법을, 예외 예시에는 새 패키지 또는 `common`에 둘지 판단하기 어려운 경우의 확인 절차를 담는다([결정 6](#decision-6)). 템플릿·생성 명령은 배치 규칙과 반복 생성 필요가 확인된 뒤 검토한다.
  - 결정 이유·근거: 업무 기능·데이터의 소유 모듈과 공개 계약을 명시하면 다른 모듈이 의존할 범위를 알 수 있다. 용도에 맞는 조회 계약은 반복 조회를 줄일 수 있다. Phase 1의 운영·테스트 Java 배치와 빌드 설정을 대조한 결과, 첫 버전은 작성 규칙과 예시로 배치와 위반 수정 방법을 안내할 수 있다.

### 결정 3

- [x] 결정할 사항: 어떤 규칙을 자동 검사하고 어떤 방식으로 구현할까?
  - 결정 범위: [첫 적용 범위](#decision-1)의 경로·패키지·이름 검사에 더해, 의존 방향·순환 등 구조 위반과 기존 Java 내용 수정의 어노테이션·공개 API 계약 변화 중 자동으로 감지하거나 판정할 항목을 정한다.
  - 판단 기준: 자동 판정이 필요한 규칙은 검증 가능한 위반 사례를 정할 수 있어야 한다.
  - Task 검토 후보: 경량 스크립트·Checkstyle·ArchUnit·Spring Modulith의 판정 범위, Spotless와의 역할 중복, 실행 비용과 오탐을 비교한다. API 계약 검사에 사용할 승인 목록의 형식과 실제 등록된 URL·HTTP 메서드의 대조 방식을 설계한다. Phase 1에서 Checkstyle 등 추가 검사기의 동시 도입을 보류한 결정을 검토 근거로 삼는다.
  - 결정 내용: 첫 자동 검사에 경로·패키지·이름, 다른 업무 모듈의 내부 타입 참조, 업무 모듈 간 직접·간접 순환 의존을 포함한다. 소유 모듈이 공개한 계약을 통한 비순환 의존은 허용하고, 순환이 발견되면 의존 경로를 표시한다. 공개 HTTP API 변경은 승인 범위 검수와 회귀 테스트로 먼저 확인한다. 승인된 API 목록을 마련하고 실제 등록된 URL·HTTP 메서드를 자동 대조하는 작업은 이 Issue 안에서 구현하고 검증한다.
  - 결정 이유·근거: 타입 참조를 소유 모듈과 공개 계약에 대조하면 [모듈 간 공개 계약 원칙](#decision-2)을 위반하는 의존을 자동으로 검출할 수 있다. 공개 계약만 참조해도 업무 모듈이 서로를 참조하는 의존 순환이 생길 수 있어 모듈 단위로 검사한다. 승인된 API 목록과 실제 등록 결과의 차이를 확인하면, 승인 없이 공개 경로나 HTTP 메서드가 늘거나 줄어드는 변경을 발견할 수 있다.

### 결정 4

- [x] 결정할 사항: 훅은 어느 시점에 무엇을 경고하거나 차단할까?
  - 결정 범위: 사용자가 언제 판정 결과를 받아야 하는지, 어떤 위반이나 공개 API 계약 불일치를 경고 또는 차단할지, 예외를 허용할 조건이 있는지 정한다.
  - 판단 기준: Codex 외부 변경의 검사 필요성, 기존 TDD·포맷·기록 검사와의 간섭, 개발 중 허용할 지연을 고려한다.
  - Task 검토 후보: 지원 편집 도구의 범위, CI의 구체적인 실행 조건과 검사 입력 경로, 오류 코드·안내 문구·재실행 명령·시간 제한을 설계한다. Phase 1의 기존 TDD 검사기와 등록 정의(`72c27a1:scripts/tdd-check.py`, `72c27a1:.codex/hooks.json`, `72c27a1:scripts/install-hooks.py`)의 재사용과 기존 포맷·기록 검사와의 간섭을 검토한다.
  - 결정 내용: 편집 중 빠른 피드백, 커밋 후보 확인, CI의 제출 후보 검증을 적용한다.
    - Codex 편집 전: 지원 도구에서 대상 경로를 식별할 수 있는 운영 Java 동작 변경은 유효한 Red 또는 적용 범위에 맞는 승인된 예외를 확인한다. 필수 근거를 확인할 수 없으면 해당 구현 편집을 차단한다.
    - 편집 직후: [결정 1](#decision-1) 대상 파일의 경로·패키지·이름 위반을 알린다.
    - 커밋 전: 실제 스테이징된 후보에서 [결정 1](#decision-1)의 Java 생성·이동 범위에 경로·패키지·이름 검사를 적용한다. TDD 대상 변경은 후보 내용과 테스트 실행 기록 또는 승인된 예외를 대조한다. 확정 위반이나 필수 미확인은 커밋을 차단한다. 정상 결과 커밋에 필요한 기존 검증 근거도 실제 후보에 대해 확보한다.
    - CI·병합 전: 내부 타입 참조, 순환 의존, 공개 HTTP API 계약을 제출 후보에서 검사한다. 모듈 정책·승인 API 목록·예외·검사 설정 등 판정 입력의 변경도 관련 검사 범위에 포함한다. 입력 자체가 바뀌면 승인된 작업 범위와 대조한다. 병합 실행자가 최종 head·base에 대응하는 개별 필수 검사 결과를 확인하며, 위반이나 필수 미확인이 남으면 병합을 보류한다.
    - 판정과 안내: 확인 가능한 위반은 위반으로 판정한다. 필수 검사 미실행, 환경 오류·시간 초과·판독 실패 등으로 판단할 수 없으면 미확인으로 처리한다. 적용 대상 없음은 비대상 근거가 있을 때만 사용한다. 경고·차단 메시지에는 대상·이유·다음 허용 행동을 표시한다. 대표 원인은 누락 테스트 실행·기록, 위반 수정, 변경 승인 확인, 환경 복구 후 재검사처럼 원인에 맞는 조치를 안내한다. 기타 원인은 확인 가능한 정보와 재실행 조건을 안내한다.
  - 결정 이유·근거: 실제 스테이징 내용과 최종 제출 후보를 기준으로 해야 작업 폴더나 이전 CI 결과의 통과를 잘못 적용하지 않는다. Phase 1 CI는 문서 변경만 있을 때 백엔드 검사 없이 종합 검사가 성공할 수 있으며(`72c27a1:.github/workflows/quality.yml`, `72c27a1:scripts/quality/paths.mjs`, `72c27a1:scripts/quality/changes.mjs`), 승인 목록까지 함께 변경된 후보는 목록과 실제 API의 일치만으로 승인 여부를 판정하기 어렵다. 병합 전 확인은 [PR과 병합 기준](<../../../../docs/details/git/PR과 병합 기준.md>)을 적용한다.

### 결정 5

- [x] 결정할 사항: 백엔드가 아직 없는 main과 Phase 1 백엔드에 어떤 순서로 적용하고 확인할까?
  - 결정 범위: `main` 기준의 독립 작업을 전제로, Phase 1 실소스 검증을 어느 시점에 어떤 작업 환경에서 수행하며 그 결과를 Issue 수용의 선행 조건으로 둘지 정한다. 검증할 파일의 범위는 [결정 1](#decision-1)을 따른다.
  - 판단 기준: `main`에서 `backend/`가 없을 때의 기대 동작과 Phase 1에서 정상·위반·예외를 재현할 수 있는지를 확인한다.
  - Task 검토 후보: 실행 시점의 Phase 1 기준 커밋, 검증용 worktree와 CI의 실행 방법, 정상·위반·예외 사례를 구체화한다. 기존 TDD·포맷·기록 검사와 새 검사가 결합 후보에서 함께 동작하는지 확인한다.
  - 결정 내용: 공통 규칙을 `main` 기준의 독립 Issue에서 구현하고 다음 순서로 검증한다.
    - main 기준 후보: 백엔드 존재 여부를 실제 Git 후보 내용으로 판정한다. 후보에 백엔드가 없으면 Java·Spring 검사를 적용 대상 없음으로 표시하고 검사 진입점이 정상 종료하는지 확인한다.
    - Phase 1 결합 후보: 별도 검증용 worktree에서 확인한 Phase 1 기준 커밋과 #106 후보를 결합한다. 기준·후보 커밋과 결합 결과를 기록하고, 실제 Spring 소스로 편집 훅·커밋 전 검사·CI에서 경로·이름, TDD 기록, 모듈 의존 및 HTTP API 대조를 검증한다.
    - 병합과 수용: Phase 1 실소스 검증을 #106의 필수 수용 조건으로 삼고, 필수 검증을 통과한 뒤 `main`에 병합한다. 최종 후보나 검증 조건이 바뀌면 영향받은 검사를 다시 확인한다. Phase 1에서 필수 검사를 실행할 수 없으면 미확인으로 기록하고 병합과 Issue 완료를 보류한다.
  - 결정 이유·근거: 현재 `main`에는 추적된 백엔드가 없고 작업 폴더에는 미추적 `backend/`가 있어, 검사 적용 여부는 Git 후보로 판단해야 한다. Phase 1에는 실제 Spring 소스와 기존 훅이 있고 로컬 브랜치와 원격 추적 브랜치의 커밋이 다르므로, 검증에 사용한 결합 후보와 실행 결과를 식별한다.

### 결정 6

- [x] 결정할 사항: 새 패키지를 누가, 어떤 기준으로 승인하고, 근거는 어디에 남길까?
  - 결정 범위: 새 패키지·허용 경로를 추가하거나 바꿀 때 승인이 필요한 경우와 시점, 승인·위임 주체, 근거 기록 위치와 필수 정보를 정한다.
  - 판단 기준: 기존 허용 경로로 해결하기 어려운 이유와 새 패키지의 소유 업무·책임·공개 범위를 확인할 수 있고, 변경 후보와 승인 근거를 추적할 수 있는지 비교한다.
  - Task 검토 후보: 규칙과 검사기가 참조할 승인 데이터의 형식·경로, 승인 기록과 실제 후보의 대조 방식, 승인·위임·임시 예외의 검증 사례를 설계한다.
  - 결정 내용: 공통 허용 경로 기준은 한 원천에서 관리한다. 실제 패키지는 업무 모듈별로 두고 운영·테스트 소스 경로를 구분한다. 승인 수준은 업무 모듈의 소유 범위나 공개 범위에 미치는 영향에 따라 정한다.
    - 기존 허용 패키지: 승인된 Task 범위에서 파일을 생성하거나 이동할 수 있다.
    - 모듈 내부 새 하위 패키지: 기존 경로로 수용하기 어렵고 소유 모듈·공개 범위가 유지되는 경우에 위임할 수 있다. 승인된 Task 배정에 대상 경로·역할·한계가 명시되어야 하며, 구체적인 판단과 근거는 담당 Task에 남긴다.
    - 모듈 경계·공통 적용 범위 변경: 새 최상위 업무 모듈, `common` 공유 범위 확대, 공통 허용 경로 규칙 변경은 프로젝트 결정권자 또는 명시적으로 위임받은 승인권자의 사전 승인을 받는다. 승인 결정은 담당 Issue에서 관리하며, Task에서 이를 참조한 뒤 대상 패키지를 생성·이동하거나 규칙을 바꾼다.
    - 승인 기록과 임시 예외: 대상 경로, 소유·책임, 공개 범위, 기존 경로로 해결하기 어려운 이유, 적용 한계와 승인·위임 근거를 기록한다. 임시 예외는 적용 대상·사유·종료 조건·정리 책임을 명시하며, 효력이 끝난 뒤에는 승인 근거로 쓰지 않는다. 연장하려면 새 승인을 받는다.
    - 검사: 실제 변경을 승인·위임의 대상과 효력에 대조한다. 같은 후보에서 허용 기준이나 예외와 패키지를 함께 바꾸더라도 승인된 원천에 대조한다. 확인 가능한 승인 범위 위반과 판독할 수 없는 필수 근거는 [결정 4](#decision-4)의 판정 기준으로 구분한다.
  - 결정 이유·근거: 업무 모듈 내부의 배치 판단은 소유 범위 안에서 처리할 수 있다. 경계와 공통 허용 규칙의 변경은 다른 모듈에도 영향을 주므로 사전 승인과 추적 가능한 근거가 필요하다. 승인 원천과 실제 후보를 대조하면 후보에 적힌 규칙 변경만으로 허용 범위가 확대되는 일을 막을 수 있다.
