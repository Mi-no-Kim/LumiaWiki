# Issue #72 수용·검증 근거

[담당 Issue의 현재 판단](../issue.md#verification)에 연결하는 보존 근거다. 본문 정리 전 기록에서 기존 원문·수용 범위·실패/보완·실행 관찰과 한계를 확인하는 데 필요한 부분만 옮겼다. 양식·규칙의 작성 원천이나 새로운 실행 기록이 아니며, 아래 과거 수치·지문을 현재 파일의 기대값이나 이번 정리의 재실행 결과로 사용하지 않는다.

## Task 생성·문서 관리의 현행 반영

문서 관리 시험 C의 기존 12개·충돌 3개 사례와 17개 입력을 별도 문맥에서 실행·판정해 보완 후 수용했다. 회귀 15개와 readonly verify/judge 통과는 [해당 시험 묶음](task-doc-suite-c/run.md#results)의 근거다. B의 수용 보류, TC-11의 조기 체크 정정과 보완, A·실제 A안 응답 TC-01·중단 시험·고정 모의 입력의 구별은 각 기존 실행 기록에 보존한다.

현행 반영 대상은 docs의 작업 기록 체계·작업 기록 작성 기준·검증과 완료·별도 검수, harness의 문서 관리·작업별 절차·Task/Issue/GitHub Task 양식의 9개 파일이었다. 배정 결과·범위·완료 조건·원본·식별의 생성 전 확인과 Task 상세 설계·계획·지연 입력의 실행 시점 확인을 구분했다. 실제 수행 뒤 체크, 조건별 관찰·근거 대조, 자식 취소의 부모 잔여, 중복 필드·원천/권한 부족·동시 수정의 처리도 연결했다. 현행 일곱 상태·기존 구역 표식과 기록 경계를 유지했다.

자체 검수와 같은 모델의 별도 문맥 검토자가 변경 전후 및 정상 생성·필수값 누락·지연 입력·거짓 완료·자식 취소·동시 수정 경로를 읽기 전용으로 대조해 필수 결함이 없음을 확인했다. 후속 계획과 상세 수행 기록의 작성 시점을 혼동할 수 있던 표현을 보완했다. 9개 파일의 로컬 참조 114곳이 유효했고 기존 시험 370개 파일은 변경 전후 바이트가 같았다. 실제 Task 발급·GitHub 반영·제품 수행·CI·운영 효과는 검증하지 않았으며 시험 도구도 운영 검사기로 배포하지 않았다.

## Task 공통 절차와 수행 기록 예시 검토

사용자는 수행 기록 주석의 양과 위치를 지적했다. 파일 공통 규칙이 할 일 구역 안에 있어 후속 구역을 만들 때 반복 복사할 수 있었고 작성·판단 조건의 중복도 많았다. 같은 #72의 양식·기록 절차 보완으로 처리하며 새 Task·Issue·브랜치·커밋·실제 생성 시험으로 확대하지 않는다.

[수행 기록 양식](task-execution-template-draft.md#execution-body)의 규칙을 머리말의 execution-rule:recording 한 블록으로 합쳤다. 주석 본문은 23줄·1,316자에서 8줄·584자로 약 56% 줄였다. Task당 한 파일·착수한 할 일의 왕복 연결·실제 조치/선택과 상태 구별·사용자 응답/AI 위임 확인·검증 대상/관찰/판정·현재 결론의 본문 반영·근거/연결 보존·원본 복사/미발생 결과 금지를 남겼다. 공통 조건의 반복 설명은 줄이고 머리말의 기록 기준에서 [공통 절차](task-common-procedure-draft.md#recording-proposal)를 직접 참조한다. 기존 주석에만 명시했던 판정에 영향을 주는 태그 변경의 당시 태그·기준·이유 식별은 공통 절차에 유지한다.

후속 할 일은 작업 표식·제목·할 일 링크·조치·판단 / 확인 / 잔여의 구조만 주석 없이 추가한다. 머리말·기록 기준·규칙 주석은 한 번만 두며 이전 실제 값은 복사하지 않는다. 생성 양식으로 돌아가지 않고 실제 파일의 머리말 규칙을 따른다. [구조 합의](task-structure-agreement.md)와 최초 생성·기록 절차도 같은 구분으로 맞췄다.

[기존 수행 기록 예시](task-execution-example.md#execution-example)에는 같은 머리말·기록 기준·한 번의 주석만 반영했다. 논의·선정·반영 상세와 [Task 본문의 핵심 결론·링크](task-body-example-recording.md#sequence), 태그·상태·권한·체크는 유지한다. 새 사례·기록 파일·미착수 구역·증명 파일은 만들지 않는다.

자체 대조에서 양식·예시의 주석 한 개가 같고 모두 첫 작업 표식 앞에 있으며, 반복할 작업 구역에는 주석이 없음을 확인했다. 정적 기록 기준 링크를 포함해 양식의 값 자리 일곱 곳을 채운 전체 본문이 예시와 같고 기존 논의·선정·반영의 세 항목 값은 변경 전과 같다. 수정은 양식·예시·공통 절차·구조 합의·담당 기록 다섯 파일이며 추가/삭제 없이 나머지 37파일과 Task 본문 양식·세 본문 예시·입력·보존 원문은 바이트가 같다. 현재 Markdown 22파일의 로컬 참조 304곳이 유효하고 기록 위반은 없다. 생성 양식의 복사 블록은 생성 본문으로 확인하며 과거 코드 발췌는 현재 참조에서 제외했다. 담당 Issue 길이만 기존 비차단 경고다.

같은 모델의 별도 문맥 검토자가 삭제·통합한 문장을 머리말과 연결된 상세 조건에 대조했다. 필요한 의미·실제 응답/위임·확인/재확인·본문 요약·당시 기준/실패 근거 보존·원본 복사와 불필요한 증명 파일 금지가 유지되고, 동일 주석 한 개의 위치와 주석 없는 반복 구조·기존 값·관련 현재 안내가 일치함을 확인했다. 잔여 필수 결함·선택 의견은 없다. 마지막 결과 기록은 자체 대조하고 이 별도 검수 근거를 재사용한다. 실제 생성 시험·제품 수행·운영·Git 제출·CI는 확인하지 않았다.

## 초기 질문 확인 시점의 요약 보완

사용자는 직전 3번의 확인 시점 요약 보완점을 skill과 생성 지시서에 최소 반영하고 기대 답안 없는 새 문맥에서 3번을 재테스트하도록 요청했다. 같은 #72의 보완으로 별도 작업·브랜치·커밋을 만들지 않는다. 직전 1~7번은 작성 5건·보완 요청 2건으로 이전과 같았지만, 3번의 반환 요약은 더 이른 목록 확인 시점을 생략했다. 실제 본문에는 1단계 확인 행동과 공통 절차가 유지되어 이를 권한 확대로 판정하지 않았다.

skill의 반환 문단에 목록 확인과 답 확정의 시점 구별·상세 위치 연결을 한 문장으로, 생성 지시서의 생성 후 확인에 해당 공통 절차 참조를 한 항목으로 추가했다. 목록 확인은 1단계 완료 전, 답 확정은 Task 분해·배정 전이라는 기존 기준을 요약에서도 유지하기 위한 보완이다. 질문 목록 미확인을 생성 반려 사유로 바꾸거나 Task 상세 방법의 사전 확정을 요구하지 않는다. 본문 양식·예시·규칙 주석과 입력 보존·기존 네 단계·승인/실행 경계는 유지한다.

3번 원입력과 현재 skill·필수 원천만 같은 모델의 새 문맥에 전달했으며 기대 답안·이전 결과·수정 요지는 제공하지 않았다. 생성 전 보완 요청 없이 실제 본문을 메모리에서 구성했고 6,792자·172줄이었다. 초기 질문은 미확인으로 유지하고 실제 질문을 추가하지 않았다. 반환 요약은 목록 확인을 1단계 완료 전, 답 확정을 Task 분해·배정 전으로 구별했으며 두 시점을 본문·공통 절차와 대조했다. 조사 방법 자체의 소관·시점은 관련 판단 전 확인 대상으로 남겨 생성·모든 논의·배정의 선행 조건으로 확대하지 않았다.

실행 문맥에서 원입력·질문 미확인과 양식 칸, 규칙 주석 10개/보호 대상 4개·네 단계·미체크·예정·미수행·미정·미생성과 내부/외부 참조를 대조했다. 최종 요약도 메모리 본문·검사 결과와 다시 확인했다. 실제 준비·등록·실행 성공은 만들지 않았고 파일·임시파일·실제 발급·등록·제품/DB 수행은 하지 않았다. 부모는 전체 메모리 본문을 직접 재검수한 것이 아니라 해당 문맥의 결과를 수합했다. 동일 모델의 1회 명시적 적용이며 자동 선택·실제 파일 작성·발급·운영은 미확인이다.

별도 읽기 전용 검토자가 skill 반환 문단·생성 후 확인 항목을 공통 절차 1·2단계와 입력/본문 양식에 대조했다. 기존 시점 기준과 생성 허용·Task 상세 합의·배정 조건을 유지하며 필수 결함·추가 선택 개선은 없었다. 두 원천의 로컬 참조 14곳과 현재 양식/예시의 주석 대응·지문/현황 표기를 확인했다. 검토자는 3번 행동·변경 전 전체 바이트·전체 후보 검사를 독립 확인하지 않았으며, 작성자는 실제 확인 범위에 맞춰 현황과 기록을 갱신했다.

자체 대조에서 추가한 한 문장/한 항목을 제외하면 두 원천의 바이트가 변경 전과 일치한다. 본문 양식·예시와 나머지 28파일·공통 절차·다른 현황 항목, 과거 지문 19개·기존 표식·상세 근거를 유지한다. 번들 quick_validate 형식 검사를 통과했고 검사에만 사용한 임시 의존성은 제거했다. 변경 문서·skill의 로컬 참조 147곳은 유효하며 양쪽 현황 후보·표 대응과 기록 형식 검사를 통과했다. 기존 기록 길이 경고는 비차단 한계로 남긴다. 실제 Issue/Task 발급·GitHub 갱신·브랜치·커밋은 하지 않았다.

## Issue 규칙 주석 자동 검사

사용자는 이미 수행한 변경을 되돌리지 않아도 되며 수정 후 검사와 pre-commit을 함께 사용하도록 허용했다. 이전의 검토 전용·hook 미구현 범위는 이번 두 실행 지점의 구현·검증·설치에 한해 갱신한다. 같은 #72의 반복 확인·주석 보호 보완이며 새 Issue·Task·브랜치를 만들지 않는다. 기존 미커밋 skill·문안과 제품·환경 파일은 보존한다.

공유 읽기 전용 검사기는 `issue-rule:start`·`state`·`position`·`completion`의 식별자·내용·경계만 보호한다. [검사 정책](../../../../../harness/issue-rule-comments.json)의 명시 대상은 현재 본문 작성안과 대응 예시 두 파일이다. 실제 Issue는 양식을 채택하고 정확한 경로를 등록한 범위에서 적용한다. 기존 Issue 전체에 작성안을 강제하지 않는다. 기준본은 네 주석에서 자동 추출한 검사 스냅샷이며 정상 편집에서 재설정하지 않는다. 사용자 명시 개정은 파일·규칙·전후 원문·실제 승인 기록 참조를 한정한 예외로 관리한다. 참조 존재 확인이 승인 진위의 자동 판정을 뜻하지 않는다.

[Codex 정의](../../../../../.codex/hooks.json)는 지원 도구 종료 후 작업 파일을 동기로 검사하고 위반 피드백을 반환한다. [Git 정의](../../../../../scripts/hooks/pre-commit)는 기존 hook과 현황·기록 검사를 유지한 뒤 실제 index를 검사한다. 검사 호출 누락에 의존하지 않는 실행 지점을 정의했으며 자동 되돌림은 없다. 실제 앱의 신뢰 설정·자동 발동은 정의·핸들러 직접 검사와 구분한다. 세부 사용·개정·한계는 [문서 관리 안내](../../../../../harness/문서 관리.md#issue-rule-comment-check)를 따른다.

검증·검수 결과:

- 최종 `python -B -X utf8 -m unittest discover -s scripts/tests -p test_*.py -v`의 73개 사례(주석 검사 24·현황/hook 38·기록 11)가 통과했다. 정상 갱신, 네 주석 삭제·변조·중복·경계, 전체 제거·파일 삭제·등록 제거, 코드/이스케이프/속성/raw text의 가짜 주석·승인 표식, 정확한 명시 개정·삭제 예외, 기준본 재정의 거부, 작업 파일/index 분리, Windows 하위 경로의 실제 등록 명령과 실패 피드백, 기존 hook 연결을 확인했다. 임시 저장소의 Git 커밋은 검사 연결 시험이며 실제 저장소 커밋·스테이징·발급을 뜻하지 않는다.
- 기본 샌드박스에서 MSYS 셸·junction·로컬 sparse clone 실행이 제한되어 해당 회귀가 실패했다. 같은 최종 전체 검사를 승인된 샌드박스 밖 실행으로 다시 확인했고 모두 통과했다. 제한을 코드 성공으로 보고하지 않았다.
