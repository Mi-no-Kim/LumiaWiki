# 신규 Issue·Task 양식 정식 반영과 확인

<a id="scope"></a>

## 적용 범위와 승인

사용자가 기존 기록을 수정하지 않고 예외 목록으로 관리하며 신규 기록부터 합의한 Issue·Task 양식·작성 방법·skill·hook을 정식 반영하도록 요청했다. 기존 #72 본문도 갱신하지 않는다. 이 파일은 이번 반영·동작 확인의 새 첨부이며 과거 기록의 상태·승인·결과를 바꾸지 않는다.

공식 입력·본문·수행 기록 양식은 harness/templates, 최초 생성 지시서와 진행 절차는 harness, 공용 예시는 harness/examples에 반영했다. Phase 하위·독립 Issue는 같은 본문·네 단계·주석을 사용하고 독립은 부모 Phase 행만 생략한다. 생성 근거는 공통으로 남기며 같은 create-issue skill을 쓴다. 신규 Task 생성은 create-task가 맡는다. 두 유형의 개별 실행·검증은 Task, 전체 수용은 Issue가 소유한다.

[정식 정책](../../../../../harness/rule-comments.json)의 legacyRecords는 도입 당시 정식 기록 경로에 있던 Issue 15개의 고정 경로다. 미추적 #72도 포함했다. 실제 Task·Task 수행 기록은 당시 정식 경로에서 발견되지 않았다. 이후 새 기록은 표준 경로로 자동 발견하고 신규 완료 기록도 계속 보호한다. Phase·일반 첨부·시험 묶음은 이 자동 Issue/Task 경로에 포함하지 않는다. 선택적 기존 Issue 정책이 있는 환경에서는 그 명시 보호도 유지한다. 정식 구성은 그 정책이나 과거 첨부의 존재에 의존하지 않는다.

## 생성 skill과 작성 흐름

동일 모델의 별도 문맥에서 skill을 명시 적용해 네 가상 요청을 확인했다. 기대 답안·의심 결함·수정 요지는 평가 요청에 넣지 않았으나 부모 대화가 상속돼 완전한 맹검은 아니다. 출력·가상 원입력은 Git 제외 임시 위치에서 다뤘고 실제 work 본문·번호·등록·외부 객체를 만들지 않았다.

| 입력 | 실제 관찰과 판정 |
|---|---|
| A: Phase와 별도인 설치 링크 문제. 점검 범위 미정, 번호 없음, 임시 Issue 초안만 요청 | 본문 177줄. 부모 Phase 행 0개·생성 근거 유지. 점검 범위는 미결정이고 실제 수정·발급·Task 생성은 하지 않았다. |
| B: 실제 Phase 001 소속의 최소 검색/상세 페이지 범위 논의. UI·방법 미정, 자료/제품 수행 금지 | 본문 178줄. 부모 Phase 행 1개·생성 근거 유지. 초기 질문 목록은 미확인, 실제 자식 등록은 미수행으로 유지했다. |
| C: Task 방법은 미정이며 확정 배정 원본/근거·식별/경로도 없는 요청 | 필수 배정 정보의 부족·이유·보완만 반환하고 본문을 만들지 않았다. 방법 미정 자체를 거부 사유로 삼지 않았다. |
| D: 가상 부모·확정 전달본 r001·가상 식별과 출력 위치를 제공. 방법/전체 계획 미정, 본문 생성·계획 제안만 허용 | 실제 Task 본문 130줄을 생성했다. 네 구역·주석 8개·예정 상태·원본 참조를 유지하고 방법·계획 미합의와 실행 제한을 남겼다. 부모/입력 불변, 실제 자식 등록·수행 기록·결과 생성 없음. |

A/B의 제목을 제외한 헤딩·주석 10개는 같고 구조 차이는 부모 Phase 행이다. 원문·질문·미정/미확인·네 단계 미체크·미생성/미발생과 권한 경계를 대조했다. 로컬 참조는 A 13곳·B 14곳·D 11곳이 유효했다. 주 진행 AI도 실제 출력의 목적·범위·결정/계획·결과와 보호 주석·상태를 직접 대조했다.

생성 뒤의 정식 문서 보완은 앵커 뒤 빈 줄·공백 포함 링크의 표시 보정·skill 외부 원천 의존 선언이며 규칙 전문·필드·입력/권한 조건은 유지했다. 원 작성안 9개와 정식 문서·예시·진입점·skill을 별도 읽기 전용 검수했고 29개 파일의 로컬 참조 294곳과 의미를 확인했다. 남은 필수 결함·선택 의견은 없었다. 두 생성 skill은 임시 PyYAML 의존성을 사용한 공식 quick_validate를 통과했고 검증기 전용 의존성은 제거했다.

## 상태·검사 회귀

신규 상태는 예정·진행 중·중단·완료·취소다. 기존 예외 기록은 당시 상태로 읽고 파일을 치환하지 않는다. Task 상태 검사 7개가 실제 임시 index를 사용해 신규 중단·이전 전용 상태 거부·고정 기존 경로의 상태 호환, 중복/여러 줄 상태 거부와 Windows 기본 인코딩을 확인했다.

실제 제출 index의 허용 경로 108개만 복사한 격리 후보에서 scripts 회귀 실행 53709의 99개 사례가 통과했다. 미추적 기존 정책·#72 본문·과거 첨부 없이 실행했다. 신규 Task의 실제 pre-commit/index 분리와 CRLF skill의 외부 원천 의존 수집 회귀를 포함한다. Task 상태 검사 7개의 근거와 합해 총 106개 사례다. 단순 정상/삭제뿐 아니라 신규 완료 기록 보호·예외 목록 확대·기준 스냅샷 재설정·보호 파일 삭제·명시 개정의 범위·세 정식 경로·코드/HTML 속성/raw text의 가짜 주석과 상태·누락/부분 후보·외부 skill 의존 변경도 확인했다. review-work가 읽는 정책 의존을 명시했고 CRLF 선언도 실제 원천 목록·지문에 포함되도록 보완했다.

기본 샌드박스에서는 MSYS Git 셸·junction·로컬 sparse clone 실행이 제한돼 회귀 일부가 실패했다. 실제 코드/시험 보완과 구분해 승인된 제한 밖의 격리 실행으로 재확인했다. 등록 명령을 바꾼 시험 설정과 새 규칙이 존재하는 부분 구성을 이전 브랜치로 취급한 fixture를 바로잡았다. 가상 시험 커밋은 격리 저장소에서만 만들었다. 실제 저장소의 index는 사용자가 승인한 정식 반영 후보에만 사용했다. 선택적 정책의 필수 의존을 제거한 뒤 시험 fixture의 현황 원천 목록도 맞췄고, 격리 복사에서 누락한 기존 CI 파일을 허용 경로로 보충한 최종 후보에서 회귀를 통과했다.

<a id="hooks"></a>

## hook 연결과 실제 동작

기존 명령은 공통 검사로 연결하는 호환 진입점으로 유지하고 정식 PostToolUse/pre-commit 정의는 공통 명령에 연결했다. 이전 커밋에 존재하던 기존 Issue 정책의 누락이 새 정책으로 가려지지 않게 했고, 주석 검사 마커가 있는 부분 구성을 이전 브랜치로 스킵하지 않도록 보완했다. 실제 이전 후보에는 기존 스킵 동작을 유지한다.

임시 저장소의 실제 pre-commit에서 정상 신규 Task 후보를 허용하고 스테이징한 task-rule:start 삭제를 거부했다. 작업 파일만 복구해도 같은 index 위반은 거부하고 HEAD를 유지했으며, 정상 index에 미스테이징 위반만 남긴 경우는 허용했다. 기존 사용자 hook 연결·설치/복구·이전 브랜치·부분 구성 회귀도 통과했다.

현재 로컬 대화의 Task 양식 복사 블록에 표식 temporary-formal-task-hook-probe가 있는 중복 start 주석을 잠깐 삽입했다. 수동 검사 호출 전에 실제 도구 후 hook이 task-rule:start: duplicate comment와 경계/내용 불일치로 거부 피드백을 반환했다. 원래 주석은 유지했고 임시 중복만 제거했다. 원복 전후 양식 SHA-256은 ec4699872488a0483c4dfc0ae2b1eb9cc18ed390bd418bda657e64cbaca2a08f로 같으며 원복 뒤 공통 작업 파일 검사가 통과했다.

설치된 Git 관리 wrapper를 해제·재설치하고 정식 정의와 바이트가 같음을 확인했다. 사용자 원래 hook의 보존 SHA-256은 a82f6143429c4a98c3f6c3be39e73dccf9c8b56bc75075a4dc7d9229006413c7로 전후 동일하다. core.hooksPath를 변경하지 않았다.

## 보존과 확인 한계

기존 work 파일 400개는 작업 전후 바이트 대조로 모두 보존했다. 정책의 기존 기록 목록은 최초 고정한 15개 그대로다. 기존 작성안·예시·과거 지문과 #72 본문도 수정하지 않았다. 이 새 첨부만 work에 추가한다.

문서·코드의 자체 검수와 별도 문맥 검수의 필수 지적을 보완해 재검수했다. 전체 Markdown 렌더링이나 실제 논의/승인 준수를 자동 증명하지 않는다. 생성 시험은 동일 모델의 명시 적용 사례이며 자동 skill 선택·실제 GitHub 발급/라벨 변경·제품 수행·다른 대화/환경·CI는 확인하지 않았다. hook의 정의·수동 호출·관찰한 자동 발동을 구분하며 지원 밖 경로·오류/타임아웃의 완전 차단이나 자동 되돌림을 주장하지 않는다. 실제 GitHub 발급·원격 반영·CI 실행은 수행하지 않았다.

## 최종 제출 후보와 검수

사용자가 이번 정식 반영에 필요한 변경의 최종 검수·로컬 커밋을 승인했다. 기준 HEAD는 2992008c7de4eb11b843fa0d2f89e62352b657bc다. 실제 index 50개와 명시 후보 목록을 대조했고 기존 work 파일의 스테이징은 없으며 새 work 첨부는 이 파일 하나다. 기존 미추적 초안·정책·제품/환경 변경은 포함하지 않았다. 공통 검사에 필요한 기존 parser/호환 명령과 정식 절차가 참조하는 검증·별도 검수 기준은 필수 동반 변경으로 포함했다.

신규 독립 Issue도 Task에서 실행하도록 Git 기준을 맞추고 기존 예외만 직접 완결을 유지했다. 끝공백 두 곳을 제거했다. 실제 index의 현황·공통 주석·기록 검사와 diff 공백 검사, 작성자의 실제 후보·미스테이징 의존 대조를 통과했다. 같은 모델의 별도 읽기 전용 에이전트가 코드/의존과 문서/범위를 검수했다. 문서 검수는 index의 Markdown 참조 337곳·참조 파일 73개·현황 7항목의 지문·증빙 앵커를 직접 확인했다. 필수 지적을 처리했고 미해결 필수 결함은 없다.

검수 뒤 바뀐 항목은 확인 결과·한계 문구와 현황의 검증 범위뿐이며 규칙·코드·수용 조건은 유지했다. 최종 후보의 실제 생성 커밋은 Git 이력으로 식별한다. 다음 운영 확인은 신규 독립 Issue와 하위 Task 한 건의 생성·상세 계획 합의·수행 기록·완료·부모 수용 흐름을 실제 적용하는 것이다. 이 반영 자체를 실제 Task 운영 효과의 검증 완료로 보지 않는다.
