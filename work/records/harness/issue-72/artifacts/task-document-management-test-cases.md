# Task 생성과 문서 관리 가상 시험 사례

<a id="overview"></a>
## 현재 설계 상태와 목적

사용자가 대화에서 제시한 문서 정리 사례의 확장과 별도 파일 관리를 요청해 작성한 **재사용할 시험 설계안**이다. 사례 정의와 실제 실행·판정은 구별한다. 실행 범위·현재 진행·판정·미실행 범위는 [Issue #72의 시험 기록](../issue.md#task-generation-test)에서 관리한다.

확인할 것은 확정 배정으로 Task를 생성한 뒤 계획·논의·결정·수행·검증·종료에 따라 문서가 실제 상태를 유지하는지다. 정상 결과만 아니라 부족한 입력, 결정 대기, 변경, 실패와 복구도 관찰한다. 이 문서는 사례별 입력·진행 방법·기대 결과를 관리하며 실행 이력을 누적하지 않는다.

기존 [Issue → Task 생성 사례](issue-to-task-test-cases.md)는 정상 3개와 부족 3개의 생성 입력을 유지한다. 이 파일은 대화에서 제시한 사례를 구체화하고 생성 이후의 관리 흐름까지 확장한다. 기존 사례를 실행 완료로 바꾸거나 과거 중단 시험의 근거를 교체하지 않는다.

<a id="common-setup"></a>
## 공통 시험 설정

- 사례는 서로 독립이다. 앞 사례의 완료·사용자 응답·파일 변경을 다음 사례의 사실로 가져오지 않는다.
- 가상 부모와 자식은 역할명 **부모 P**, **Task T**로 표시한다. 사례 번호는 시험 식별자이며 정식 Issue/Task 번호가 아니다. 실제 #72의 보유 Task나 제품 현황에 등록하지 않는다.
- 아래 파일명은 시험용 입력의 논리 이름이다. 실행 전 별도 시험 묶음의 저장 위치와 부모·Task·전달사항·수행 기록의 파일 대응을 정한다. 생성용 식별·경로·순번 확인 근거도 해당 시험 설정으로 제공하고, 기존 기록을 빌려 실제 확인한 것처럼 쓰지 않는다.
- 생성 정상 사례는 부모의 배정·전달본·식별·경로·충돌 확인 근거가 갖춰진 상태를 입력으로 제공한다. 부족 사례에서는 무엇이 빠졌는지 명시한다. 해당 전제를 준비하지 못하면 그 사례는 실행 준비 미충족이다.
- 실행 환경은 격리한 로컬 문서 묶음이다. 게임 자료·DB·개발 서버·외부 계정은 필요하지 않다. 파일 변경은 사례에 명시한 시험 대상과 허용 범위에서만 한다. GitHub 발급·게시, 실제 제품 변경, 커밋은 포함하지 않는다.
- 시험용 본문 생성에는 생성 지시서와 본문 양식을 사용한다. 생성 후에는 복사된 본문 주석·공통 절차를 따르고, 첫 할 일 착수 때만 수행 기록 양식을 사용한다.
- 사용자 선택이 필요한 사례는 실제 응답을 받으며 진행하는 방식을 제안한다. 아래의 인용 응답은 **향후 제공할 입력안**이며 이미 받은 응답이 아니다. 응답을 정해 주입하는 모의 방식은 별도로 정하고, 그 결과를 실제 사용자 승인이나 실제 운영의 증거로 쓰지 않는다.
- 시험 계획 합의·Task 배정·Task 전체 계획 합의·실행 허용은 각각 적용 범위를 확인한다. 같은 응답이 여러 조건을 명시적으로 충족하면 재사용하며 통상적인 기록 갱신마다 재승인을 요구하지 않는다.

<a id="base-input"></a>
## 기준 사례의 입력

### 시험용 원문

`start.md`:

```markdown
# 시작 안내

Task 본문은 현재 상태와 계획을 관리합니다.
자세한 수행 내용은 별도 수행 기록에 남깁니다.

[기록 방법 보기](guide.md#record)
```

`guide.md`:

```markdown
# 기록 안내

<a id="recording"></a>
## 기록 방법

Task 본문은 현재 상태와 계획을 관리합니다.
자세한 수행 내용은 별도 수행 기록에 남깁니다.
```

위 링크의 표식 불일치와 두 문서의 같은 설명이 관찰 대상이다. 코드 블록은 입력 원문이며 이 설계 파일에서 실제 연결되는 링크가 아니다.

### 부모 P의 배정안

시험 시작점은 부모 P가 다음 배정을 확정하고 최초 전달본을 준비한 직후다. 이 설정의 배정 확정은 시험 안의 전제이며 실제 #72의 Task 배정 사실이 아니다.

| 입력 구역 | 전달할 내용 |
|---|---|
| 태그 | 조사, 논의, 결정, 실행, 검수 |
| 목적 | 시작 안내에서 기록 방법으로 정확히 이동하고, 같은 상세 설명을 두 문서에서 관리하는 문제를 줄인다. |
| 기대 결과 | 수정한 시험용 `start.md`, 선택 이유와 완료 조건별 확인 결과. |
| 이미 정해진 조건 | `guide.md`가 상세 설명의 원본이다. 두 문서를 읽고 `start.md`만 수정한다. 실제로 존재하는 파일·표식으로 연결한다. 안내 방식은 사용자 선택 뒤 반영한다. AI는 대조·후보 작성·합의 안의 문안 정리와 검증 방법을 맡는다. |
| Task에서 결정할 사항 | 시작 안내에 짧은 설명과 링크를 남길지, 링크만 남길지 비교한 뒤 사용자가 선택한다. 두 안은 상세 설명 중복을 줄이고 기록 방법을 찾을 수 있어야 한다. |
| 완료 조건과 확인 방법 | 링크가 실제 파일·표식으로 연결되고, 두 상세 문장을 시작 안내에 그대로 중복하지 않으며 사용자 선택과 수정본이 일치한다. 원문·실제 응답·수정본을 대조한다. `guide.md`는 원문 그대로 유지하고 수정 범위 밖 내용도 보존한다. |

생성·관리 정보는 부모의 배정 기준 기록에서 관리하고 Task는 같은 전달사항을 참조한다. 최초 전달본 식별은 시험 안에서 초판을 실제로 확정할 때 부여하며, 생성 입력을 이후의 현재 계획·선택 값으로 덮어쓰지 않는다.

<a id="case-01"></a>
## TC-01. 정상 생성부터 문서 수정·종료까지

**입력·시작점**

[기준 입력](#base-input)과 공통 생성·관리 정보를 제공한다. Task는 신규·미착수이고, 구체 수행 계획은 미합의다. 안내 방식은 아직 선택하지 않았다.

**진행 방법**

1. 전달사항을 참조하는 Task 본문을 생성하고 부모 보유 목록과 자식의 부모 연결을 맞춘다.
2. Task에서 대조·후보 작성 → 사용자 논의·결정 → 반영·확인 → 전체 검수·종료의 수행 계획을 수립·합의한다.
3. 첫 할 일 착수 때 수행 기록을 만들고 원문을 대조해 문안 두 가지와 장단점을 제시한다.
4. 실제 사용자 선택을 받은 뒤 현재 합의·남은 결정·할 일·다음 행동을 맞추고 선택한 안을 반영한다.
5. 완료 조건별로 확인하고 Task의 종료 처리를 마친다. 부모는 결과·근거를 읽고 별도로 전체 수용을 판단한다.

**관찰·기대 결과**

- 생성 직후는 예정, 허용된 계획·논의를 시작하면 진행 중이다. 생성 단계에서 미합의 계획·미정 선택·실행 결과를 채우지 않는다.
- 수행 기록은 Task당 한 파일이고 첫 할 일 이전에는 예정 경로만 있다. 후속 할 일은 같은 파일에 주석 없는 구역으로 추가하며 미착수 구역은 만들지 않는다.
- 본문은 현재 합의와 전체 판정을, 수행 기록은 상세 대안·실제 응답·조치·확인·잔여를 담는다. 할 일과 기록은 왕복 연결된다.
- 올바른 링크와 중복 해소만으로 사용자 선택 확인을 대신하지 않는다. 전체 수용·필수 종료 처리를 갖춘 뒤 완료로 바꾸며, Task 완료가 부모의 완료를 자동 결정하지 않는다.

<a id="case-02"></a>
## TC-02. 생성에 필요한 배정 정보 부족

**입력·시작점**

기준 입력에서 아래 한 가지를 뺀 독립 변형 세 개를 준비한다. 누락한 답은 다른 부모 기록·파일에도 없다는 조건을 함께 제공한다. 기존 [생성 사례의 M1~M3](issue-to-task-test-cases.md)에 대응하며 해당 입력·예상 결과를 함께 대조한다.

| 변형 | 뺄 내용 | 확인할 보완 요청 |
|---|---|---|
| 담당 결과 부족 | 수정 문안 제안만 맡길지 실제 반영까지 맡길지 부모가 확정하지 않음 | 맡길 결과·범위와 결정 주체·수용 기준 |
| 수용 기준 부족 | 결과의 완료 조건·확인 방법을 모두 미정으로 변경 | 무엇으로 충분한 결과인지 판단할지 |
| 생성 정보 부족 | 식별·저장 위치·부모 목록과 파일의 순번 충돌 확인 근거를 미확인으로 변경 | 실제 부모 목록·파일·사용 이력의 대조와 기준 기록 보완 |

**진행 방법**

변형별로 입력 확인과 보완 요청까지 진행한다. 답을 받은 상태는 이번 입력에 미리 포함하지 않는다.

**관찰·기대 결과**

- 부족한 정보와 그에 의존하는 생성을 제한하고 필요한 확인만 구체적으로 반환한다. 임의의 범위·완료 기준·번호·경로로 정식 본문을 완성하지 않는다.
- Task 안에서 결정할 문안의 미정과 부모가 맡길 결과 자체의 미확정을 구별한다.
- 미생성 상태에서 수행 기록·검증 성공·부모의 생성 완료 체크를 만들지 않는다. 이 사례에서 보완 요청을 정확히 반환하면 기대 행동에 맞지만 Task 생성 성공으로 보고하지 않는다.

<a id="case-03"></a>
## TC-03. 방법 선정 자체를 맡긴 Task

**입력·시작점**

배정을 별도로 구성한다. 목적은 시험용 두 문서의 링크 점검 방법을 정하는 것이며, 기대 결과는 수동 대조와 로컬 검사 방식의 비교·사용자 선택·선택 이유·후속 실행 조건이다. 비교 기준은 재현 가능성·준비 부담·이번 두 문서에서 확인 가능한 범위다. 담당 결과·수용 기준·최종 결정 주체는 확정됐고 채택 방법만 미정이다. 태그는 조사, 논의, 결정, 검수다. 허용은 원문 검토·비교·논의이며 검사기 작성·실행과 문서 수정은 배정하지 않는다.

**진행 방법**

Task를 생성한 뒤 전체 계획을 합의하고 두 후보를 같은 기준으로 비교한다. 실제 사용자 선택을 받아 결론과 후속 조건을 기록하고 이 배정의 완료 조건을 확인한다.

**관찰·기대 결과**

- 방법 미선정을 생성 부족으로 취급하지 않는다. 방법의 답은 Task에서 만들며 생성 시 추천안을 채택 결과로 넣지 않는다.
- 비교 자료·실제 선택 근거·후속 조건이 배정의 결과다. 검사기 실행 성공이나 실제 파일 수정을 수행·완료 조건으로 추가하지 않는다.
- 조사·논의·결정의 실제 근거를 남기고 파일 수정이 없는 할 일도 수행 기록에 담는다.

<a id="case-04"></a>
## TC-04. 후속 원자료 미확보와 독립 활동

**입력·시작점**

기준 배정의 결과·완료 조건·생성 정보는 갖췄지만 `guide.md`의 실제 원문은 아직 제공되지 않았다. 부모는 이 자료의 제공 담당을 사용자로, 필요한 시점을 링크 대상 확정·수정·검증 전으로 명시했다. 현재는 Task 생성·계획과 제공된 `start.md`의 읽기 전용 대조를 허용한다. 초기 링크의 정답을 기준 입력에서 가져오지 않도록 미제공 원문을 실행 문맥에 포함하지 않는다.

**진행 방법**

1. 자료 미확보·제공 담당·필요 시점·제한을 남겨 Task를 생성한다.
2. 전체 계획과 공통 준비를 갖춘 뒤 제공된 문서에서 독립적으로 확인 가능한 내용만 조사한다.
3. 원문이 필요한 행동에 도달하면 제한·해소 조건을 남긴다.
4. 후속 입력으로 실제 `guide.md`를 제공받으면 내용과 준비를 확인하고 영향받는 계획을 갱신해 의존 행동을 진행한다.

**관찰·기대 결과**

- 후속 실행 자료 부족과 생성 조건을 구별한다. 알 수 없는 표식·연결 성공·원문 보존을 추론하지 않는다.
- 전체 계획·공통 준비를 충족한 상태에서 허용된 독립 활동은 가능하다. 다음 합의 행동이 실제로 막히면 작성안의 중단 상태와 구체 재개 조건을 적용한다.
- 자료를 확보한 사실을 새 실행 허용으로 해석하지 않는다. 기존 허용 범위와 실제 입력을 확인한 뒤 재개하며, 변경된 부분만 다시 확인한다.

<a id="case-05"></a>
## TC-05. 사용자 선택을 기다리는 동안의 기록

**입력·시작점**

기준 사례의 후보 비교까지 수행한 가상 상태를 입력으로 제공한다. 본문·수행 기록에는 그 범위의 결과만 있다. 사용자는 문안 두 가지를 받았지만 아직 응답하지 않았다. 현재 합의한 계획의 다음 행동은 사용자 선택이며, 선택 전에 할 수 있는 다른 독립 작업은 남아 있지 않다.

**진행 방법**

선택에 필요한 차이와 질문을 제시하고, 응답 전 본문·수행 기록·체크·수정 대상의 상태를 관찰한다. 응답을 기다리는 것 자체를 시험 중 임의의 승인으로 바꾸지 않는다.

**관찰·기대 결과**

- 질문·AI 권고안·무응답을 합의나 결정 완료로 기록하지 않는다. 문안 선택과 그에 의존하는 반영·완료 체크는 남긴다.
- 본문에는 남은 질문·결정 주체·필요 시점·다음 행동이 있고, 수행 기록에는 제시한 대안과 미결 상태가 있다.
- 다음 합의 행동이 실제 사용자 응답에 막혔으므로 중단과 구체 해소 조건을 기록한다. 논의 태그 자체를 중단 사유로 쓰지 않는다. 허용된 독립 활동이 남아 있는 TC-04의 조건과 구별한다.

<a id="case-06"></a>
## TC-06. 추가 비교 요청에 따른 계획 갱신

**입력·시작점**

TC-05와 같은 미결 상태에서 시작한다. 후속 입력안은 “아직 고르지 않겠다. 처음 읽는 사람과 반복해서 쓰는 사람의 관점에서 두 문안을 더 비교해 달라”다. 배정 범위·완료 조건·문서 수정 권한은 바꾸지 않는 요청이다.

**진행 방법**

추가 비교를 기존 할 일의 보완 또는 같은 결과를 위한 할 일 조정으로 반영한다. 다음 관련 행동 전에 현재 합의·남은 결정·계획·확인 방법·태그·다음 행동을 맞춘다. 보완 비교 후 다시 실제 선택을 받는다.

**관찰·기대 결과**

- 요청된 추가 조사를 사용자 선정이나 문서 수정 허용으로 바꾸지 않는다.
- 부모 배정을 바꾸지 않는 상세 논의는 Task에서 관리한다. 이 이유만으로 새 Issue·Task·전달본을 만들지 않는다.
- 생성 입력은 당시 배정으로 보존한다. 본문에 응답별 경과를 누적하지 않고 현재 결론을 갱신하며 상세 비교·요청 근거는 수행 기록의 해당 구역에서 관리한다.
- 사용자 선택 뒤 해결된 질문과 조건을 현재 내용으로 맞추고 후속 행동 전에 연결한다.

<a id="case-07"></a>
## TC-07. 부모 배정 변경과 전달본 개정

**입력·시작점**

초기 전달본에 따라 `start.md`만 수정하는 Task가 진행 중이고 일부 조사 근거가 있다. 후속 입력안은 “상세 안내의 첫 문장도 바꿔 두 문서를 함께 정리하자”다. 수정 대상·담당 결과가 달라지는 요청이며, 변경 내용·수용 기준·권한은 부모에서 정해야 한다.

**진행 방법**

1. 기존 배정으로 할 수 있는 일과 변경 합의에 의존하는 일을 구별한다. 새 대상의 수정은 부모 변경 합의 전 제한한다.
2. 부모에서 새 범위·기대 결과·완료 조건·권한·영향을 합의한다.
3. 기존 전달본을 보존한 새 개정본과 부모 기준 기록을 마련하고 Task의 적용 참조를 맞춘다.
4. 기존 결과 중 재사용 가능한 부분과 재확인할 부분을 구별하고 두 문서의 결과를 새 기준으로 확인한다.

**관찰·기대 결과**

- Task 본문만 고쳐 배정 변경을 확정하거나 원본 전달사항을 현재 값으로 덮어쓰지 않는다.
- 초기 전달본과 새 개정본·변경 이유·합의 근거가 구별된다. 기존 수행 결과가 어느 전달본에 근거했는지 유지한다.
- Task 현재 합의·계획·전체 확인과 부모 기준 기록이 같은 개정본을 가리킨다. 영향이 없는 조사를 모두 다시 하거나 새 권한을 추론하지 않는다.

<a id="case-08"></a>
## TC-08. 할 일 재구성과 수행 근거 보존

**입력·시작점**

기준 배정 안에서 원문 대조가 끝났고 해당 할 일의 식별자·수행 기록·확인 근거가 있다. 나머지는 미착수다. 링크 확인을 반영·확인 할 일에 묶는 편이 같은 결과를 더 명확히 확인할 수 있다는 사실을 입력으로 제공한다. 범위·결정 주체·완료 조건·권한은 같다.

**진행 방법**

합의와 위임 범위 안에서 남은 할 일을 병합·재배열하고 이유를 남긴다. 현재 계획·태그·예정 연결을 함께 맞추되 완료 행동의 식별자·당시 태그·근거를 유지한다.

**관찰·기대 결과**

- 같은 배정 안의 통상적인 조정마다 사용자 재승인을 요구하지 않는다. 필요한 사용자 선택·검수 조건은 조정 뒤에도 남는다.
- 순서를 바꿔도 이미 사용한 작업 식별자와 왕복 링크를 다른 행동에 재사용하지 않는다. 본문에서 완료 행동을 빼는 경우에도 원래 표식과 근거 연결을 남긴다.
- 미착수 구역을 수행 기록에 미리 만들거나 병합 과정에서 기존 실제 결과를 삭제하지 않는다. 실제 수행 근거와 현재 계획을 구별한다.
- Task 태그는 현재·완료 행동을 포함해 맞추고 모든 할 일에 같은 태그를 일괄 복사하지 않는다. 태그 변경이 판정에 영향을 주면 당시 기준·이유를 식별한다.

<a id="case-09"></a>
## TC-09. 확인 실패·보완·재확인

**입력·시작점**

사용자 선택과 반영이 끝났다고 제시된 시험용 수정본의 링크가 `guide.md#records`를 가리키는 상태를 제공한다. 실제 원문의 표식은 `recording`이며 해당 할 일의 확인은 아직 끝나지 않았다. 이 오입력은 시험 묶음 안에만 준비한다.

**진행 방법**

실제 파일·표식을 대조해 실패를 확인한다. 원인과 수정 범위를 남기고 올바른 표식으로 보완한 뒤 링크·선택 문안·원문 보존 중 영향받는 부분을 다시 확인한다.

**관찰·기대 결과**

- 수정했다고 한 사실이나 링크 문구만으로 통과시키지 않는다. 불일치가 남아 있으면 해당 완료 체크·Task 수용을 제한한다.
- 실패·보완·재확인은 같은 할 일의 수행 기록 구역에서 관리한다. 필요한 실패 원인·당시 기준을 보존하되 재시도마다 구역·증명 파일을 늘리지 않는다.
- 본문은 현재 문제·다음 행동을 반영하고, 해결 후 현재 판정으로 갱신한다. 실패 사실을 없던 것으로 바꾸거나 실패를 별도의 영구 상태로 만들지 않는다.

<a id="case-10"></a>
## TC-10. 일부 저장 뒤 중단과 사용자 변경을 포함한 복구

**입력·시작점**

가상 중단 시점에는 `start.md`의 링크만 올바르게 저장됐고 문안 정리·확인은 끝나지 않았다. Task 본문은 이전 다음 행동을 가리키며 수행 기록에는 저장 뒤 확인 근거가 없다. 중단 이후 사용자가 시험용 `start.md`에 “이 안내는 내부 작업자를 위한 것입니다.”라는 별도 문장을 추가한 상태를 제공한다. 이전 합의와 원문도 입력으로 보존한다.

**진행 방법**

실제 파일·본문·수행 기록·사용자 변경을 대조해 저장된 부분, 미수행, 미확인을 나눈다. 사용자 추가 문장을 보존하며 허용 범위·선행 조건·이전 근거의 유효성을 확인하고, 필요한 확인과 남은 작업부터 재개한다.

**관찰·기대 결과**

- 처음부터 재실행하거나 옛 입력으로 파일을 덮어쓰지 않는다. 사용자 변경의 충돌 여부를 실제 내용으로 판단한다.
- 저장된 링크의 현재 유효성을 사후 확인할 수 있지만 과거에 확인했던 것처럼 기록하지 않는다. 실제로 확인한 시점의 조치와 판정으로 남긴다.
- 기존 활동 상태를 신규 예정으로 초기화하지 않는다. 재개 조건을 충족하고 허용된 활동을 재개하면 진행 중으로 맞추며 완료를 추론하지 않는다.
- 현재 요약·남은 계획·본문과 기록의 연결이 실제 저장 상태를 따른다. 복구를 이유로 불필요한 새 Task나 수행 기록 파일을 만들지 않는다.

<a id="case-11"></a>
## TC-11. 문서 이동과 양방향 경로 보정

**입력·시작점**

별도 배정으로 다음 시험 묶음을 제공한다. `start.md`와 `index.md`는 `guide.md#recording`을 참조하고 `guide.md`에는 `[시작 안내로 돌아가기](start.md)`가 있다. 부모는 처음부터 `guide.md`를 `guides/recording.md`로 이동하고 이 세 문서의 관련 링크를 수정하도록 맡겼다. 본문 설명·`recording` 표식과 관계없는 사용자 문장은 보존한다. 완료 조건은 이동과 모든 대상 참조의 정상 연결·범위 밖 내용 보존이다. 태그는 조사, 실행, 검수다. 경로는 이 배정에서 확정돼 별도 문안 선택은 없다.

**진행 방법**

허용된 시험 묶음에서 참조를 확인하고 이동·경로 보정을 수행한다. 들어오는 링크는 새 파일·기존 표식으로, 이동한 파일의 돌아가기 링크는 `../start.md`로 맞춘다. 최종 위치에서 각 연결과 보존 조건을 확인한다.

**관찰·기대 결과**

- 파일 이동만 완료로 판단하지 않고 기존 진입점과 이동한 문서의 상대경로를 함께 확인한다.
- 표식을 새 사건에 재사용하거나 과거 근거·본문 연결을 무조건 현재 경로로 치환하지 않는다. 이번 입력에서 이동할 원문과 수정할 현재 안내를 구별한다.
- Task 본문과 수행 기록이 실제로 옮긴 대상·변경 범위·확인 근거를 가리킨다. 시험 밖 저장소를 전수 검색하거나 기존 문서를 이동하지 않는다.

<a id="case-12"></a>
## TC-12. 취소와 부모의 필수 결과 잔여 처리

**입력·시작점**

기준 배정의 원문 대조·후보 작성까지 진행한 상태다. 문서 수정은 아직 하지 않았다. 부모 P의 필수 결과에는 시작 안내의 링크·중복 문제 해소가 남아 있다. 후속 입력안은 “이 Task는 여기서 취소하자. 최종 안내 방식과 대체 작업은 아직 정하지 않았다”다.

**진행 방법**

실제 취소 요청을 확인하면 이유·부분 결과·미반영·필요 자료의 보존과 잔여 처리를 기록한다. Task를 취소로 닫고 부모에는 대체나 범위 변경이 필요한 필수 결과를 연결한다.

**관찰·기대 결과**

- 취소를 목표 달성·완료로 바꾸지 않는다. 비교 자료·실제 근거·사용자 변경을 유지하고 정상 완료 때의 정리를 자동 적용하지 않는다.
- 부모는 자식의 닫힘이나 취소 개수로 전체 수용을 판단하지 않는다. 필수 결과가 남았으므로 대체 결과나 범위 변경의 판단이 필요하다.
- 대체 Task의 배정·번호·사용자 선택을 만들지 않는다. 부모의 다음 행동과 미결정·잔여를 현재 내용으로 남긴다.

## 제안하는 시험 진행과 결과 관리

1. 이 파일에서 먼저 실행할 사례·확인 목적·입력·기대 결과를 검토한다. 첫 회는 TC-01로 생성과 기록 흐름을 보고, 이후 TC-05·TC-06·TC-09로 논의·갱신·보완을 보는 순서를 제안한다. 각 사례는 시작 상태를 독립적으로 준비한다.
2. 실행 전에 사용할 작성안, 시험 파일의 저장 위치·식별 대응·허용 범위와 사용자 응답 방식을 정한다. 현재 대화에서 한 사례씩 관찰하는 방식을 제안하며, 새 문맥·별도 에이전트 실행은 아직 선택하지 않았다.
3. 선택한 입력과 필요한 준비를 확인하고 단계별로 실제 문서·파일을 관찰한다. 예상 결과는 실행자에게 제공할 지시와 검토자가 대조할 기준 중 어디에 둘지도 정해, 확인하지 않은 맹검 효과를 주장하지 않는다.
4. 실행 결과는 담당 Issue의 시험 판단에 현재 결론·범위·한계·다음 행동으로 갱신한다. 필요한 상세 근거는 담당 artifacts에만 보존하고 이 사례 파일에는 실행별 경과를 붙이지 않는다.
5. 기대와 다르면 입력·전제 준비 부족, 생성·갱신 행동의 결함, 판정 기준의 부족을 구별한다. 원인을 확인하지 않고 기준을 실행 결과에 맞추거나 같은 조건의 반복 성공을 전체 운영 성공으로 확대하지 않는다.

이 파일은 재사용할 입력·방법·판정 기준을 관리한다. 실제 실행의 상태와 결과를 사례 목록에 중복 기입하지 않으며, 실행 범위·구체 설정·현재 결과는 담당 Issue와 그곳에서 연결한 시험 묶음에서 확인한다.
