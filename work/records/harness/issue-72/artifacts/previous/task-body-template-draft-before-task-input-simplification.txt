# Issue 하위 Task 본문 양식 — 작성안

Task 본문 네 구역과 Task별 수행 기록의 작성 틀이다. 상태·초기값은 [Task 공통 절차의 상태 규칙](task-common-procedure-draft.md#state-rules)을 따른다. 현행 원천 적용과 실제 사용성은 별도 확인 대상이다.

[전달사항 양식](task-creation-input-draft.md#assignment-body) · [생성 지시서](task-file-creation-guide-draft.md#creation) · [본문 참조 예시](task-body-example-43-002.md)

<a id="body"></a>
## 본문 사용

아래 첫 코드 블록으로 Task 본문을 작성하고 최종 위치에 맞게 링크를 보정한다. 진행 규칙은 [Task 공통 절차](task-common-procedure-draft.md)를 따른다. 수행 기록은 아래 별도 양식을 사용한다.

배정 합의·현재 전체 계획의 제안/합의·현재 허용을 구별해 기록한다. 위임 범위 안의 계획 갱신과 사용자 확인의 경계는 [수행 판단](task-common-procedure-draft.md#judgment)을 따른다.

배정 안에서 논의·선정한 방법은 본문의 계획과 합의에 기록한다. 배정된 결과·범위·기존 결정·완료 조건·권한을 바꾸는 경우의 Issue 처리와 전달본 개정은 [전달사항 변경](task-common-procedure-draft.md#revision)을 따른다.

```markdown
# Task <부모 Issue 번호>-<로컬 순번> — <작업 제목>

공통 규칙: [Task 공통 절차](task-common-procedure-draft.md)
```

<a id="execution-body"></a>
## Task별 수행 기록 양식

담당 Issue의 `artifacts/task-<실제 순번>-execution.md`에 아래 틀을 사용한다. 첫 할 일 착수 때 파일을 만들고 이후 각 할 일에 같은 구역을 추가한다. 실제 과정·결과만 기록하고 예정은 Task 본문으로 연결한다. 할 일 추가·삭제·분할·병합과 근거 보존은 공통 절차를 따른다.

```markdown
# Task <부모 Issue 번호>-<실제 순번> 수행 기록

- Task: <상위 Task 본문 링크>

<a id="work-<작업식별자>"></a>
## <할 일 이름>

- Task 예정: <상위 Task 본문의 해당 할 일 링크>

### 과정

<실제 조치·관찰·중요한 판단·문제/보완과 필요한 이유를 짧게>

### 결과

- 내용: <실제 변경과 현재 결과>
- 확인: <실제 적용 기준·입력/대상·방법·관찰·판정·근거·한계. 당시 적용 전달본과 필요한 커밋을 식별한다. 계획과 같은 검증 방법은 참조하고 달라진 점만 덧붙일 수 있다>
- 잔여: <미반영·미확인·막힘·재개 조건과 다음 행동. 없으면 없음>
```

<a id="planned-example"></a>
## 예정과 수행 기록의 연결 예시

가상의 문서 정리 Task에서 첫 할 일을 마치고 두 번째를 시작하기 전의 모습이다. 배정·준비·전체 계획의 합의는 갖췄다고 가정한다. 실제 Task 발급·승인·검증·커밋 기록이 아니며 아래 근거는 자리표시자다. 구역은 각 할 일 착수 때 만들고, 형식만으로 완료 표시하지 않는다.

Task 본문의 계획과 합의:

```markdown
합의·위임: 배정은 <배정 확정 근거>, 현재 전체 계획은 <이 계획을 합의한 가상의 근거·적용 범위>를 따른다. 실제 승인 기록이 아닌 자리표시자다.
공통 조건: <수용한 구조 합의·수정 범위·위임 근거·현재 허용·실행 선행 조건>을 따른다. 기존 합의·범위·권한의 변경은 관련 실행 전에 사용자와 논의한다.
공통 커밋 범위: 아래 두 할 일의 변경·검증·수행 기록을 "Task 구조 반영"으로 묶는 계획이다. 실제 허용·실행 조건은 공통 조건을 참조한다.

<a id="work-record-format"></a>
- [x] 공통 조건에서 허용한 작성안·양식·예시를 합의한 구조로 맞추고 자체·별도 검수와 필요한 보완·기록까지 마치라. 본문 네 구역·전달본 식별/확정 근거·왕복 연결과 수행 기록의 Task별 통합을 대조하라.
  - 수행 근거: [과정과 결과](artifacts/task-<순번>-execution.md#work-record-format)

<a id="work-submit"></a>
- [ ] 앞 할 일의 변경·검수·보완·수행 기록이 준비되면 검수 근거와 실제 후보를 대조하고 허용된 커밋·반영·보존·정리까지 처리하라. 전체 결과·잔여를 Task 본문에 맞추고 전달본의 완료 조건에 대조해 종료를 판단하라.
  - 수행 근거 예정 구역: artifacts/task-<순번>-execution.md#work-submit
```

<a id="db-method-plan-example"></a>
## DB 생성 방법 논의의 가상 본문·전체 계획 예시

[가상 배정·전달사항](task-creation-input-draft.md#db-method-assignment-example)을 본문 생성 지시서에 대입하는 사례다. 부모의 논의 배정과 식별/저장 경로 확인은 가정 안에서 갖췄지만 생성 방법은 미정이다. 실제 번호·URL·발급·승인·실행 결과를 나타내지 않는다.

| Task 본문 구역 | 가상 작성 내용 |
|---|---|
| 현재 요약 | 허용된 계획 수립 중인 가정이므로 진행 중이다. 현재 위치는 계획과 합의, 다음 행동은 전체 계획 초안 논의다. 방법 미정은 Task가 논의할 과제이며 실제 DB 작업의 미허용과 구별한다. |
| 전달사항 참조 | 가상 부모의 배정 결정·식별/경로 확인 근거와 위 전달사항을 참조한다. 실제 원본 경로·전달본 식별·기준 기록을 새로 발급한 것으로 쓰지 않는다. |
| 계획과 합의 | 논의 과제의 배정은 가정에서 확정했지만 현재 전체 계획은 제안·미합의다. 생성 방법도 미정이다. 현재 허용은 계획·자료 검토·사용자 논의이며 DB 생성·DDL 실행·기존 DB 변경·커밋 권한은 없다. |
| 결과 | 실제 후보 비교·사용자 선정·검수가 발생하지 않은 가정이다. 선정 방법·수용·완료 결과를 미리 기록하지 않는다. |

이 사례에서 구성할 수 있는 전체 계획 초안은 다음과 같다. Task의 공통 고정 단계가 아니며 계획의 합의와 실제 진입 조건은 [실행 전 전체 계획](task-common-procedure-draft.md#sequence-rules)·[착수 확인](task-common-procedure-draft.md#start-check)을 따른다.

1. 대상 환경·기존 제약·판정 기준을 확인하고 후보를 자료로 비교한다. 시험 실행이 필요하면 필요한 권한·환경·확인 시점을 분리해 남긴다.
2. 후보·비교 근거·남은 불확실성을 사용자에게 제시해 생성 방법을 논의·선정한다. 방법 값을 사전에 확정하지 않는다.
3. 배정 안에서 합의한 방법·이유·후속 실행 조건을 Task의 계획과 합의에 기록한다. Issue가 고정한 조건·범위·권한을 바꿔야 한다면 기존 전달사항 변경 절차로 연결한다.
4. 비교 자료·사용자 논의 근거·선정 기록을 담당 결과와 수용 기준에 대조해 검수하고 허용된 전달·정리를 계획한다. 실제 DB 생성·커밋을 이 논의 과제의 필수 할 일로 추가하지 않는다.

이 가정의 완료 기준은 후보 비교와 사용자 선정 내용·이유·남은 실행 조건의 정리다. 방법 선정만으로 DB 실행을 허용하거나, 논의가 있었다는 사실만으로 아직 미선정인 결과를 완료로 처리하지 않는다.
