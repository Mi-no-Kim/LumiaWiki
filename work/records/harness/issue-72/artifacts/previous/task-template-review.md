## 검토 범위와 위치

- 담당 Issue: [Issue #72 — 실행 가이드와 반복 확인 방식 정비](../../issue.md#summary).
- 용도: 대화에서 진행한 Task 양식의 요소별 검토를 보존하고 후속 논의에서 참조하는 하위 검토 자료다. 별도 Task나 채택된 새 운영 규칙이 아니다.
- 관점: GitHub 게시용 양식이 아닌, 계획·판단·실제 수행·검증·인계를 담는 로컬 작업 기록의 원본으로 평가한다. 정보 자체의 필요성과 독립 항목·구역의 필요성을 구분한다.
- 검토 입력: [커밋 76e26221ce8b334b462273660c9b4b7e79a81e01의 Task 양식](https://github.com/Mi-no-Kim/LumiaWiki/blob/76e26221ce8b334b462273660c9b4b7e79a81e01/harness/templates/task.md), Git blob `a9ca9232510f14b3f1f4f79bd120cc340fce4429`. 아래 행 번호는 이 입력을 기준으로 한다.
- 현재 독립 브랜치의 [Task 양식](../../../../../../harness/templates/task.md)은 Git blob `5d0fe5750c22b52981bae6607cc8c975ae79fdd6`으로 내용이 다르다. 사용자 확인 목록·결과·요청의 세 항목과 서식 차이가 있으므로 구체 수정 전에 적용 범위를 재확인한다.
- 판정의 성격: 필요성·중복·작동 가능성에 대한 정적 검토 의견이다. Issue의 큰 변경 방향에 대한 합의와 각 항목의 유지·통합·삭제·보강 채택은 구분한다. 실제 누락 감소와 운영 효과는 확인하지 않았다.
- 관련 원천: [기록 체계](<../../../../../../docs/작업 기록 체계.md#ownership>)와 [기록 작성 기준](<../../../../../../docs/작업 기록 작성 기준.md#minimum>). 현재 기준을 바꾸거나 기존 양식을 수정하는 문서가 아니다.

## 1. 문서 제목과 상단 작성 안내 — 1~5행

| 요소 | 필요성과 작동 평가 |
|---|---|
| `# Task 작성 양식` | 양식의 제목으로 필요하다. 실제 기록으로 복사할 때는 Task 식별자와 구체적인 작업 제목으로 바뀌어야 하며, 변환 안내를 명확히 할 여지가 있다. |
| GitHub 반영 시 별도 게시 양식 사용 | 로컬 기록과 게시 양식의 역할을 구분하는 짧은 안내로 유용하다. 로컬 기록의 작성 내용을 GitHub 게시 형식에 맞출 이유는 없다. |
| 실제 실행 단위가 필요할 때 복사 | 불필요한 Task 생성을 줄이는 조건으로 필요하다. 어떤 단위로 작업할지 판단한 결과를 어디에 남길지는 불명확하다. |
| 부모 Issue에 등록 | 필요한 실행 지시다. 등록 완료 여부를 확인하는 자리가 없어 안내를 읽고도 본문만 작성할 수 있다. |
| 최종 위치에서 링크 정비 | 상대 링크를 실제 기록 위치에 맞추는 데 필요하다. 정비 지시와 실제 확인 결과의 연결은 약하다. |
| 계획·수용 조건은 착수 전에 작성 | 결과를 만든 뒤 그 결과에 맞춰 계획·완료 조건을 작성하는 일을 방지한다. 작성된 계획이 사용자와 논의한 내용인지 AI의 임의 계획인지는 구별하지 못한다. |
| 사건·검증·종료는 실제 해당 시점에 작성 | 미래의 성공이나 미발생 사건을 미리 기록하지 않도록 유지할 필요가 있다. |
| 미발생 승인·성공을 채우지 않기 | 승인 기록란이 있다는 이유로 승인을 가정하지 못하게 한다. 실행 전에 어떤 승인이 필요한지는 별도로 정해야 한다. |
| 보존 근거를 덮어쓰지 않기 | 현재 결론 갱신과 과거 실행 근거 훼손을 구별하는 데 필요하다. 두 정보의 경계가 함께 이해돼야 한다. |
| 현재 요약부터 필요한 근거만 읽기 | 재개 효율에는 도움이 된다. AI가 필요한 근거를 임의로 좁히지 않도록 해당 작업의 적용 지침과 확인 시점이 본문에 드러나야 한다. |

상단에는 행동 지시가 있지만 이를 실제로 수행했는지 확인하는 구조가 충분히 이어지지는 않는다.

## 2. 현재 요약 — 7~15행

재개할 때 현재 위치를 빠르게 파악하는 구역으로 필요하다.

| 요소 | 필요성과 작동 평가 |
|---|---|
| 제목 | 정보는 필요하지만 문서 최상단에 실제 Task 제목이 있으면 별도 관리 항목은 중복이다. |
| GitHub sub-issue 저장소·번호·URL | 로컬 기록에도 외부 대응 객체의 식별 정보는 필요하다. “실제 연결 시”와 빈칸만으로는 미등록·실패·보류를 구별할 수 없어 누락이 드러나지 않는다. |
| 상태 | 필요하지만 완료한 범위와 남은 절차를 상태 하나로 설명할 수는 없다. 자기 수용과 전체 종료의 구별이 함께 보여야 한다. |
| 현재 진행 위치 | 같은 상태에서도 어느 단계인지 알아야 하므로 필요하다. 수행 계획의 단계와 연결하면 모호함을 줄일 수 있다. |
| 다음 행동 | 필요하다. 이미 허용된 행동인지 먼저 논의해야 할 행동인지 구별돼야 한다. |
| 막힌 조건/근거 | 필요하지만 다음 행동과는 다른 정보다. 실행할 작업만 적으면 그 전에 필요한 논의나 준비가 끝났는지 알기 어렵다. |

`## 현재 요약`과 `- 상태:` 표기는 [현재 상태 검사기](../../../../../../.agents/skills/review-work/scripts/check_task_status.py)가 직접 읽는다. 제목·표기를 바꾸면 이 연동도 확인해야 한다.

## 3. 목적과 허용 범위 및 완료 조건 — 17~24행

필요성이 높은 구역이지만 서로 다른 질문을 한 줄에 많이 묶었다.

| 요소 | 필요성과 작동 평가 |
|---|---|
| 부모 Issue | 소속 목표를 찾는 연결로 필요하다. 자식의 부모 링크만으로 부모 보유 목록에 등록됐다고 판단할 수는 없다. |
| 목적/요청 결과 | 왜 하는지와 무엇을 만들어야 하는지를 설명하는 필수 정보다. 활동명보다 해결할 문제와 기대 결과가 드러나야 한다. |
| 허용 범위 | 임의 확장을 통제하는 핵심 정보다. 작업 주제뿐 아니라 이번에 허용된 행동 범위를 알아야 한다. |
| 실제 대상/입력 | 어떤 파일·자료·환경을 다루는지 식별하는 필수 정보다. 목표나 허용 범위와 구별해 읽을 수 있어야 한다. |
| 제약 | 필요하지만 뒤의 현재 결정과 제약에도 있어 중복 관리 위험이 있다. |
| 자기 완료 조건 | 결과를 만들기 전에 실제 확인 가능한 성공 기준을 정해야 한다. 검증 항목과 대응돼야 한다. |
| 현재 기준 | 어떤 요구·규칙으로 판단하는지 연결하는 데 필요하다. 완료 조건과 묶이면 단순 참고 링크로 밀릴 수 있다. |
| 권한 근거 | 무엇을 실행해도 되는지 확인하는 데 필요하다. 올바른 결과를 정하는 기준과 실행을 허용하는 권한은 다른 정보다. |

`자기 완료 조건·현재 기준/권한 근거`는 세 질문을 묶어 일부만 채워도 전체를 다룬 것처럼 보일 수 있다. 합의한 범위·적용 지침·추가 논의가 필요한 선택이 분명히 드러나는지도 확인할 필요가 있다.

## 4. 계획과 예정 검증 — 26~34행

계획을 작성하고 점검하는 중심 구역이다. 현재 문구는 계획의 작성 수준을 AI에게 많이 맡긴다.

| 요소 | 필요성과 작동 평가 |
|---|---|
| 준비/선행 조건 | 필수다. 필요한 자료·환경·앞선 작업을 나열하는 것과 실제 준비 완료를 확인하는 것이 구분되지 않는다. |
| 미정 | 필요하지만 선행 조건과 성격이 다르다. 누가 언제 결정하고 그 결정 전 어떤 행동을 제한할지 연결돼야 한다. |
| 수행 계획 | 필수지만 안내가 넓다. 작업 목록이나 “구현 후 검증” 한 줄로 끝날 수 있어 순서·단계별 결과·확인 지점이 필요하다. |
| 화면 디자인·구현 순서와 검증 흐름 | 제품 기능에서는 필요하다. 사용할 화면과 선행 관계를 연결하되 모든 Task의 형식적인 작성 부담으로 만들지는 않아야 한다. |
| 사용자 확인 목록 | 해당 기능·동작 변경에서 필요하다. 준비 조건·조작·기대 결과를 미리 정해 실제 검증에 재사용한다. |
| 구현 전 공유·공유 여부/미정 | 시점과 상태를 확인하는 데 필요하다. 공유 사실과 계획 전체의 승인·실행 권한은 구별해야 한다. |
| 자동 검사·직접 조작과의 연결 | 사전 목록이 검증으로 이어지게 한다. 같은 사례를 여러 구역에서 재작성하기보다 연결하는 방식이 적절하다. |
| 확인할 결과/방법 | 필수다. 완료 조건과 대응되지 않으면 검사를 많이 해도 필요한 결과를 확인하지 못할 수 있다. |
| 필요한 별도 검수 | 필요하다. 대상·시점·조건을 계획에 포함해야 하며 “예정”만 적으면 실행 단계에서 다시 빠뜨릴 수 있다. |

계획을 언제 다시 읽고 점검해야 하는지는 명시되지 않는다. 계획의 존재와 계획에 따른 실제 수행의 연결이 약하다.

## 5. 조건부 항목의 적용 판단과 기록 — 36~40행

| 요소 | 필요성과 작동 평가 |
|---|---|
| 독립된 하위 구역 | 취지는 필요하지만 별도 구역의 필요성은 낮다. 실제 작성란보다 작성 지침에 가깝고 앞선 조건부 항목과 중복될 수 있다. |
| 조건·원천·확인 대상·시점 | 정보는 필요하다. 문구가 추상적이어서 실제 행동을 구체화하는 부담이 작성자에게 남는다. |
| 현재 적용 판단·활동 근거 | 적용 여부와 수행 여부를 구분하는 데 필요하다. 조건 성립을 수행 성공처럼 기록하지 않아야 한다. |
| 모르는 조건은 해당 없음이 아님 | 미확인을 부적용으로 처리하지 않게 하는 중요한 안내다. 필요한 확인과 제한할 행동까지 이어지면 실용적이다. |

관련 항목에 붙일지 공통 안내로 둘지 논의할 수 있다. 모든 Task에 추상적인 빈 구역을 유지하는 효과는 크지 않아 보인다.

## 6. 현재 결정과 제약 — 42~49행

같은 논의를 반복하거나 합의를 바꾸지 않도록 이유와 조건을 남기는 중요한 기록 구역이다.

| 요소 | 필요성과 작동 평가 |
|---|---|
| 유효한 결정 | 필수다. 합의한 결정과 미채택 제안을 구별해야 한다. |
| 결정 이유 | 필수에 가깝다. 이유가 없으면 다음 AI가 기존 선택을 불필요하다고 판단해 바꾸기 쉽다. |
| 승인과 근거 | 필요하다. 승인 대상·범위를 알아야 하며 “승인받음”만으로는 실행 가능 범위를 알기 어렵다. |
| 제약 | 필요하지만 허용 범위 구역과 중복된다. 한곳에서 관리하고 필요한 부분을 참조하는 편이 안정적이다. |
| 현재 막힌 실패·미확인 | 필요하지만 요약의 막힌 조건·검증의 미확인과 겹친다. 여기서는 현재 판단에 미치는 영향과 처리 방향을 남기는 역할이 적합하다. |
| 해결 후 최종 결론 | 현재 선택의 이유가 되는 결론은 남길 필요가 있다. 상세 재시도 과정까지 계속 누적할 필요는 없다. |
| 다음 행동 | 현재 요약·종료 구역에도 있어 독립된 반복 항목으로는 중복이다. 서로 다른 다음 행동이 남을 수 있다. |
| 같은 항목을 갱신하고 경과를 누적하지 않기 | 현재 기록을 읽기 쉽게 유지하는 데 필요하다. 결정 이유·승인 범위·필요한 근거까지 지우지는 않아야 한다. |
| 상세 과정·출력을 artifacts로 연결 | 조건부로 필요하다. 본문에서 이해해야 할 수행 결과까지 모두 밖으로 빼거나 매 실행마다 첨부를 만들면 부담이 커진다. |

의미 있는 실제 수행과 중간 결과를 어디에 적을지도 중요하다. 현재는 자리가 명확하지 않아 이 구역에 수행 경과가 몰릴 가능성이 있다.

## 7. 검증과 근거 — 51~60행

계획과 실제 결과를 구분하는 데 필요한 구역이다.

| 요소 | 필요성과 작동 평가 |
|---|---|
| 대상/입력·기준/조건·방법 | 실제 검증 정보로 필요하다. 계획을 복사하는 자리가 되어서는 안 되며 실제 후보·환경·입력과 달라진 조건을 식별해야 한다. |
| 실제 관찰 | 필수다. 실제로 무엇을 보았는지 남겨야 하며 “정상”이라는 결론만으로는 부족할 수 있다. |
| 판정 | 필수다. 관찰이 어떤 완료 조건을 충족하는지 설명하고 검사 통과와 Task 전체 수용을 구별한다. |
| 확인 범위/한계 | 필수다. 결과의 적용 범위와 확인하지 못한 부분을 남긴다. |
| 사전 목록별 자동 검사 결과 | 해당 목록이 있을 때 필요하다. 계획의 사례와 연결해 사후에 유리한 사례만 고르는 일을 줄인다. |
| AI 직접 조작 결과 | 해당 시 필요하다. 자동 검사 통과와 실제 조작 확인을 구별한다. |
| 사용자 확인 결과/미확인 | 해당 시 필요하다. AI 확인을 사용자 확인으로 대신 기록하지 않으며 응답 전에는 미확인으로 남긴다. |
| 필요한 artifacts 근거 링크 | 조건부로 필요하다. 본문이나 기존 근거로 충분하면 새 첨부를 만들 필요는 없다. |
| 계획/추론과 실행 사실 구별 | 유지할 지침이다. 작성 항목에서도 예정·관찰·판정이 실제로 구분돼야 한다. |

계획의 방법·기대 결과와 실제 결과를 대응시키면 작동할 수 있다. 같은 목록을 두 구역에 별도로 복제하면 불일치가 생길 수 있다.

## 8. 중단과 전환 및 재개 — 62~69행

| 요소 | 필요성과 작동 평가 |
|---|---|
| 구역 자체 | 중단·전환이 발생한 작업에서 다음 AI가 이어갈 위치를 판단하는 데 중요하다. |
| “이 틀은 유지” | 항상 빈 구역을 남길지는 논의할 만하다. 발견하기 쉽지만 모든 기록에 미발생 사건의 빈 항목이 남는다. |
| 실제 사건 때만 작성 | 아직 발생하지 않은 중단·재개를 미리 기록하지 않게 하므로 필요하다. |
| 계획 전환은 B 착수 전 보존/등록 | 행동과 시점이 분명한 지시다. 다만 설명되지 않은 `B`보다 “다음 작업”처럼 직접 표현하는 편이 읽기 쉽다. |
| 예기치 않은 중단은 실제 상태부터 복구 | 기록만 믿고 재실행·덮어쓰기하는 일을 막는 데 필요하다. 당시 기록과 재개 후 확인 사실을 구별해야 한다. |
| 이유·실제 멈춘 상태 | 왜 멈췄고 어디까지 수행됐는지 확인하는 필수 정보다. |
| 전환/선행 대상과 관계 | 해당 시 필요하다. 다른 작업을 먼저 하는 이유와 의존을 연결하되 참조·소속을 혼동하지 않아야 한다. |
| 복귀 조건 | 무엇이 해결되면 돌아오는지 명시하는 필수 정보다. |
| 다음 행동·재개 판단 | 필요하지만 중단 당시의 예정 행동과 복귀 후 실제 상태에 따른 판단을 구별해야 한다. |

“다음 작업 착수 전”처럼 행동·시점·선행 조건을 연결한 문구는 실행 가이드로 작동할 여지가 크다.

## 9. 결과와 잔여 및 인계 — 71~80행

| 요소 | 필요성과 작동 평가 |
|---|---|
| 종료 절차에 따라 작성 | 필요하다. 이번 Task에 필요한 종료 단계가 계획에 연결돼 있으면 링크만 두는 것보다 누락을 줄일 수 있다. |
| 현재 요약/관련 현황 맞추기 | 필요한 실행 지시다. 변경 대상과 실제 반영 여부를 확인하는 구조는 약하다. |
| 부모 수용은 별도 | Task 종료가 Issue 전체의 성공을 뜻하지 않도록 유지해야 한다. |
| 정상 완료/취소/미완료 인계 | 필요한 구분이다. 해당 종료 형태와 이유가 명확해야 한다. |
| 요청 대비 실제 결과 | 실제 달성·잔여를 설명하는 필수 정보다. |
| 판정·근거 | 필요하다. 검증 구역을 연결하면 되며 같은 내용을 전문으로 다시 적을 필요는 없다. |
| 반영/미반영 | 필요하다. 결과 생성과 실제 적용·제출 범위를 구별하고 무엇에 대한 반영인지 밝혀야 한다. |
| 한계·잔여 | 필수다. 검증의 한계와 절차상 잔여를 구별하면 전체 종료를 과장하지 않을 수 있다. |
| 재개 조건 | 미완료 인계 등에서 필요하다. 정상 완료마다 형식적으로 채울 항목은 아니다. |
| 다음 허용 행동 | 필요하지만 요약·현재 결정 구역과 중복된다. 현재 내용을 기준으로 일치시켜야 한다. |
| 사용자 확인 요청 | 해당 시 필요하다. 무엇을 요청했고 응답이 왔는지 기록한다. |
| 실행/접속 방법·버전/자료·확인 목록·AI 결과 | 사용자 확인에 필요한 정보다. 계획·검증의 내용을 모두 재작성하기보다 기존 사례·방법·결과와 연결하고 요청 대상·응답 상태를 명확히 하는 구성이 적합하다. |
| 임시 자료 보존/참조·정리 결과 | 임시 자료가 있을 때 필요하다. 필요한 근거 삭제와 불필요 자료 잔존을 방지한다. |
| 계속 보존할 이유 | 정리하지 않을 때 필요하다. 재개에 필요한 자료인지 판단할 수 있어야 하며 자료가 없으면 형식적인 정리 기록도 필요하지 않다. |

종료 형태·결과·판정·근거를 한 항목에 묶으면 일부만 채웠을 때 빠진 정보가 잘 드러나지 않는다.

## 10. 링크 표식과 문서 구조

입력에는 `summary`·`goal`·`plan`·`conditional-guidance`·`activity`·`verification`·`transition`·`result`의 여덟 표식이 있다.

특정 구역으로 연결하기 위한 구조로 유용하지만, 표식의 존재가 내용·절차의 충족을 의미하지는 않는다. 구역 통합·이동 시 기존 참조를 확인해야 한다. `activity`의 실제 제목은 “현재 결정과 제약”이므로 수행 기록을 맡길지 판단할 때 역할을 명확히 할 필요가 있다. 빈 줄은 읽기 위한 서식이며 기록 정보와 구별한다.

## 11. 보고된 문제에 대한 대응력과 후속 논의

| 보고된 문제 | 현재 입력에 있는 요소 | 부족한 연결 |
|---|---|---|
| 논의 없이 진행 | 허용 범위·권한 근거·승인 기록 | 먼저 논의할 선택과 계획의 합의 여부 |
| 작성 양식 미준수 | 상단 작성 안내·기준 링크 | 이번 산출물에 적용할 양식과 작성 전·후 대조 |
| main에서 작업 | 준비·선행 조건이라는 일반 항목 | 담당 브랜치 준비와 실제 현재 브랜치 확인 |
| GitHub 미등록 | 외부 객체 연결 정보 | 등록 시점과 실제 결과 확인 |
| 진행 중 지침을 잊음 | 계획·기준을 기록하는 자리 | 단계 전환·요구 변경·재개 시 재확인 |

단순히 없애기 좋은 정보는 많지 않다. 제목·다음 행동·제약·한계처럼 반복되는 정보의 소유 위치를 정하고, 한 줄에 묶인 서로 다른 질문을 구분하는 것이 간소화의 주요 검토 대상이다.

후속 논의에서는 항목의 유지·통합·조건부 배치와 착수·반복 점검의 연결을 정한다. 이 문서의 항목별 의견을 채택한 것으로 보거나, 정적 검토를 실제 운영 효과의 검증으로 확대하지 않는다.
