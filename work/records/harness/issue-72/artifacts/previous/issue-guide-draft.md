# Phase 하위 Issue 지시서 — 작성안

<a id="summary"></a>

> 이전 통합 작성안이며 비교용으로 보존한다. 현재 검토 경로는 [파일 생성 지시서](../issue-file-creation-guide-draft.md)·[진행 지시서](../issue-progress-guide-draft.md)와 [담당 기록의 문서 구분](../../issue.md#draft-map)을 따른다. 아래 본문은 현행 기준·절차·양식을 대체하지 않는다.

<a id="role"></a>

## 역할

Phase에서 배정받은 Issue를 작성·보완·진행하는 AI가 사용한다. [양식의 기본 본문](issue-template-draft.md#body)에 현재 아는 내용부터 적고, 시작 전 필요한 내용과 실제 진행 결과를 채워간다.

양식의 `issue-rule:` 규칙 주석도 함께 복사하고, 기록을 갱신하거나 종료할 때도 유지한다. AI는 Markdown 원문의 주석을 읽고 따르며, 사용자가 해당 규칙 변경을 명시적으로 요청한 범위 외에는 식별자·내용·경계를 수정·삭제하지 않는다.

<a id="writing-requirements"></a>

## 반드시 작성할 내용

| 항목 | 필요한 내용 |
|---|---|
| 기본 정보·현재 상태 | 실제 Issue 번호·URL, 부모 Phase와 배정 근거, 자기 상태·진행 위치·다음 행동·막힌 조건 |
| 목적·담당 결과 | 해결할 문제와 이번 Issue가 남길 결과 |
| 대상·범위·권한 | 실제 대상·입력, 할 일과 경계, 허용 근거·위임 범위, 적용 지침과 준비의 실제 값·근거 |
| 완료 조건·확인 방법 | Issue 전체의 결과 기준과 기준별 확인 대상·기대 결과·방법. 필요한 검수·화면 확인도 포함 |
| 진행 순서 | 대화로 합의한 할 일·순서·선행 조건과 항목별 완료 조건 |

각 항목은 실제 기록·합의·상태를 확인해 작성한다. 같은 내용이나 근거가 이미 있으면 연결하며, 별도 점검표에 다시 적지 않는다. 적용 지침·준비 근거는 대상·범위·권한 구역에 모으고, 결과의 완료 조건·확인 방법만 별도 구역에 둔다. 진행 순서의 각 할 일 완료 조건과 Issue 전체의 결과 기준을 구분한다.

모르는 내용은 해당 항목에 미정·미확인으로 표시하고 **확인·결정 방법과 필요한 시점**을 남긴다. 기존 사실과 위임된 상세는 직접 보완하고, 새 범위·권한이나 위임되지 않은 선택은 논의한다. 하나라도 필요한 결정이 남으면 해당 내용을 확정하거나 그에 의존하는 실행용 계획·결과물을 만들지 않는다. 제안·논의용 초안은 확정 내용과 구분한다.

<a id="sequence"></a>

## 진행 순서와 다음 행동

진행 순서는 Issue 생성 시 해당 과제의 목표·배정·미정 사항을 바탕으로 대화에서 정한다. 할 일과 완료 조건을 번호가 있는 체크리스트로 기록하고 공통 단계 목록을 일괄 복사하지 않는다. 미정 상세는 이를 결정할 일을 먼저 넣고 채워간다. 항목의 추가·삭제·수정·재배열은 대화로 합의하며 기존 자유 서술형 수행 순서와 중복 관리하지 않는다.

다음 행동은 첫 미완료 순서 항목 안에서 현재 허용된 행동 하나를 적는다. 막힌 조건은 제한되는 순서 번호·미충족 조건·해소 조건으로 분리한다. 순서가 없거나 대응하는 번호가 없으면 `번호 미정 — 미충족 조건 — 해소 조건`으로 적고, 이미 아는 조건은 유지한다. 제한 여부 자체가 미확인이면 확인할 대상·방법을 남긴다. 번호가 정해지면 조건을 해당 번호에 연결한다. 후속 항목의 제한을 현재 항목의 정보 확인·논의·본문 보완 금지로 확대하지 않는다. 실제 완료 조건과 근거로 체크하며 기존 시작 조건과 실행 권한은 별도로 확인한다.

제품 기능은 [화면 기준](<../../../../../../docs/details/operations/검증과 완료.md#screen-first>)에 따라 화면 디자인 검토 → 동작 구현 → 화면을 통한 동작 확인의 선후 관계를 진행 순서에 연결한다. 사용할 화면의 위치와 검증할 흐름을 적고, 기존 화면을 사용해도 이번 기능과의 관계를 확인한다. 화면 디자인 검토와 구현 후 동작 확인의 결과를 구분한다.

<a id="decisions"></a>

## Task 분해 전 결정 사항

Issue의 방향·범위 등 Task로 나누기 전에 결정할 사항은 양식의 체크리스트에 모은다. 항목은 대화에서 추가하기로 합의한 것만 넣고, AI가 발견한 후보는 먼저 대화에서 제안한다. 양식의 자리표시자는 합의한 첫 항목으로 교체하며 실제 결정 항목으로 취급하지 않는다. 빈 목록이나 자리표시자만으로 결정 완료를 판단하지 않는다.

미결정 항목이 남아 있는 동안에는 기존 항목의 문구·순서를 유지하고 체크 표시만 바꾼다. 삭제·축약·병합·다른 구역 이동으로 미정 사항을 없애지 않는다. 결정 내용·이유·근거는 목적·범위·완료 조건 등 담당 구역에 기록한 뒤 체크하고, 다시 미정이 되면 체크를 해제한다. 다른 구역의 작성·보완은 계속할 수 있다.

전부 결정하기 전에는 Task 분해·배정을 확정하지 않는다. Issue 본작업의 시작·재개는 아래 시작 조건에 따라 별도로 판단하며, 체크리스트 완료만으로 허용됐다고 보지 않는다. 목록 정리로 필요한 결정 내용·이유·근거를 지우지 않는다.

<a id="start-check"></a>

## 시작 조건

**위 필수 내용이 하나라도 비어 있거나 미정·미확인이면 Issue 본작업을 시작·재개할 수 없다.** 별도 판정값 없이 진행 순서의 해당 항목에서 기입·결정과 실제 준비 근거를 확인하고, 미충족 내용·해소 조건은 막힌 조건에 기록한다. 순서의 체크만으로 시작 조건을 대신하지 않으며 자리표시자·TODO·근거 없는 ‘해당 없음’은 충족으로 보지 않는다.

그전에는 필수 정보의 기존 기록 확인·질문·작업기록 작성과 이미 허용된 등록·브랜치·환경 준비만 한다. 배정 과제의 조사·설계·구현·검증·Task 수행을 준비로 취급해 먼저 진행하지 않는다. 이번 Issue가 만들 결과물 자체의 완성을 시작 조건으로 요구하지 않는다.

착수·재개·조건 변경·주요 단계 전환·수용 판단 때 기록과 적용 지침을 실제 상태에 대조한다. 조건이 바뀌면 이미 체크한 항목도 영향을 다시 확인하고 관련 내용·준비 근거·막힌 조건을 갱신한다.

<a id="acceptance"></a>

## 진행하며 필요한 기록

[진행·결과 구역](issue-template-draft.md#event-body)은 실제 해당 일이 생길 때만 붙인다.

- 결정: 현재 유효한 판단·이유·허용 근거·제약과 진행을 막는 실패·미확인. 실제 자식 Task가 있으면 담당 결과를 링크하고 상세 상태를 복사하지 않는다.
- 검증: 완료 조건 표의 각 조건을 식별할 수 있는 문구·참조로 연결하고, 조건별로 대상·입력·기준·방법·관찰·판정·이유·한계·근거를 기록한다. 판정은 충족·불충족·미확인·해당 없음으로 구분하며 해당 없음의 이유도 남긴다. 수행하지 못한 필수 확인은 미확인으로 남기고, 조건을 생략하거나 종합 성공 한 줄로 대신하지 않는다. 상세 확인 내용은 근거를 연결해 중복을 줄인다. Task 완료를 Issue 수용으로, Issue 완료를 Phase 수용으로 전파하지 않는다.
- 중단·종료·인계: 실제 결과·반영·미반영·잔여·재개 조건과 다음 행동, 필요한 관련 갱신·보존·정리 결과.

같은 항목은 현재 내용으로 갱신하고, 상세 실행 근거만 필요한 경우 artifacts에 연결한다. 작성·기록 기준은 [기록 작성 기준](<../../../../../../docs/작업 기록 작성 기준.md#minimum>), 준비·등록·종료의 상세 절차는 [문서 관리](<../../../../../../harness/문서 관리.md#entry>)와 [Git 작업](<../../../../../../harness/Git 작업 절차.md#start>), 실제 수용은 [검증과 완료](<../../../../../../docs/details/operations/검증과 완료.md>)를 따른다.
