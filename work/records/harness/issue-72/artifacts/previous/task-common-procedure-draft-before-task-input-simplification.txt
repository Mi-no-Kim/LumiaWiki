# Task 공통 절차 — 작성안

확정된 전달사항을 기준으로 Task의 계획·수행·확인·종료를 진행한다. 본문과 수행 기록은 [Task 본문 양식](task-body-template-draft.md)을 사용한다. 현행 원천 적용과 실제 운영 확인은 별도다.

<a id="agreement-rules"></a>
## 입력과 책임

Issue는 Task의 담당 결과·범위·완료 조건, 이미 결정한 동작·계약·제약, 선행 입력, AI 위임과 사용자 확인이 필요한 선택을 확정 전달사항·배정 기준 기록으로 관리한다. 생성 지시서는 이를 최초 Task 본문에 반영한다.

<a id="assignment-record"></a>
Task는 부모 Issue·적용 전달사항·전달본 식별·확정 근거를 참조하고 Issue의 배정과 일치하는지 읽어 확인한다. 과거 기준은 필요하면 해당 커밋으로 식별한다.

<a id="body-structure"></a>
전달사항 원문은 해당 파일에 두고 Task 본문은 **현재 요약·전달사항 참조·계획과 합의·결과** 네 구역에서 자기 계획·합의·상태·전체 결과를 관리한다.

<a id="state-rules"></a>
### 상태와 전환

작성안의 상태는 **예정·진행 중·중단·완료·취소**다. 현재 요약의 `- 상태: 값` 한 줄에 하나만 기록한다. 현행 일곱 상태·검사기·라벨·실제 Task 상태는 유지한다.

| 상태 | 의미·판단 기준 |
|---|---|
| 예정 | 허용된 활동 미착수. 목표·알려진 조건·미정을 유지한다. |
| 진행 중 | 허용된 계획·논의부터 수행·확인·보완·검증·검수·종료 확인을 진행 중. |
| 중단 | 다음 합의 행동이 구체 조건에 막히거나 지금 추진하지 않기로 멈춤. 미착수 때도 가능하다. |
| 완료 | 자기 수용과 필수 종료 처리를 충족함. 상세 판정은 [수용·종료](#completion-rules)를 따른다. |
| 취소 | 목표 달성으로 처리하지 않고 작업을 닫음. |

- 신규 생성·미착수 초기값은 **예정**이다. 실제 상태 우선·기존 상태 보존·미확정 예시 처리는 [초기 기입](task-file-creation-guide-draft.md#initial-state)을 따른다.
- 허용된 활동을 시작·재개하면 진행 중, 막힘 해소 뒤에도 미착수면 예정이다. 재개는 [준비·권한 확인](#start-check)을 따른다. 필요 시점 전의 미정이나 계획 보완만으로 중단하지 않으며 [부분 막힘](#integrity-failure) 중 독립 수행이 가능하면 진행 중을 유지한다.
- 미생성·미정·검수 실패·부분 완료를 별도 상태로 추가하거나 부모/자식·GitHub의 상태를 자동 전파하지 않는다.

검증·검수는 현재 위치에, 대기·보류의 이유·재개 조건은 막힌 조건 등 기존 기록에 남긴다. 상태는 진행 위치·실행 권한·검사 결과와 구분하며 상태 변경만으로 실행 준비나 수용을 충족하지 않는다.

<a id="sequence-rules"></a>
## 실행 전 전체 계획

<a id="boundary"></a>
Task 생성 후 첫 할 일 실행 전에 목표 달성부터 검증·검수·커밋·종료까지 전체 계획을 합의하고 공통 실행 준비를 갖춘다. 할 일의 개수·순서는 목표·의존 관계에 맞추며 의미 있는 결과와 필요한 검증·보완·기록까지 묶는다. 명령·파일마다 나누지 않는다.

<a id="body-placement-proposal"></a>
실행자가 할 일의 지시와 연결 원천을 읽고 다음을 구분할 수 있게 작성한다.

- 담당 결과·수행 범위
- 기존 결정·제약·선행 조건
- AI가 판단할 부분
- 사용자 확인 대상·시점·조건
- 검증할 결과·방법·커밋 범위

짧은 지시문과 공통 조건으로 표현하고 공통 준비·전체 확인·커밋 묶음은 한 번만 둔다.

조사 후 정할 선택도 전체 계획에 포함해 조사 내용·결정 시점·후속 계획 구체화 시점을 정한다. 결론에 의존하는 실행 전에 선택을 확정한다.

계획·논의를 위한 허용된 준비는 진행할 수 있다. 제품 기능은 [화면 선행·화면을 통한 검증 기준](<../../../../../docs/details/operations/검증과 완료.md#screen-first>)을 계획에 반영한다.

<a id="plan-update"></a>
## 할 일 수행과 계획 갱신

<a id="start-check"></a>
할 일 착수 때 계획과 실제 입력·권한·선행 결과·등록·브랜치 등 필요한 준비를 확인한다. 재개·주요 전환·조건 변경 때는 영향을 받은 조건을 재확인한다. 막힘 해소는 새 실행 승인이 아니다.

<a id="integrity-failure"></a>
부족·충돌 조건에 의존하는 행동은 제한하고 원인·해소 조건을 남긴다. 전체 계획·공통 준비를 충족하고 일부 할 일의 조건만 부족하면 이미 허용된 독립적인 일은 진행할 수 있다.

지시·위임 범위에 따라 수행하고 사용자 확인 조건에 도달하면 관련 후속 실행 전에 확인받는다. 실제 결과·필수 확인·보완·기록을 갖춘 할 일만 완료 표시한다.

<a id="judgment"></a>
AI는 합의된 목표·범위·완료 기준·동작/계약·권한과 위임 범위 안에서 수행 방법을 판단하고 할 일을 수정·추가·삭제·재배열·분할·병합할 수 있다. 중요한 변경 이유를 남기고 관련 다음 행동 전에 계획·연결·막힌 조건을 갱신한다.

이 경계를 바꾸거나 필수 확인을 생략할 필요가 있으면 관련 실행 전에 사용자와 논의한다. 통상적인 조정마다 재승인을 요구하지 않는다.

<a id="revision"></a>
## 전달사항 변경

배정 안의 상세 합의는 Task 본문에 기록한다. 배정된 결과·범위·기존 결정·완료 조건·권한이 바뀌면 Issue에서 변경 내용·이유·영향을 합의한다.

기존 전달사항은 보존한 채 새 개정본을 만들고 Issue의 기준 기록과 Task의 적용 참조를 맞춘다. 계획과 기존 결과에 미치는 영향을 확인해 필요한 부분만 보완·재검증한다. 기존 결과가 어느 전달사항을 기준으로 했는지 유지한다.

<a id="decision-rules"></a>
<a id="recording-proposal"></a>
## Task별 수행 기록

수행 기록은 Task당 `artifacts/task-<실제 순번>-execution.md` 한 파일이다. 첫 할 일 착수 때 만들고 이후 착수하는 할 일의 구역을 추가한다.

모든 구역에 같은 [수행 기록 양식](task-body-template-draft.md#execution-body)을 사용하고 본문의 해당 할 일과 왕복 연결한다. 미착수 경로·구역은 예정으로 표시하고 식별자는 실행 순서와 분리한다.

예정은 Task 본문에, 실제 과정·상세 결과는 수행 기록의 양식에 맞춰 남긴다. 검증의 대상·입력·적용 전달사항과 기준·방법·관찰·판정·근거·한계를 기록하며 예정과 같은 방법은 참조하고 차이만 덧붙일 수 있다.

보완·재시도는 같은 구역에서 갱신한다. 할 일을 삭제·분할·병합해도 수행 사실·유효한 근거·원래 식별자/연결을 보존하고 변경 이유·후속 할 일을 연결한다. 수행한 할 일을 본문에서 빼면 원래 표식·수행 근거 연결을 계획과 합의에 남긴다.

본문은 현재 판단·제약·전체 결과·근거 연결을 유지하고 상세 과정을 복제하지 않는다. 명령·재시도마다 기록을 늘리거나 미발생 결과를 채우지 않는다.

<a id="commits"></a>
## 검수와 커밋

할 일 완료·커밋·Task 전체 완료는 구분한다. 커밋은 [변경 목적](<../../../../../docs/details/git/작업 커밋 기준.md#working-commits>)에 따라 필요한 변경과 수행 기록을 함께 묶으며 여러 할 일을 포함할 수 있다.

[필수 별도 검수 조건](<../../../../../docs/details/operations/별도 검수.md>)을 지키고, 커밋 전에는 실제 후보를 자체·별도 검수한다. 유효한 근거는 재사용하고 달라진 영향만 다시 확인한다. 필수 결함·미확인을 해결하고 허용된 범위에서 커밋한다.

<a id="completion-rules"></a>
## 수용·종료와 중단

실제 전체 결과를 적용 전달사항의 완료 조건과 대조하고 판정·근거·한계·잔여를 본문에 남긴다. Task 자기 수용 조건과 필수 확인·관련 반영·보존·정리·종료 처리를 충족해야 완료이며 미충족 범위는 미완료다. 할 일 체크·커밋·부모 완료가 이를 대신하지 않는다.

Task의 수용과 부모 Issue의 수용은 구분하고 [프로젝트 종료 절차](<../../../../../harness/문서 관리.md#close>)를 따른다.

중단·전환·취소 때는 기존 현재 요약·계획/결과에 실제 상태·이유·영향 범위·보존한 결과와 근거·잔여·해소/재개 조건·다음 행동을 남긴다. 취소는 이유·잔여 처리·보존을 확인한 뒤 판단한다.

<a id="fingerprint-rule"></a>
과거 지문 근거는 [담당 기록](../issue.md#task-common-review)에 보존한다.
