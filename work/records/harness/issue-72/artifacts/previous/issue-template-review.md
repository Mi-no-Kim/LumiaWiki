# 로컬 Issue 양식과 작성 지침의 수정 범위 조사

> 아래는 조사 당시의 수정 후보와 비교 근거다. 현재 검토 문서와 이전 작성안의 역할은 [담당 기록의 문서 구분](../../issue.md#draft-map)에서 확인한다. 아래 후보·과거 연결을 새 작성안의 채택이나 현재 진입점으로 취급하지 않는다.

<a id="summary"></a>

## 조사 범위와 현재 판단

- 담당 Issue: [Issue #72 — 실행 가이드와 반복 확인 방식 정비](../../issue.md#summary).
- 용도: [Task 요소별 검토](task-template-review.md#summary)와 같은 방식으로 현행 Issue 양식을 검토하고, Issue 작성 양식과 지시서를 만들 때 손볼 위치·이유·연결 영향을 정리한다.
- 후속 작성안: [Phase 하위 Issue 지시서](issue-guide-draft.md#summary)에 합의한 「역할과 사용 시점」을 반영했다. Phase 하위 Issue의 지시서·양식을 먼저 완성하고 독립 Issue는 이후 별도로 다룬다. 아래 요소별 수정·배치 후보는 조사 의견이며 해당 구역의 채택과 구분한다.
- 이번 결과는 수정 후보에 대한 조사 의견이다. 항목별 채택이나 새 양식·운영 규칙의 확정이 아니며, 현행 양식·기준·절차는 수정하지 않는다.
- 검토 입력: 커밋 `2992008c7de4eb11b843fa0d2f89e62352b657bc`의 [로컬 Issue 양식](../../../../../../harness/templates/issue.md), Git blob `2261f15bc1684c40a2cd117591242368c9c9e5bc`. 작업 폴더의 입력도 이 blob과 같으며, 아래 행 번호는 이 75행 입력을 기준으로 한다.
- 기준: [단위와 소유](<../../../../../../docs/작업 기록 체계.md#ownership>)·[필요한 정보와 작성 시점](<../../../../../../docs/작업 기록 작성 기준.md#minimum>)·[권한](<../../../../../../docs/details/operations/권한과 실행 범위.md>)·[검증과 완료](<../../../../../../docs/details/operations/검증과 완료.md>).
- 핵심 판단: Issue가 맡는 문제·범위·수용 판단과 Task에 배정할 실행 결과를 먼저 구분해야 한다. 현재는 필요한 정보와 참조가 있지만, 생성·착수·Task 배정·재확인 때 수행할 행동과 실제 확인 결과의 연결이 약하다.

## 1. 수정할 위치와 연결 영향

| 위치 | 조사 결과와 후속 수정 후보 | 처리 조건 |
|---|---|---|
| [현행 로컬 Issue 양식](../../../../../../harness/templates/issue.md) | 역할·문제·목표·허용 범위, 계획과 Task 배정, 재확인 지침, 실제 결과의 기록 위치를 정비할 중심 대상이다. 아래 요소별 검토를 사용한다. | 먼저 별도 작성안에서 문안을 논의하고, 채택·적용 범위를 정한 뒤 반영한다. |
| [Phase 하위 Issue 지시서 작성안](issue-guide-draft.md#summary) | Phase 하위 Issue의 준비·작성·진행을 먼저 설계한다. Phase에서의 생성·배정 시점과 전달 내용, 등록·생성 후 보완의 구체 문안은 후속 논의 대상이다. | 합의한 「역할과 사용 시점」을 보존했다. Phase 하위 Issue용 지시서·양식을 완성한 뒤 독립 Issue를 별도로 다룬다. |

| [Task 생성 지침](task-creation-guide.md#creation)·[Task 작성 양식](task-template-draft.md#body) | Issue가 제공할 최소 배정과 Task가 시작할 때 보완할 내용의 접점이다. Issue 쪽에서 정한 분해·배정 안내와 중복·누락을 대조해야 한다. | 기존 작성안은 보존한다. Issue 쪽 분담을 정한 뒤 영향을 받은 부분을 다시 논의한다. |
| [생성·등록 절차](<../../../../../../harness/문서 관리.md#create>)·[Git 작업 시작 절차](<../../../../../../harness/Git 작업 절차.md#start>) | 실제 번호·경로·부모 등록과 브랜치 준비의 담당 원천이다. 작성 지침에서 수행 시점과 실제 확인을 연결할 곳이다. | 기존 절차를 참조한다. 조사만으로 절차 자체의 변경 필요성을 확정하지 않는다. |
| [기록 체계](<../../../../../../docs/작업 기록 체계.md#ownership>)·[기록 작성 기준](<../../../../../../docs/작업 기록 작성 기준.md#minimum>) | 소유·상태·필수 정보·기록 경계의 기준이다. 항목을 줄이거나 합칠 때 빠뜨릴 수 없는 의미를 확인한다. | 기준 전문을 양식에 복제하지 않는다. 새 의미·조건이 필요하면 별도 논의한다. |
| [GitHub Issue 게시 양식](../../../../../../harness/templates/github-issue.md) | 이미 Task 분해 방향·통합 확인을 기록할 항목이 있다. 로컬 양식에는 같은 안내가 명시되지 않아, 로컬 원본에서 해당 정보를 어디에 둘지 정해야 한다. | 로컬 설계 후 게시 내용과의 대응을 확인한다. 게시 양식의 동시 개편을 이번 요청으로 확정하지 않는다. |
| [Phase 양식](../../../../../../harness/templates/phase.md)·[work 안내](../../../../../README.md#start)와 기존 기록 | Phase 소유와 독립 Issue 경로, 새 작성 지침으로 들어가는 연결을 확인할 대상이다. | 실제 진입 위치·표식이 달라질 때 관련 참조만 정비한다. 기존 기록의 일괄 변환은 미정이다. |
| [기록 검사기](../../../../../../scripts/check-work-records.py)·[Task 상태 검사기](../../../../../../.agents/skills/review-work/scripts/check_task_status.py) | 기록 검사기는 새로 추가된 명시적 기록 날짜·실행 근거 블록과 변경된 Issue의 길이를 확인한다. 상태 검사기는 Task 경로만 허용하므로 Issue 양식의 상태를 검사하지 않는다. | 자동 검사 확대는 별도 선택이다. Issue 구역명 변경이 곧 Task 상태 검사기 수정 사유는 아니다. |

## 2. 작성 지침과 실제 Issue 본문을 나눌 후보

| 내용 | 작성 지침에 둘 후보 | 실제 Issue에 남길 후보 |
|---|---|---|
| Issue의 필요성과 소속 | 기존 작업 보완·새 Task·독립 Issue 판단 방법, Phase 소속·독립 경로의 차이 | 이번 문제·배정 근거·실제 소속과 관계 |
| 생성과 등록 | 번호 발급 전 초안부터 정식 기록·부모 등록·GitHub 원본 연결까지의 작성 방법 | 실제 식별 정보·등록 결과와 미해결 조건 |
| 목적과 범위 | 항목별 기입 기준·예시와 미정 보완 방법 | 문제·기대 결과·허용 행동·대상·제약·수용 조건 |
| Task 분해·배정 | 별도 실행·수용 단위가 필요한지 판단하고 Task 초안을 채우는 방법 | 이번 분해 이유·배정할 결과·경계·의존과 실제 보유 Task 링크 |
| 진행 중 재확인 | 재확인 항목을 구체화하는 방법과 사례 | 이번 Issue에서 다시 읽을 지침·시점·대조 대상·판정과 제한할 행동 |
| 검증과 종료 | 계획과 관찰을 구분하는 작성 방법·근거 보존 원칙 | 실제 수용 판정·근거·한계·반영과 잔여·다음 행동 |

이 구분은 배치 제안이다. 생성자가 읽는 설명만 별도 문서로 옮기고, 실행자가 계속 따라야 할 지침까지 Issue 본문에서 빠뜨리지 않도록 논의해야 한다. 작성 지침의 설명·예시를 매 Issue에 복사하는 방식도 피할 필요가 있다.

## 3. 현행 양식의 요소별 검토

### 3.1. 제목과 상단 작성 안내 — 1~7행

| 요소 | 필요성과 수정 후보 |
|---|---|
| `# Issue 작성 양식` | 복사 후 실제 과제 제목·식별자로 바꾸는 방법과 Issue의 역할 설명을 검토한다. 현재 본문에는 과제 전체의 판단과 자식 실행의 관계를 설명하는 짧은 안내가 없다. |
| GitHub 게시 양식 분리 | 로컬 원본과 외부 게시의 역할을 유지한다. 작성 지침에서는 로컬 내용을 언제 게시용으로 옮기는지와 실제 반영 확인을 연결할 수 있다. |
| 복사·생성/등록·실제 번호 확인 | 필요한 안내다. 번호 발급 전 초안과 정식 기록의 순서, Phase가 없는 독립 Issue의 경로를 작성 방법으로 구체화할 후보이다. |
| 작성 시점·현재 요약부터 읽기·기존 기록 보호 | 유지할 의미다. 이번 Issue에 필요한 원천과 작성 전후 대조가 어디에 기록되는지 보강할 수 있다. |

### 3.2. 현재 요약 — 9~19행

| 요소 | 필요성과 수정 후보 |
|---|---|
| 제목 | 실제 문서 제목과 중복될 수 있다. 별도 항목으로 유지할지 정한다. |
| 실제 GitHub 번호/출처·확인한 URL | 식별 정보와 실제 확인 결과를 구분할 필요는 있지만, 같은 URL을 두 번 관리할 가능성이 있다. 확인 대상·결과의 목적을 정하고 통합 여부를 논의한다. |
| 소속 Phase 탐색 연결 | Phase 소속일 때 필요하다. 독립 Issue에 가짜 부모를 만들지 않고, 탐색 링크와 부모의 보유 등록을 구별해야 한다. |
| 상태·현재 진행 위치 | Issue 자신의 상태와 과제 전체의 진행 위치를 보여야 한다. 자식 상태·완료 수로 대체하지 않는다. |
| 다음 판단/행동 | 무엇을 논의할지와 이미 허용된 행동을 구분할 수 있어야 한다. 계획의 현재 단계와 연결할 후보이다. |
| 막힌 조건·근거 | 상태와 구분되는 필수 맥락이다. 상세 미정·검증 근거를 복제하지 않고 현재 진행에 미치는 영향을 요약할 수 있다. |

### 3.3. 문제와 목표 및 수용 조건 — 21~26행

| 요소 | 필요성과 수정 후보 |
|---|---|
| 문제/요구·기대 결과 | 현재 부족한 상태·그 근거와 달성할 결과가 한 항목에 묶였다. 활동명만으로 목적을 대신하지 않도록 작성 형식을 구체화할 후보이다. |
| 범위/제약 | 무엇을 바꾸는지 외에 이번에 허용된 행동·실제 대상과 넘지 않을 경계를 식별해야 한다. 현재 결정 구역과 제약의 소유 위치도 정한다. |
| 자기 수용 조건·기준 원천 | 성공 조건과 그 근거는 다른 질문이다. 조건별 판정·예정 확인으로 이어지도록 작성 방법을 구분할 필요가 있다. |
| 현재 드러나지 않는 구분 | 합의한 내용·AI에게 위임한 상세·추가 논의할 선택을 어디에 기록할지 정한다. 목표에 적었다는 사실을 실행 허용으로 취급하지 않게 해야 한다. |

### 3.4. 해결 계획·조건부 사항·미정 — 28~44행

| 요소 | 필요성과 수정 후보 |
|---|---|
| 준비/계획 | 준비와 본작업을 구분하고 순서·선행 조건·단계별 결과·확인 지점을 작성할 후보이다. 브랜치·등록을 계획했다는 것과 실제 준비된 상태를 구별해야 한다. |
| 의존·착수 조건 | 선행 과제·입력·허용 범위를 실제 확인하고, 미충족·미확인일 때 어떤 행동이 제한되는지 연결할 필요가 있다. |
| 화면 디자인·구현 순서와 검증 흐름 | 제품 기능일 때 적용한다. 사용할 화면과 이번 Issue의 결과·Task 선후 관계를 연결하며 모든 하네스 Issue에 형식적으로 채우지 않는다. |
| 예정 확인 | Issue 자체의 수용 조건과 자식 결과를 합친 확인을 연결할 후보이다. 확인 방법뿐 아니라 대상·기대 결과·필요한 검수 시점도 구체화해야 한다. |
| 조건부 항목의 적용 판단 | 조건 성립·부적용·미확인과 수행 성공을 구별하는 의미를 유지한다. 공통 작성법과 이번 Issue의 판단을 어디에 둘지 정한다. |
| 미정·제안·합의한 후속 | 현재도 구분과 결정 시점을 요구한다. 결정 근거·주체가 필요한 경우와 결정 전 제한할 행동을 함께 연결할 수 있다. |
| Task 분해와 재확인 안내 | 현재 로컬 양식에는 명시 항목이 없다. Task를 나누는 이유·배정·통합 계획과, 재개·요구 변경·단계 전환 때 다시 대조할 내용을 추가할 주요 후보이다. |

### 3.5. 보유 Task — 46~49행

| 요소 | 필요성과 수정 후보 |
|---|---|
| 실제 자식 등록·순번/중복 확인 | 부모가 소유하는 필수 등록이다. 실제 Task 파일·번호·GitHub sub-issue 관계와 대조할 시점을 생성 안내에 연결할 수 있다. |
| Task의 상태·실행 전문을 복사하지 않기 | 유지할 경계다. 목록에는 자식의 담당 결과를 설명하는 링크를 두고 현재 상세는 자식에서 읽게 한다. |
| 생성·분해 안내와 등록 목록의 구분 | 현재는 생성된 자식의 등록 안내만 있다. 별도 실행·수용 단위의 필요성을 판단하고 목적·결과·범위·경계를 배정하는 안내가 필요하다. Task 생성 지침과의 분담을 먼저 정해야 한다. |
| Task가 없는 직접 수행 Issue | 기존 기준이 허용하는 경로다. 모든 Issue에 Task를 강제하지 않고, 직접 수행할 계획·근거와 Issue 자신의 수용 판단을 남길 수 있어야 한다. |

### 3.6. 관련 과제 — 51~54행

관련·의존 이유와 조건은 필요하다. 보유 Task 목록이나 계획의 의존 조건과 같은 정보를 별도로 갱신하지 않도록, 관계의 설명 위치와 계획에서 참조할 방법을 정할 후보이다. 관련 과제 링크를 소유 관계나 실행 허용으로 해석하지 않는다.

### 3.7. 수용 판단과 검증 근거 — 56~62행

| 요소 | 필요성과 수정 후보 |
|---|---|
| 검증 대상·입력·기준·방법·관찰 연결 | 실제 확인의 재현에 필요한 정보다. 계획을 복사하거나 검사 통과만 적지 않고 실제 후보와 관찰을 식별할 수 있어야 한다. |
| 자기 수용 조건별 판정·근거 | Issue가 소유하는 핵심 판단이다. Task 결과를 읽고 무엇이 충족됐는지, 필요한 결합 결과를 무엇으로 확인했는지 연결할 후보이다. |
| 미확인·확인 범위/한계 | 필수 확인의 미수행과 선택적 미확인을 구분해야 한다. 자식 완료를 Issue 전체의 완료로 확대하지 않는다. |
| 본문과 artifacts의 경계 | 현재 수용 결론과 이유는 본문에 남기고, 필요한 상세 출력만 연결한다. 모든 검증마다 새 첨부를 만들 필요는 없다. |

### 3.8. 현재 결정과 제약 — 64~70행

| 요소 | 필요성과 수정 후보 |
|---|---|
| 유효한 결정·이유·승인·제약 | 합의와 권한을 유지하는 정보다. 제안·미정과 구별하고 어떤 행동까지 허용됐는지 식별하도록 작성법을 구체화할 수 있다. |
| 막힌 실패·미확인·해결 후 최종 결론·다음 행동 | 서로 다른 질문이 한 항목에 묶였다. 현재 판단에 남은 영향과 제약을 기록하고 요약·검증·결과와의 중복을 줄일 후보이다. |
| 현재 내용 갱신·근거 유지 | 실행 경과를 계속 덧붙이지 않는 원칙을 유지한다. 갱신해도 남겨야 할 결정 이유·승인 범위·보존 근거를 확인하는 조건을 정해야 한다. |
| 중단·전환·재개 | 별도 작성란은 없지만 기존 전환·복구 절차는 적용된다. 발생 시 멈춘 상태·전환 이유·복귀 조건을 이 구역에 둘지 별도 구역으로 둘지는 미정이다. |

### 3.9. 결과와 미해결 — 72~75행

| 요소 | 필요성과 수정 후보 |
|---|---|
| 자기 결과·수용/취소/인계 근거 | 필요하다. 한 문장에 여러 요구가 묶여 있어 실제 작성 형식을 구체화할 후보이다. |
| 반영/미반영·한계·잔여/재개 조건 | 결과 생성·적용·검증과 남은 종료 절차를 구분할 수 있어야 한다. 이미 있는 판정·근거는 연결하고 반복하지 않는다. |
| Task 완료를 Issue/Phase 수용으로 전파하지 않기 | 유지할 핵심 경계다. 필수 Task를 취소했을 때 결과의 대체나 범위 변경을 판단하는 기존 기준도 함께 연결해야 한다. |
| 관련 갱신과 실제 처리 확인 | 필요한 로컬 요약·부모 등록·제품 현황·GitHub 표시·보존을 이번 범위에 맞게 정하고 실제 반영과 미반영을 구분할 후보이다. 전부를 항상 실행하는 체크리스트로 만들지는 않는다. |

### 3.10. 표식과 자동 검사

입력의 표식은 `summary`·`goal`·`plan`·`conditional-guidance`·`pending`·`owned-tasks`·`related`·`verification`·`activity`·`result`의 열 개다. 구역을 합치거나 옮길 때 기존 참조와 양식 복사 후의 상대 링크를 확인해야 한다.

[Task 상태 검사기](../../../../../../.agents/skills/review-work/scripts/check_task_status.py)는 Task 경로의 `## 현재 요약`·`- 상태:`를 읽는다. 이번 Issue 문서에 그 검사를 적용하거나 Issue의 상태 확인까지 보장한다고 해석하지 않는다. [기록 검사기](../../../../../../scripts/check-work-records.py)도 합의 준수·등록·브랜치 준비·실제 운영 효과를 판정하는 검사는 아니다.

<a id="issue-task-boundary"></a>

## 4. Task보다 먼저 정할 Issue 쪽 접점

| 질문 | Issue에서 정할 후보 | Task에 연결할 내용 |
|---|---|---|
| 왜 이 실행 단위가 필요한가 | Issue 문제·수용 조건에서 어떤 결과를 맡길지와 분해 이유 | 배정 근거·목적 |
| 무엇을 어디까지 맡기는가 | 담당 결과·허용된 수행 범위·다른 자식과의 경계·의존 | 작업 단위·제약·시작 시 보완할 내용 |
| 무엇을 더 논의해야 하는가 | 미정 선택과 위임 범위·결정이 필요한 시점 | Task가 직접 보완할 상세와 관련 행동 전 논의할 선택 |
| 언제 준비됐다고 판단하는가 | 등록·부모 관계·담당 브랜치와 필요한 선행 결과의 실제 확인 | Task 실행자의 착수 전 대조 |
| 자식 결과를 어떻게 받아들이는가 | Task별 결과의 연결과 Issue 자체의 수용·통합 확인 | Task 자신의 완료 판단·근거·한계 |

Issue가 Task의 세부 계획·실행·상태를 별도로 관리하지 않으면서도, 배정 내용과 Issue 자신의 수용 책임을 찾을 수 있게 하는 것이 주요 설계 과제다. 기존 Task 작성안의 목적·작업 단위·시작 시 보완 형식은 보존하고, 이 접점을 정한 뒤 정합성을 다시 확인한다.

<a id="next-discussion"></a>

## 5. 다음 논의 순서 제안과 미정

1. **Phase 하위 Issue의 생성·배정과 목적·작업 범위:** Phase에서 어떤 결과를 하위 Issue에 맡기고 언제 생성하는지, 생성 시 채울 내용과 Issue에서 보완할 내용을 구분한다. 실제 Issue에 남길 역할 설명과 목적·범위의 작성 형식을 정한다.
2. **계획과 Task 생성·배정:** 직접 수행과 Task 분해의 판단, 최소 배정 내용·기록 위치·등록 확인과 Task 생성 지침의 분담을 정한다.
3. **착수·진행 중 재확인:** 시점마다 확인할 원천·기대값·실제값·판정·불일치 시 행동을 정하고, 계획과 실제 결과·근거 유지 방식을 연결한다.
4. **나머지 본문 구성:** 현재 요약·조건부 사항·결정·검증·결과의 역할과 중복을 조정하고, 설명·예시와 본문 지침을 나누어 작성안을 만든다.
5. **Phase 하위 Issue용 작성안의 완성과 후속:** 지시서·양식의 완성 조건을 정하고 해당 작성안을 완성한 뒤 독립 Issue의 지시서·양식을 별도로 다룬다. 현행 원천·기존 기록의 적용 범위와 최종 수용 조건·대표 사례·후속 사용의 확인 방법은 별도 합의한다.

위 순서와 각 수정 후보는 제안이다. 이번에 확인한 것은 현행 문서·코드의 내용과 연결 영향이며, 새 양식의 채택·자동 검사 확대·실제 후속 운영 효과는 확인하지 않았다.
