<a id="goal"></a>

## 목표와 수용 조건

확인된 결과를 상태에 옮기는 작업의 재검수와 작업 브랜치 push·PR의 중복 CI 실행을 줄인다.

1. 기존 수용 조건과 확인된 실행 결과에 따른 기록·상태 갱신은 자체 확인과 기존 별도 검수 재사용을 허용한다. 조건·해석·수용 범위나 새로운 주장이 바뀌면 해당 부분을 재검수한다.
2. 검수 스킬과 커밋 기준이 같은 재사용 조건을 따른다. 이번 규칙 변경에는 기존 기준의 자체·별도 검수를 적용한다.
3. CI의 push 대상만 main으로 제한한다. pull_request·workflow_dispatch와 기존 검사 내용은 유지한다.
4. 변경한 스킬의 실제 수행 범위·근거를 현재 원천과 연결해 stale을 해소한다. 확인 전에는 기존 근거를 보존한다.

<a id="plan"></a>

## 범위와 확인 방법

- 검수 스킬 두 문장 구역·커밋 기준 첫 문장·workflow 이벤트와 기존 스킬 현황의 해당 항목만 수정한다. 새 규칙 문서·검사 기능은 추가하지 않는다.
- 문구의 조건 경계, YAML 이벤트·기존 검사 내용 보존, 스킬 형식·현황·제출 후보를 확인한다. 변경하지 않은 검사기·설치기의 전체 회귀는 재실행하지 않는다.
- 사용자가 등록·최소 수정에 이어 스킬의 실제 수행 검증·현황 갱신·로컬 커밋을 허용했다. 같은 미병합 Issue 브랜치에서 수행하며 push·PR·병합·실제 원격 실행은 포함하지 않는다.

<a id="verification"></a>

## 검증과 결과

- 최초 도입: 현재 지문을 갱신하고 마지막 확인 지문·환경·범위·근거는 보존했다. 당시에는 새 동작을 수행하지 않아 stale로 표시했다.
- YAML 판독에서 push의 main 필터만 달라졌고 PR·수동 실행, job·권한·검사 명령은 기준 커밋과 같음을 확인했다. 실제 원격 이벤트 실행은 확인하지 않았다.
- Skill Creator 형식 검사·work/index 현황 검사·로컬 참조 12개·기록 날짜 부재·공백 검사를 통과했다. 실행 소스와 job이 같아 기존 전체 회귀 근거는 재사용한다.
- 자체·별도 검수에서 실제 staged 5파일과 합의안·조건 경계·근거 보존·후보 대응을 확인했고 필수 결함을 발견하지 못했다. 완료 표기도 검수했으며 검사 전후 index 바이트는 같았다.
