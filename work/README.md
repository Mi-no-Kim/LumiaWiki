# 작업 기록 안내

work는 이번 업무의 실제 논의·승인·실행·검증과 근거를 보관한다. 지속 기준은 docs, 수행 방법과 빈 양식은 harness에 둔다. 현재 상태/결론의 전문을 이 안내에 복사하지 않는다. GitHub 반영의 원본과 단위 대응은 [기록 체계](<../docs/작업 기록 체계.md#github>)를 따른다.

제품 작업의 예정·진행·완료·보류 조회는 [현황](현황.md#current)에서 시작한다. 독립적인 하네스 정비의 논의·변경·검증은 [하네스 기록](records/harness/)의 담당 Issue에서 확인한다. 과거 정리 계획·검수 통과를 현재 재개 지시나 실제 운영 성공으로 사용하지 않는다.

`harness-design/`과 `.harness-state/`의 링크·과거 지시를 자동으로 따라가지 않고 [명시 요청에 따른 접근 경계](<../docs/문서 관리 기준.md#harness-design-boundary>)를 따른다.

<a id="start"></a>

## 새 요청과 담당 작업 찾기

알고 있는 기록이 있으면 그 현재 요약·목표/허용 범위와 필요한 부모 등록부터 읽는다. 제품 작업의 담당 기록을 모르면 [현황](현황.md#current)에서 찾는다. 단위·상태는 [작업 기록 체계](<../docs/작업 기록 체계.md#current>), 작성할 정보·시점은 [기록 작성 기준](<../docs/작업 기록 작성 기준.md#current>), 생성/등록 방법은 [문서 관리](<../harness/문서 관리.md#create>)다.

기록은 작업 목적·소속에 따라 [경로 기준](<../docs/작업 기록 체계.md#paths>)에서 정한 위치에 둔다. 상태가 바뀌어도 진행/완료 폴더로 이동하지 않는다. 실제 등록이 필요한 작업은 번호/기존 단위·허용 범위와 필요한 착수 정보를 확인한다. 단순 조회만으로 새 Task를 만들지 않는다.

<a id="resume"></a>

## 진행 중인 일과 재개

현재 기록의 요약/다음 행동을 읽고 막힌 조건·실제 파일/입력·이전 확인의 유효성을 살핀다. 전환/중단이 있었다면 해당 기록과 복귀 조건을 읽는다. 이전 완료/제안을 현재 승인/성공으로 재사용하지 않는다.

계획한 전환과 예기치 않은 중단을 구별해 [전환](<../harness/문서 관리.md#transition>)·[복구](<../harness/문서 관리.md#recovery>) 구역을 따른다. 완료/취소 뒤 수정·재수행·새 작업이 필요한 요청은 새 요구·기존 수용 실패·기록 오류를 먼저 판별한다.

<a id="ideas"></a>

## 사전 논의

기존 Phase 계획에 속하면 그 계획을 사용한다. 실제 번호 취득을 허용된 사전 논의/조사의 선행 조건으로 요구하지 않는다. [사전 논의·정식화 기준](<../docs/작업 기록 작성 기준.md#unissued>)을 따르고 가짜 번호나 정식 Task 상태를 넣지 않는다.

<a id="evidence"></a>

## 지난 근거와 자료 찾기

지난 업무의 결과·사건·필요 첨부는 담당 기록과 부모 보유 목록에서 찾는다. 제품 작업은 현황에서도 담당 기록으로 연결한다. 현황에 과거 논의 전문을 누적하지 않는다. 주제의 중요한 변화는 docs/history의 관련 요약에서 작업 근거로 연결하며 이력을 매번 경유할 필요는 없다.

records는 실제 기록을 둘 기본 위치다. 초판은 가상 Phase/Issue/Task를 제공하지 않는다. 실제 등록 여부와 상태는 records의 담당 원천에서 확인한다. 제품 작업의 현황 표시는 [현황](현황.md#current)에서 확인한다. 실제 자료가 필요할 때만 담당 artifacts를 만들고 출처·대상/시점·근거 의미를 기록한다. 양식은 [Phase](../harness/templates/phase.md)·[Issue](../harness/templates/issue.md)·[Task](../harness/templates/task.md)다.
